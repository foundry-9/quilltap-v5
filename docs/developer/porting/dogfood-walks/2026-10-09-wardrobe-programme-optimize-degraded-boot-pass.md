## §4 Findings

- **#153 — a stopped `quilltap-web` never released the instance lock (Port divergence).** Found stopping A1's server with SIGTERM: exit 143, NO shutdown line, `data/quilltap.lock` left behind holding PID 44809 with a heartbeat seconds old. v4 registers `handleShutdown` on SIGTERM / SIGINT (`lib/database/backends/sqlite/client.ts:278-293`: close the mount-index, LLM-logs and main clients, then `releaseActiveInstanceLock()` → INFO `Instance lock released {lockPath, pid}`, the file unlinked) and `server.ts:94-121` logs `Shutting down {signal}`, closes every WebSocket client, `server.close()` → `HTTP server closed`, with a 5 s `Shutdown timed out, forcing exit` and a second-signal `Forced exit on second signal`. v5's `main.rs` ran `axum::serve` with no signal handling, so the host teardown that releases the lock (`AssemblyTeardown::run`, reached only through the engine's `Lock` verb) never ran on a stop, and `release_instance_lock` lacked v4's INFO line. Same-host relaunches recover through the dead-PID stale claim (A2); **a v4 on ANOTHER machine sharing the iCloud instance sees a foreign-host lock with a fresh heartbeat and refuses for the five-minute stale window**. Fix: see the finding row in `dogfood-findings.md`.
- **#159 — a `new-account` restore leaves every character on a fresh vault, the archive's orphaned (v4-shared; RULING REQUESTED).** #141's preserve-at-create covers `replace` only (P4.147 R-B); measured here, the cost in `new-account` mode is the whole wardrobe and vault of every restored character (Friday: 0 items visible; her 847-link vault unreferenced). v4 does the same (its create path mints a fresh vault). Proposal for the human: extend Shape A to `new-account` with the remapped store id.
- **#158 — every multipart `.qtap` import over 2 MB answered 400 `No file provided` (Port divergence).** Found exporting Ariel (8 MB with her 2,042 memories) and importing it back. `qtap_routes.rs` buffers the body, then rebuilds a bare `Request::new(Body::from(body))` for `FormData` — carrying the headers but not the extensions, where the router's `DefaultBodyLimit::max(10 GB)` marker lives — so axum's `Multipart` applied its 2 MB default, `from_request` failed, and both legs mapped that to `No file provided`. A 30-byte file parses; a 5.8 MB one does not. The SPA's Import dialog ALWAYS uses these multipart legs (`import-dialog.ts:47-51`), so any real character/chat export with memories could not be imported through the UI. v4 `await req.formData()` has no 2 MB cap. Every other multipart route passes the real request and is unaffected.
- **#156 — on a degraded mount index, every `with_both_conns` caller answers 500 `image job requires the mount-index database` (Port divergence; ORDER-PENDING).** `services/image_job_common.rs:541-557` refuses a missing mount-index writer with `DbError::Internal("image job requires the mount-index database")` — an image-job sentence on a helper with **115 callers** — and `db_error_response` has no `PartitionUnavailable` arm, so it is a 500 either way. v4 reaches each route's own handling: `handleAddChat` (`app/api/v1/projects/[id]/actions/chats.ts:137`) calls `repos.projects.findById` first, whose overlay hydrate throws on the unreadable store and the context middleware answers 503 `Project document store unavailable` (the shape v5's chat PUT gate already gives, E1). Measured: `projectChatAdd`, `projectAestheticSet`. Needs an order: classify the 115 sites against v4 per surface.
- **#157 — `Failed to log LLM call` on a degraded LLM-logs file carries v5's error and keys (Port divergence, log text; smalls).** v4 `llm-logging.service.ts:238` logs `{userId, type, provider, model, error}` and its guard's error is `LLM logs database is in degraded mode` (`llm-logs-guard.ts:21`); v5 `services/llm_logging.rs:353` logs `{log_type, provider, error: "partition not available: llmLogs"}` (the `DbError::PartitionUnavailable` Display).
- **#155 — the character view's Start Chat was a dead click inside the workspace (Port divergence).** v4's `CharacterHeader` Start Chat is a `<button onClick={onStartChat}>` that opens New Chat with the character preselected. v5's header rendered `<a routerLink="/characters/<id>" ?action=chat>`; inside the workspace (the default shell) the capture-phase link interceptor maps `/characters/<id>` to the `character-view` tab — the one already showing — and drops the query, so the click only re-focused the current tab. A full page load of the same URL works (the redirect guard + `workspace-intent.ts`'s `action=chat` arm), which is why the deep-link e2e never caught it.
