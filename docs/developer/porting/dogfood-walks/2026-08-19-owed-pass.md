## D6c — OAC with an API key: **IMPOSSIBLE IN BOTH APPS, and v5 is faithful**

The human tried to add the key and found the Add-New-API-Key dialog offers only
Anthropic, DeepSeek, Google Gemini, Grok (xAI), OpenAI, OpenRouter, Z.AI —
**no OpenAI-Compatible option**. Checked against v4 rather than assumed:

- v4's `components/settings/api-keys/ApiKeyModal.tsx:68` builds that dropdown as
  `providers.filter((p) => p.configRequirements?.requiresApiKey)`.
- v4's own `plugins/dist/qtap-plugin-openai-compatible/index.js` declares
  **`requiresApiKey: false`**.

So v4 omits OpenAI-Compatible from that list too. **v5 reproduces v4 exactly —
no finding against the port.**

**What it means for D6:** an `OPENAI_COMPATIBLE` profile can never carry an API
key through the UI in either app, so v4 bug 71's OAC arm is only ever reachable
against an **unauthenticated** endpoint. That is exactly the llama-server setup
of D6a, which makes D6a the complete OAC story available — there is no hosted
OAC configuration to compare it against.

**FILED UPSTREAM as v4 bug 81** (`docs/developer/bugs/bug-81-oac-cannot-hold-an-api-key.md`,
v4 commit `93bd3e7c`), at the human's direction, with the ordered shape being
**an OPTIONAL key for OAC** — split `requiresApiKey` into requires/accepts so a
hosted endpoint can carry a bearer token while local unauthenticated servers
keep working untouched. The data model already
supports the combination the UI cannot create — OAC profiles carry `apiKeyId`,
and the create path validates provider match ("API key provider does not match
profile provider"). Any hosted OpenAI-compatible service that needs a bearer
token (Together, Fireworks, vLLM behind auth) is therefore unusable, while the
plumbing for it exists.

## D6 — final state, after the wire tap

**The request half of v4 bug 71's OAC arm is PROVEN against a real server, at
the byte level, for the first time on either side.** With
`harness/tools/wire-tap.py` in front of llama-server (Qwen3.6-35B, native
template) and an `OPENAI_COMPATIBLE` profile pointed at the tap, the captured
request carries a **native OpenAI-style `tools[]` array**:

```json
"tools": [ { "type": "function",
             "function": { "name": "ask_carina", "description": "…",
                           "parameters": { "additionalProperties": false, … } } }, … ]
```

Function names seen on the wire: `ask_carina`, `delete_annotation`,
`list_email`, `read_conversation`, `request_full_context`, `rng`, `run_custom`.
**Not** pseudo-tool prose — so the profile's `pseudoToolMode: "auto"` resolved
to native advertisement, which was the open question the `toolCount` projection
could not answer. No `tool_choice` key is sent.

**What remains unexercised, and why it is not a v5 defect:** neither local model
returned `tool_calls` (`finishReason: None` on both attempts, against DeepSeek's
`"tool_calls"` in D6b), so **nothing tool-shaped came back to parse**. The 9B
answered in prose; the 35B *narrated* calling the tool and quoted invented
output. Closing the parse-back half needs a local model that reliably emits
tool calls, or an unauthenticated hosted OAC endpoint — and per D6c there can
be no authenticated one in either app.

**A nice incidental:** the 35B's narration contained "4d20", which tripped the
**auto-detect dice roller** — a real `TOOL` row
(`{"tool":"rng","initiatedBy":"auto-detect-response","success":true,"result":"Rolled 4d20: [11, 12, 17, 3] = 43"}`)
produced by the model's prose rather than by any tool call. v4 has the same
auto-detect, so this is faithful; it is recorded because it is an easy thing to
mistake for a genuine tool call when reading a transcript.
