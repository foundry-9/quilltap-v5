## The drift, classified (surveyed 2026-08-17, from the `d123658d` diff)

Three defects, all in the seam between what the form shows and what it
sends:

- **Bug 72** — clearing a numeric provider option snapped back to the
  schema default and swallowed the next keystroke (clear 300, type 5, store
  3005): emptying the box emits `undefined`, `setParameter` deletes the
  key, and `fieldValue` falls back to `field.default`, repainting the
  default with the caret behind it. v4's fix: NumberField holds its own
  **draft string**, reconciled against a **`syncedFrom` companion** that
  tells its own echo from the parameter genuinely moving underneath it —
  v4's commit message warns the naive re-sync-on-prop-change spelling
  REINTRODUCES the bug for any field with a stored value before the clear.
  `fieldValue` also returns `undefined` for number fields so the default
  renders as a **placeholder** (without that, a fresh mount seeds the
  default as a value and "leave blank for the default" is unreachable).
- **Bug 73** — a base URL survived a provider change while its field was
  hidden (Ollama fills `localhost:11434`; a hosted provider hides the field
  but kept the value; all four outbound sites sent it on truthiness).
  v4's fix: a **`outboundBaseUrl` chokepoint** gates every outbound site on
  `requiresBaseUrl`, the save body **always sends the `baseUrl` key**
  (`''` when the provider takes none — omitting it leaves the PUT's
  `!== undefined` gate untripped and every already-poisoned row broken
  forever), and an **unknown provider keeps its stored URL** (an unloaded
  provider list is not evidence that a provider takes no base URL).
- **Bug 74 (client layers)** — TagEditor's profile branch called
  `/api/v1/profiles/<id>` (never existed) and ProfileCard read `tag.name`
  off the `{tagId, tag}` envelope, drawing empty pills. v4 fixed the path
  to `/api/v1/connection-profiles/<id>` and the card now destructures
  `{ tagId, tag }` (`ProfileCard.tsx:163–168` at the pin).

## Shared contract (binding — identical in P4.D85 and P4.D86)

- **Verbs** (Request, serde camelCase like the character trio at
  `types.rs:440–460`):
  - `connectionProfileGetTags { profileId }`
  - `connectionProfileAddTag { profileId, tagId }`
  - `connectionProfileRemoveTag { profileId, tagId }`
- **Wire shapes** (v4 `route.ts` at `d123658d` is the oracle):
  - get-tags success: `{ "tags": [ { "id", "name", "visualStyle" } ] }` —
    the FLAT `EditorTag` shape (`enrichment.ts:113–124`), entity order
    preserved, missing tag ids dropped silently.
  - add-tag success: status **201**, `{ "success": true, "tag": <full tag
    row> }`; unknown `tagId` → 404 `notFound('Tag')`.
  - remove-tag success: `{ "success": true }` (no tag existence check).
  - Unknown GET action → 400
    `Unknown action: <action>. Available actions: get-tags`.
  - Unknown POST action → 400
    `Unknown action: <action>. Available actions: add-tag, remove-tag,
    auto-configure`.
  - `auto-configure` → v5's loud typed refusal (P4.D85 owns the sentence;
    this lane must not depend on it).
- **PUT baseUrl**: the client ALWAYS sends the `baseUrl` key (`''` when the
  resolved provider takes no base URL; the stored value verbatim when the
  provider is unknown/unloaded); the server arm stores `baseUrl || null`
  (v4 `route.ts:234–236`) so `''` lands as NULL. No server change; the
  coercion is load-bearing for the client's poisoned-row clear.
- **Card display**: the profile LIST/GET enrichment keeps the
  `{ tagId, tag }` envelope (`EnrichedTag`); `get-tags` is the FLAT shape.
  Two shapes, each with one owner — never conflate
  (that conflation WAS bug 74's second layer).
