## The drift, classified (surveyed FRESH 2026-08-13 at `48396682`)

### `07d4ccce` — bug 61 (the staged replay)

New v4 `lib/wardrobe/staged-live-outfits.ts` (93 lines):

```ts
type SlotsMutator = (prev: EquippedSlots) => EquippedSlots
equippedSlotsEqual(a, b)                     // moved OUT of the dialog
rebaseStagedSlots(wornSlots, pending: readonly SlotsMutator[])
classifyStagedOutfits(staged, baselines) -> { dirty: [{characterId, slots}], unresolved: string[] }
```

Dialog mechanism (`wardrobe-control-dialog.tsx`, three moving parts):

1. **Record the gesture, not its result.** A `pendingLiveMutatorsRef`
   queue: in `updateLiveStaged`, when in-chat and the character's worn
   snapshot has NOT yet seeded, the mutator is appended to the queue
   before the optimistic paint against the empty fallback.
2. **Replay on seed.** The seeding effect drains the character's queue and
   seeds with `rebaseStagedSlots(wornSlots, pending)` instead of cloning
   the worn snapshot — so the click survives and lands ON TOP of what was
   already worn (mutators are pure; double-application is safe).
3. **The Done confirm arm.** The flush classifies via
   `classifyStagedOutfits`; `unresolved.length > 0` triggers a
   confirmation — *"Word of what {names} is presently wearing never
   reached us, so your alterations cannot be saved. Close the wardrobe and
   let them go?"* — declining keeps the dialog open (a late snapshot can
   still seed and save); confirming falls through to the normal dirty
   flush. Previously `if (!baseline) continue` silently classified
   unresolved as clean — that is the lost-edit bug.

v4 shipped two test suites to port case-for-case:
`__tests__/unit/lib/wardrobe/staged-live-outfits.test.ts` (132 lines,
rebase + classification) and
`__tests__/unit/components/wardrobe/wardrobe-control-dialog.race.test.tsx`
(214 lines — holds the outfit response open across the click and asserts
ONE `set_all` carrying both the already-worn item and the just-clicked
one).

## Shared contract (BINDING — identical text in P4.D71)

1. **The group-scope wardrobe read.** REST:
   `GET /api/v1/characters/{id}/wardrobe?scope=group` → 200
   `{ "wardrobeItems": [...] }` (v4's exact envelope). Dispatch: the
   existing character-wardrobe-list verb gains an optional `scope` field
   (JSON key `scope`, accepted value `"group"`; absent = today's
   behavior). If the frozen request type cannot take the field directly,
   use the established flatten-seam pattern — the JSON wire above is what
   is binding, name-for-name.
2. **Dissolution semantics.** The SERVER is authoritative: after any
   wear/replace/add_to_slot/set-default/llm-choose of a **resolvable**
   bundle, persisted equipped slots contain leaf ids only (unresolvable →
   stored whole). The client's optimistic math mirrors v4's client
   (`wearItemIntoSlots`/`addItemToSlot` with `itemsById`), and the server
   result overwrites it on reconcile.
3. **Version bumps:** P4.D71 bumps `quilltap-core`/`quilltap-harness`/
   `quilltap-web`; THIS lane bumps the SPA (`apps/web/package.json`) only.
