## Mandate

Close the embedding family. Four deliverables, in dependency order: port v4's
**CONVERSATION_RENDER** background-job handler (which requires porting the pure
`lib/scriptorium/markdown-renderer.ts`), port the **startup
reconcile-conversation-rendering pass** (deferred loudly by P4.6BL precisely
because a verbatim port would have minted DEAD render jobs — that blocker
dissolves the moment the handler exists), port the **EMBEDDING_REINDEX_ALL**
handler, and un-refuse **`chatQueueMemories`**.

One of these is quietly a live bug, not just a deferral: **v5 already mints
`EMBEDDING_REINDEX_ALL` jobs** — `services/embedding_refit_job.rs:159–168`
enqueues one whenever a BUILTIN refit runs with `triggerReindex`, and
`EMBEDDING_REFIT` *is* registered (`quilltap-host/src/host.rs:470-471`). Every
such job retries three times and dies, exactly the finding-#35 shape. The same
is true of the manual "render conversation" button: `ChatRenderConversation`
is live (`api/engine.rs:1220` → `services/chat_admin.rs:440` →
`queue_service.rs:969` `enqueue_conversation_render`) and its jobs die today.

**Must NOT touch:** `apps/web/**` (P4.9E4B's); `api/files.rs`, `api/salon.rs`,
any new attach/describe module, and the `EngineAssembly` seam P4.9E4A adds
(P4.9E4A's). The refusal arm this lane un-arms
(`api/engine.rs:2800-2803` → `memories::not_available("queue-memories")`) is
this lane's to edit; nothing else inside another lane's labelled regions.

### 1. v4 `CONVERSATION_RENDER` — `lib/background-jobs/handlers/conversation-render.ts` (127 LOC)

`handleConversationRender` at :18–127; registered `handlers/index.ts:54`.
Payload `{ chatId, fullReembed? }` (`queue-service.ts:237-241`) — a bare TS
interface cast, **no Zod**; mirror the leniency the way
`EmbeddingGeneratePayload::from_json` does (`embedding_generate_job.rs:56-58`).

Pure template rendering — **no LLM call**:

1. `repos.chats.findById`; missing → warn + return (:24–31).
2. participantId → displayName map; user-controlled participants without a
   character render as `"User"` (:34–46).
3. `repos.chats.getMessages(chatId)`; empty → silent return (:49–53).
4. `renderConversationMarkdown(...)` → `{markdown, interchanges[]}` — from
   **`lib/scriptorium/markdown-renderer.ts` (224 LOC, single export at :52),
   UNPORTED**; v5's `scriptorium.rs` ports only `annotation-merger.ts`. This
   pure module is the substantive blocker and ports first, tier-1.
5. Writes `chats.renderedMarkdown` via `repos.chats.update` — deliberately
   does NOT touch `updatedAt` (:63–66). Carry that; a bumped `updatedAt`
   would reorder every recents list.
6. Upserts `conversation_chunks` per interchange
   (`{chatId, interchangeIndex, content, participantNames, messageIds}`,
   :70–78). The upsert preserves existing embeddings.
7. Re-enqueues embeddings (:82–117): resolve the default embedding profile
   (`isDefault` or `[0]`); per interchange, `findByInterchangeIndex` then
   `enqueueEmbeddingGenerate({entityType:'CONVERSATION_CHUNK', …})` when
   `payload.fullReembed || !chunk.embedding`. The whole block is try/caught —
   an enqueue failure does not fail the render.

Enqueue helper `enqueueConversationRender` (`queue-service.ts:399-425`)
dedupes per-chat via `findPendingForChat` filtered to the type, priority −1 —
**already ported** (`queue_service.rs:969-1000`).

### 2. v4 startup reconcile — `lib/startup/reconcile-conversation-rendering.ts` (158 LOC)

Entry `reconcileConversationRendering()` at :96. Boot wiring
`instrumentation.ts:836-860` ("PHASE 3.6"), fire-and-forget with an outer
try/catch. One raw SQL scan (`SELECT_INCOMPLETE_CHATS`, :53–73), two arms:

- Arm A: `chats.renderedMarkdown IS NULL` AND a real USER/ASSISTANT message
  exists.
- Arm B (OR): a `conversation_chunks` row with `embedding IS NULL AND
  LENGTH(content) BETWEEN 1 AND ?` — the bind is `EMBEDDING_MAX_CHARS`
  (v5 already has it: `embedding_generate_job.rs:54`, 128 KiB). Oversize/empty
  chunks are deliberately excluded so a permanently-unembeddable chunk cannot
  pin its chat "incomplete" forever (module doc :30–34).

Per row: one `enqueueConversationRender(userId, {chatId})` (:131), counters
`{incompleteChats, enqueued, reused, failed}` (:75–84); `setImmediate` yield
between enqueues (:147) — in Rust the yield is a non-item (the repair runs on
its own thread; follow the P4.6BL boot-repair shape). Scan failure → warn +
zeros. Dedupe is delegated entirely to the enqueue helper.

**Relation to P4.6BL's boot repair:** `embedding_backlog_repair.rs` (294 LOC;
call site `quilltap-host/src/host.rs:744-768`, fenced `=== P4.6BL ===`) was
the sanctioned v5-only stand-in, enqueuing `EMBEDDING_GENERATE` directly. The
reconcile is a superset of its arm-B intent (it also heals arm A) but goes
through render jobs. **Decide and record**: v4 runs only the reconcile; once
CONVERSATION_RENDER is live the faithful shape is to port the reconcile and
retire (or subordinate) the v5-only direct repair — but do not delete the
repair without proving the reconcile covers its cases (its module doc
:7–25 records why it exists). The differential should pin whichever shape you
land.

**The sibling that must NOT be confused with this:**
`lib/startup/repair-text-embeddings.ts` (legacy TEXT→BLOB conversion,
PHASE 1.1) — v5 explicitly needs no port (`db/help_docs.rs:71`).

### 3. v4 `EMBEDDING_REINDEX_ALL` — `lib/background-jobs/handlers/embedding-reindex.ts` (274 LOC)

`handleEmbeddingReindexAll` :69–274; registered `handlers/index.ts:48`.
Payload `{ profileId, scope?: 'all' | 'mismatched-dim' }`
(`queue-service.ts:152-168`), bare interface, no Zod. `BATCH_SIZE = 200`
(:25). Sequence:

- Load profile; missing → throw (:82–85).
- `mismatched-dim`: target dim = `truncateToDimensions ?? dimensions`; BUILTIN
  (neither set) → throw "Use scope='all' instead" (:91–99).
- Always: invalidate the mount-chunk cache (:103–104 — v5 analog:
  whatever `invalidateMountPoint`'s all-points sibling is in the mount cache;
  if v5 has no global invalidate, record and match observable behavior).
- `scope === 'all'`: `cancelByType('EMBEDDING_GENERATE')` then
  `embeddingStatus.markAllPendingByProfileId(profileId)` (:110–120; the
  `markedCount` local is dead — port the call, not the variable). v5's
  `cancel_by_type` already exists and sets `lastError = 'Superseded by new
  reindex'` (`background_jobs.rs:588-593`) — this lane is its first caller.
- **Phase 1 help docs** (:134–175): `syncHelpDocs()` first (v5:
  `services/help_doc_sync.rs:220`, signature differs — takes `&Connection` +
  pre-read files; its docs at :37/:215/:407 already annotate this deferral);
  `scope==='all'` → `helpDocs.clearAllEmbeddings()`; per-doc dim check under
  partial scope. Whole phase try/caught — continues on failure.
- **Phase 2 memories** (:180–210): per character, `scope==='all'` →
  `vectorStoreManager.deleteStore(character.id)` (resets the dim constraint),
  then every memory → a job. **NOT try/caught in v4** — reproduce the
  asymmetry (a phase-2 throw fails the job; phases 1/3 don't).
- **Phase 3 conversation chunks** (:215–240): chats → chunks → jobs;
  try/caught.
- Batch insert :245–255: slices of 200 → `createBatch`; jobs built flat
  **priority 0** (NOT `EMBEDDING_ENTITY_PRIORITIES` — differs from both
  `enqueueEmbeddingGenerate` and v5's boot repair at 10.0), maxAttempts 3;
  then `ensureProcessorRunning()`.
- **No dedupe anywhere on this path** — `createBatch` bypasses
  `findPendingForEntity`; the scope=all `cancelByType` is the only collision
  control, partial scope has none. Reproduce; do not "improve".
- `MOUNT_CHUNK` is NOT covered by this handler in v4. Match that.

Enqueue helper `enqueueEmbeddingReindexAll` — **already ported**
(`queue_service.rs:689-702`) but its payload deliberately omits `scope`
(doc :693–694). This lane widens it to carry `scope` and updates the one
caller (`embedding_refit_job.rs:159-168` — refit passes no scope in v4
either; check v4 `embedding-refit.ts:145` for what it sends and match).

v4 route entry points (`embedding-profiles` create/PUT/`?action=reindex`,
`app/api/v1/embedding-profiles/{route.ts:349-350, [id]/route.ts:210-212,
347-360}`): **v5 has no embedding-profiles API module at all** — that whole
management surface is `p4.9h`'s (m6 row 6). Tier 3 here: do NOT build the
route surface; the handler + the refit-chain caller are this lane's scope.
