## The drift, classified (surveyed 2026-08-18 from the `4423ad10` diff)

v4 adds a FIFTH wardrobe slot, `hair` — a hairdo, not hair (braids, an
updo, a wig; natural hair stays in the physical description) — and pays
down its own duplication on the way: one ordered slot list +
`WARDROBE_SLOT_META` registry replaces every local copy. Hair is
deliberately not clothing: slots gain `reportWhenEmpty` (garment slots
announce vacancies — "topless", "barefoot"; hair says NOTHING when empty,
because empty means unstyled, never bald), nudity semantics compute over
clothing slots only, avatars carry the hairdo on BOTH branches (the
bare-top guard used to key on accessories alone — v4 calls that "the
likeliest silent-drop bug in the whole feature"), undressing keeps the
hairstyle in scene state, hats remain accessories. No DDL, no migration:
`equippedOutfit` is unconstrained JSON, absent keys default `[]`. The
outfit hash gains the hair key unconditionally — one accepted cache miss
per chat, **no conditional key omission** (v4's design doc forbids it).

**On the consolidation (a human question at planning, answered here):**
collapsing v5's ten slot-list copies onto one registry is NOT v5-invented
tidiness to be banked post-port — it is `4423ad10`'s OWN refactor, done in
the same commit v4 shipped hair in, and v4's design doc pins the success
criterion ("slot #6 = extend two constants + CSS + prompt text + export
enum — everything else type-errors"). Adding `hair` to all ten copies is
mandatory either way; keeping them as ten hand-synced copies is the
divergence, and it would make every FUTURE drift commit on these files
(which will edit v4's registry) fan out to ten v5 sites. The
`reportWhenEmpty`/`emptyFallback` semantics need a meta table to live in
regardless. The refactor changes no output bytes, so the same oracle runs
this lane must do anyway prove it safe. The three FROZEN legacy lists stay
copies deliberately — that too is v4's shape.
