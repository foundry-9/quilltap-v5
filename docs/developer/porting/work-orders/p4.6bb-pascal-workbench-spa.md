### 2. tool-draft + the client-safe schema (the pure-TS ports)

- `tool-draft.ts` is the **bijection** between a schema-valid document
  and the form-friendly `ToolDraft` (numbers as text, conditions as
  flat chips, unknown top-level keys in an opaque bag):
  `draftFromDefinition`, `serializeDraft`, `validateDraft`. Canonical
  emission (§6.2 of v4's feature doc): **`$schema` first, known keys in
  declaration order, defaulted optionals omitted, unknown keys appended
  verbatim, 2-space indent, trailing newline.** Draft ids
  (`nextDraftId`) are session-local counters — Angular can keep the
  same idiom for `@for` track keys.
- The SPA has **no zod** (verified: no dependency, no imports). The
  client-safe validation half of `custom-tool.types.ts`
  (`QtapCustomToolSchema.safeParse` + per-issue `path.join('.')`-
  prefixed messages + `formatDefinitionIssues` + `collectUnknownKeys` +
  the constants `COMPARATOR_KEYS`, `IDENTIFIER_PATTERN`, `MAX_*`) must
  be **hand-ported to TS preserving Zod's message strings and
  abort/hoist behavior** (`[[p4.6ay-units-1-3-zod-and-js]]` — porting
  Zod = porting its abort/hoist rules; v5's Rust
  `pascal/custom_tool_types.rs` is a proven second reference for the
  exact strings). The Workbench needs it in the JSON editor mode
  (issues list + summary), for `canSwitchToForm`, for name extraction
  (`currentName`), and inside `draftFromDefinition`.
- **The corpus differential** (the teeth for both ports): regenerate
  the pascal-definition oracle at `d68638b4` (recipe: the
  `pascal_custom_tool_definition_equivalence.rs` header / the unit-11
  status-log record — 105 defs + 10 titles, full Zod message strings)

### 4. WorkbenchEditor (635) — the heart

- State (`:103-115`): `editorMode: 'form'|'json'`, `repairReason`,
  `dirty`, `location {mountPointId, path} | null`, `mtime`,
  `loadedName`, `benchOpen` (default true), `pickerOpen:
  'save'|'save-as'|null`, `conflictContent`, `flashOutcomeId`.
- **Load**: v4 GETs the file envelope on the mount-file item route; v5
  uses the **`mountFileRead` dispatch verb** (§W2 — mirror it from the
  existing Rust union; do NOT use the REST JSON leg, which is
  refusal-armed in v5). A file that parses as a valid definition →
  form mode via `draftFromDefinition`; an invalid/unparseable file →
  **JSON mode with `repairReason` set** (the repair flow the popup's
  and library's broken-entry links open).
- **Mode switch** (`:203-223`): `switchToJson` serializes the draft;
  `switchToForm` only when the JSON parses AND validates
  (`canSwitchToForm`); JSON→form clears `repairReason`.
- **JSON mode validation** (`:176-197`): debounced 300ms; not-JSON →
  one issue line; schema-invalid → per-issue `path: message` lines +
  the `formatDefinitionIssues` summary + `collectUnknownKeys`; valid →
  unknown keys only.
- **Save** (`:228-290`): form mode writes `serializeDraft(draft)`;
  **JSON mode writes the user's bytes VERBATIM** ("canonicalization
  applies to form-mode emission only" — carry the why-comment).
  `saveIsBlocked`: form → `!formValid`; JSON → invalid AND not in
  repair mode. Writes go through the **`mountFileWrite` dispatch verb**
  (§W2) carrying `{content, expected_mtime?, force?}`; same-location
  saves send the held `mtime` as `expected_mtime`, save-as/new send
  none; a conflict populates `conflictContent` (the fresh remote
  content is re-fetched, `:388`) and the force path sets `force: true`.
  Success: update `location`/`mtime`/`loadedName`, clear dirty +
  conflict, invalidate the library query, toast **"Pascal has filed
  the contrivance."** (the voice — carry it).
- **Save vs Save-As**: `pickerOpen` drives the `DestinationPicker`;
  save-as (and first save of a create) picks a destination store +
  filename; delete goes through `mountFileDelete` (already mirrored).
  `fileExists` probes before overwrite-into-new-path (`:262-270`).
- `onOpenOther(mountPointId, path)` — the editor can jump to another
  definition (collision advisory links).

### §W1 — the four Workbench dispatch verbs (OWNER: lane AY — CONSUMER: lane BB)

- Request variants (added to the CoreRequest union on both sides,
  name-for-name; response `type` strings are AY-owned and pinned here):
  - `{ type: 'customToolsLibrary' }` → response type
    `customToolsLibrary`, data `CustomToolLibraryResponse` =
    `{ tools: CustomToolLibraryEntry[], errors: CustomToolLibraryError[] }`
  - `{ type: 'customToolsDestinations' }` → response type
    `customToolsDestinations`, data `CustomToolDestinations`
  - `{ type: 'customToolPreview', definition, params?, private?, metadata? }`
    → response type `customToolPreview`, data `CustomToolRunResult`
  - `{ type: 'customToolAudit', definition, params?, metadata? }` →
    response type `customToolAudit`, data `CustomToolAuditResult`
- Every DTO is transcribed field-for-field from the SAME v4 lines;
  neither lane invents fields: `MountAttachment`,
  `CustomToolLibraryEntry`, `CustomToolLibraryError`,
  `CustomToolLibraryResponse`, `DestinationStore`,
  `CustomToolDestinations` — v4 `lib/pascal/workbench.ts:22-77`;
  `CustomToolRunResult` — v4 `lib/pascal/custom-tools.ts:431-451`
  (incl. `metadataTested?`); `CustomToolAuditResult` — v4
  `lib/pascal/custom-tools.ts:962-968` (`{runs, outcomes:
  [{index, hits, share}], valueMin, valueMax, valueMean}`).
- `metadata` on preview/audit is v4's `MetadataInputSchema` union
  (route.ts:61-64): a plain object passes through VERBATIM; a
  `{ characterId }` object (exactly one key, a string) hydrates that
  character's sheet server-side; **the `{characterId}` branch is
  checked FIRST** (it would also satisfy the catch-all record). The
  SPA sends either form and never resolves the sheet itself.
- `AUDIT_RUNS = 10_000` is server-fixed (route.ts:33); no `runs` field
  crosses the wire.
- Error arms (the SPA renders the server's strings, never re-derives):
  non-JSON body → 400 `Request body must be JSON`; body-parse failure
  → 400 `Invalid request body` (+ issues); invalid definition → 400
  with the `formatDefinitionIssues` string; unknown `characterId` →
  404 (Character); broken vault → 422 (the error's message, never
  papered with `{}`); `CustomToolRunError` on preview/audit → 422 (the
  message).
- The REST legs land with the verbs (`GET /api/v1/custom-tools`, GET

  `p4_6ar_wire_contract` precedent) over the four verbs + every DTO
