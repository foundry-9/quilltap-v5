# Work order P4.10 — the dev-grade packaging close-out (the Docker image actually ships the SPA)

> **STATUS: OPEN — not started (written 2026-07-22).** Single lane, no
> siblings. This closes the one Phase-4 deliverable that was written down and
> then never finished: `phase-4.md:45-46` item 6, *"Packaging (dev-grade) — a
> Dockerfile for the web deployment and a Tauri bundle."* The Dockerfile
> exists but predates the SPA (it was written at P4.2, before P4.5), so the
> image it builds cannot serve the app — and, since P4.4u4 added the
> compile-time seed assets, cannot compile at all.
>
> **This order does NOT initiate a release** (the standing CLAUDE.md hard
> stop, and D21). Nothing here is published, signed, tagged, or pushed to a
> registry. The deliverable is a locally-built image and a locally-runnable
> binary — dev-grade, exactly as item 6 scoped it.

Work on a lane branch (`lane/p4.10-packaging`) — normal carryout rules apply.
`docs/CHANGELOG.md` and `docs/developer/porting/status-log.md` are
append-only.

## Mandate

Make all three shipped modes actually runnable by a human who did not build
them, at dev-grade quality:

1. **The server build** — `docker build` produces an image that serves the
   real Angular SPA (not the placeholder pages), and the bare `quilltap-web`
   binary finds its dist without the caller knowing about `--spa-dir`.
2. **The CLI** — present inside the image, so `docker exec` can reach the
   running instance the way D12 intends.
3. **The desktop build** — documented as a build recipe only. Bundling
   targets, signing, notarization, and the updater stay deferred (D21).

Plus one short developer-facing doc that says which binary to run, because
nothing in the repo says it today.

## Survey-verified starting points (surveyed 2026-07-22, v5 at `8a864746`)

Every claim below was read out of the tree; re-verify at lane start.

**The three failures, in the order they bite:**

1. **The build stage cannot compile.** [`Dockerfile`](../../../Dockerfile)
   COPYs exactly `rust-toolchain.toml`, `Cargo.toml`, `Cargo.lock`,
   `crates/quilltap-sqlite3mc-sys`, and `crates` — it never copies
   `assets/`. But `crates/quilltap-core/src/services/quilltap_import/
   seed_assets.rs:10,25,31` reaches **out of the workspace** at compile time:

   ```
   include_str!("../../../../../assets/first-startup/imports/lorian-and-riya.qtap")
   include_bytes!("../../../../../assets/first-startup/avatars/Lorian.webp")
   include_bytes!("../../../../../assets/first-startup/avatars/Riya.webp")
   ```

   Those three are the whole set of includes escaping `crates/` (checked by
   grep). They landed with the P4.4u4 sample-content seed (2026-07-11), five
   months of rounds after the Dockerfile. **Verify the failure first** — run
   `docker build .` at lane start and capture the error; the order's premise
   is that it fails here, and a lane that finds otherwise should stop and
   report rather than "fix" a working build.

2. **There is no SPA in the image.** `.dockerignore` excludes `apps`
   wholesale, and the Dockerfile has no Node stage — nothing ever runs
   `ng build`.

3. **Nothing would point the server at a dist even if one were there.** The
   dist directory arrives **only** via `--spa-dir`
   ([`crates/quilltap-web/src/main.rs:47,87`](../../../crates/quilltap-web/src/main.rs:47));
   there is no env-var fallback and no binary-relative default (grep for
   `spa_dir` finds only the flag, the struct field, and
   `state.spa_dir`). The container ENTRYPOINT passes `--host`/`--port` and
   nothing else, so `spa_dir` is `None` and
   [`static_serve.rs:13-15`](../../../crates/quilltap-web/src/static_serve.rs:13)
   serves the two embedded placeholder pages
   (`crates/quilltap-web/static/{index,setup}.html`).

**What already works, and is therefore not this lane's problem:**

- **The dist + binary combination is proven in CI.** `apps/web/e2e/
  global-setup.ts:434` spawns the real `quilltap-web` with
  `['--host','127.0.0.1','--port',…,'--data-dir',…,'--spa-dir',dist]`, and
  the whole Playwright suite (111 specs at the P4.6bj gate) runs against it,
  including the locked-vault `/setup` path (`setup-flow.spec.ts:49`). The
  pieces fit; they have simply never been assembled in a Dockerfile.
- **The container data-dir branch exists.** `quilltap-host::paths::
  platform_default_base_dir` returns `/app/quilltap` under
  `is_docker_environment()` (paths.rs:23-26), and the Dockerfile already sets
  `QUILLTAP_DATA_DIR=/app/quilltap` + `VOLUME`.
- **The SPA build is a plain Angular build.** `apps/web/package.json` →
  `"build": "ng build"`; `angular.json` needs `src/`, `public/`,
  `tsconfig*.json`, `angular.json`, and `node_modules` (its `styles` array
  pulls `node_modules/@xterm/xterm/css/xterm.css` and
  `node_modules/katex/dist/katex.min.css`). `tsconfig.app.json` includes only
  `src/**/*.ts`, so `e2e/` and `tooling/` are **not** build inputs.
  `apps/web/.nvmrc` pins **Node v24.13.1**; `packageManager` is npm 11.8.0; a
  committed `package-lock.json` exists (so `npm ci`).
- **The dist path** is `apps/web/dist/quilltap/browser` — the same path
  `crates/quilltap-tauri/tauri.conf.json` names as `frontendDist`.

## Units

Land them in order; each is independently committable.

### Unit 1 — the build inputs (make `docker build` compile again)

Add `COPY assets ./assets` to the build stage, positioned with the
slow-changing layers (it is ~200 KB of committed binaries that almost never
change, so it belongs **above** `COPY crates`). Adjust `.dockerignore` so the
SPA sources enter the context while the junk stays out: replace the blanket
`apps` with `apps/web/node_modules`, `apps/web/dist`, `apps/web/.angular`,
and `apps/web/e2e` (the last only after confirming `ng build` does not need
it — `tsconfig.app.json` says it does not; confirm by building).

Exit: `docker build` gets past the Rust stage.

### Unit 2 — the SPA build stage

A Node stage pinned to the `.nvmrc` major (`node:24-bookworm` — read the
actual pin at lane start, do not paste this one), doing the standard
lockfile-first split so `npm ci` caches:

```
COPY apps/web/package.json apps/web/package-lock.json ./
RUN npm ci
COPY apps/web/ ./
RUN npm run build
```

Order it so the Rust stage and the Node stage are independent (BuildKit runs
them concurrently). Keep the existing cache-mount discipline for cargo.

Exit: the stage emits `dist/quilltap/browser/index.html`.

### Unit 3 — the dist lands in the runtime image and is served

`COPY --from=<spa stage> …/dist/quilltap/browser /usr/local/share/quilltap/spa`
and extend the ENTRYPOINT (or the env, per unit 4) so the server actually
serves it. Keep `EXPOSE 3000` and the `--host 0.0.0.0` container policy (D2 —
the container boundary is the trust boundary).

Exit: `docker run -p 127.0.0.1:3000:3000 …` serves the Angular index at `/`,
not the placeholder. Assert on a marker only the real dist has (a hashed
`main-*.js` script tag); asserting "200 OK" would pass against the
placeholder and prove nothing.

### Unit 4 — `quilltap-web` finds its dist without being told (a small Rust change)

Give the dist a resolution chain, mirroring how `--data-dir` already resolves
(`paths.rs:47-60`): `--spa-dir` flag → `QUILLTAP_SPA_DIR` env →
a binary-relative conventional default (`<exe dir>/spa`, and the container
path if that is cleaner) → `None` (placeholders, unchanged). This is what
makes the **bare binary** deployment real, not only the container: today a
`quilltap-web` copied out of `target/release` serves placeholders forever
with no diagnostic.

This is the one unit touching Rust. It needs:

- a unit test per branch of the chain (precedence, and the `None` tail),
- the startup banner in `main.rs:92-96` extended to say where the SPA is
  being served from, or that it is running UI-less — a silent placeholder is
  the failure mode that produced this whole order,
- `cargo clippy` both feature sets + the workspace test run green.

Do **not** change `static_serve.rs`'s serving semantics (the traversal guard
and index fallback are frozen — the Playwright suite is their proof).

### Unit 5 — the CLI in the image (D12)

Build `-p quilltap-cli` in the same Rust stage and copy the `quilltap` binary
into the runtime image, so `docker exec -it <c> quilltap db --tables` works.
Note in the doc (unit 7) that inside a running container the CLI is subject
to the single-writer rule — D12's HTTP-client mode, and the write-lock
refusal against a live server, are the designed behavior, not a bug.

### Unit 6 — a compose file (optional, dev-grade)

A root `docker-compose.yml` publishing `127.0.0.1:3000:3000` against a named
volume, so the documented run command is one word. Skip it if unit 3's
`docker run` line is short enough to live in the doc; do not invent
configuration surface.

### Unit 7 — say how to run the three modes

Write `docs/developer/running.md`: the three modes, what each is for, the
exact commands, where the data dir lands per platform (`paths.rs`), the
first-run unlock/setup flow (readiness → 503 + `setupUrl` → `/setup`), the
no-auth/bind policy (D2, stated plainly — `127.0.0.1` by default; widening it
puts an unauthenticated app on the network), and the fresh-boot sample seed
(Lorian + Riya + 42 memories, default ON). For desktop, a build recipe only:
`ng build` then `cargo tauri build`, with `bundle.targets` currently `["app"]`
— **no** dmg/msi/deb, no signing, no updater (D21).

**Open question for the human, do not decide it in-lane:** whether the repo
also gets an end-user-facing `README.md`. That is adjacent to the v4
retirement / release story ([`m6-screen-parity.md` §5.3](../m6-screen-parity.md)),
which is a human call, not a porting decision.

## Exit gate

- `docker build -t quilltap .` succeeds from a clean context.
- `docker run --rm -p 127.0.0.1:3000:3000 -v quilltap-data:/app/quilltap quilltap`
  → `GET /health` answers, `GET /` returns the **real** dist (hashed bundle
  marker), `GET /setup` renders the SPA setup screen, and a browser can walk
  first-run setup → unlock → the home dashboard against a fresh volume.
  Record the walk in the round record; this is a human-eyes step like the M5
  walk, not something a headless assertion fully covers.
- `docker exec … quilltap --version` / `db --tables` behaves.
- The bare binary, copied alone to a scratch directory next to its `spa/`,
  serves the SPA with no flags (unit 4).
- The standing automated floor stays green: `cargo test --workspace`, clippy
  both feature sets, release build, `ng test`, full Playwright zero skips.
  **Unit 4 is the only unit that can move any of those numbers** — if a
  Dockerfile-only unit changes a test count, something is wrong.

  per-commit crate bumps, no signing/notarization/updater. D21 + the CLAUDE.md
