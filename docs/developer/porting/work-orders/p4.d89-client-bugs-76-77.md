## Fix A — bug 76 (surveyed 2026-08-18; v4 lines on main @ `979652a9`)

Bug 73's shape one field over: `handleProviderChange` never cleared
`apiKeyId`, the select cannot express what is stored once the provider
moves (not rendered on a keyless provider; blank on a different hosted
one, its options being filtered to the current provider), and every
outbound site sent it on truthiness. v4's fix, the `outboundBaseUrl`
twin:

- **The chokepoint** `outboundApiKeyId`
  (`components/settings/connection-profiles/hooks/useProfileForm.ts:63-98`)
  answers "could the select show this id right now?", refusing on BOTH
  counts the select can: (1) the provider renders no key control
  (`known && !known.configRequirements?.requiresApiKey` → `''`); (2) the
  id is outside the options the select would list
  (`apiKeys.some(k => k.id === stored && k.provider === provider)` —
  the select's own filter, asked as a question). Two
  **absence-is-not-evidence** arms: an UNKNOWN provider keeps the stored
  id (the `known &&` guard — an unloaded provider list proves nothing),
  and an UNLOADED key list (`apiKeys.length === 0`) skips the
  displayability test entirely — stripping a key off a working profile
  would be the worse bug.
- **The always-send save body** (`useProfileForm.ts:210-217`):
  `requestBody.apiKeyId = outboundApiKeyId() || null` unconditionally —
  omitting the field leaves the PUT's `apiKeyId !== undefined` gate
  untripped and every already-poisoned row broken forever; `null` clears
  the column, so a poisoned row **heals on its next ordinary save**.
- **`handleConnect` judges what may LEAVE, not what is held**
  (`:243-249`): `if (requirements.requiresApiKey && !outboundApiKeyId())
  throw new Error('API Key is required for this provider')`.
- All four outbound sites read the chokepoint (`:217`, `:257`, `:292`,
  `:326` — `outboundApiKeyId() || undefined`).
- **The fifth site — the edit-time model fetch twin**
  (`ProfileModal.tsx:84-88,100`): `savedProviderTakesApiKey =
  !savedProvider || (savedProvider.configRequirements?.requiresApiKey ??
  true)` — note the default is **`?? true`** (keys are the common case),
  where the base-URL twin defaults `?? false`. Reads the SAVED profile,
  not form state.
- **`handleProviderChange` stays untouched** (`ProfileModal.tsx:242`) —
  the value is inert while it cannot be shown, not destroyed, and returns
  if the user switches back.
- **v4's new test suite is the parity corpus:**
  `__tests__/unit/components/settings/profile-modal-api-key.test.tsx`
  (304 lines; the real modal over the real hook through the real dropdown
  gesture, `fetchJson` captured; **4 of its 7 cases fail pre-fix**):
  `:135` no key after ANTHROPIC→OLLAMA; `:157` none on hosted→hosted;
  `:180` clears the column on save; `:200` still sends a picked matching
  key; `:218` restores the remembered key on switch-back; `:241` leaves a
  stored key alone when neither list has loaded; `:272` heals a
  mismatched row on its next ordinary save. Mirror all seven 1:1.

## Fix B — bug 77 (surveyed 2026-08-18)

v4's banner ("Generating image..." / "Successfully generated N
image(s)!") above the composer had one teardown — a detached `setTimeout`
in `sendMessage`'s terminal `onDone` — so every other route out of a turn
stranded it, and it had no close control. v4 moves ownership onto the
notice itself (`app/salon/[id]/hooks/useSSEStreaming.ts`):

- `TOOL_STATUS_DISMISS_MS = 6000` (`:37-38`, was inline 3000);
  `toolStatusTimerRef` (`:228`).
- `publishToolExecutionStatus(status)` (`:342-357`) — **the single door**:
  clears any live timer first, sets state; `'pending'` stays up
  indefinitely; a settled status arms its own 6 s dismissal; superseded
  on each new publish; cleared on unmount (`:308-322`).
- `clearPendingToolExecutionStatus()` (`:333-340`) — drops ONLY a
  stranded `'pending'`; a settled notice keeps its own countdown. Called
  at BOTH `onDone` boundaries (`:848` send, `:1016` continue).
- `dismissToolExecutionStatus()` (`:324-331`) — exported; wired through
  `SalonView.tsx:1571-1572` to a new close button on the ChatComposer
  alert (`ChatComposer.tsx:223-254`): `role="status"` (`:226`),
  `aria-live="polite"` (`:227`), message span `flex-1`, close button
  `qt-button-ghost flex-shrink-0 p-1`, `title="Dismiss"`,
  `aria-label="Dismiss notice"`, close icon `w-4 h-4`.
  `stopStreaming` calls dismiss directly (`:1128`).
- Raise sites: `trackToolsDetected:381` (pending, "Generating image..."),
  `trackToolResult:417` (success) / `:424` (error). No new v4 test file
  shipped — the parity spec surface is this lane's to write.
