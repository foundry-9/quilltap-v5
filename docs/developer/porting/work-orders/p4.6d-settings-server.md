## Mandate

the Providers tab + the setup wizard + basic Appearance) consumes, as
dispatch variants: the chat-settings PUT + default-injection, connection
profiles (CRUD + enrichment + the provider actions), API keys (CRUD +
masking + test), the providers listing, and the models read/fetch. You own

handlers in a new `api/settings.rs` (do not grow `api/salon.rs`, which
P4.6c owns).

**Survey-verified starting points:** every family's WRITE repo is ported
(`chat_settings` [full net-read marshaling + typed sub-structs],
`connection_profiles` [incl. `find_by_user_id`/`find_default`], `api_keys`
[W4.7d] + `services::api_key_service`, `provider_models` [upserts],
`roleplay_templates`, `text_replacement_rules`); the provider wire is
ported (`model::provider_models_api` validate/models builders+parsers,

`Registry`). What's missing is the read/list/enrichment side, the
validation layers, the provider-action orchestration, and the dispatch

## Shared contract (BINDING — identical text in p4.6d and p4.6e)

P4.6e codes against these without seeing this lane's code. Implement
EXACTLY; on a conflict STOP and report. All `data` bodies are faithful to
the named v4 route body (same field names/nesting). `Request` internally
tagged camelCase; `Response` adjacently tagged.

- `{"type":"chatSettingsUpdate","settings":{…partial…}}` →
  `{"type":"chatSettings","data":{…}}` (v4's PUT echo — the updated
  settings row); invalid fields → `bad-request` with v4's message. The
  existing `chatSettings` READ now default-injects instead of erroring.
- `{"type":"connectionProfileList"}` →
  `{"type":"connectionProfiles","data":{"profiles":[…],"count":n}}` (v4's
  enriched list shape: each profile + `apiKey:{id,label,provider,isActive}`
  + `tags`).
- `{"type":"connectionProfileCreate","profile":{…}}` /
  `{"type":"connectionProfileUpdate","profileId","profile":{…}}` →
  `{"type":"connectionProfile","data":{"profile":{…}}}`;
  `{"type":"connectionProfileDelete","profileId"}` →
  `{"type":"ack","data":{}}` (v4 `{success:true}` → ack);
  `{"type":"connectionProfileReorder","orderedIds":[…]}` +
  `{"type":"connectionProfileResetSort"}` → ack. Name collision →
  `bad-request`, v4's copy.
- `{"type":"connectionProfileTest","profile":{…}}` →
  `{"type":"connectionTest","data":{"valid":bool,"error"?}}`;
  `{"type":"connectionProfileTestMessage","profile":{…}}` → data faithful
  to v4's test-message body.
- `{"type":"apiKeyList"}` → `{"type":"apiKeys","data":{"apiKeys":[…],
  "count":n}}` (the MASKED projection — `keyPreview`, never the key);
  `{"type":"apiKeyCreate","label","provider","apiKey"}` →
  `{"type":"apiKey","data":{"apiKey":{…,"associations":[…]}}}`;
  `{"type":"apiKeyUpdate","apiKeyId",…}` / `{"type":"apiKeyDelete",
  "apiKeyId"}` / `{"type":"apiKeyTest","apiKeyId"}` →
  faithful bodies (test → `{valid, error?}`).
- `{"type":"providerList"}` → `{"type":"providers","data":{"providers":
  […],"count":n}}` (v4's GET /providers rows; absent-in-manifest fields
  are omitted, documented).
- `{"type":"modelList","provider"?}` → `{"type":"models","data":{…}}`
  (the cached read); `{"type":"modelFetch","provider","apiKeyId"?,
  "baseUrl"?}` → the live fetch+cache, v4's POST /models body.
- Theme preference: P4.6d surveys v4's store and reports; until then
  P4.6e persists via `chatSettingsUpdate {themePreference}` (the typed
  column) and treats a dedicated variant as a possible amendment at
  unification.
- P4.6e builds against a MOCKED CoreClient for anything not yet on main
  (the P4.5 precedent); live wire-up at unification.
