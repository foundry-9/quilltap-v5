## The gap (why this order exists)

**v4.** `uploadChatFile` has one production caller,
`app/api/v1/chats/[id]/files/route.ts:77`. Inside `uploadFileToProject`,
after `repos.files.create`, gated on `category === 'IMAGE'` (from the INPUT
mime, `chat-files-v2.ts:167`), it fires (`:425-437`):

```ts
void autoDescribeChatImageAttachment({ fileEntryId: fileEntry.id, userId, repos })
  .catch(err => logger.warn('Auto-describe failed for chat image upload', {
    module: 'chat-files-v2', fileId: fileEntry.id, error: … }))
```

- **No `chatId`.** The uncensored vision fallback therefore sees
  `chat = null` and only the global on-duty switch decides
  (`file-attachment-fallback.ts:185-205`), so a Locked chat's upload can
  still reach the uncensored desk. That is v4's own gap; **port it
  faithfully (`None`)** and record it as a candidate v4 note, do not fix it.
- **Fires on:** a new row, including the `replace` and `keepBoth` conflict
  resolutions (both go through `uploadFileToProject`).
- **Does NOT fire on:** the duplicate-conflict return, `skip`, and the
  non-project sha-dedup return (`:289-318`, which only re-links an existing
  row).
- The module (skip arms `not-found`, `not-image`, `no-sha`,
  `already-described`, `no-bytes` + warn, `describe-failed` + info) picks
  the image-description profile (else a cheap vision profile, else the
  first vision profile), walks the fallback chain and the Concierge vision
  desk; writes `files.description`, every blank same-sha
  `doc_mount_file_links` row's `description` / `descriptionUpdatedAt` /
  `extractedText` / `extractedTextSha256` / `extractionStatus: 'converted'`
  plus chunks; and calls `enqueueEmbeddingJobsForMountPoint` once per
  touched mount. Log lines: `auto-describe: failed to read bytes…`, `…did
  not produce a description`, `…failed to update link`, `…failed to enqueue
  embedding for mount`, `auto-describe: completed` (with
  `usedUncensoredFallback`).

**v5.** The pipeline is ported and differential-covered
(`photos/auto_describe_attachment.rs:246`; `photo_tools_equivalence` over
`photo-tools.test.ts:325-343`, seven `autodescribe_*` + three `describe_*`
rows) and is live behind the `describe_image` tool (`tools/executor.rs:1333`).
The upload call is a named no-op (`services/chat_files.rs:1137`, inside the
SYNC `upload_file_to_project` on the writer's connection). Measured on the
Friday copy 2026-09-29: four chat uploads described at send time all kept
`files.description IS NULL`.

**The wider gap found while surveying:** there is **no production
`SaveImageSideEffects`**. Only `NoSideEffects` exists
(`photos/save_image_to_album.rs:222`); the engine passes it literally
(`api/engine.rs:4487`, `:4512`), and `with_photo_side_effects`
(`tools/executor.rs:514`) is never called in production. So v4's
`invalidateMountPoint` and `enqueueEmbeddingJobsForMountPoint` after a
photo write are no-ops on EVERY v5 photo path today — save-to-album, the
`describe_image` tool, and (once wired) this upload.

**v4's send-before-describe race is v4's shape, not a bug to fix:** v4's
send-time fallback never persists a description, so a message sent before
the background describe lands makes a second, independent vision call. v5's
send-time reuse (`services/file_fallback.rs:1169`) already matches that
shape. Do not add a wait.
