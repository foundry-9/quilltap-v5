## The ruling (why this order exists)

v4 formats every human-readable date below with `toLocaleString` /
`toLocaleDateString` / `toLocaleTimeString` / `Intl.DateTimeFormat` and **no
`timeZone`** — the host's system zone. The harness runs v4 under `TZ=UTC`, so
at port time "matches v4 under `TZ=UTC`" became "always format in UTC", and
the harness could never see the difference. On real data (#121) it costs:
every chat v5 re-renders gets different chunk text than v4 wrote, so the
v4-faithful upsert nulls every embedding (39 re-embeds at first boot where 5
were owed; a shared v4↔v5 instance churns forever); the model reads times
five hours off in recalled transcripts and the mail tools; v5-WRITTEN letter
prefaces persist the wrong time; and v5 is internally inconsistent (the
Host's `marks the time as …` line is already local). **Ruled (a):** format in
the host zone in production; keep `TZ=UTC` as the pin for both sides.
Declined: (b) keep UTC; (c) a per-instance zone setting (v4 has none).

## Mandate

1. **One explicit zone, passed in.** Every display formatter in the table
   below takes a `&jiff::tz::TimeZone` (a zone VALUE, not a name — a POSIX
   `TZ` string has no IANA name, and `iana_name().unwrap_or("UTC")` would
   silently fall back) and renders each instant with **that instant's own
   offset** (`Timestamp::to_zoned`). **Not** `local_offset_minutes`: that is
   ONE offset taken at `now`, which puts a January letter an hour off when
   rendered in July. Production passes the host zone; tests pass
   `TimeZone::UTC` explicitly.
2. **One home for the host zone.** A core helper (e.g.
   `crate::host_zone::system_display_zone() -> TimeZone`, wrapping
   `TimeZone::system()`; UTC only if the system zone cannot be read), used by
   production call sites and by the three duplicate readers it replaces
   (`quilltap-host/src/paths.rs:88` `system_timezone`,
   `api/autonomous_rooms.rs:46` `system_tz`,
   `services/markdown_transcript.rs:498` `system_tz`) — those keep returning
   a NAME where a name is what they need. `quilltap-web/src/main.rs:155-175`
   already reconciles `QUILLTAP_TIMEZONE` / `TZ` before boot, so Docker's
   setting reaches `TimeZone::system()`; do not move that.
3. **Parse zone-less inputs in the same zone** where v4's `new Date(s)` does
   (V8 reads a zone-less datetime as LOCAL): the Almanack's space-form
   fallback (`format_time.rs` `almanack_date_parse_ms`, the SQLite
   `datetime('now')` vintage) and `almanack/phase1_premises.rs:149`
   `parse_backup_filename`. Render-local over parse-UTC would SHIFT stored
   wall-clock digits by the offset; v4 prints them back unchanged. Do NOT
   widen the shared `episodic::js_date_parse_ms` (its callers are the
   deliberately-UTC set below).
4. **No `std::env::set_var("TZ")` in any test** — it races across parallel
   test threads. Zones are arguments.
5. **Must NOT change** (v4 is explicitly UTC or zone-free there):
   `clock::iso_from_unix_ms`, `system_backup::iso_from_millis`
   (`toISOString`); `episodic.rs`'s anchor line, `resolve_when_phrase`,
   `utc_day_of_week` (v4 `episodic.ts:108,156,204` — `toISOString().slice`,
   `getUTC*`); the distill clock (`memory-tasks.ts:131`);
   `almanack::report_filename`; `memory_weighting::format_relative_age`;
   progressions with an EXPLICIT chat zone (`build_context.rs:3635`); the
   already-local precedents (`chat_timestamp`,
   `markdown_transcript::LocalOffset::Zone`, `day_references`,
   `memory_recap/distill.rs:148` `local_date_stamp`,
   `scenario_builder/system_prompt.rs:201` `format_iso_with_offset`, the
   CLI's `docs_cmd.rs:736` `format_ls_date`) — copy their shape, do not
   touch them.

## Tier 1 — the port

1. **The zone seam** — the core helper (Mandate 2) + the three readers
   consolidated. Unit: the helper returns the system zone; a unit test
   drives every formatter with an injected zone, never the environment.
2. **H1–H4 take a zone** (`format_time.rs`); per-instant offset; the
   Almanack parse made zone-aware for zone-less inputs (Mandate 3) + the
   `parse_backup_filename` twin. Red-first under `America/Chicago`: a
   winter instant and a summer instant rendered from the same process (the
   DST pair — proves per-instant, not one offset); the space-form round trip
   prints the stored digits unchanged.
3. **H5–H8 take a zone** through `render_chat_conversation` and every
   caller (the render job, `read_conversation`, `upsert_annotation`); the
   same-day test (H8) compares dates IN the zone — a pair of messages that
   straddle UTC midnight but not local midnight is ONE day locally (a
   red-first case that proves the span's shape moves, not just its digits).
4. **The Post Office + Suparṇā** — `format_letter_date`,
   `build_reply_preface`, the mail context and whisper take the zone.
   Red-first: a reply preface for a 19:40Z letter reads `02:40 PM` under
   `America/Chicago` (the walk's own D2 bytes).
5. **Web search (H2)** and **the Almanack callers (H3/H4)** thread it.
6. **H9's fallbacks** — `None` and an invalid zone fall back to the passed
   HOST zone, not UTC; `chat_initialize.rs:206` / `carina_query.rs:480`
   pass the host zone as v4's no-zone call resolves. Flip `engine.rs:908-909`.
7. **Production wiring** — every production caller passes
   `system_display_zone()` (or the host's threaded value). A host-level
   test with an injected non-UTC zone proves each surface in the caller
   table receives it (one row per surface — a census, so a new caller that
   forgets the zone is caught).

## Tier 2 — the differential proof that (a) is v4's behaviour, not a new one

8. **Every family listed above re-run from the pin under `TZ=UTC` — zero
   byte moves.** This is the proof the change is invisible under the pin.
9. **A second-zone arm** on `conversation_markdown_equivalence` and
   `mail_carina_tools_equivalence` (or `post_office_routes_equivalence`,
   whichever reaches `build_reply_preface`): the oracle recipe run ALSO
   under `TZ=America/Chicago`, v5 fed the same zone by argument — the
   `day_references` / `enclave_cron` model. Include a DST-straddling
   instant. **This is the first time the harness can see the host-zone
   behaviour at all** — the reason #121 was invisible.
10. **The Almanack space-form parse** under the second zone, if
    `almanack_render_equivalence`'s corpus carries a zone-less stamp (add
    one if it does not; v4's real `new Date` decides the expected bytes).
