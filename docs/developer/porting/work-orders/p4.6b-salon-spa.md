## Mandate

Build the Salon in `apps/web`: the chat list screen, the conversation
screen (header, message list with faithful rendering, composer), and the
live streaming send — v4's `app/salon/**` is the reference. Introduce real
Angular routing. Exit state: with both lanes unified, a browser walks
unlock → salon list → open a fixture chat with real history → send → a
streamed reply renders live, looking like Quilltap.

## Deliverables

### 1. Routing + the list screen

- Introduce the Angular router: `/salon` (list) + `/salon/:id`
  (conversation); the startup gate keeps owning the pre-operational states,
  the shell hosts the router outlet. The shell's existing `chats-list`
  placeholder is superseded by the Salon list (keep the nav rail pointing
  at `/salon`).
- The Salon list screen from `SalonListView` + `ChatCard`: the enriched
  `listChats` DTO (Shared contract) → cards with title, participant avatar
  stack + names, tags, message/memory counts, `updatedAt`, project chip,
  danger badge; empty state with v4's copy; click → `/salon/:id`.
  TanStack Query per the foundation pattern. (Until the sibling lane
  lands, the enriched fields aren't served — code against the pinned DTO
  with graceful absence, and keep the mocked-CoreClient component tests
  authoritative.)

### 2. The conversation read path

- A `ChatDataService` equivalent of `useChatData`: `chatGet` (Shared
  contract) → chat + participants + messages; **port the swipe-group
  splitting** (messages sharing `swipeGroupId` collapse to the newest
  variant by default — this lives in the READ path even before swipe
  arrows exist) and the participant/avatar lookups. Also fetch
  `chatSettings` on open (avatar mode, token display, thinking display,
  danger display).
- The message list: virtualized if cheap in Angular (a plain scroll
  container with `useAutoScroll`-equivalent anchoring is an acceptable MVP
  — record the choice), built from the render-items pipeline: message rows,
  collapsed staff/announcement chips (`system-message-labels.ts` port —
  the personified-sender display names verbatim), whisper + silent labels,
  danger flag badges, timestamps + token badges, avatars.
- **The rendering pipeline (the pure-port exception):** port v4's markdown
  pipeline as a TS service using the SAME npm libs — unified/remark-parse/
  remark-gfm/remark-breaks/remark-rehype/rehype-stringify(+highlight),
  composing `lib/chat/roleplay-rendering.ts` (the inline/line/wrap pattern
  tokenizer + `DEFAULT_RENDERING_PATTERNS` fallback),
  `lib/chat/qtap-linkify.ts` (lookbehind is fine in TS), and
  `escapeMarkdownInBrackets` — v4's own server renderer
  (`lib/services/markdown-renderer.service.ts`) is the closest single-file
  reference since it produces the HTML v4 itself injects via the
  `renderedHtml` fast path. Render into sanitized innerHTML. qtap:// links
  render as styled links; their in-app navigation target is a recorded
  deferral (Document Mode vertical).
- Reasoning display: `ThinkingBlock` (collapsible, gated on the
  thinking-display setting) positioned via the `intersperse-reasoning`
  port. TOOL rows: a minimal standalone row (tool name + success + a
  preformatted result body) — the full 667-line `ToolMessage` renderer is
  deferred.

### 3. The header

Title, the copy-conversation-UUID button (v4 `CopyChatIdButton` inline
variant — icon-only clipboard, same microcopy), project name when present,
and the danger badge. The toolbar-injection indirection is v4 workspace
plumbing — render inline in the conversation screen this round.

### 4. Send + live streaming

- The composer MVP: a plain textarea (Lexical is a locked deferral, D17
  spike later), send + stop buttons, Enter-to-send per v4's behavior,
  draft kept per chat (in-memory is fine; `useDraftPersistence` parity is
  a deferral), and Continue (a `chatSend` with `continueMode: true`).
- Streaming: the P4.5 reducer + `CoreClient.events$` are the engine —
  subscribe/filter by `chatId` BEFORE dispatching, optimistic user bubble,
  the live `StreamingMessage` bubble rendering content through the SAME
  markdown pipeline (rAF/coalesced re-render per v4's buffering if naive
  re-render stutters), status line, tool frames as minimal rows, error
  frame surfaced with v4's styling, `done` reconciliation → re-fetch or
  fold the final message into the list (v4 re-fetches; match it).
  Multi-turn chains (`turnStart`/`turnComplete`/`chainComplete`) render as
  sequential bubbles — the reducer already models this.
- Message actions tier 1: Copy (client-only), Edit (user messages →
  `messageEdit`), Delete (→ `messageDelete` incl. the memory-cascade
  confirmation dialog protocol), swipe arrows + Regenerate (client-side
  variant switching over the swipe groups; `messageSwipe` for
  switch/generate). Tier 2 (only if budget allows, else named deferrals):
  the Speaking-As selector (`chatSetActiveSpeaker` + `speakingAsParticipantId`),
  pause/resume (`chatUpdate {isPaused}`), the user-turn Skip banner —
  which requires porting the pure `skip-signal.ts` to TS (near-verbatim;
  unit-test against cases lifted from v4's own skip-signal tests) and the
  `chatTurnAction skipUserTurn` dispatch.

### 5. The M4 e2e + the mock LLM

- Ship a tiny Node mock LLM (an HTTP server speaking OPENAI-compatible

  mocked-dispatch Playwright variant (route interception) carry the lane.

## Shared contract (BINDING — identical text in both orders)

P4.6b codes its client against these shapes without seeing this lane's
code. Implement them EXACTLY; if implementation reveals a problem with a
pinned shape, STOP and report (the unification pass arbitrates — do not
silently deviate).

Already on main (P4.6b may use today): everything in the P4.4/P4.5 round's
contract (`health`/`unlockState`/`unlock`/`lock`/`setup`/`storePepper`/
`changePassphrase`/`listInstances`/`listChats`/`chatSend`/`chatCreate`,
the global `/api/events` SSE with Green-Room replay-on-subscribe, the
binary GET routes, the terminal REST+WS surface).
`crates/quilltap-core/src/api/types.rs` is the source of truth; `Request`
internally tagged camelCase, `Response` adjacently tagged
(`{"type":…,"data":…}`), errors
`{"type":"error","data":{kind,message,pepperState?}}`.

New/changed this round (P4.6a implements; all `data` bodies are faithful
to the named v4 route body — same field names, same nesting — with the
single documented exception that message projections carry NO
`renderedHtml`):

- `listChats` gains optional fields `excludeTagIds?: string[]`,
  `limit?: number`, `includeAutonomous?: boolean`; its `data` becomes the
  array of v4 `EnrichedChatSummary` objects (`handleList`'s
  `cleanEnrichedChats` output: `id, title, contextSummary, createdAt,
  updatedAt, lastMessageAt, participants[], tags[], project,
  storyBackground, isDangerousChat, conciergeOverride, chatType,
  scriptoriumStatus, _count:{messages,memories}`).
- `{"type":"chatGet","chatId"}` → `{"type":"chat","data":{"chat":{…}}}` —
  v4 `handleGet`'s `{chat}` body (enriched participants, `user`,
  `messages[]` with the full per-message projection minus `renderedHtml`,
  `projectName`, `resolvedAgentModeEnabled`/`agentModeSource`,
  `offSceneCharacters[]`, and the chat flags incl. `turnSkippingEnabled`,
  `isPaused`).
- `chatSend` gains `nudge?: boolean` and `pendingToolResults?: […]`
  (v4 `sendMessageSchema` element shape); blank content with no
  files/tool-results → `bad-request`, v4's exact message.
- `{"type":"chatTurnAction","chatId","action":
  "nudge"|"queue"|"dequeue"|"query"|"skipUserTurn","participantId"?}` →
  `{"type":"turnAction","data":{…}}` — v4 `handleTurnAction`'s body; the
  all-others-skipped refusal is `bad-request` with v4's copy.
- `{"type":"messageEdit","messageId","content"}` →
  `{"type":"message","data":{…}}` (v4's PUT body).
- `{"type":"messageDelete","messageId","memoryAction"?,
  "skipConfirmation"?}` → `{"type":"messageDelete","data":{…}}` — either
  the confirmation body `{requiresConfirmation, memoryCount, messageIds,
  isSwipeGroup}` or `{success, memoriesDeleted}`.
- `{"type":"messageSwipe","messageId","swipeIndex"?}` →
  `{"type":"message","data":{"message":{…}}}` (v4's swipe body).
- `{"type":"chatUpdate","chatId","chat":{…partial…}}` →
  `{"type":"chat","data":{"chat":{…}}}` (v4's PUT `{chat}` body).
- `{"type":"chatImpersonate"|"chatStopImpersonate"|
  "chatSetActiveSpeaker","chatId",…}` — per-verb fields + response bodies
  faithful to v4 `actions/participants.ts`.
- `{"type":"chatSettings"}` → `{"type":"chatSettings","data":{…}}` — v4's
  `GET /api/v1/settings/chat` body.
- The chat-create DTO stays `{chat:{…}}` (v4's 201 echo semantics are a
  standing recorded follow-up — do not change its shape this round).
- **The M4 mock-LLM e2e recipe (unification runs it):** the committed
  Salon fixture (P4.6a unit 8) carries an OPENAI_COMPATIBLE connection
  profile; Playwright's global setup spawns a tiny Node mock speaking
  chat-completions SSE, rewrites the profile's `baseUrl` in the fixture
  COPY via `quilltap db --write`, and the live send round-trips through
  the real binary. P4.6b ships the mock + the spec; the live run happens
  at unification once both lanes are on main.
