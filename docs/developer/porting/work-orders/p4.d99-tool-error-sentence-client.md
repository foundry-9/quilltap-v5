## The drift, classified (surveyed 2026-08-21, fresh at `12fe3e6f`)

v4's SSE `toolResult` frame carries a failing tool's human-readable text
in `error`, a **sibling** of `result` (the emitter hoists it there
precisely because `result` is null on failure). v4's client read
`result?.error` — one level too deep — so a failed `generate_image`
always rendered the generic `Failed to generate image` /
`Image generation failed: Unknown error`. v5 reproduced this faithfully
(finding #99); the pin was deliberate: stay faithful until v4 fixes it.
v4 has now fixed it:

- New exported helper `resolveToolResultErrorText(toolResult)` in
  `app/salon/[id]/hooks/useSSEStreaming.ts` (v4 `d9c98cf2`): prefers the
  sibling `error`, keeps the nested `result.error` read as a fallback,
  strips the executor's own leading `Error: ` prefix
  (`raw?.replace(/^Error:\s*/, '').trim()`), returns `undefined` for
  anything empty so the caller's generic string still fires.
- Both render sites (the composer tool-execution notice via
  `publishToolExecutionStatus`, and the error toast) render the same
  resolved sentence: `detail || 'Failed to generate image'` and
  `Image generation failed: ${detail || 'Unknown error'}`.
- The SSE interface gains the documented sibling `error?: string`.
- v4's regression test: `__tests__/unit/hooks/useSSEStreaming-tool-error.
  test.ts` (56 lines) — pins the real failure shape (`result: null` plus
  sibling `error`), the prefix strip, the nested fallback, sibling-wins
  precedence, and the empty cases.
- v4's commit note corrects the original filing: one `imageProfileId`
  feeds both the tool slate and the executor, so the filed
  "offered-but-refused" repro is not reachable that way; the frame
  shape, which is all the defect turns on, is identical either way.
