### Unit 1 — the `chatGetCost` verb

**v4 route arm** — `app/api/v1/chats/[id]/handlers/get.ts:213-231`:
`action === 'cost'`; loads the chat, missing row → `notFound('Chat')`;
`detailed = searchParams.get('detailed') === 'true'` (exact string compare);
dispatches to `getDetailedChatCostBreakdown` or `getChatCostBreakdown`; **the
response is `NextResponse.json(breakdown)` RAW — NOT the successResponse
envelope** (unlike nearly every other action arm; carry this faithfully at
the web edge). Errors → `serverError('Failed to get cost breakdown')`.

**v4 service** — `lib/services/cost-estimation.service.ts`:

- `getChatCostBreakdown` (`:139-190`) reads **stored chat-row aggregates**,
  no recompute: `totalPromptTokens || 0`, `totalCompletionTokens || 0`
  (JS-falsy — a 0/NULL both coerce), `totalTokens` = their sum,
  `estimatedCostUSD ?? null`. `priceSource`: the stored `chat.priceSource` if
  set; else **legacy inference** — a non-null cost with no stored source →
  `'registry'`; else `'unavailable'`. Chat-not-found and the catch arm both
  return the all-zeros object with `priceSource: 'unavailable'` — the service
  never throws.
- `getDetailedChatCostBreakdown` (`:196-289`) iterates
  `repos.chats.getMessages(chatId)`; empty/none → the all-zeros object. Per
  `type === 'message'` row: `promptTokens ?? 0`, `completionTokens ?? 0`,
  `totalTokens = tokenCount ?? (prompt + completion)`, and **per-message
  `cost` is ALWAYS `null` with `source: 'unavailable'`** (v4's own comment:
  "Would need model info to estimate" — port the deadness faithfully). Per
  `type === 'system'` row: `totalTokens = event.totalTokens ?? (p + c)`; the
  cost **accumulation** guard is `!== null && !== undefined`, but the
  per-event `source` ternary checks **`!== null` ONLY** — so a row with
  `estimatedCostUSD === undefined` gets `cost: null` (via `?? null`) with
  `source: 'registry'`. That asymmetry is a real JS quirk; carry it, and put
  a case in the differential that exercises it. `hasAnyCost` →
  `priceSource: 'registry'` for the whole breakdown; the detailed shape adds
  `messageBreakdown[]` + `systemEventBreakdown[]` (see the Shared contract
  for both shapes).

**v5 already has** the write side and the arithmetic — do NOT re-port:
`db/chats_tokens.rs` (`increment_token_aggregates`), `services/cost_events.rs`
(system events + the best-effort bump), `pricing.rs::estimate_cost`. The read
service + verb are the whole gap. The chat-row aggregate columns
(`totalPromptTokens`, `totalCompletionTokens`, `estimatedCostUSD`,
`priceSource`) already exist in the schema and the `db::chats` reads.

**v5 landing spots:** new `Request::ChatGetCost` + `Response::ChatCost`
variants in `api/types.rs` (append after the P4.6ak block, same doc-comment
style); the dispatch arm in `api/engine.rs` (ready-gated like its
neighbors); the implementation beside the other chat reads (either
`api/chat_media.rs` next to `chat_get_background`, or `api/salon.rs` — your
call, one place); the REST leg in `crates/quilltap-web` on the chats GET
route (remember: RAW body, no envelope).

## Shared contract (BINDING — reproduced verbatim in all three orders)

**§1 — the `chatGetCost` verb (lane A provides; lane B consumes).**

- Wire request: `{"type": "chatGetCost", "chatId": "<uuid>", "detailed": <boolean, optional — absent means false>}`.
  Rust: `Request::ChatGetCost { chat_id: String, detailed: Option<bool> }`,
  serde camelCase, appended to the union in
  `crates/quilltap-core/src/api/types.rs`.
- Response: `Response::ChatCost(Value)` carrying v4's breakdown object
  VERBATIM.
  - Non-detailed (v4 `getChatCostBreakdown`,
    `lib/services/cost-estimation.service.ts:139-190`):
    `{"totalTokens", "promptTokens", "completionTokens", "estimatedCostUSD"
    (number|null), "priceSource" ("openrouter"|"registry"|"fallback"|
    "openrouter-estimate"|"unavailable")}`.
  - Detailed (`:196-289`): the same five keys plus
    `"messageBreakdown": [{id, promptTokens, completionTokens, totalTokens,
    cost, source}]` and `"systemEventBreakdown": [{id, type, promptTokens,
    completionTokens, totalTokens, cost, source}]`.
- REST edge: `GET /api/v1/chats/{id}?action=cost[&detailed=true]` returns the
  breakdown **RAW** (v4 `NextResponse.json(breakdown)` — NOT the
  successResponse envelope). Missing chat row → 404 `notFound('Chat')`.
- The SPA client type is `ChatGetCostRequest` in a lane-B-owned api file;
  lane B develops against a route mock until unification.

**§2 — the `chatRegenerateBackground` edge (lane A un-refuses; lane B
consumes).**

- The `Request::ChatRegenerateBackground { chat_id }` variant already exists
  (`types.rs:1832-1842`, wire name `chatRegenerateBackground`) — the variant
  and wire name DO NOT change; only the dispatch target does.
- Success (both arms) is v4's successResponse data:
  `{"message": "Story background regeneration queued" |
  "Story background generation already in progress", "queued": true,
  "jobId": "<uuid>"}`.
- The three badRequest strings, verbatim:
  1. `Story backgrounds are not enabled. Enable them in Settings > Chat Settings > Story Backgrounds.`
  2. `No image profile available for story background generation. Configure an image profile in Chat Settings.`
  3. `No characters in chat to generate background for.`
- Failure fallback: serverError
  `Failed to queue story background regeneration`.

**§3 — merge mechanics.**

- Lane B beats that need lane A's live verbs run ROUTE-MOCKED in-lane and are
  marked `ACTIVATE-AT-UNIFY` in the spec; the unifier drops the mocks and
  runs them live (the established P4.6ab/ac pattern).
- `docs/CHANGELOG.md` and `docs/developer/porting/status-log.md` are
  append-only for all lanes (union-merge at unification).
- Version bumps: lane A bumps the crates it touches (core, web, host,
  harness) per commit; lanes B and C each bump the SPA
  `apps/web/package.json` patch version per commit; the unifier accumulates
  and syncs the LOCKFILE's own version fields (the P4.6an lesson).
