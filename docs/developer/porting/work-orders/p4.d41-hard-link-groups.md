## The drift, classified (surveyed 2026-08-03)

One commit, ~1,190 lines, all on ported surface. The v4 model:

1. **A hard link now has a representation of its own.** New nullable
   `doc_mount_file_links.linkGroupId` + partial index
   `idx_doc_mount_file_links_linkGroupId … WHERE linkGroupId IS NOT NULL`
   (migration `add-doc-mount-link-groups-v1`). Links sharing a non-null
   group are ONE file; a shared `fileId` alone still means nothing — content
   rows are sha256-addressed, so unrelated byte-identical files share a row
   by coincidence (one row in a real instance was shared by 36 character
   vaults). The Zod schema (`lib/schemas/mount-index.types.ts:109`) carries
   the column, so v4's `generateDDL` emits it on fresh instances.
2. **`fanOutGroupFileId`** (`doc-mount-file-links.repository.ts`, inside both
   write transactions): a write through any group member repoints EVERY
   member's `fileId`, carrying `plainTextLength` + conversion status + the
   three `allow*` flags on the document leg (`textState`), and ONLY
   `fileId`/`lastModified`/`updatedAt` on the blob leg (`textState: null`).
   Per-link `description`/`extractedText` are NEVER propagated. Null group →
   no-op. Both `linkDocumentContent` and `linkBlobContent` now select
   `id, fileId, linkGroupId` off the existing link (previously just `id`)
   and return `groupSiblings: GroupSibling[]`.
3. **`gcOrphanedFileRow`** (same file): after a content-addressed rewrite
   repoints a link (`existingLink.fileId !== fileRow.id`), the abandoned
   `doc_mount_files` row is collected if NO link references it — deleting
   `doc_mount_documents` + `doc_mount_blobs` payload rows EXPLICITLY first
   (the FK cascade only exists on migration-created tables; schema-generated
   tables have no FKs at all), then the file row. Shared with `deleteWithGC`.
   This fires on the ORDINARY ungrouped write path too — it is the part of
   the drift every tier-2 rewrite family will see.
4. **`deleteWithGC`**: selects `linkGroupId` too; after deleting the link,
   if the group has ≤1 survivor the group id is NULLed on the survivors
   ("a group of one is not a link"); the terminal file-row drop goes through
   `gcOrphanedFileRow` (explicit payload deletes replace the cascade
   reliance).
5. **`bindLinkGroup(sourceLinkId, destLinkId)`** + **`findByLinkGroupId`**:
   enrol two links in one group — reuses the source's existing group id
   (linking a third location EXTENDS the group), mints `randomUUID()`
   otherwise; returns null if either link is gone. Only `docs link` calls
   it; `docs copy` deliberately does not.
6. **`lib/mount-index/link-groups.ts` (NEW)** — `reindexLinkGroupSiblings
   (mountPointId, relativePath)`: after a write lands, re-chunk every OTHER
   member of the group (chunks are keyed per-linkId). Never throws (log +
   skip — the triggering write already succeeded); cheap no-op for ungrouped
   links. v4's "parent-process only" caveat is the forked-job-child IPC
   buffer — v5 is in-process, so per the locked job-runner non-port ruling
   the v5 analogue simply runs it directly; record that as a non-divergence.
   Call sites: `database-store.ts` `writeDatabaseDocument` (after the chunk
   pass, its own try/log), and `doc-edit/shared.ts:471`
   `triggerReindexIfNeeded` (chained after `reindexSingleFile`, before the
   embedding enqueue + refreshStats).
7. **`file-ops.ts`**: `hardLinkDbToDb` gains `bindGroup: boolean` and returns
   the dest link id it minted; `copyFile`'s db-link branch passes
   `bindGroup: false` (a copy shares a deduped row until the first write,
   then forks); `linkFile`'s db→db branch passes `bindGroup: true`; the
   fs→fs branch — where the OS already shares bytes through the inode —
   looks up the dest link after `linkFilesystemFile` and calls
   `bindLinkGroup(sourceInfo.linkId, destLink.id)`, warning (not failing)
   if either id is missing.
8. **`ensureLinkGroupColumn`** (`mount-index-case-repair.ts:299+`): PRAGMA
   `table_info`, `ALTER TABLE … ADD COLUMN "linkGroupId" TEXT DEFAULT NULL`
   if absent, then `CREATE INDEX IF NOT EXISTS` the partial index. v4 calls
   it from BOTH repositories' init because v4's `safeQuery` turns "no such
   column" into silent nulls. **v5's premise differs** (survey below).
9. **`doc-mount-documents.repository.ts`**: the joined view
   `DocMountDocumentWithLink` gains `linkGroupId: string | null`; all four
   joined SELECTs add `l.linkGroupId`.
10. **Export/import**: `ExportedDocumentStoreDocument.linkGroupId?: string |
    null`; the NDJSON writer emits `linkGroupId: d.linkGroupId ?? null` —
    **always present, null when unlinked** (the type comment says "omitted",
    the writer does not omit; match the WRITER's bytes). Import
    (`lib/import/quilltap-import/import-document-stores.ts`) collects
    `membersByExportedGroup` during the document loop, then a second pass
    re-binds each group with ≥2 members via `bindLinkGroup(anchor, member)`
    — the exported id is only a grouping token; fresh ids are minted, so
    importing an archive twice cannot fuse the copies; failures push a
    warning `Failed to restore hard link for group "<id>": <msg>`. A group
    whose other members fell outside the export imports as an inert group
    of one. (v4 also added `folderId` + `linkGroupId` to
    `public/schemas/qtap-export.schema.json`; v5 ships no copy of that
    schema — record as no-counterpart.)
11. **CLI (`packages/quilltap/lib/docs-commands.js`)**: `lsFileColumns(db)`
    replaces the static `LS_FILE_COLUMNS` — `linkCount` becomes
    `CASE WHEN l.linkGroupId IS NULL THEN 1 ELSE (SELECT COUNT(*) FROM
    doc_mount_file_links g WHERE g.linkGroupId = l.linkGroupId) END`, with a
    per-process `hasLinkGroupColumn(db)` PRAGMA probe degrading to `1`
    against an un-migrated instance; `linkGroupId` rides in the selection.
    The `--links` sibling expansion + help text change accordingly (survey
    the rest of the diff — the sibling fetch keys move off `fileId`).
    Help-text wording for move/copy/link updated.
12. **The migration** `add-doc-mount-link-groups-v1` (column + index + a
    one-time sweep of the orphaned-content-row backlog) and the migration
    registry guard test — v5 has no migration runner (locked deferral), so
    the column/index arrive via the D23 re-dump (fresh instances) + the boot
    ensure (existing instances), and the backlog sweep becomes part of the
    boot hook (below). The registry guard test is NO-PORT.
13. Docs-only riders: README/API.md/CLI.md/DDL.md, `startup/prettify.ts`
    label (v5 has no migration runner — NO-PORT), `help/cli-docs.md` +
    `help/mount-points.md` (v5 syncs help docs from disk at runtime; bank
    both for `p4.9i2`).
