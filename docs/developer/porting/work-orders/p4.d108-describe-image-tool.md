## The drift, classified (surveyed 2026-08-23, fresh at `a14a1811`)

v4's image vocabulary was three custodial tools and no way to ask what a
picture contains, so models reached for `attach_image` and were told to
file the image first. The commit adds `describe_image(uuid)` and rewrites
the surrounding copy so filing, showing, and looking stay distinct. All v4
line numbers post-commit.

### The new tool

1. **`lib/tools/describe-image-tool.ts`** (NEW, 67 lines). Schema: single
   required `uuid: z.string().min(1)` with describe-text:
   `UUID of the image to look at: the uuid from a Librarian upload
   announcement, an image-v2 file uuid, the id returned by generate_image,
   or an album link uuid from keep_image / list_images.`
   Tool description verbatim (`:38`):
   `Look at an image and get a detailed description of what it contains.
   Use this whenever you need to know what is IN a picture — one the user
   just uploaded, one you generated, or one in an album. This is the only
   tool that tells you what an image depicts; keep_image and attach_image
   are filing and display, and neither shows you anything. Most images are
   already described, so this is usually instant; otherwise it runs a
   vision model. If the image was attached to a recent message and you can
   already see it, you don't need this — use it when you can't, or when
   you want the detail.`
   Also exports `validateDescribeImageInput` and `DescribeImageOutput`:
   `file_id, filename, mime_type, width?, height?, description, source`
   where `source: 'stored-description' | 'generation-prompt' |
   'vision-call'`.
2. **The handler** (`photo-handlers.ts`):
   - `resolveDescribableFileEntry(uuid)` (`:493`, private):
     `getImageById(uuid)` → accept if `category === 'IMAGE'`; else
     `docMountFileLinks.findByIdWithContent(uuid)` →
     `files.findBySha256(link.sha256)` →
     `sisters.find(f => f.category === 'IMAGE') ?? sisters[0]`; else
     `null`. **No album-membership check, deliberately** — the doc comment:
     "a character may want to look at an image they have not filed, which
     was the whole trap." Carry it.
   - `handleDescribeImage` (`:509`), three-tier serve order:
     (1) `entry.description?.trim()` → `'stored-description'`;
     (2) `generationRevisedPrompt?.trim() || generationPrompt?.trim()` →
     `'generation-prompt'`;
     (3) `autoDescribeChatImageAttachment({fileEntryId, userId, repos})`
     (dynamic import of `@/lib/photos/auto-describe-attachment`) →
     `'vision-call'`; race arm: `skipReason === 'already-described'` →
     re-read `files.findById` and serve as `'stored-description'`.
   - `formattedText` = `` `${entry.originalFilename}:\n\n${description}` ``;
     the log line `'Described image for character'` with
     `fileEntryId, characterId, source, descriptionLength`.
   - Error strings verbatim:
     `No image found for uuid ${uuid}. Use the uuid from the Librarian's
     upload announcement, the id generate_image returned, or a uuid from
     list_images.` /
     `${originalFilename} is not an image (${mimeType}).` /
     `Could not describe ${originalFilename}: the vision describer
     produced nothing (${skipReason ?? 'unknown reason'}). Check Settings
     → Chat → Image Description Profile.`
3. **`handleAttachImage` error rewrite** (`:413`) — the no-kept-image
   sentence now names both verbs (full new text in the v4 diff; ends
   "…call describe_image with this uuid instead; it does not require the
   image to be in your album.").
