### `llmNumber` exact semantics (v4 `lib/tools/llm-number.ts` — a `z.preprocess` wrapper)

1. `typeof value !== 'string'` → **return untouched**. Numbers, `true`,
   `null`, `[]`, `{}` fall through to the inner schema and are
   rejected/accepted on their own merits. **This is the deliberate
   divergence from `z.coerce.number()`**, which would turn `true`→1 and
   `null`/`[]`→0 — trading a rejected call for a WRONG RESULT, the worse
   failure. Carry that *why* into the port's doc-comment.
2. `value.trim()`; trimmed `''` → **return the ORIGINAL string** (not 0).
   An empty string is a missing value, not a zero.
3. `Number(trimmed)`; `Number.isFinite(parsed)` → return the number; else
   **return the ORIGINAL string** so the error names what the model
   actually sent.

**Consequences:** bounds and `.int()` apply **AFTER** conversion —
`"1001"` fails `max(1000)` exactly as `1001` does; `"6.5"` fails `.int()`.
`Number()` semantics, **NOT** parseInt: `"0x10"`→16, `" 5 "`→5,
`"1e3"`→1000, `"Infinity"`→**rejected** (not finite), `"5px"`→NaN→rejected.

**The refactor shape matters:** `.describe()` moved **INSIDE**
`llmNumber(...)`, `.default()`/`.optional()` stayed **OUTSIDE** — that
ordering is what keeps the emitted JSON Schema byte-identical.

### `lib/pascal/dice.ts` (NEW, 234 lines)

Constants: `MIN_DIE_SIDES=2`, `MAX_DIE_SIDES=1000`, `MIN_DICE_COUNT=1`,
`MAX_DICE_COUNT=100`, `MAX_DICE_MODIFIER=1000`.

**Two regexes, deliberately different:**

- `DICE_NOTATION_SCAN = /\b(\d+)?d(\d+)(?:([+-])(\d+))?\b/gi`
  (`dice.ts:69`) — the **prose scanner**; **no whitespace allowed around
  the sign**, which is what keeps `"2d6 - 1 apple"` a plain 2d6.
- `DICE_NOTATION_STRICT = /^\s*(\d+)?d(\d+)(?:\s*([+-])\s*(\d+))?\s*$/i`
  (`dice.ts:71`) — anchored; **whitespace around the sign IS allowed**,
  because the whole string must be notation and nothing else.

`fromCaptures`: count defaults 1 when absent; modifier magnitude defaults
0; sign `-` negates. Then `withinBounds` — all three integers, count
∈ [1,100], sides ∈ [2,1000], `Math.abs(modifier) <= 1000`.
**Out of bounds → null: SKIPPED, never clamped.**

Exports: `parseDiceNotation` (strict), `scanDiceNotation` (resets
`lastIndex` first; adds `matchText`), `formatDiceNotation` → `"3d6+2"` /
bare `"3d6"` when modifier 0, `secureRandomInt` / `rollDice` / `flipCoin`
(**moved VERBATIM out of `rng-handler.ts` — algorithm unchanged, which is
why v5's byte-stream fidelity survives**), `rollNotation` →
`{count, sides, modifier, results, subtotal, total}` where `subtotal` =
sum of faces and `total` = subtotal + modifier, `formatDiceBreakdown` →
`"3d6+2: [4, 2, 6] + 2 = 14"` / modifier 0 → `"3d6: [4, 2, 6] = 12"`.

### rng-tool / rng-handler changes

`rng-handler` deleted its private `secureRandomInt`/`rollDice`/`flipCoin`
and imports them from `@/lib/pascal/dice`. The executor destructures
`modifier = 0`, computes `total = sum + modifier`, and adds `modifier` +
`total` to **BOTH** the log line and `RngToolOutput`. `RngToolOutput`
gained optional `modifier?` / `total?`. `formatRngResults` gained two
branches (**the zero-modifier strings are byte-for-byte unchanged**):

- single + modifier:
  `` `Rolled a d${type}${sign}${mag}: ${results[0]} ${sign} ${mag} = **${total}**` ``
- multi + modifier:
  `` `Rolled ${rollCount}d${type}${sign}${mag}: [${results.join(', ')}] ${sign} ${mag} = **${total}** total` ``

**The `3d6+2` bug was really two things:** the prose regex now CAPTURES
the modifier, and the rng tool now HAS somewhere to put it.

```rust
/// v4's bounds. Out-of-bounds notation is SKIPPED, never clamped.
pub const MIN_DIE_SIDES: u32 = 2;
pub const MAX_DIE_SIDES: u32 = 1000;
pub const MIN_DICE_COUNT: u32 = 1;
pub const MAX_DICE_COUNT: u32 = 100;
pub const MAX_DICE_MODIFIER: i64 = 1000;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct DiceNotation {
    pub count: u32,
    pub sides: u32,
    pub modifier: i64,
}

#[derive(Debug, Clone, PartialEq)]
pub struct DiceRollResult {
    pub count: u32,
    pub sides: u32,
    pub modifier: i64,
    pub results: Vec<i64>,
    pub subtotal: i64,
    pub total: i64,
}

/// v4 `parseDiceNotation` — the STRICT anchored form
/// (`/^\s*(\d+)?d(\d+)(?:\s*([+-])\s*(\d+))?\s*$/i`): whitespace around the
/// sign IS allowed here. `None` when unparseable OR out of bounds.
pub fn parse_dice_notation(s: &str) -> Option<DiceNotation>;

/// v4 `rollNotation` — `subtotal` = sum of faces; `total` = subtotal + modifier.
pub fn roll_notation(n: &DiceNotation, rng: &mut dyn RandomBytes) -> DiceRollResult;

/// v4 `formatDiceBreakdown` — `"3d6+2: [4, 2, 6] + 2 = 14"`;
/// modifier 0 → `"3d6: [4, 2, 6] = 12"`.
pub fn format_dice_breakdown(r: &DiceRollResult) -> String;
```

**The randomness seam.** `RandomBytes` (+ `OsRandomBytes`, `FixedBytes`) is the
**existing** trait at `crates/quilltap-core/src/tools/rng.rs:99-146`. Lane A MAY
relocate it into `pascal::dice` to mirror v4's own move of the crypto into
`lib/pascal/dice.ts` — but **`crate::tools::rng::RandomBytes` MUST continue to
resolve** (re-export if moved). Lane C imports it by whichever path resolves at
merge and **MUST NOT define its own seam**. `FixedBytes::consumed()` is
load-bearing for both lanes' differentials and must survive any relocation.

**The two regexes are NOT interchangeable** (v4 `dice.ts:69` scan vs `:71`
strict): the scan form forbids whitespace around the sign — that is what keeps
`"2d6 - 1 apple"` a plain 2d6 — while the strict form allows it. Lane A owns
both. Lane C consumes **only** `parse_dice_notation` (strict).
