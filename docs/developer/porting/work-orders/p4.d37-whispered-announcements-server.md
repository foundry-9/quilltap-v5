## The drift, classified (surveyed 2026-08-01)

**`a163862c`** — Insert Announcement gains an audience. The API takes an
optional `targetParticipantIds` on `?action=announcement` and
`?action=announcement-preview` (CHAT PARTICIPANT ids, not character ids);
every id is re-verified server-side against the chat's CURRENT participants
— a removed participant or a foreign-chat id is a 400 on POST (the
alternative is storing a message no filter will ever surface); an empty
array normalizes to NULL (exactly one representation of "public" on the
row). The whispered announcement persists through the ordinary whisper
machinery (`targetParticipantIds` on the message; still
`participantId: null`, `systemKind: 'announcement'`). The in-character
rewrite is told the audience and given those names IN PLACE of the room's
roster. Plus one filter alignment: single-character context building
applied the whisper rule to TOOL messages only — the one path where a
targeted non-TOOL message could reach a character it wasn't addressed to;
it now applies the same test to every role.

**`424a7381`** — two fixes found investigating a misattributed whisper:
(1) ad-hoc announcements now name their speaker in LLM context — new pure
`lib/chat/context/announcement-attribution.ts`, applied in
`buildMessageContext` so single- AND multi-character paths get it; a
`customAnnouncer` that cannot be resolved passes through unnamed (a wrong
name is worse than none); the pass is idempotent; applied at context-build
time only (nothing written back). (2) Prospero's `group-context` whispers
ignored the All Whispers toggle — the sender-level exemption set is
replaced by a (sender → systemKind set) map; that half is SPA-side
(P4.D38's), but its jest suite pins arrive with the pinned worktree.
