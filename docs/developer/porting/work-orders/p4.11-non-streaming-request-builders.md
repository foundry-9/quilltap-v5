## Mandate

1. **Every builder honours `RequestInput.stream`**, producing v4's
   `sendMessage` body byte-for-byte when it is `false` and leaving the
   existing `streamMessage` body **byte-unchanged** when it is `true`.
2. **The request-envelope differential grows a non-streaming leg** — the
   recorder drives v4's real `sendMessage`, the corpus carries a
   `stream:false` vector per provider per shape, and the Rust diff checks
   both halves.
3. **A failed cheap-LLM call becomes visible** (the rider): match v4 on
   whether `llm_logs` records provider failures, so the next outage of this
   class is a one-query diagnosis instead of a four-hour dig.
4. **Prove it on real data** — a closed turn on the Friday copy mints
   memories, which is P4.6bj's still-owed live proof.

## Survey-verified starting points (surveyed 2026-07-22, v5 at `412d7648`)

Every claim below was read out of the tree or empirically confirmed;
re-verify at lane start.

**The defect.** `RequestInput.stream` exists and is set correctly by both
callers — `completion_provider.rs:53` (`stream: false`) and
`streaming_provider.rs:183` (`stream: true`) — but only
`google_chat_url(…, input.stream)` (`request_builder/mod.rs:200`) ever reads
it. Every body builder hard-codes `true`:

| File | Line(s) | Builder |
| --- | --- | --- |
| `request_builder/chat_completions.rs` | `105-106` | `base_body` — shared by OPENAI_COMPATIBLE, DEEPSEEK, Z_AI |
| `request_builder/chat_completions.rs` | `311` | `build_openrouter_body` |
| `request_builder/chat_completions.rs` | `368` | `build_ollama_body` |
| `request_builder/anthropic.rs` | `268` | `build_body` |
| `request_builder/responses_api.rs` | `305`, `309` | `build_openai_body` — **two branches**: chained (`previous_response_id`) and first-call |
| `request_builder/responses_api.rs` | `330` | `build_grok_body` |
| `request_builder/google.rs` | `451` | `build_google_wire_body` — URL already switches on `stream`; the BODY must be checked (unit 6) |

**v4's two bodies (DeepSeek verified field-for-field; the others are unit
2's job).** `plugins/dist/qtap-plugin-deepseek/provider.ts`:

- `sendMessage` (`:183-190`) — `{model, messages, temperature ?? 0.7,
  max_tokens ?? 4096, top_p ?? 1, stream: false}`
- `streamMessage` (`:282-290`) — the same six keys with `stream: true`, plus
  `stream_options: {include_usage: true}`

Everything layered after (`stop`, `tools`/`tool_choice`, `response_format`,
`user_id` from `cacheKey`, `applyProfileParameters`,
`stripThinkingIncompatibleParams`) is **shared verbatim** between the two.
So for this provider the Rust change is exactly:

```rust
.set("stream", json!(input.stream));
if input.stream {
    b.set("stream_options", json!({ "include_usage": true }));
}
```

which preserves key ORDER (v4 keeps `stream` in the same slot and simply
omits `stream_options`). **Do not assume this generalizes** — see unit 2.

**The empirical proof** (two live DeepSeek calls, real key, identical but for
the flag):

```
stream:true  → 200, body starts  data: {"object":"chat.completion.chunk", …
stream:false → 200, body is      {"choices":[{"message":{"content":"pong", …
```

The SSE body reaches `TransportResponse::json()`
(`completion_provider.rs:116`), `serde_json` rejects the leading `d`, and the
caller gets `response parse: expected value at line 1 column 1`. Note the
transport is NOT at fault: `ReqwestTransport::execute`
(`model/transport.rs:218`) correctly converts non-2xx into `TransportError`;
this is a clean 200 with the wrong content type of body.

**Why the differential missed it.**
`crates/quilltap-harness/tests/request_builder_equivalence.rs:7` states it
diffs against envelopes recorded "by intercepting the outgoing `fetch` of v4's
REAL plugin **`streamMessage`**", and every one of the 34 corpus lines sets
`stream: true` (`:126`). The recorder
(`harness/oracle/providers/record-request-envelopes.mjs:192`) drains
`inst.streamMessage(params, 'test-api-key')`. The non-streaming half of the
builder has **never been oracle-checked**. Corpus:
`harness/oracle/fixtures/request-envelopes/request-envelopes.recorded.ndjson`
(34 lines) + `google-request` / `google-wire` (5 each).

**Helpful recorder property:** the interceptor captures the request *before*
any response parse, and the drive loop already wraps the call in
`try/catch … finally` with the comment "The request is captured before any
parse error; keep going" (`:187-196`). So a `sendMessage` that throws on the
canned SSE body still records its envelope — unit 1 does not need a
non-streaming canned response to get correct captures, though supplying one
is cleaner.

**Symptom-hiding rider.** `CheapLlmTaskExecutor::log_call`
(`services/cheap_llm_exec.rs:~176`) is called only on the success arms of
`send_to_provider`, so a failed cheap call writes no `llm_logs` row and the
LLM Inspector shows nothing. This is what made the outage read as "extraction
never ran".

**Two diagnosis facts worth keeping** (they cost hours to rediscover):
`quilltap-web`/`quilltap-host` emit nothing after the startup banner — there
is no tracing subscriber in the workspace and the job runner logs nothing, so
the console is never the instrument; use `./target/release/quilltap db
--data-dir <instance> --json "<sql>"` (read-only, no passphrase on the Friday
copy, safe alongside a running server). And the memory handler persists its
own reasoning to `chat_messages.debugMemoryLogs` on the turn's last assistant
message — read that column first.

## Units

Order matters: unit 1 first, so the corpus can *witness* each builder fix as
it lands; unit 2 before any builder edit, so no fix is written from a guess.

### Unit 1 — the oracle grows a non-streaming leg

Extend `record-request-envelopes.mjs` with a mode flag (`--mode stream|send`,
default `stream` so existing invocations are unchanged) that calls
`await inst.sendMessage(params, 'test-api-key')` instead of draining the
generator. Emit the mode on each line (`{provider, case, mode, input, method,
url, body}`) and **default a missing `mode` to `"stream"`** so the 34
committed lines stay valid without rewriting them.

Update `regenerate-request-envelopes.sh` to drive both modes per provider and
concatenate. Regenerate the corpus at the current oracle baseline
(`e646f58b`; drift-check first) and commit the extended NDJSON.

**Watch:** a provider whose `sendMessage` is not implemented, or that throws
before `fetch`, must record a loud line rather than a silent absence — a
missing capture that reads as "no case" is precisely how this bug hid. Assert
in unit 7 that every provider × mode pair is present.

### Unit 2 — read v4's `sendMessage` for EVERY provider (no edits)

For each of the eight plugins under `~/source/quilltap-server/plugins/dist/`
(`anthropic`, `deepseek`, `z-ai`, `openrouter`, `ollama`, `openai`, `grok`,
`google`), diff `sendMessage`'s body construction against `streamMessage`'s
and write the delta into the lane record. DeepSeek is done (above): `stream`
flips, `stream_options` disappears, nothing else moves.

**Expect at least one provider to differ by more than the flag.** The
Responses-API providers (OPENAI, GROK) and ANTHROPIC build their bodies
differently enough that a separate non-streaming shape is plausible; OLLAMA
and OPENAI_COMPATIBLE may not implement `sendMessage` at all. Record what is
true, then build to it. Anything ambiguous gets resolved by the unit-1
recording, not by reasoning.

### Unit 3 — `chat_completions.rs`

(`:311`) and `build_ollama_body` (`:368`), per unit 2's findings. Key order is

### Unit 8 — rider: make a failed cheap call visible

Read v4's `sendToProvider` (`lib/llm/cheap-llm.ts` and its `logLLMCall` call

leave it — but say so out loud in the lane record either way, because the

## Non-goals (explicit)

- **No streaming-path changes.** The streaming bodies are frozen and
  corpus-pinned; this lane only stops non-streaming callers from borrowing
  them.
- **No transport or response-parser changes.** `ReqwestTransport` handles
  non-2xx correctly and `parse_for_provider` is already the non-streaming
  parser — both were exonerated during the finding-#23 diagnosis.
- **No retry/fallback redesign.** The `profiles_without_custom_temp` retry and
  the uncensored-fallback chain stay as ported.
- **No new logging subsystem.** Unit 8 is a v4-faithful `llm_logs` question,
  not a tracing-subscriber project. Whether the server should log to the
  console at all is a real question this lane deliberately does not answer —
  raise it in the round record.
- **No schema change** (D23 unaffected) and **no release** (D21 + the
  CLAUDE.md hard stop stand).
