## Rulings made at planning (the planner's calls; the human may overrule before lane start — a STOP item if they do)

- **R-A — a failed `quick_check` DROPS the writer and the read pool.** v4
  keeps the connection open after a failed integrity check and lets the
  two guards throw on every use (`mount-index-protection.ts:52-63` sets
  the flag; `requireMountIndexDb` throws `Mount index database is in
  degraded mode`). v5 has no guard layer — its `Option<Writer>` /
  `Option<PartitionPool>` IS the guard — so the same boundary behaviour
  (every read and write of that partition refuses with
  `PartitionUnavailable`) is reached by dropping both and recording
  `Degraded`. Equivalent at every ported seam; the record says so.
- **R-B — absent and degraded stay DISTINCT states.** `PartitionState::
  {Open, Absent, Degraded}` (or the lane's equivalent) on `Db`: Absent =
  no path (today's `None`, R4's "skipped, not counted" stays), Degraded =
  a path that failed to open or failed `quick_check` (COUNTED by the
  structural pass, reported by `/health`). Mapping an open failure to the
  existing `None` alone would answer a healthy 200 — the §R.4(a) trap.
- **R-C — the ladder's delays are v4's constants; tests pay them.** `[200,
  600, 1500]` ms (`OPEN_RETRY_BACKOFF_MS`, `mount-index-client.ts:43`),
  `maxAttempts = 4` (`:113`); the sleeps happen on the opening thread (v4's
  `sleepSync` blocks the event loop — v5 blocks the boot the same ~2.3 s).
  No injection seam (YAGNI): a garbage-mount-index boot arm costs 2.3 s
  once; the record states the measured arm time.
- **R-D — the verify probe is ported as v4 wrote it.** `attemptOpenMountIndex`
  (`:50-84`) runs `SELECT count(*) AS cnt FROM sqlite_master` AFTER the key
  and BEFORE the pragmas; v5's `open_writable` (`db/mod.rs:256-280`) issues
  key → `foreign_keys` → `journal_mode = TRUNCATE` and fails at the
  journal-mode pragma on a garbage file. CLAUDE.md's open-sequence rule
  (`key` first; no `journal_mode` on a READ path) stands; the writable
  path may add the probe between `key` and `foreign_keys`, so the `error`
  the ladder logs is SQLite's `file is not a database` from the SAME step
  as v4's — measured; if the message bytes already agree without the
  probe, record that and skip it.
- **R-E — the structural pass's degraded problems come from v5's
  structural table list, in v4's container order.** v4's
  `verifyStructuralTables` asks each structure-verifiable repository
  (the 11 of `STRUCTURAL_TABLES` — nine mount-index + two LLM-logs? —
  MEASURE: the survey counted NINE mount-index problems and ONE LLM-logs
  problem on v4, i.e. ten of the eleven; find which table has no
  `verifyStructure` on the LLM-logs side and record it) and gets `<label>
  database unavailable: <Sentence>` when `acquireDb()` throws
  (`dedicated-db.repository.ts:176-182`). v5's pass iterates
  `STRUCTURAL_TABLES` (`table_shape.rs`, container order pinned by
  `table_shape_equivalence`'s `census` rows); the new arm emits the SAME
  string per table of a degraded partition, COUNTED, with v4's per-problem
  ERROR `Structural table check failed; reads through this repository will
  come back empty {repository, problem}` and the summary ERROR, and NO
  `Verified dedicated-database table structure` DEBUG for them.
- **R-F — the four INFO lines are ported too.** `Initializing mount index
  database connection {path, walMode}`, `Mount index database connection
  established {path, attempts}`, and the LLM-logs pair (`llm-logs-client.
  ts:54,85`) fire on EVERY v4 boot; they are in the hunks this lane reads
  (§R.4) and cost nothing — ported at INFO with capture pins (Tier 2), the
  `walMode` value as v4 computes it for TRUNCATE journaling (`false` —
  measure).
