## Why this is a re-divergence, not a fresh port (read `impersonation-overlay-spa-gaps`)

Impersonation is a pure OVERLAY (Bug 44): an impersonated seat keeps
`controlledBy: 'llm'` and its id lives in `chat.impersonatingParticipantIds`.
On the 2026-08-07 dogfood walk of P4.D56, v5's `salon-conversation.ts` turn
banner was briefly "fixed" (dogfood #70) to consult the overlay, then
**REVERTED** (`3435055c`) because at that time v4's own client banner keyed on
the bare `controlledBy` — so v5 was already faithful and the change was a
divergence. **v4 has now changed its client** (`1bed814f`) to gate the banner
on `isUserDrivenSeat` and to reconcile the optimistic bubble via
`findActiveUserParticipant`. So this lane **re-applies exactly what P4.D56
reverted, and more** — v5 now diverges to match v4's new client. The memory note
`impersonation-overlay-spa-gaps` is the full context; the hard lesson stands:
**the oracle for an SPA behavior is v4's CLIENT component**, and v4's client has
now moved. Findings #71/#72 (v4 Bugs 45/46) are what this closes.

## The drift, classified (surveyed 2026-08-07)

v4 `1bed814f` changes four salon files + adds one component:

**Bug 45 — the optimistic bubble flickers to the wrong author while impersonating.**
`app/salon/[id]/hooks/useSSEStreaming.ts`: the optimistic user bubble attributed
the just-sent message to the bare `activeTypingParticipantId`, which diverged
from the server's `findActiveUserParticipant` resolution and re-attributed on
refetch. v4 now resolves the optimistic author with `findActiveUserParticipant`
(threading `impersonatingParticipantIds` in from SalonView through refs), so the
bubble is authored correctly from first paint:

```ts
const optimisticAuthor = findActiveUserParticipant(
  participantsAsBaseRef.current,
  activeTypingParticipantIdRef.current,
  impersonatingParticipantIdsRef.current,
)
// participantId: optimisticAuthor?.id ?? activeTypingParticipantIdRef.current ?? undefined
```

**Bug 46(a) — the user-turn banner is now impersonation-overlay aware.**
`app/salon/[id]/SalonView.tsx:~1414`: previously `if (!next || next.controlledBy
!== 'user') return null`. Now:

```ts
if (!next || !isUserDrivenSeat({ id: next.id, controlledBy: next.controlledBy ?? 'llm' },
                               impersonation.impersonatingParticipantIds)) return null
```

i.e. an impersonated seat's own turn IS now announced (and offers Skip), matching
`help/chat-turn-manager.md`.

**Bug 46(b) — new `SpeakingAsAvatar` cue.** A persistent full-height portrait of
the character you're speaking as, seated inside the composer directly left of the
action-button cluster. Bright when you may type, dimmed (`opacity-60
brightness-50`) while a reply is in flight; hidden on the narrowest viewports
(`hidden sm:flex`). Resolved via `findActiveUserParticipant` so it matches server
attribution. New `app/salon/[id]/components/SpeakingAsAvatar.tsx` (60 lines) +
`ChatComposer` gains a `speakingAs` prop; `SalonView` computes `speakingAsSeat`
(a `useMemo` over `findActiveUserParticipant` + roster hydration for the avatar).

**The two helpers (client-safe, from `lib/chat/turn-manager/utils.ts`):**

- `isUserDrivenSeat(participant: {id, controlledBy}, impersonatingParticipantIds?)`:
  `controlledBy === 'user'` OR `impersonatingParticipantIds.includes(id)`.
- `findActiveUserParticipant(participants, activeTypingParticipantId?, impersonatingParticipantIds?)`:
  if `activeTypingParticipantId` names a PRESENT, user-driven seat → return it;
  else fall back to `findUserParticipant` (first PRESENT `controlledBy === 'user'`).

(Full v4 bodies with the invariant comments: `lib/chat/turn-manager/utils.ts:82`
and `:129`. The Rust engine's `participant_filters::is_user_driven_seat` /
`find_active_user_participant` are the already-differential-proven authority;
these client twins must match them byte-for-byte in behavior.)

## ⚠ e2e limitation (from `impersonation-overlay-spa-gaps` / `e2e-playwright-traps`)

You **cannot deterministically force an impersonated LLM seat to be the NEXT
speaker** in a Playwright fixture — turn selection is weighted-random and the
fixture's genuine user seat tends to win. The P4.D56 revert's restored beat
exercises the ordinary user-turn banner (a genuine user seat), NOT the
impersonated-seat banner. Prove Bug 46(a) at the **unit-spec** level (the banner
computeds over a fixed roster + impersonation overlay) rather than via a flaky
e2e assertion; keep the e2e beat exercising the paths that ARE deterministic
(the composer, the `SpeakingAsAvatar` presence when a user seat is active). Do
not add an assertion that depends on a specific weighted-random turn winner.
