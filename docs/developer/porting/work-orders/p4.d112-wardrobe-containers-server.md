- `app/api/v1/wardrobe/transfers/route.ts` end state (604 lines). Key
  shapes:
  - `transferRequestSchema`: adds `source?: { scope: 'character'|'project'|
    'group'|'general', id?: string }` (explicit container — used when the
    dialog browses a shared container directly) alongside the legacy
    `sourceCharacterId` probe, and `components?: 'move'|'copy'|'none'`.
    Two `.refine`s: `'Either sourceCharacterId or source is required'` and
    `'Copying an outfit cannot move its components — the original outfit

    `error.issues.map(i => i.message).join('; ')`.
  - `collectContainerComponents` (:106) — transitive closure of the
    outfit's components **living in the same source container** (other-tier
    components stay put); cycle-tolerant via visited set.
  - `resolveExplicitSource` (:220) — resolves the item within the named
    container; both resolvers now return `containerItems` (the whole source
    container list) on `ResolvedSource`.
  - POST flow (:442-604): plan-first `idMap` (moves keep ids, copies mint
    `randomUUID()`), `remapComponentIds` rewrites every travelling
    reference, planned components carry `characterId:
    destinationCharacterId` and copy-mode fresh timestamps; **refuse before
    any write** if any planned id exists at the destination

    destination` `` — note v4 renders the TITLE inside "the ID of", keep the
    quirk byte-for-byte); components land FIRST, then the outfit; move-mode
    deletes travelling components then the item

    `'Failed to remove item from source after move'`); **post-write

    `nextItem.componentItemIds` against the read-back outfit's, logs

## Shared contract (BINDING — identical text in P4.D112 and P4.D113)

1. **Five dispatch verbs** (serde camelCase over the Request enum),
   mirroring the `ProjectWardrobe*` field shapes exactly:
   - `groupWardrobeList { groupId }` → `{ mountPointId, wardrobeItems }`
   - `groupWardrobeCreate { groupId, item }` → `{ wardrobeItem }`
   - `groupWardrobeGet { groupId, itemId }` → `{ wardrobeItem }`
   - `groupWardrobeUpdate { groupId, itemId, item }` → `{ wardrobeItem }`
   - `groupWardrobeDelete { groupId, itemId }` → `{ success: true }`
   Error bodies: v4's — 404 `Group`, 404 `Group wardrobe item`, 400 with
   the schema's message on create/update.
2. **Transfers body additions** on `wardrobeTransferApply`:
   `source?: { scope: 'character'|'project'|'group'|'general', id?: string }`,
   `components?: 'move'|'copy'|'none'`. Legacy `sourceCharacterId` /
   `sourceProjectId` keep working; at least one of
   `sourceCharacterId`/`source` is required (v4's refine sentence).
3. **Transfers response additions:** `componentsTransferred: number`
   (always) and `unresolvedComponentIds: string[]` (only when non-empty).
4. **The client-safe container module** (P4.D113 transcribes v4's
   `lib/wardrobe/wardrobe-container.ts` 1:1): scope strings
   `'character'|'general'|'project'|'group'`, `encodeWardrobeContainer` =
   `` `${scope}:${id ?? ''}` ``. The server never sees this encoding — it is
   client-only — but the scope-string spellings above are shared with the
   transfers `source.scope` field and MUST NOT drift.
