## The drift, classified (surveyed 2026-08-19, fresh at `9125f492`)

Both halves are v4 fixing bugs **this port filed and reproduces
faithfully today** — so this is a behavior-change port on ported surfaces,
not a convergence-tripwire retirement.

**Bug 81 — one boolean answered two questions.** `requiresApiKey` was
asked both "must this provider have a key?" and "may it?". For
OpenAI-Compatible those answers differ (unauthenticated llama.cpp vs a
hosted endpoint behind a bearer token), and `false` removed OAC from the
Add-New-API-Key provider list and from the profile form's key field. v4
adds an optional `acceptsApiKey` to `ProviderConfigRequirements` (omitted
= "same answer as `requiresApiKey`"), reads BOTH flags through one pure
predicate pair, declares `false`/`true` on the OAC plugin only, and —
the half the filing did not see — routes the four server-side key-lookup
gates through a shared `resolveConnectionProfileApiKey` that requires a
key where required, forwards it where merely accepted, and **fails
loudly on a dangling `apiKeyId`** even where the key is optional.

**Bug 82 — three leading system messages break strict local chat
templates.** The context builder deliberately emits up to three leading
system blocks (cache-prefix design — untouched). The fix is at
request-build time only: `collapseLeadingSystemMessages` folds the
leading run into one block, applied **unconditionally in the Ollama
builder** and, on the OAC base class, gated by a new
`acceptsRepeatedSystemMessages` property defaulting `true` — only the
local-endpoint OAC plugin overrides it `false`, so DeepSeek and every
hosted subclass stays **byte-identical on the wire**.
