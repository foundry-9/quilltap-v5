## Why this order exists (dogfood #37, corrected scope)

Attaching a document-store image via the library picker produced a vision
"description" of a completely different image — the classic
no-image-received signature. Traced end to end on the Friday copy: blob
resolution and byte extraction are CORRECT; the loss is at the wire.
`request_input_from_params` builds each wire message from `m.content` alone
and never reads `params.attachments`; `RequestInput`/`StreamMessage` carry no
image field; NO v5 builder emits an image part for any provider.

**The 2026-07-30 survey settled the open scoping question: in-chat vision IS
affected, not just the describe path.** v4 emits attachments on ALL
completions — streaming chat, non-streaming/regenerate, and describe —
through one shared `messages[].attachments` field feeding the same
per-provider builders. v5 faithfully ports the entire attachment-LOADING
pipeline (chat files → fallback processing → stamping onto the last user
message) and then discards the result at four wire-boundary sites. The
P4.9E4A describe leg, though wired live, has never actually sent an image.

**Why no test caught it:** the harness's canned completion provider keys its
response on `canned_completion_key_with_attachments(…)` — the TEST substrate
reads attachments to pick a canned reply, so the describe differential passed
green while the REAL path dropped them. And the request-envelope corpus (93
lines) contains ZERO attachment vectors. The same blind-spot class as #36 and
the P4.11 one-mode corpus. Closing the corpus blind spot is as much the
mandate as the fix.

## Mandate

Carry image (and v4's document/text) attachments from the formatted-message
layer to the provider wire on every completion path — streaming, tool loops,
non-streaming, regenerate, describe — reproducing v4's per-provider wire
shapes byte-for-byte, including the three providers that DROP attachments and
report failures. Extend the request-envelope corpus with attachment vectors
so the whole surface is differential-pinned. Do NOT touch: `api/types.rs` /
`engine.rs` (P4.9P's — the §1 contract does not move for this lane; the work
is internal model/spine types), `services/pre_compute.rs` / `enclave/**`
(P4.20's), `db/document_store_overlay.rs` (P4.D29's), the SPA.

   attachment rides the LAST user message; tool-loop continuations follow

   regenerate_swipe, `request_input_from_params`. The describe path then
   sends bytes with ZERO further change above the seam (file_fallback

   re-deriving).
3. **The nine builders.** Emit v4's exact wire shapes per the table above —
   including Anthropic's PDF + text `document` blocks, Z.AI's vision-model
   gate, OpenRouter's forced chat-completions path for vision requests, and
   the three drop-and-report providers (DeepSeek/Ollama/OpenAI-compatible)
   with v4's exact failure strings. `attachmentResults` populated on the
   response/final chunk both modes.
4. **The corpus closes the blind spot.** Extend the recorder with attachment
   vectors: image attachment × all nine providers × BOTH modes
   (send/stream), plus Anthropic PDF + text-document arms, plus a
   no-data (`File data not loaded`) failure arm, plus at least one
   multi-attachment message. Regenerate
   `request-envelopes.recorded.ndjson` (+ google legs) at `dcd9440a` with a

   shape, not a hand count) — the 93 pre-existing vectors must stay

   Mutation-proof: with the builder emission disabled, the new vectors must

5. **The wire call-site pin.** Extend the always-on `tool_wire_call_site`
   byte-pin pattern (or add a sibling) so the bytes `execute_completion` and
   the streaming transport hand the wire INCLUDE the image parts — the
   #36/#37 lesson is that the boundary between "params built" and "bytes
   sent" is exactly where green tests concealed a total outage.
