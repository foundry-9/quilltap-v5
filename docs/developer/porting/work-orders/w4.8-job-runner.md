## Architecture decisions (made 2026-07-06 — encode, don't relitigate)

1. **The fork/IPC/buffered-proxy architecture does not port.** It exists
   because Node needed a separate process + a sole-writer parent. v5's
   single-writer runtime (`db::runtime`) already enforces the invariant in
   the type system. v5 job handlers run **in-process** (spawned from the
   runner onto the tokio runtime / a blocking task as appropriate) and write
   through `Db` like every other ported service.
2. **The job-level all-or-nothing write buffer is deliberately dropped** for
   handlers ported as direct-writing services: v4 itself runs those same
   services unbuffered on the request path, and each was differential-
   verified in that form. Document this as a recorded divergence in the
   module doc (the "keep correctness, drop Node workarounds" rule). The
   `write_apply` path REMAINS available for batch-mode handlers — the
   autonomous turn (Unit 4) uses it to keep v4's main-primary ordering.
3. **All timers are host-driver seams.** The runner core exposes
   `tick_claim()` / `tick_stuck_reset()` / `tick_scheduler(kind)` as plain
   functions; a per-host driver (Tauri/CLI/tokio interval in tests) owns
   cadence — the enclave `step()` philosophy (api-boundary.md Part 3), so
   nothing assumes an always-on host.

## What to port (new `services::job_runner`)

1. **The claim loop core** (`pump_claim`): the `claiming` reentrancy lock,
   `maxConcurrentJobs` read from instance settings each pump (default 4,
   clamp 1–32 — add the scoped `instance_settings` read), the
   claim-until-full loop over the ported `claim_next_job`, the
   wake-timer decision for the next `scheduledAt` (`clamp(rawMs, 100,
   300_000)` — return the delay, the host schedules it), and
   wake-on-enqueue (`queue_service` calls a runner wake hook).
2. **Dispatch by job type**: a registry mapping the type string to the
   ported service function — wire every handler that exists today
   (MEMORY_EXTRACTION → `memory_processor`, MEMORY_HOUSEKEEPING →
   `housekeeping`, CHAT_DANGER_CLASSIFICATION →
   `gatekeeper_job`, CONTEXT_SUMMARY → `context_summary`, TITLE_UPDATE,
   CARINA_MEMORY_EXTRACTION / WARDROBE_OUTFIT_ANNOUNCEMENT /
   SCENE_STATE_TRACKING as their orders land) with a **loud fallback** for
   unported types (the `BuiltInToolRunner` precedent: mark failed with a
   "recognized but not yet available" `lastError`; unknown types get v4's
   failure shape — read the source for it). Later orders add rows without
   touching callers.
3. **Completion/failure**: `markCompleted` (NOW wire the v5-only
   `merge_result_into_payload` — the pure merge + tests exist; this closes
   the Phase-2 deferral #3, and the module doc records it as forward-only
   capability since v4-on-SQLite throws there), `markFailed` with the
   ported backoff, per-job error capture (handler panic/Err → the exact
   `lastError` string family), and immediate re-pump after either.
4. **Recovery**: `reset_orphaned_jobs` at startup, `reset_stuck_jobs`
   (ported repo op) on the stuck tick (5-min cadence, host-driven), and the
   interval-boundary error swallowing (a pump failure never kills the
   loop).
5. **The enqueue-helper remainder** in `queue_service` (from
   queue-service.ts): the per-type dedupe rules (memory extraction's
   `(chatId, turnOpenerMessageId, extractionAnchorMessageId)` triple —
   verify the ported one matches; per-chat dedupe for danger / scene-state /
   conversation-render; per-user for housekeeping — PENDING+PROCESSING
   only), `getJobStatus` / `getQueueStats` / `getActiveCountsByType` /
   `cancelJob` / `getPendingJobsForChat` / `cleanupOldJobs` (scoped reads +
   the retention windows).
6. **The scheduler decision leaves** (pure, from the four `scheduled-*.ts`):
   the 24 h cadence + startup grace (5 min / 30 s per kind) + the
   recent-run window (skip if completed within 20 h) as pure
   `should_run(kind, now, last_run)` functions the host driver consults;
   plus the per-kind sweep bodies that are portable — the daily
   housekeeping enqueuer (all-users loop) and the finished-job reaper.
7. **The maintenance sweep** (`collapse-stale-chat-assets.ts`, 264 +
   `chats.getLastPlayedMessageAt`): the new scoped read (last USER or
   character `type:'message'` with `systemSender IS NULL`, falling back to
   `chat.updatedAt`), the staleness rule (STALE_CHAT_RETENTION_DAYS), and
   the protected-file exclusions (storyBackgroundImageId, characterAvatars,
   character default/override image sha256s, photo-album/vault-saved) over
   the ported files/doc-mount delete machinery (`delete_with_gc`).
8. **`ensureProcessorRunning` closure**: the oracle-pinned no-op in the
   watermark/context-summary differentials becomes the real wake hook —
   regenerate those differentials with the hook recorded (the DB effect is
   unchanged; the hook is in-process now).

## Verification plan

The queue SEMANTICS are already tier-2-verified on the repo; the runner adds
policy. Three layers:

- **Tier-1 differentials** for the pure leaves: the wake-delay clamp, the
  scheduler `should_run` window logic, the stale-chat eligibility rule +
  exclusion filter (drive v4's real functions via tsx where exported;
  where inline, extract the oracle by driving the enclosing function with
  injected clock/repos — read the source and pick per function).
- **A tsx real-DB tier-2 differential** for `collapse_stale_chat_assets`
  (parent-side in v4, directly driveable): a fixture with stale + fresh
  chats + every protected-file category; diff `files` +
  the mount-index tables + the return counts.
- **v5 self-tests** for the loop mechanics (no v4 analogue survives the
  architecture change): concurrency cap honored, wake-on-enqueue,
  claim-order (priority/FIFO) observed end-to-end, loud fallback rows,
  stuck reset re-runs, drain-on-shutdown; plus one end-to-end test running
  a REAL ported handler (memory extraction with canned boundaries) from
  enqueue → claim → dispatch → markCompleted, asserting the same table
  state the handler's own differential banks.
- Regenerate `memory_watermark_tier3` + `context_summary_service_tier3`
  (the `ensureProcessorRunning` pin is replaced by the recorded hook).
