### v4 — the bus (`lib/realtime/bus.ts`, 176 lines)

- `COALESCE_WINDOW_MS = 250`, trailing edge, keyed `topic` or
  `topic:id`. First publish arms a timer; publishes inside the window
  only bump a `coalesced` counter (debug-logged); the timer fires ONE
  event with a FRESH `at: Date.now()`, then logs the flush when
  `coalesced > 0`. `timer.unref?.()` — a pending hint never holds the
  process open (v5 twin: the coalesce task must not block shutdown).
- `IS_JOB_CHILD` no-op — **NO-PORT** (in-process runner). The v5
  analogue of "no-op where publishing can't reach a socket" is: no-op
  before the bus is ARMED with the engine's broadcast sender.
- Fan-out: per-socket send, failures swallowed + socket dropped, debug
  "fanned out {delivered}". v5's fan-out IS the broadcast channel —
  the per-socket legs collapse into one `send` on
  `broadcast::Sender<Event>`; log at emit instead and record the
  logging-shape divergence (`differential-blind-to-a-log-only-fix.md`
  applies to the log legs you DO keep — pin with a capturing layer only
  where a log is contractual; these are debug lines, so a comment
  suffices).
- v5 home: a new `quilltap-core` module (e.g. `services/realtime_bus.rs`
  or `realtime/bus.rs` — lane's call). Armed by the engine at boot with
  its `broadcast::Sender<Event>` (`api/engine.rs:552`, accessor
  `event_sender()` at `:695`); a `static OnceLock` mirrors v4's
  deliberate global-singleton choice so services publish without
  signature churn. Publishing before arming (or after engine drop) is a
  silent no-op — unit-pin that.

### v4 — the topic computation (`lib/realtime/job-topics.ts`, 159 lines — PURE)

- `topicsForCompletedJob(jobType | undefined, payload?)`: the switch —
  AUTONOMOUS_ROOM_TURN/SCHEDULE_TICK → `autonomousRooms` +
  `chats:{chatId}`; STORY_BACKGROUND_GENERATION → `chats:{chatId}` ELSE
  `projects:{projectId}` ELSE nothing (the payload says which);
  CHARACTER_AVATAR_GENERATION → `chats:{chatId}` +
  `characters:{characterId}`; CHARACTER_HEADSHOULDERS_BACKFILL →
  `characters:{characterId}`; TITLE_UPDATE / CONTEXT_SUMMARY /
  CHAT_DANGER_CLASSIFICATION / SCENE_STATE_TRACKING /
  WARDROBE_OUTFIT_ANNOUNCEMENT → `chats:{chatId}`; CONVERSATION_RENDER →
  `mountPoints` (collection) + `chats:{chatId}`; default → `[]`. The
  `str()` reader: only non-empty strings count; a hint with an
  unreadable id still emits (id absent = collection-wide, via the
  chats/characters rows whose `str()` returns undefined — the
  `{topic, id: undefined}` shape).
- `topicsForWriteBatch(writes)`: keyed on the buffered write's `method`
  before the first dot. `REPOSITORY_TOPICS`: characters→characters,
  chats→chats, projects→projects, docMountPoints / docMountFiles /
  docMountFileLinks / docMountFolders / docMountDocuments→mountPoints;
  absent namespaces skipped. Id extraction: first arg if non-empty
  string, else first-arg object probed through `TOPIC_ID_FIELDS`
  (characters: characterId,id; chats: chatId,id; projects: projectId,id;
  mountPoints: mountPointId,id). Unreadable id → collection-wide hint
  ("coarser than ideal, never wrong"). Dedup by `topic:id` key across
  the batch, order-preserving.
- ⚠ **v5 has no `method` strings** — its buffered writes are typed
  (`write_partition.rs` / `write_apply.rs:150`). The v5 twin maps v5's
  OWN write representation onto the same topics. Survey the write types
  first; the differential is a PAIRED corpus (see §Differentials).

## Shared contract (BINDING — identical text in `p4.d123-jobs-activity-server.md` and `p4.d125-activity-realtime-spa.md`)

**§A The jobs snapshot** (P4.D123 serves it; P4.D125 reads it):

1. `GET /api/v1/system/jobs` (and the dispatch verb behind it) answers,
   ALWAYS: `stats` (unchanged), `activeByKind`, `startedByKind`,
   `processor` (unchanged).
2. `activeByKind` and `startedByKind` are objects with EXACTLY the five
   keys, in this order: `memory`, `embedding`, `summary`, `danger`,
   `image`; integer values ≥ 0. `activeByKind` = PENDING+PROCESSING job
   rows mapped through the kind table PLUS in-flight registry counts.
   `startedByKind` = monotonic per-kind totals of ended spans ≥ 250 ms,
   since process boot (a fresh server answers zeros; the client treats it
   as a delta base, never absolute).
3. `activeByType` is present iff `includeByType=true` OR
   `includeJobs=true` (v4's `includeByType = param === 'true' ||
   includeJobs`); same shape as before this round.
4. The five kind ids above are the server↔client join; chip labels,
   titles, and CSS classes are client-side (P4.D125 transcribes v4's
   `ACTIVITY_CHIPS`, including the `image`→`qt-queue-badge-story`
   badgeClass quirk).

**§B The realtime hint** (P4.D124 emits it; P4.D125 consumes it):

1. A NEW `EventPayload` variant (working name
   `EventPayload::Realtime(RealtimeHint)`) rides v5's EXISTING event
   channel — the engine broadcast → SSE `GET /api/events`
   (`quilltap-web/src/events.rs`) in HTTP mode, → `quilltap://event`
   (`quilltap-tauri/src/events_pump.rs`) in the shell. **No new
   WebSocket endpoint** — this is a documented mechanism divergence from
   v4's `/api/v1/system/realtime/stream` socket, mandated by the locked
   transport-agnostic boundary ("streaming only ever on the Event
   channel"); record it in the round's divergence notes with this
   rationale.
2. Wire bytes (the `Event` flatten): `{"v":1,"topic":"<topic>"}` plus
   `"id":"<id>"` ONLY when scoped (omitted, never null — v4's spread)
   and `"at":<server-ms>`; no `chat_id`/`room_id`/`progress_id` keys.
   `at` is debugging-only — clients must not order, dedupe, or expire on
   it.
3. Topics, verbatim and closed for this round: `jobs`,
   `autonomousRooms`, `chats`, `projects`, `characters`, `mountPoints`.
   The client IGNORES unknown topics (an older tab must survive a newer
   server).
4. The server coalesces per `topic` / `topic:id` with a 250 ms
   trailing-edge debounce. Clients must tolerate BOTH missed hints (any
   (re)connect, SSE `id` gap, or Tauri `quilltap://resync` ⇒ invalidate
   every mapped prefix) and duplicate hints (invalidation is
   idempotent).
5. Client discrimination on the shared stream: a frame is a hint iff it
   carries both `topic` and `v` (chat/creation frames carry `type` /
   their own keys; the server lane verifies the untagged serde round
   trip stays unambiguous).
6. Fallback polling survives everywhere, gated on channel health: every
   migrated site keeps its original cadence wired but returns
   `false`/long while the channel is healthy (v4 decision 5). In the
   Tauri shell the pump is in-process — "connected" is true whenever
   the listener is attached.
