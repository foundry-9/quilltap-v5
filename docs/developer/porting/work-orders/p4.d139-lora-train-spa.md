## Shared contracts (binding, identical across all six orders)

**§A — the LoRA wire (P4.D138 ↔ P4.D139).**
- `GET /api/v1/image-profiles?action=list-models` response gains
  `loraSupport: Record<modelId, ImageLoraSupport>` between `source` and the
  conditional `fetchError`; models resolving no support are ABSENT from the
  map (the editor's "offer no LoRA rows" signal).
- NEW `GET /api/v1/image-profiles?action=options-schema&provider=…[&model=…]`
  → `{ provider, model: model ?? null, optionsSchema: ProviderOptionsSchema
  | null, loraSupport: ImageLoraSupport | null }` — `null`, never a zero-cap
  object. 400s: `Provider is required`; `` Provider ${provider} is not
  available ``.
- NEW `POST /api/v1/image-profiles?action=lora-metadata`, body
  `{ source: string, hfToken?: string }` → HTTP **200** carrying the
  `HuggingFaceLookupResult` verbatim (`{ok:true,facts}` |
  `{ok:false,reason,repoId,url,detail?}`; reasons `not-a-repo-id |
  missing-or-private | not-found | rate-limited | timeout | network |
  http`). Guards in order, exact sentences: bad JSON or non-object body →
  400 ``A JSON body with a `source` is required``; blank/non-string source
  → 400 `A LoRA source is required`; non-string hfToken → 400
  `hfToken must be a string when supplied`. POST-not-GET because hfToken is
  a credential (carry the comment).
- The stored `loras` entry: `{ source: string (trimmed, min 1), scale?:
  number (finite, 0..10), triggerPhrase?: string, label?: string }`.
  Write-side rejection is the Zod envelope
  `{ error: 'Validation error', details: issues }`, HTTP 400 — never a
  bespoke sentence. No server-side cap.
- `ImageLoraSupport = { maxLoras: number, scale?: {min,max,default,step?},
  sourceKinds: ('url'|'hf-repo'|'provider-id')[],
  supportsPrivateWeightsToken?: boolean }`;
  `DEFAULT_LORA_SCALE = {min:0,max:2,default:1,step:0.05}`.
