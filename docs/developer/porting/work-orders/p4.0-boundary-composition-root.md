# Work order P4.0 — the boundary + composition root

> The first Phase-4 unit, per `phase-4.md` "Decomposition and ordering".
> Drift check at round start (2026-07-08): v4 HEAD is still `2494a84b` — the
> kickoff baseline; no ported unit stale, no re-audit needed.

## Mandate

Build the two pieces between the finished Phase-3 engine library and a
running process:

1. **`quilltap-core::api`** — the `Request`/`Response`/`Event` contract from
   `api-boundary.md` Part 1 (pure types, D8), the `QuilltapCore` trait, and
   the engine-backed implementation (`CoreEngine`) with the first variants:
   **health, the unlock family, instances, list-chats** (D7's
   no-speculative-enumeration rule: exactly the variants this unit's
   consumers — the integration test and the coming P4.2/P4.3 transports —
   need).
2. **`quilltap-host`** — the composition-root crate skeleton (D8/D20): Db
   assembly from an instance directory, the job-runner pump driver, the
   stuck-job reset tick, the enclave 60 s schedule-tick driver, instance
   registry + data-dir resolution, and seam wiring for what is already real.

**Exit criterion:** an integration test boots a fixture instance headless
through `quilltap-host` and pumps enqueued jobs to completion (milestone M0).

## Locked shape (from the surveys)

### The contract (`quilltap-core::api`)

- `QuilltapCore` trait: `dispatch(&self, Request) -> impl Future<Output =
  Response> + Send` (RPITIT, the Phase-3 async-seam precedent) +
  `subscribe(&self) -> tokio::sync::broadcast::Receiver<Event>`. Transports
  are generic over `C: QuilltapCore` (no dyn needed).
- `Request` is internally tagged (`{"type": "...", ...params}`) — the natural
  dispatch-JSON shape; `Response` is adjacently tagged (`type` + `data`) so
  list payloads carry a tag. The HTTP envelope mapping (v4
  `lib/api/responses.ts` semantics, the 503/423 readiness statuses) is
  P4.2's marshalling, not this layer's.
- `Event` is the scope-tagged envelope from D3: optional
  `chatId`/`roomId`/`progressId` + an untagged payload. P4.0 defines the one
  family that already exists (`services::chat_events::ChatEvent`, which
  serializes byte-identical to v4's SSE frames); nothing is emitted yet —
  the channel + envelope exist so every later unit adds variants, not
  plumbing.
- `PepperState` = v4 `DbKeyState` verbatim: `resolved` / `needs-setup` /
  `needs-passphrase` / `needs-vault-storage` (kebab-case on the wire).
- The readiness gate is enforced **in dispatch** (D2): ready-gated variants
  answer `CoreError { kind: Locked }` until the pepper resolves. Health,
  unlock-state, unlock, and list-instances are the always-available family.

### Pepper provisioning (v4 `provisionDbKey`, control-flow port)

`api::provision` reproduces `lib/startup/dbkey.ts`'s resolution order:

1. env pepper + `.dbkey`: SHA-256 hash match → `resolved`; mismatch → a hard
   typed error (v4 `process.exit(1)` becomes `ProvisionError::PepperHashMismatch`).
2. env pepper, no `.dbkey` → `needs-vault-storage` (**operational** — the
   engine boots; this is also the fixture-boot path for tests).
3. `.dbkey` only: internal passphrase decrypts → `resolved`; else
   `needs-passphrase` (+ `hasUserPassphrase = true`).
4. neither → `needs-setup`.

`Unlock { passphrase }` drives `dbkey::load_pepper(dir, Some(pass))`; `Lock`
tears the engine down (drops every `Db` clone via the host teardown) and
returns to `needs-passphrase` — faithful to v4 `lockDbKey` (including the
consequence that an env-pepper-booted, vault-less instance cannot re-unlock;
v4 behaves identically).

**Differential status:** this is the *minimal boot core* of the P4.4
"unlock / pepper-vault service" backfill unit. P4.4 ports the full service
(the `setup`/`store`/`change-passphrase` actions, the 3-attempt limit,
auto-lock resume, the exact response envelopes) **with its differential**
and subsumes/verifies these internals. P4.0 ships unit tests only — the
crypto halves it composes (`load_pepper` decrypt) are already
Friday-verified.

### The `.dbkey` writer primitive

`dbkey::save_dbkey` / `encrypt_pepper` / `generate_pepper` — the encrypt
half of `pepper-crypto.ts` (`PBKDF2-SHA256 × 600 000`, 32-byte salt, 16-byte
IV, AES-256-GCM, `pepperHash` = SHA-256 hex; JSON field order and 0o600 mode
as v4 writes them). Needed so tests (and later the CLI/setup flow) can mint
passphrase-protected instances; round-trip-verified against the ported,
Friday-verified reader. The **`Setup` Request variant is deliberately NOT
implemented**: a fresh instance also needs schema creation (migrations),
which is unported P4.4 surface — wiring Setup without it would mint empty
cipher-correct DBs with no tables.

### First ready-gated read: `ListChats`

`chats_read::find_by_user_id(SINGLE_USER_ID)` (v4
`ffffffff-ffff-ffff-ffff-ffffffffffff`, `lib/auth/single-user.ts`) projected
to a summary DTO (id, title, chatType, messageCount, lastMessageAt,
createdAt, updatedAt). The full chat read shape is already
differential-verified; the DTO is a projection, not new marshaling.

### `ListInstances`

An `InstanceDirectory` seam trait in `api` (the Phase-3 injected-seam
pattern); `quilltap-host` implements the **read path** of the v4 launcher's
instance registry (`packages/quilltap/lib/instances.js`): platform app dir
(`~/Library/Application Support/Quilltap` / `%APPDATA%\Quilltap` /
`~/.quilltap`), `instances.json` schema v1, the POSIX owner/0600 permission
refusal (the file may hold passphrases), names + paths + default. Write
verbs (`add`/`remove`/…) are P4.3 CLI work.

### The host drivers (P4.0 slice)

- **Db assembly:** `<base>/data/{quilltap.db, quilltap-mount-index.db,
  quilltap-llm-logs.db, quilltap.dbkey}` (v4 `lib/paths.ts` layout); main
  required, siblings opened when present. Base-dir resolution: explicit →
  `QUILLTAP_DATA_DIR` → platform default (the docker default lands with
  P4.2's Dockerfile).
- **Job pump loop:** the host registers a composite wake hook
  (`queue_service::set_wake_hook` → runner.wake + a tokio `Notify`), then
  loops `pump_claim` → sleep `next_wake_ms` clamped, else `POLL_INTERVAL_MS`,
  interrupted by the notify or shutdown. v4 `armWakeTimer`/`dispatcherWake`
  semantics over the ported `PumpOutcome`.
- **Stuck-job reset:** every `STUCK_JOB_CHECK_INTERVAL_MS` →
  `tick_stuck_reset(STUCK_JOB_TIMEOUT_MINUTES)`; `reset_orphaned_jobs()`
  once at startup (both already ported, W4.8).
- **Enclave schedule tick:** v4 `scheduled-autonomous-rooms.ts` — every 60 s
  (plus immediately at startup) enumerate `chat_settings` users and
  `enqueue_autonomous_room_schedule_tick(userId)` (dedupe is in the ported
  enqueue). The tick *handler* is the already-ported seam-free
  `AutonomousRoomScheduleTickHandler { tz }`.
- **Handler registry (seam-free set only):** `AUTONOMOUS_ROOM_SCHEDULE_TICK`,
  `WARDROBE_OUTFIT_ANNOUNCEMENT`, `EMBEDDING_REFIT` — the handlers that need
  no model/host seams. Everything else stays on the runner's loud fallback
  until its P4.1 lane lands (`AUTONOMOUS_ROOM_TURN` needs the P4.1a
  streaming composer; avatar/story need image providers; …). The host
  exposes a `with_handler` hook so tests and later lanes register more.
- **Teardown:** the assembler returns a shutdown handle (flag + notify);
  `Lock` dispatch calls it, the loops exit, the runner/Db clones drop, the
  writer thread ends.

## Deferred (tracked, with owners)

- The scheduler sweeps' cadence (daily housekeeping/cleanup, danger scan,
  startup grace) → P4.1d (the bodies `run_scheduled_housekeeping` /
  `run_scheduled_cleanup` are already ported).
- The full unlock/pepper-vault service + its differential + the `Setup`/
  `Store`/`ChangePassphrase` variants → P4.4.
- The instance-registry write verbs + the default-instance resolution chain
  → P4.3 (CLI).
- Event emission (nothing publishes to the broadcast channel yet); the chat
  send dispatch variant → the P4.2 smoke / first SPA vertical.
- The instance lock (v4 single-instance lock semantics) → P4.1d.
