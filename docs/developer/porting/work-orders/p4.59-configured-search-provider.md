## Mandate

Close **dogfood finding #98**: on a real instance configured the way v4 tells
the user to configure it (a `SERPER` row in `api_keys`, created through
Settings → API Keys), v5's web search never runs — v5 builds its provider from
the `SERPER_API_KEY` env var alone with `serper_registered = false`, because
the plugin registry was the standing P4.42 deferral. This lane makes the
**registered-provider half real, natively** — the same move the LLM provider
layer made (declarative manifest data + a native implementation, no plugin
runtime): the Serper search provider is registered the way v4's
`enabledByDefault: true` dist plugin is, the per-call API key resolves from
`api_keys` through the already-wired `DbSearchApiKeys` lookup, the
`GET /api/v1/providers` listing carries v4's `type: 'search'` entry, and the
SPA's API-keys surface can create and show a Serper key.

**Must NOT touch:** the `quilltap-web` route files P4.60 owns; core
`services/title_update_job.rs` (P4.61); no general plugin runtime (loading,
install, hot-load — all stay deferred, tier 3); no other search provider
(Serper is the only search plugin v4 ships); the moderation/theme/tool
registries. The P4.42 invariant stands: **the assembly carries the provider
and the inventory bool derives from it — advertised and executed can never
disagree** (the *shape* changes: registered means advertised-true always, and
a missing key surfaces per-call as v4's `MissingApiKey` sentence — that IS
v4's shape).

## Survey-verified starting points (fresh survey 2026-08-24, at `0ba942b1`)

### v4 — the handler (`lib/tools/handlers/web-search-handler.ts`, 383 lines)

- `:81` `isWebSearchConfigured()` =
  `searchProviderRegistry.isSearchConfigured() || !!process.env.SERPER_API_KEY`.
  `isSearchConfigured()` is **"at least one provider registered"** — it does
  NOT check whether a key exists. So on a default v4 install the tool is
  always advertised; a missing key surfaces per-call.
- `:87–112` `getSearchProviderApiKey(providerName, userId)`:
  `repos.connections.getAllApiKeys()` →
  `find(key => key.provider === providerName && key.isActive)` →
  `apiKeyRecord.key_value` (the RAW secret — v5's `db/api_keys.rs:11` matches;
  no read-time decryption). Any lookup error → `logger.error` + `null`
  (indistinguishable from missing — carry that fold).
- `executeWebSearchTool` (~:124+): validate input → `provider =
  searchProviderRegistry.getDefaultProvider()`. If a provider exists:
  - `provider.config.requiresApiKey` → lookup; missing →
    `logger.warn('Web search provider requires API key but none found', …)` +
    `{ success: false, error: `No API key configured for
    ${provider.metadata.displayName}. Please add your API key in Settings >
    API Keys.`, totalFound: 0, query }`.
  - `provider.executeSearch(query, maxResults, apiKey ?? '', undefined)` →
    map `results` to `{title, url, snippet, publishedDate}` →
    `logger.info('Web search completed via provider plugin', …)` →
    provider failure → `error ?? 'Search provider returned an error'`;
    success → `{success: true, results, totalFound: results.length, query}`.
  - No provider → `executeSerperFallback` (the deprecated env path v5
    already ports, incl. the `'Web search is not configured. Please add a
    search provider API key in Settings > API Keys.'` sentence and the
    deprecation `logger.warn`).
- The outer catch → `error.message ?? 'Unknown error during web search'`.

### v4 — registration (`lib/startup/plugin-initialization.ts:464–500`)

`pluginRegistry.getEnabledByCapability('SEARCH_PROVIDER')` → dynamic module
