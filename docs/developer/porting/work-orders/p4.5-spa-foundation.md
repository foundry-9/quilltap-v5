## Mandate

Build the `apps/web` Angular SPA foundation per `phase-4.md` P4.5 and locked
decisions D13–D18: the scaffold, the one `CoreClient` transport seam, the
SSE stream reducer, the `qt-*` CSS + theme port, the UI primitive set, and
the startup-gate / unlock / setup-wizard screens. Exit state: a browser
pointed at the axum server (serving your built SPA via `--spa-dir`) walks
health-gate → unlock → an app shell, looking like Quilltap.

## Deliverables

  No Nx, no component library, no NgModules.
- Dev loop: `ng serve` with a proxy config forwarding `/api` and `/health`
  to a locally running `cargo run -p quilltap-web -- --port … --data-dir …`
  (the binary exists on main; `--spa-dir` serves a built dist). Document
  both loops (proxy dev + built-dist serving) in `apps/web/README.md`.
- Root `.gitignore`: append node artifacts (`apps/web/node_modules`, dist,
  Angular cache) — append-only, per Ownership.
- Node 24 is available. Commit `package-lock.json`.

### 2. `CoreClient` — the one transport seam (D14)

A single injectable wrapping the whole server surface; components never
touch `fetch`/`EventSource` directly (the Tauri shell later swaps this one
class):

- `dispatch(request: Request): Promise<Response>` — `POST /api/dispatch`.
  Mirror the Rust contract types as TS discriminated unions
  (`crates/quilltap-core/src/api/types.rs` is the source of truth: `Request`
  internally tagged `{"type":"unlock",…}` camelCase; `Response` adjacently
  tagged `{"type":…,"data":…}`; the error envelope
  `{"type":"error","data":{kind,message,pepperState?}}`). Hand-write the TS
  types (small, stable surface) — no codegen this round; keep them in one
  `core-contract.ts` module so unification diffs them against the Rust enums
  easily.
- The readiness refusal: HTTP 503/423 carries v4's `{error:"Setup
  required", setupUrl:"/setup", pepperState}` body alongside the typed
  envelope — surface `pepperState` so the router can redirect without a
  second round-trip.
- `events$` — ONE `EventSource` on `GET /api/events` per app instance
  (global scope-tagged stream, D3): `data:` frames of the `Event` envelope
  (`chatId`/`roomId`/`progressId` scope tags + the flattened payload),
  incrementing `id:` fields, `: keep-alive` comments every 15 s. Parse,
  expose as a typed stream; auto-reconnect (EventSource default) and treat
  a reconnect as a resync signal.
- **TanStack Query for Angular** (the current v5 Angular adapter package)
  layered over `dispatch` for server state (v4's ~52 `useQuery`/`useMutation`
  sites port 1:1 in mental model). Wire the QueryClient provider; use it in
  the screens below.

### 3. The SSE stream reducer (the subtle part)

One service that folds chat-scoped `Event` frames into per-chat streaming
view state. **The spec is v4's client hooks**:
`app/salon/[id]/hooks/useSSEStreaming.ts` + `useMessageStreaming.ts` — read
them closely and port the union semantics:

- `content` — **incremental append**.
- `reasoning` — **cumulative live-replace** (each frame carries the full
  text so far; replace, don't append).
- `reasoningSegments` — positioned segments (anchor offsets into the
  content).
- Tool frames (`toolsDetected` / `toolResult` / TOOL batches) — **spliced at
  `anchorOffset`** into the rendered stream.
- `status` stages, `turnStart`/`turnComplete`/`chainComplete`,
  `hostAnnouncement`, the `done` payload family (incl.
  `skipped`/`skippedParticipantId`), and the transport error frame
  `{error, errorType, details}`.

**One structural difference from v4, handle it explicitly:** v4 streams
frames in the POST response body per request; v5 rides the GLOBAL
`/api/events` stream (scope-tagged by `chatId`) while `dispatch(chatSend)`
resolves only when the turn COMPLETES. So: subscribe/filter by `chatId`
BEFORE dispatching, run the dispatch promise concurrently, and reconcile the
final `done`/result at the end. Do not await dispatch before rendering
frames.

Unit-test the reducer against a **committed frame-trace fixture** — author
it from the real vocabulary (`crates/quilltap-core/src/services/
chat_events.rs` serializes byte-identical to v4's SSE frames; the
quilltap-web m2 e2e and the orchestrator differential expectations show real
orderings). Cover: content+reasoning interleave, a tool batch spliced at an
anchor, a multi-turn chain, a skip done frame, and a mid-stream error.

### 4. The `qt-*` CSS + theme port (D15 — load-bearing, not a reskin)

- Port v4's semantic CSS system: `app/styles/qt-components/_*.css` (~11k
  lines: `_variables`, `_layout`, `_surfaces`, `_typography`, `_chat`,
  `_content`, `_interactive`, `_icons`, `_roleplay`, `_utilities`,
  `_workspace`, `_index`) + `app/globals.css` — custom-property-driven,
  framework-neutral; carry it over structurally intact (file-per-file), not
  rewritten.
- Tailwind v4 with `darkMode: 'class'`, matching v4's config.
- **The six bundled themes** (`themes/bundled/{art-deco, earl-grey,
  great-estate, madmans-box, old-school, rains}/styles.css`) port as
  client-side theme packs this round: a `ThemeService` (signals) that
  applies a theme's custom-property tokens + dark/light class, persists the
  choice (localStorage for now), and exposes a seam shaped like the server
  read (`listThemes` → descriptors; apply by id) — the server themes service
  (the `.qtap-theme` install/registry surface) is deliberately deferred to
  the Settings vertical, and this seam is where it will plug in. If a
  bundled theme's CSS references `/api/themes/assets/...` URLs, copy those
  assets from v4's `themes/bundled/<id>/` into the app bundle and rewrite
  the references — record each rewrite as a documented divergence to
  reconcile when the themes service lands.
- Fonts: survey what v4 bundles/serves (`themes/fonts` route exists for
  theme-supplied fonts); bundle the app's base fonts locally.

### 6. Screens: the startup-gate chain + unlock + setup wizard + shell

Survey v4's equivalents (`/setup` flow, the unlock screen, the startup
status handling) for structure, copy, and visuals, then build:

- **The startup gate**: on boot, `health` → route by `pepperState`
  (`needs-setup` → setup wizard; `needs-passphrase` → unlock;
  operational → shell). Handle the 409 lock-conflict and 503 states with
  v4-voiced screens.
- **The unlock screen**: passphrase → `dispatch(unlock)`; wrong passphrase
  shows v4's error copy; success routes to the shell. (The 3-attempt limit
  and auto-lock idle timer are v4 CLIENT behaviors — survey where they live;
  implement the attempt limit if it's cheap, otherwise record as a vertical
  follow-up. `unlockState.autoLockMinutes` is already in the contract.)
- **The setup wizard**: the first-run flow ending in
  `dispatch({type:"setup", passphrase})` and the **show-the-pepper-once**
  screen (`data.pepper` + v4's exact warning message). Built against the
  pinned Shared contract below; the server variant lands in the P4.4 lane,
  so drive the wizard's submit in component tests against a mocked
  `CoreClient` — the LIVE wire-up e2e happens at unification. Everything
  up to the final dispatch must be real.
- **The app shell**: the outer frame (nav skeleton, theme switcher, the
  chats list from `listChats` as the first real data on screen — an
  empty-state is fine). This is scaffolding for the P4.6 verticals, not a
  Salon.

## Shared contract (BINDING — identical text in both orders)

The P4.5 lane codes its client against these shapes without seeing this
lane's code. Implement them EXACTLY; if implementation reveals a problem
with a pinned shape, STOP and report (the unification pass arbitrates —
do not silently deviate).

Already on main (P4.5 may use today): `POST /api/dispatch`, `GET
/api/events` (global SSE, scope-tagged, `data:` frames + `id:` fields +
15 s keep-alive comments), `GET /health` (200/423/409/503), and the
`Request` variants `health` / `unlockState` / `unlock{passphrase}` / `lock`
/ `listInstances` / `listChats` / `chatSend{…}` with their `Response` DTOs
(`crates/quilltap-core/src/api/types.rs` is the source of truth; the Locked
refusal is `{"type":"error","data":{"kind":"locked","message":…,
"pepperState":…}}` and HTTP 503 carries v4's `setupUrl` body alongside).

New this round (P4.4 implements):

- `{"type":"setup","passphrase":"…"}` →
  `{"type":"setup","data":{"pepper":"<the minted pepper, shown once>",
  "message":"Encryption key generated and stored. Save this value — it will
  not be displayed again."}}`. Refusals use the standard error envelope
  (`bad-request` when the state is not `needs-setup`, etc.).
- `{"type":"storePepper","passphrase":"…"}` → `{"type":"ack","data":{}}`.
- `{"type":"changePassphrase","oldPassphrase":"…","newPassphrase":"…"}` →
  `{"type":"ack","data":{}}` (empty strings allowed — the no-passphrase
  sentinel); wrong old passphrase → error kind mapping to 401-family
  (survey v4's `unauthorized`; extend `ErrorKind` if needed).
- `{"type":"chatCreate", …}` → `{"type":"chatCreate","data":{…}}` — the body
  and DTO are THIS lane's to design from the v4 POST body (P4.5 does not
  consume it this round; the first Salon vertical does next round).
- Creation-progress events: `Event` envelope rows on `/api/events` carrying
  `progressId` scope + a payload with `level`
  (`log|info|warn|error|status`) / `message` / terminal `done|error` —
  field names faithful to v4's frame shapes (survey
  `creation-progress.ts`); P4.5 does not consume these this round.
