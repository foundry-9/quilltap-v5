## Survey-verified starting points (2026-07-24, v4 `e646f58b`)

### The structural divergence: v5 has no proactive distill path

The classifier is `extractMemorySearchKeywords`
(`lib/memory/cheap-llm-tasks/memory-tasks.ts:1221`) — internally
`slice(-20)`, 500-UTF-16-unit per-message cap, the `TODAY:` clock line as
user content, defaults (temp 0.3 / max_tokens 2048 / strict) via
`core-execution.ts:92-128`, task tag `memory-keyword-extraction`. v4 has
THREE callers, each feeding a different window:

- **(a) Proactive — `pre-compute.service.ts:238`** (fires FIRST on a
  normal turn): feeds `messagesSinceLastSpoke` (`:199-210` —
  `messageEvents.slice(lastCharacterMessageIndex + 1)` filtered
  USER/ASSISTANT + the just-saved user message; NO `slice(-12)`). On a
  single-question turn this is often **just the backward-looking question
  alone**. Result flows as `options.recallSignals` into `buildContext`.
- **(b) Fallback — `context-manager.ts:1174`** (only when (a) did not
  pre-search): `existingMessages.slice(-12)` + the new user message
  (`:1164-1172`).
- **(c) Replay — `recall-replay.ts:151`**: `window.slice(-12)` with the
  historical turn's own clock.

**v5 has ONLY the fallback**: `build_context.rs:2077`
(`distill_memory_search`), input assembly `:2043-2076` verified
field-by-field identical to v4's (b). There is no `recall_signals` /
`pre_searched` field on `BuildContextInput` (`:444`) and no pre-compute
service in the crate — only seam comments referencing the proactive path
(`build_context.rs:2141`, `orchestrator.rs:271,870` — read these + the
status log at lane start to establish whether the proactive path was a
RECORDED deferral or a silent gap; that changes the record's wording, not
the work). So v5 always classifies the question diluted by 12 messages of
mostly present-tense context; v4 production usually classifies it nearly
alone. Same prompt, different input — the leading candidate cause.

## The decision procedure (tier 1)

1. **Capture the evidence turns.** Pull the two backward-looking turns
   from the Friday copy's `llm_logs` (the finding's sampled distills read
   `"retrospective": false`) — the full 12-message window v5 sent is IN
   the logged request; reconstruct the `messagesSinceLastSpoke` slice for
   the same turns from `chat_messages`.
2. **Bench v4's real classifier on BOTH windows** (~5 repetitions each —
   the call is sampled at temp 0.3; a verdict that flips run-to-run is
   itself evidence). Record every raw response.
3. **Disposition by the 2×2:**
   - v4 `retrospective:true` on the tight window, `false` on the
     12-window → **port divergence CONFIRMED: the missing proactive path
     is the cause.** Go to "If the fix is ordered" below.
   - v4 `false` on both windows → **NOT-A-BUG** (the classifier is weak
     on this phrasing in v4 too). Record in the findings table with the
     bench transcript; if the prompt deserves strengthening, that is a
     v4-first product change — bank the note, change nothing in v5.
   - v4 `true` on BOTH windows → the window is not the discriminator and
     v5's identical-input fallback should also fire — re-run the same
     window through v5's distill against the same model; if v5 differs on
     identical input, STOP and escalate (that would contradict the tier-1
     differential and means something below the prompt — params,
     provider, parse — diverges in production; survey it before touching
     anything).
   - Mixed/unstable verdicts → record the distribution; treat ≥half
     `true` on the tight window + ≤a-quarter on the wide one as the
     first bullet, otherwise NOT-A-BUG-leaning; surface the transcript
     for the human's read at unification.
