## Rulings made at planning (the planner's calls; the human may overrule before lane start — a STOP item if they do)

- **R-A — the index family is ADDED to provisioning; the TABLE text stays
  the generateDDL surface.** A real v4 first boot creates its tables from
  `SQLITE_TABLES`' hand-written DDL (migration text, ALTER-appended
  columns, `"id" TEXT PRIMARY KEY` without `NOT NULL`) — a DIFFERENT
  `CREATE TABLE` text from generateDDL's with the SAME column set, which
  `dump-fresh-schema.ts:14-21` already records as the accepted asymmetry
  and every tier-2 fixture (built through the repositories) shares with
  v5. Re-dumping the TABLE text from a migrations-first boot would move
  v5's fresh instances AWAY from every committed fixture's shape for no
  behavioural gain (v4's repositories are column-name-addressed; proven).
  The INDEX family has no such defence: an index changes query plans and
  — for the UNIQUE four — write semantics. So: tables from generateDDL
  (unchanged), indexes = generateDDL's set (unchanged, already in
  `fresh_schema.json`) PLUS the migration-created set, dumped from the real
  runner into a SECOND committed artifact `migration_indexes.json`,
  replayed AFTER each partition's `fresh_schema.json` statements.
- **R-B — the measurement is a REAL `tsx server.ts` boot at the pin, not
  the runner called from a script.** The oracle dumper (R-D) drives the
  runner directly for the committed artifact, but the MEASUREMENT that
  decides whether v4 even builds the family on a fresh instance is the
  real boot (`ENCRYPTION_MASTER_PEPPER=<test pepper> QUILLTAP_DATA_DIR=
  <empty dir> PORT=<free> LOG_LEVEL=info npx tsx server.ts` from the pin;
  wait for the startup `Server ready` / `/api/health` 200; SIGTERM; dump
  the three partitions' `sqlite_master` with the test pepper). If the
  real boot's index set differs from the script-driven runner's, the real
  boot wins and the difference is a FINDING in the record.
- **R-C — the boot-time ensures count.** The acceptance set is
  `setup` + ONE v5 host boot, because `seed_built_ins` creates indexes at
  boot that v4 creates in migrations (`idx_folders_userId_projectId_path`
  via `folders_unique_path_repair`, `idx_files_generationKey` via
  `files_generation_key_repair`, the `chat_informs` three via
  `ensure_chat_informs_table`, the help-doc-chunks index, the mount-index
  nocase pair via `mount_index_case_repair`) — the walk's 57 were counted
  AFTER a boot, so they are the net gap. The dump therefore EXCLUDES
  nothing: provisioning replays the whole migration family idempotently
  (`CREATE … IF NOT EXISTS` as v4 writes them), and the boot-time ensures
  stay as they are (a re-homed migration belongs in the boot chain — the
  memory note — but a FRESH instance is the provisioner's to finish).
  Replaying an index the boot also ensures is a no-op by construction;
  the host test pins that the second boot creates nothing.
- **R-D — the dumper drives v4's REAL `MigrationRunner` on an empty data
  dir, then diffs against the generateDDL surface.** `dump-migration-
  indexes.ts` (new, beside `dump-fresh-schema.ts`): the env block
  `build-provision-oracle.ts:26-32` sets (`ENCRYPTION_MASTER_PEPPER`, the
  three `SQLITE_*_PATH`s, `QUILLTAP_DATA_DIR`, `LOG_LEVEL`), `new
  MigrationRunner().runMigrations()` (`migrations/index.ts:92-94` — the
  registry is `migrations/scripts/index.ts:424`), THEN the repositories'
  `ensureCollection` pass the fresh-schema dumper already makes (so the
  generateDDL indexes exist too), then `sqlite_master` per partition; the
  artifact = every `type = 'index'` row whose NAME is not in
  `fresh_schema.json`'s set, as `{ main: string[], mountIndex: string[],
  llmLogs: string[] }` ordered by name, the SQL VERBATIM from
  `sqlite_master` (that is what replays; SQLite stores the statement as
  written). Names in BOTH (an index generateDDL and a migration both
  create under one name) are the generateDDL copy's — recorded in the
  record with the count.
- **R-E — the UNIQUE four are semantics, pinned by behaviour.**
  `idx_chat_documents_unique` (`chatId, filePath, scope, mountPoint`),
  `idx_connection_profiles_userId_name` (`userId, lower(trim("name"))` —
  note the EXPRESSION; the migration also de-duplicates names first, which
  a fresh instance never needs), `idx_group_character_members_group_char`,
  `idx_project_doc_mount_links_proj_mp`: each gets ONE write-path arm on a

- **R-F — no Docker / CLI change.** `api/engine.rs:6807` (`Request::Setup`)
  is the ONE production caller; the no-auth deployment and `quilltap
