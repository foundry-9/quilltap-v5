## Mandate

Close the last refusing leg of the chat-files surface: port v4's
**`handleAttachMountFile`** (`app/api/v1/chats/[id]/files/route.ts:250-346`)
so the composer's "Attach file from library" can attach a document-store file
— the Librarian announcement, the three-source description ladder, and the
vision-LLM describe arm — and replace the loud refusal at
`quilltap-web/src/files_routes.rs:848-858` with the real dispatch.

The refusal's stated reason ("needs the vision-LLM describe seam this build
has no host seam for") is **stale — the survey found every dependency already
on main** (see §Survey). What is missing is the `Request` variant, the
handler, the dispatch arm, and one erased completion-provider thread through
`EngineAssembly` so the dispatch layer can run the describe. That last item is
the only genuinely new machinery, and it has three exact precedents:
`ConsultRunner` (P4.6bd), the `llm_choose` driver (P4.6BL round), and
`announcement_preview` (P4.9E2A round) — all host-side erased runners that
rebuild the LOGGING cheap executor per call.

**⚠ Real spend:** once wired, an attach of an undescribed image costs one
vision-LLM call. The e2e fixture instance has no API keys by design, so the
committed beats must pin the no-key / cached-description arms at zero spend;
the live describe is the next dogfood walk's.

**Must NOT touch:** `apps/web/**` (P4.9E4B's); the embedding/job family
(`services/embedding_*`, `services/queue_service.rs`, `db/conversation_chunks.rs`,
`db/background_jobs.rs`, `api/memories.rs` — P4.6BM's).

## Survey-verified starting points (2026-07-27 — do not re-derive)

### The v4 handler — `handleAttachMountFile`, `files/route.ts:250-346`

Chat-scoped: the outer POST resolves the chat and `notFound('Chat')`s before
dispatch (`:34-38`). Validation is hand-rolled, **no Zod** (`:256-264`):
`{ mountPointId, relativePath } = body ?? {}` with two `typeof !== 'string'`
guards → `badRequest('mountPointId is required')` /
`badRequest('relativePath is required')`.

Reads, in order:
1. `docMountFiles.findByMountPointAndPath` → `notFound('Mount-point file')`
   (`:266-269`).
2. `docMountBlobs.findByMountPointAndPath` → warn +
   `notFound('Mount-point file blob')` (`:271-279`).
3. `docMountPoints.findById` for the display name, **tolerant**:
   `mountPointName = mountPoint?.name ?? null` (`:281-282`).

**The three-source description ladder** (`:284-303`), tracked as
`descriptionSource: 'kept-image-markdown' | 'vision-llm-cached' |
'vision-llm-generated' | 'empty'`:
1. `isPhotosRelativePath(relativePath)` → try
   `buildAttachDescriptionFromKeptImage(mountFile.extractedText)` — preferred
   over vision because it already carries the generation prompt, scene
   snapshot, and saver caption (comment `:284-288`).
2. Else `ensureImageDescription(repos, userId, blob)` (`:188-248`):
   non-`image/*` → `''`; `blob.description` non-empty → returned, **no LLM
   call** (the cache hit); else read blob bytes (failure → warn + `''`),
   build a base64 `FileAttachment`, call
   `generateImageDescription(fileAttachment, repos, userId)`
   (`lib/chat/file-attachment-fallback.ts:483`), and on success **cache** it
   via `docMountBlobs.updateDescription(blob.id, description)` (`:235`,
   persist failure warn-only).
3. Else `''`.

**Writes: exactly one durable new row** — the Librarian announcement —
plus the optional blob-description cache above.
`postLibrarianAttachAnnouncement({chatId, displayTitle, filePath, mountPoint,
mountFileId, mimeType, description})` (`:305-313` →
`lib/services/librarian-notifications/writer.ts:496-502`). The
`doc_mount_files` row id rides as the synthetic message's single
`attachments` entry — **"the announcement message IS the attachment record"**
(`writer.ts:152-160`); no link-table row is written. Null announcement →
`serverError('Failed to post Librarian attachment announcement')`
(`:315-317`) — the only 5xx on the path; everything in the describe ladder is
warn-and-continue.

**Response** (`:331-345`):
```json
{ "file": { "id": "<mountFile.id>",
            "filename": "<blob.originalFileName || mountFile.fileName>",
            "filepath": "<url>", "mimeType": "<blob.storedMimeType>",
            "size": <blob.sizeBytes>, "url": "<url>",
            "type": "mountFile" },
  "announcement": { "id": "<...>", "createdAt": "<...>" } }
```
with `url = /api/v1/mount-points/{mountPointId}/blobs/{encodeURI(relativePath)}`
(`:319`). `descriptionSource`/`descriptionIncluded` go to the LOG LINE
(`:321-329`), not the JSON body.

**No dedupe** on attach: attaching the same `(mountPointId, relativePath)`
twice posts two announcements with the same `mountFileId`. The dedupe is on
the read side only — `GET /chats/{id}/files` carries `seenIds`
(`:389,:395,:417`), already ported. Reproduce; do not "improve".

### The describe ladder's model resolution (`file-attachment-fallback.ts`)

- Profile: `chatSettings.imageDescriptionProfileId` if resolvable (`:39-48`);
  else vision-capable profiles via `profileSupportsMimeType(p,'image/jpeg')`
  (`:55-57`), **preferring `isCheap === true`** (`:64-67`), else first.
- Prompt: the fixed `IMAGE_DESCRIPTION_INSTRUCTION` (`:26-28`). Params:
  temperature default 0.7, max_tokens default 1000; the reasoning-model bump
  to 4000 on `/o1|o3|gpt-5|reasoning/` (`:243-247`). Logged as
  `IMAGE_DESCRIPTION`, including on failure (`:330-349`, `:450-460`).
- The refusal-sniffing heuristics (`:399-425`) and the uncensored-profile
  retry (`:546-560`, only when explicitly configured and different).
- **A quirk to carry, not fix:** `generateImageDescription`'s persisted-text
  tier looks up `repos.files.findById(file.id)` (`:495-524`) but the attach
  path passes a `doc_mount_blobs` id (`files/route.ts:216`), so that tier is
  an effective miss on this path and it falls through to vision. Match the
  behavior; note it in the handler doc.

### The `allowToolUse` question — CLOSED BY THIS SURVEY, no server change

P4.9E3C escalated "v5's chat read does not project `allowToolUse`" as a
server gap. The survey found **v4 does not project it either**:
`enrichParticipantDetail` → `getConnectionProfile`
(`lib/services/chat-enrichment.service.ts:354-379`) returns exactly
`{id, name, provider, modelName, apiKey}`, so v4's own warning-box condition
(`ChatModals.tsx:392`, `p.connectionProfile?.allowToolUse === false`) is
**dead code in v4** — `undefined === false` is never true. v5's enrichment
(`chat_enrichment.rs:340-346`) is byte-faithful. **Do NOT add the
projection** — that would be v5 inventing a field v4 does not ship. The
disposition (v4-faithful-by-outcome; a v4-side item — the box wants either a
projection or deleting) is recorded by P4.9E4B in the SPA doc block and the
dogfood-findings v4-side list; this lane makes no change for it.

## Shared contract (binding — identical in P4.9E4B)

**REST, the modal's two write legs** (the SPA calls these as raw REST through
`apiUrl()`, exactly as v4 does — no §1 mirror for either):

- `POST /api/v1/chats/{chatId}/files?action=link`, JSON `{ "fileId": string }`
  → `{ "file": { "id", "filename", "filepath", "mimeType", "size", "url" } }`
  — **already live on main** (`files_routes.rs:859-878`); neither lane
  changes its shape.
- `POST /api/v1/chats/{chatId}/files?action=attach-mount-file`, JSON
  `{ "mountPointId": string, "relativePath": string }` → the v4 response body
  quoted in §Survey verbatim (`file` with `type:"mountFile"` +
  `announcement {id, createdAt}`; `url` =
  `/api/v1/mount-points/{mountPointId}/blobs/{encodeURI(relativePath)}`).
  Error arms: 400 `mountPointId is required` / `relativePath is required`;
  404 `Chat` / `Mount-point file` / `Mount-point file blob`; 500
  `Failed to post Librarian attachment announcement`.

**§1 (core-contract):** this lane adds `Request::ChatAttachMountFile`
(serde-tagged `chatAttachMountFile`, fields `chatId`, `mountPointId`,
`relativePath`) for dispatch-layer use; P4.9E4B mirrors it into
`core-contract.ts` **name-for-name** but MAY consume the REST leg instead
(v4 fidelity) — the mirror is still owed so the §1 diff stays clean. The SPA
otherwise consumes only verbs already on main: `ChatGroupStores`,
`ChatPhotoAlbums`, `MountPointList`, `ProjectList`, `ToolsList`,
`ProjectToolSettingsUpdate`, `ProjectGet` — all frozen; neither lane
changes them.
