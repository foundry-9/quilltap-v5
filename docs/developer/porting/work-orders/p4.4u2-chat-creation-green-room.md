**Unported — this unit's sub-units:**

### 1. The scenario resolvers (`lib/mount-index/{project,group,general}-scenarios.ts`, ~300 lines)

Preset-scenario body resolution out of the document stores. Read-only over
ported mount-index reads. Note `handleCreate`'s precedence chain: character
`scenarioId` > project path > group path > general path > nothing, each
miss logged-and-falling-through, and the free-text `scenario` notes then
layered via `combine_scenario_text` (preset resolved → notes appended;
none → notes ARE the scenario). The general resolver needs the "Quilltap
General" store pointer (`instance_settings`) — a fixture-provisioned store,
NOT the unit-1 built-in-stores deferral (which stays deferred).
**Read-differential** against v4's real resolvers.

### 2. `buildChatContext` (`lib/chat/initialize.ts`, 253 lines)

The `{systemPrompt, firstMessage, character, userCharacter}` assembly:
overlaid character read (+ optional user character), system-prompt
selection (`selectedSystemPromptId` → default → fallback), scenario
override, and the template pass (`processCharacterTemplates`).
**Read-differential** (real-DB, both sides reading one baked vault
fixture; zero normalization — no clock/id minting on this path; verify
that claim against the source first).

### 3. The identity-stack compiler write side (`lib/services/system-prompt-compiler/compiler.ts`, 200 lines)

`compileAllIdentityStacks` / `compileIdentityStackForParticipant` /
`getCompiledIdentityStack`: build the per-participant identity stack (the
ported `build_identity_stack`) with the chat-level `{{user}}`/
`{{scenario}}`/`{{persona}}` variables resolved, and persist the map to
`chats.compiledIdentityStacks` (a `ChatUpdate` setter likely needs adding —
check whether it mints `updatedAt` in v4 before assuming). Errors NEVER
propagate (the read-through fallback covers a missing cache — the ported
consume side already implements that). **Tier-2 differential** diffing the
persisted column against v4's real compiler over a baked multi-character
fixture. Also verify the ORCHESTRATOR feeds the cached stack per turn the
way v4 does (the ported `build_system_prompt` takes
`precompiled_identity_stack` — confirm the spine populates it from the chat
row; if it passes `None` unconditionally, that is a spine gap this unit
closes, with an orchestrator-corpus case where a compiled cache exists).

### 4. Outfit selections (`lib/wardrobe/apply-outfit-selections.ts`, 351 lines + `lib/memory/cheap-llm-tasks/outfit-selection.ts`, 194 lines)

`applyOutfitSelections` (per-participant modes: `default` / explicit outfit
/ `llm_choose` / none — survey the exact mode set), composing the ported
equip primitives + `chooseLLMOutfit` (a cheap-LLM task: prompt + parser —
generated `prompt_text` submodule per the standing precedent) +
`buildCheapLLMConfig(chatSettings)`, including the `6bf88959` progress
narration (`wardrobe-start` / `wardrobe-result` frames with the
`OutfitPreviewSlots` payload) and the continuation `sourceChatId` carry.
An outfit failure NEVER fails creation (the route's try/catch).
**Tier-3 differential** driving v4's REAL `applyOutfitSelections`
(completions pinned by oracle-recorded canned keys), diffing the chats
`equippedOutfit` effects + the emitted progress frames.

### 5. The greeting generator (`lib/chat/initial-greeting.ts`, 231 lines + route `autoGenerateFirstMessage`, ~260 lines)

`generateGreetingMessage` is a DIRECT provider call (v4 `createLLMProvider`
— the v5 `CompletionProvider` seam, NOT the cheap-LLM executor), with
`buildCharacterCacheKey`, `profileParameters` forwarding, and a `logLLMCall`
write (survey the log type). `autoGenerateFirstMessage` is the route-side
ladder: participant → connection profile → api key (empty-string key when
`apiKeyId` null — local providers), `buildFirstMessageContext` +
the recent-conversations block (each failure swallowed), then the attempt
ladder — survey it fully: attempt 1 full context, the reduced retries, and
the **content-filter Concierge fallback** (composing the ported W4.2
danger routing). Returns `''` on every no-can-do path (no profile, no key,
all attempts failed). **Differential**: canned-provider tier-3 over the
ladder's branch matrix (full-context success, retry, content-filter →
uncensored reroute, no-profile early return), the recorded canned keys
proving the greeting prompt bytes.

### 6. Chat continuation (`lib/chat/apply-chat-continuation.ts`, 334 lines)

`applyChatContinuation`: backfill from the source chat + turn-state
replication + the cross-link bubbles (survey what it copies — messages?
summaries? — and what it writes into both chats). Failure is logged, not
fatal. **Tier-2/3 differential** driving v4's real function over a baked
source chat, diffing both chats' tables.

### 7. The Green Room bus (D6; `lib/chat/creation-progress.ts`, 248 lines)

The per-`progressId` frame vocabulary — `kind`-tagged `status` / `log`
(level `info|warn|error`) / `wardrobe-start` / `wardrobe-result` / `done` /
`error` — as **`api::EventPayload` variants** scope-tagged by
`progress_id`, plus a core-adjacent replay buffer with v4's semantics
(200-frame cap, late-subscriber replay, 60 s TTL after `finish`; NOTE from
the unit-1 survey: v4's handler never actually emits the terminal `error`
frame — hard failures leave the channel to the TTL — port that faithfully,
don't "fix" it). The emitter (`createCreationProgressEmitter`) is inert
without a `progressId`. Frames ride the existing global `/api/events`
stream; implement replay-on-subscribe (or best-effort `Last-Event-ID`)
at the transport-visible layer and document the choice. Unit tests for
cap/replay/TTL; the frame TRACE is diffed in the capstone differential.
