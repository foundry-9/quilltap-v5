## The defect

`dcd9440a` (ported as **P4.D29**) hardened the document-store overlay so that a
failed `properties.json` read can no longer let a patch clobber a settings bag.
It covered **both `StoreEntity`s** — groups (a 2-key bag: `color`/`icon`) and
projects (a 16-key bag).

It did **not** cover the **character vault**, which is the third bag of exactly
the same shape and the largest by blast radius per edit:

| field | DB column? |
| --- | --- |
| `pronouns` | ❌ |
| `aliases` | ❌ |
| `title` | ❌ |
| `firstMessage` | ❌ |
| `talkativeness` | ❌ |
| `canChooseOutfit` | ❌ |

**Measured on the real Friday instance**, not reasoned:
`SELECT name FROM pragma_table_info('characters')` returns **28 columns and not
one of the six**. The vault cutover moved them into `properties.json` and
dropped the columns, so that file is their only home.

### The two halves

**Read — fail-soft, and CORRECT.** `parse_vault_properties` returns `None` on a
parse failure and the read overlay falls back to DB values (`vault_overlay.rs`,
`db/vault_read_overlay.rs:245`). This is v4-faithful (`parseVaultProperties`
returns null) and is why opening a character with a corrupt vault shows nothing
wrong. **Do not change this.**

**Write — the bug.** `db/vault_character_update.rs::read_current_properties`
returns `None` on a parse failure, and the RMW then seeds
`empty_properties_default()`. The next character patch projects those defaults
over all six fields, permanently.

### v4's stale safety comment — worth carrying upstream

v4's write site (`lib/database/repositories/vault-overlay/managed-fields.ts`,
~:236) asserts the opposite, in a comment that reads as a deliberate safety
argument:

> *"Every other field above has a DB column, so 'the caller passed nothing'
> safely reads as 'the value is empty'. `metadata` has no column: a raw
> character row simply cannot carry it."*

That was true before the vault cutover and is false now. It matters because
anyone auditing v4's write path would read it and correctly stop looking. The
v4-side repair is therefore **two things**: the guard, and deleting the claim.

### Reproduction (the dogfood walk's, verbatim)

With the server stopped, against a COPY:

```
quilltap db --data-dir <instance> --mount-points --write \
  "UPDATE doc_mount_documents SET content='{' WHERE fileId = (SELECT l.fileId
   FROM doc_mount_file_links l JOIN doc_mount_points mp ON mp.id=l.mountPointId
   WHERE mp.name='<Name> Character Vault' AND l.relativePath='properties.json')"
```

Start the server, open the character (nothing appears wrong), then **edit and
save**. All six values are gone; fields living in other vault files survive.

## Tier 1 — the fix

1. **Refuse the patch when `properties.json` is PRESENT but UNPARSEABLE.**
   Mirror `dcd9440a`'s shape and wording as P4.D29 ported it for the two
   `StoreEntity`s — including the `properties.json unparseable: <detail>`
   message form and the capitalized entity label, so all three bags refuse
   alike. Reuse P4.D29's machinery rather than inventing a second idiom.

2. **Genuine ABSENCE must still seed defaults.** This is P4.D29's Epsilon arm
   and it is load-bearing: a vault whose `properties.json` was never written
   (or was deliberately deleted) legitimately seeds from
   `empty_properties_default()`. A fix that refuses on absence would break
   provisioning. The distinction is exactly `find_by_mount_point_and_path`
   returning `None` (absent → seed) vs returning `Some(content)` that fails to
   parse (present-but-corrupt → refuse).

3. **Leave the READ overlay alone.** Fail-soft read is v4-faithful and is not
   what loses data.

## Tier 2 — the corpus (the actual deliverable)

4. **Both arms in the characters corpus**, following P4.D29's group/project
   arms case-for-case: plant malformed bytes through the REAL
   `write_database_document`, run the patch, record the thrown message; and
   delete the file, run the patch, prove it seeds.

5. **Prove "wrote nothing" from the post-state**, not just from the message —
   P4.D29's mutation 3 showed the post-state diff is independently sensitive
   and not decorative. The planted bytes must still be the vault's
   `properties.json`, and no defaults-seeded bag may exist anywhere.

6. **MUTATION-PROVE it.** P4.D29's own family was green on its first run, so
   per the D24 rule the sensitivity had to be produced rather than assumed.
   Expect the same here and produce it: short-circuit the refusal back to
   `Ok(None)` and confirm RED; neuter the post-state assertion and confirm the
   message arm still catches it.

7. **Normalization caution, inherited from P4.D29:** the parse-detail tail
   cannot cross the seam (V8's `JSON.parse` text and Zod's issue array vs
   serde's). Truncate at the marker, assert the elided tail is non-empty on
   BOTH sides, and compare everything before it byte-for-byte. A side that
   silently SUCCEEDS must record `null` so a missing refusal goes red rather
   than normalizing away.

## Tier 3 — banked, not this lane
