## Why (the finding this discharges)

Dogfood #63: a real Friday characters export is **791 MB** (chats: 407 MB), and
until 2026-08-04 the transport refused it outright at a mis-derived 100 MB
ceiling. That ceiling is now v4's real one (10 GB), so the import is
**reachable** — and immediately expensive, because v5 holds the whole archive
about three times over:

1. the raw body as `Bytes` (`qtap_routes::import_preview` / `import_execute`
   both take `body: Bytes`), then
2. `read_ndjson_lines(&[u8]) -> Vec<Value>` — every record parsed and retained
   at once, then
3. `assemble_export_from_stream(records: &[Value])`, which takes a **reference**
   and does `record.get("data").cloned()`, so each blob's base64 payload exists
   in both the `Vec` and the assembled export while both are alive.

`ndjson.rs`'s own module header already names this as "the one deliberate shape
change" and justifies it — *"the Rust edge already has the upload as bytes …
and Rust has no string-length ceiling"* — which was true and cheap when the
transport capped bodies at 100 MB. It is neither now.

## ⚠ Check this before starting: the archive is huge for a reason unrelated to streaming

Measured on the real 791 MB characters export (2026-08-04): **29,030 `memory`
records account for 789.6 MB — 99.7%** of the file, at ~29.6 KB each, of which
the `embedding` field is 29,602 bytes. `MemorySchema.embedding` validates to a
`Float32Array`, and `JSON.stringify` of a typed array emits a **1024-key
object**; v5 reproduces that byte-for-byte, so it is v4's shape, not a port
bloat.

Embeddings are derived and regenerable (both apps have an `EMBEDDING_GENERATE`
worker and a boot reconcile). Dropping them from entity exports would shrink
this archive **~300×**, and is queued as a v4-first item in
`dogfood-findings.md`. **If that lands first, this order drops from urgent to
hygiene** — the buffering is still real, but a ~2.5 MB archive does not strain
it. Check the state of that item at lane start and say in the lane record which
world you are in; do not discover it halfway through.

## What is achievable — and what is NOT (establish this before designing)

**v4 does not stream end-to-end either, and the port must not pretend to.**
`assembleExportFromStream` (`lib/import/quilltap-import-stream.ts:56`) consumes
an `AsyncIterable` of records but builds the entire `QuilltapExport` in memory,
and both `previewImport` and `executeImport` take that whole object. v4's
"only one record's worth of bytes … in a V8 string at a time" (its
`next.config.js` comment) is a claim about the **read**, not the import.

So:

- **The target is v4's shape: peak ≈ ONE assembled export** (~3× → ~1×; for the
  791 MB archive, roughly 1 GB instead of 3 GB).
- **Going below that is OUT OF SCOPE and should not be attempted.** A genuine
  record-at-a-time import means abandoning v4's ten-map orchestrator and its
  seven-loop reconcile, which need the whole graph before the first row is
  written. That is a structural divergence, categorically different from the
  reader-side bug-fix divergences the 2026-08-03 ruling authorizes. If a future
  instance makes even 1× intolerable, that is a new ruling, not this lane.

⚠ **A tempting adjacent win that is NOT free:** preview only reports the
manifest plus per-entity `{id, name, exists}`, so it *could* run in
O(entities) rather than O(archive) by never assembling `data` at all. That
departs from v4's `previewImport(exportData)` shape. **Do not take it in this
lane** — record it as a candidate with the departure named, so it is decided
deliberately rather than acquired as a side effect of a perf change.

## Tier 1 — the deliverables

1. **Stage the upload to disk at the edge.** `import_preview` and
   `import_execute` stop taking `body: Bytes`. Stream the request body — and,
   for `multipart/form-data`, the `file` field via `axum::extract::Multipart`,
   which is already chunk-wise — into a temp file, writing as it arrives. The
   shape to copy is P4.9G5's restore `?action=upload` leg on `BackupHost`
   (back-pressured, owned temp state with a `Drop` that cleans up). Nothing
   about the ported validation order may move: the loader's own messages still
   reach the user through `badRequest(err.message)`, and the JSON (non-multipart)
   leg still behaves exactly as today.
2. **Read lines from a `BufRead`.** `read_ndjson_lines` becomes an iterator over
   a reader, preserving every observable behaviour the current doc comment
   enumerates — byte-level line splitting (a multi-byte UTF-8 sequence must not
   split), blank lines and a trailing `\r` dropped, `MAX_LINE_BYTES` still
   firing with v4's verbatim message, the "final line without a newline" arm,
   and `peek_format`'s first-`PEEK_BYTES` sniff (which now needs a peek that
   does not consume). **Keep the existing `&[u8]` entry point as a thin wrapper
   over the reader version** so the committed corpus, the unit tests, and
   `load_qtap_from_upload`'s legacy branch do not move.
3. **Assemble from owned records.** `assemble_export_from_stream` takes
   `impl Iterator<Item = Value>` and **moves** each `data` out of its record
   instead of cloning. The legacy monolithic branch is unaffected (it is one
   JSON object by construction, capped at `MAX_LEGACY_IMPORT_BYTES`).
4. **Prove the memory claim, don't assert it.** A test that imports a
   synthetic multi-hundred-MB NDJSON archive and asserts peak RSS stays under a
   stated multiple of the file size. If that proves too flaky in CI, the
   fallback is a counting allocator around the parse, but **some** measurement
   must exist — the whole lane is a memory claim, and a lane that only proves
   "still correct" has proven nothing about why it was run.

## Tier 2

5. Record in the module header what replaced "the one deliberate shape change",
   with v4's own two ceilings named (the #63 trap: `bodySizeLimit` governs
   Server Actions, `proxyClientMaxBodySize` governs this path).
6. Consider whether `MAX_LEGACY_IMPORT_BYTES` (450 MB, v4's V8-string headroom)
   should still be enforced now that the legacy branch reads from disk. v4's cap
   exists because of a V8 limit v5 does not have — but it is a v4-faithful
   refusal with a v4 message, so **do not remove it without a ruling**.

## The guard

Three committed differential families cover this reader and must be run BY NAME
with `--nocapture`, zero SKIP: `system_import_equivalence` (19 preview cases),
`system_import_state` (11 execute cases), and `system_export_equivalence` (42 —
the writer must stay byte-identical; this lane touches only readers). The
restore families (`system_restore_state`, `system_restore_equivalence`) go
through `parse_backup_zip`, a different path — run them as neutrality proofs.

`EXPECTED_DIVERGENCES` in `system_import_equivalence.rs` includes the ruled
sparse-array blob read, which lives in exactly the code this lane restructures:
**that divergence must survive intact and still be pinned in both directions.**
