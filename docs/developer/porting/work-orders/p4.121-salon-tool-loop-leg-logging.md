## The gap (why this order exists)

v4 has ONE provider funnel, `lib/services/chat-message/streaming.service.ts`
`streamMessage` (`:375`). It logs every call at `chunk.done` when `userId`
is set (`:479-499`): `logLLMCall({ userId, type: 'CHAT_MESSAGE', messageId,
chatId, characterId, provider, modelName, connectionProfileId, request:
{ messages[role, content, attachments], temperature, maxTokens, tools |
undefined }, response: { content: <THIS call's accumulated content>,
finishReason }, usage: lastUsage, cacheUsage: lastCacheUsage,
rawProviderUsage, requestHashes, durationMs: now − <this call's start> })`,
with `.catch` → WARN `Failed to log LLM call from streaming service`.
`buildCharacterCacheKey(characterId)` (`:417`) rides the same argument, so a
leg that passes no `characterId` also sends no cache key.

v5 has no funnel. Its CHAT_MESSAGE writers are per call site, and the three
Salon tool-loop legs were never given one:

| v4 site | ids passed | v5 site | v5 logs? |
|---|---|---|---|
| primary `primary-stream.service.ts:224` | user, msg, chat, **char** | `primary_stream.rs:1307` → `consume_stream` → `log_chat_message_call` (`:1216`) | yes |
| tool-unsupported retry `:288` | user, msg, chat (no char) | `primary_stream.rs:1413` | yes |
| **native re-stream** `native-tool-loop.service.ts:340-350` | user, msg, chat, **char** | `native_tool_loop.rs:478-490` | **NO** |
| **native force-final** `:421` | user, msg, chat (no char) | `native_tool_loop.rs:591-602` | **NO** |
| **text continuation** `text-tool-loop.service.ts:390-400` | user, msg, chat, stop (no char) | `text_tool_loop.rs:696` (`stream_continuation` `:634`) — runs in BOTH text passes (`orchestrator.rs:3200-3230` provider markers, `:3245-3272` simple-json / text-block) | **NO** |
| empty-response recovery `provider-failover.service.ts:665` | user, msg, chat, char, stop | `provider_failover.rs:1206/1338/1689` | yes (P4.68) |
| request-limit recovery `recovery.service.ts:303` | **no userId** | `recovery.rs:390` | no — matches v4 |

(`regenerate-swipe.service.ts:237` calls `provider.streamMessage` directly,
outside the funnel, and logs nothing on either side — out of scope.)

Measured on the Friday copy 2026-09-29 (sweep row S6): a failover turn whose
understudy called `list_mail` wrote ONE row. v4 writes two there, and v4's
own tool turns on the same instance wrote up to 12 rows per message. No
v5-written message on the copy has more than one row.

**Why it matters beyond the Inspector:** `enclave/step.rs:781-791` charges
an autonomous room's token budget from `llm_logs`
(`get_total_token_usage_for_run`, `llm_logs.rs:1068`). **Every tool-loop
leg in an autonomous run is therefore uncharged today** — the budget
under-counts exactly the turns that spend most. The Almanack's usage
figures (`almanack/phase6_wire_records.rs:119-335`) read the same rows. The
chat's own token/cost totals do NOT move (they come from
`StreamingState.usage` via `message_finalizer.rs:1382` /
`cost_events.rs:122`).

**Why no differential saw it:** `orchestrator_tier3_equivalence.rs:2297-2304`
`strip_seam_rows` drops CHAT_MESSAGE on both sides (v4's service-level
`streamMessage` mock swallows its own log), and `native_tool_loop_tier3` /
`text_tool_loop_tier3` mock at the service level too
(`harness/oracle/cases/native-tool-loop-tier3.test.ts:183`; text `:143`), so
their oracles write no rows at all. #111's note that the per-call-site port
"reached the six Salon sites" never counted the loops.

## Mandate

1. **Each of the three legs logs its own row**, through the existing
   `log_chat_message_call` (`primary_stream.rs:992`), never a new writer.
2. **The profile is `state.effective_profile`** — v4's
   `streaming.effectiveProfile`, i.e. the UNDERSTUDY after a failover — not
   the orchestrator's local `effective_profile`.
3. **`characterId` per leg, as v4:** `Some` on the native re-stream; `None`
   on force-final and on the text continuation (the same rule the watchdog
   and the cache key already follow on those legs — do not let a shared
   helper "fix" it).
4. **Per-leg content, usage and duration.** `consume_stream` logs
   `state.full_response` (`:1219`) — right for the primary, wrong here. Each
   leg logs only the text IT streamed (v4's `accumulatedContent` is per
   call): the native re-stream has `current_response`; the text
   continuation has `raw_responses[idx]`; **force-final has no per-leg
   buffer yet — add one.** Track last-non-null usage, cache usage and
   `raw_provider_usage` per leg the way `consume_stream` does
   (`:1135-1182`), and a per-leg `started_at_ms`.
5. **The log gate is v4's:** log at the leg's `done` chunk, BEFORE the loop
   consumes the result, so a later throw in the loop still leaves the row.
   (Help chat logs after a clean end instead — do not copy that choice.)
6. **Plumbing:** add the missing `log_context` (and whatever of
   `StreamLogCtx`'s fields are not already reachable) to
   `RunNativeToolLoopOptions` (`native_tool_loop.rs:165`) and
   `RunTextToolPassOptions` (`text_tool_loop.rs:291`), passed at the three
   constructor sites (`orchestrator.rs:3131`, `:3210`, `:3255`). Already
   reachable and NOT to be duplicated: `chat_id`, `character_id`, `state`,
   `tool_context.user_id`, the message id via
   `preserve.pre_generated_assistant_message_id()` (native `:234`, text
   `:373`). The autonomous run id rides `log_context` — that is what makes
   the budget charge.
7. **A failed log write is v4's WARN, then the turn goes on** (the funnel's
   `.catch`).

**In-repo pattern to follow:** the Help chat (`help_chat/orchestrator.rs:1455-1477`),
Brahma (`brahma_console/orchestrator.rs:1026`) and the one-shot loop
