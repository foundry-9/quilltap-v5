## The drift, classified (surveyed FRESH 2026-08-13 at `48396682`)

### `8600c83f` — the group tier (behavior, oracle-visible)

v4's new `lib/wardrobe/shared-tiers.ts` (106 lines) is the heart:

```ts
interface SharedWardrobeTiers { groupMountPointIds?: string[]; projectMountPointIds?: string[] }
resolveSharedWardrobeTiersForChat(chatId, characterId)
resolveSharedWardrobeTiersForProject(projectId, characterId)
sharedWardrobeTiersForCharacter(characterId, projectMountPointIds)
noSharedWardrobeTiers()
```

Group resolution is per **character** (`resolveGroupMountPointIdsForCharacter`
— official AND linked memberships), project per chat/project. New
`lib/mount-index/shared-wardrobe.ts` + `group-wardrobe.ts` (v5 is already
ahead on the general/project collapse — `db/archetype_wardrobe.rs:39`
`read_shared_wardrobe` — only the group façade is missing).

Oracle-visible changes:

1. `WardrobeRepository.findArchetypes(includeArchived, opts)` — scoped mount
   list becomes `[...projectMountPointIds, ...groupMountPointIds]`,
   weakest-first, so group shadows project shadows general.
2. **New public** `findArchetypesInMounts(mountPointIds, includeArchived)` —
   reads each mount's shared `Wardrobe/` in order, later shadows earlier,
   per-mount try/catch skip.
3. `findByIdForCharacter` / `findByIdsForCharacter` /
   `findWearablePoolForCharacter` / `findArchetypeById` take the widened
   tiers object.
4. All wardrobe tool handlers thread tiers
   (`resolveSharedWardrobeTiersForChat`), replacing the bare
   `{ projectMountPointIds }` literals. **Two real fixes ride in
   `wardrobe-create-handler.ts`:** component resolution keys tiers on the
   **recipient** character (gifts assemble from what the recipient can
   reach), and the equip-now path passes tiers at all (it previously passed
   none, so a new bundle's shared components did not resolve).
5. `app/api/v1/characters/[id]/wardrobe/route.ts` — **new `?scope=group`
   arm**: `resolveGroupMountPointIdsForCharacter(id)` →
   `findArchetypesInMounts(...)` → `{ wardrobeItems }`.
6. Transfers (`app/api/v1/wardrobe/transfers/route.ts`): `SourceScope` gains
   `'group'`; source lookup scans the source character's group mounts
   **between** project and General; destination read handles group;
   delete-from-source treats group like project (delete by mount point);
   `ensureGroupWardrobeFolder`.
7. `handleGetOutfitSummary` (chat outfit action) reads the **union of all
   participants'** group mounts — the one documented cast-spanning
   exception (group stores otherwise follow the character, never a
   co-participant).
8. Chat-create equipped-items read (`app/api/v1/chats/route.ts`) and the
   three background-job handlers (`scene-state-tracking.ts:~192`,
   `story-background.ts:~254`, `wardrobe-announcement.ts:~69`) +
   `lib/chat/context-manager.ts:~1446` (buildContext's outfit-summary cache
   refresh) + `lib/wardrobe/avatar-prompt.ts:~93` all go through
   `sharedWardrobeTiersForCharacter(charId, projectMountPointIds)` — with
   v4's why-comment that group stores can't come from the turn pool (which
   is keyed on the responding character).
9. `apply-outfit-selections.ts`: `resolveDefaultOutfit` option renamed to
   `tiers`; new per-character `getGroupTier` closure — the group tier
   **cannot** join the batched shared-pool read, so it is read separately
   via `findArchetypesInMounts` and appended **after** the batch pool
   (`[...batchShared, ...group]`, group wins), failing soft to `[]` with a
   warn. Progress previews route through `sharedWardrobeTiersForCharacter`.

### `61574563` — bundle dissolution (behavior, oracle-visible)

New `lib/wardrobe/dissolve-bundles.ts` (218 lines):

```ts
slotsCoveredBy(item) / isBundle(item)
dissolveBundleToLeaves(item, itemsById?) -> DissolvedLeaf[] | null   // null = store the bundle WHOLE (fail-safe)
layLeavesIntoSlots(currentSlots, bundle, leaves, { clearCoveredSlots })
dissolveBundlesInSlots(currentSlots, itemsById)
```

Semantics to pin: `null` = unresolvable components → store whole (read-time
expansion still renders it; pre-change outfits keep their composite id and
Break-apart stays available — no migration); the leaf-equals-bundle echo
from a cyclic graph is dropped; `clearCoveredSlots` clears the **union** of
the bundle's own `types` and every slot its leaves land in (a replacing
outfit that includes boots turns out the shoes already worn);
`dissolveBundlesInSlots` substitutes **in place** (preserving layer order)
then a second pass appends leaves whose slot the bundle never claimed;
nested bundles come fully apart. New `lib/wardrobe/hydrate-components.ts`:
`hydrateComponentGraph` (pure move out of `resolve-equipped.ts` — v5 has
this inline at `tools/wardrobe_shared.rs:396-460`; extraction optional) +
**new** `loadBundleLookup` for the write side.

Write-side changes: `outfit-displacement.ts` — `wearItemIntoSlots` /
`replaceItemIntoSlots` gain an `itemsById` third param; **new export**
`addItemToSlot` (falls back to the bundle's own id when no leaf covers the
requested slot — the gesture is never a silent no-op); `equipItem` /
`replaceItem` / `addToSlot` each `Promise.all([loadSlots, lookupForBundle])`.
`buildDefaultOutfit` returns dissolved slots. `resolveDefaultOutfit` and the
`llm_choose` accepted answer dissolve against the pool. The wear tool
handler's three verbs and the outfit route's `wear`/`replace`/`add_to_slot`
pass tiers so dissolution can resolve.

## Shared contract (BINDING — identical text in P4.D72)

1. **The group-scope wardrobe read.** REST:
   `GET /api/v1/characters/{id}/wardrobe?scope=group` → 200
   `{ "wardrobeItems": [...] }` (v4's exact envelope). Dispatch: the
   existing character-wardrobe-list verb gains an optional `scope` field
   (JSON key `scope`, accepted value `"group"`; absent = today's
   behavior). If the frozen request type cannot take the field directly,
   use the established flatten-seam pattern — the JSON wire above is what
   is binding, name-for-name.
2. **Dissolution semantics.** The SERVER is authoritative: after any
   wear/replace/add_to_slot/set-default/llm-choose of a **resolvable**
   bundle, persisted equipped slots contain leaf ids only (unresolvable →
   stored whole). The client's optimistic math (P4.D72) mirrors v4's
   client (`wearItemIntoSlots`/`addItemToSlot` with `itemsById`), and the
   server result overwrites it on reconcile.
3. **Version bumps:** this lane bumps `quilltap-core`, `quilltap-harness`,
   and `quilltap-web` (its routes test); P4.D72 bumps the SPA only.
