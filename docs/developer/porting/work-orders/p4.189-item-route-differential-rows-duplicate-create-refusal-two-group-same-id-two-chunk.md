## Rulings made at planning

- **§R.6 (red-first) in this lane.** No source changes, so there is no
  "red on unported main, green after". Its substitute here is
  **non-vacuity**: a row that could pass because its plant did nothing is a
  test of nothing (memory note `tier-r-vacuous-equal-rows`). Every plant
  below therefore (a) asserts the exact number of rows it changed, on BOTH
  sides, and (b) is paired with a control row whose v4 answer must DIFFER
  from the planted row's, asserted in the Rust test against the oracle.
- **D-1 (drafter) — item 6's plant is an OVER-LONG FOLDER, not a long
  title.** The survey says "a title at the max length, so ` (copy)`
  overflows". That premise is FALSE at the pin: `createWardrobeSchema`'s
  `title` is `z.string().min(1, 'Title is required')` with NO maximum
  (`lib/schemas/wardrobe.types.ts:174`), and the reader slices titles to
  200. The only field a readable stored item can carry that today's create
  schema refuses is `folder`: the reader derives it from the file's PATH
  with no length check (`parsers.ts` `folderOfWardrobePath(doc.relativePath)`),
  and the create schema is `WardrobeFolderInputSchema = z.string().max(900)`
  (`wardrobe.types.ts:161, 191`). So the plant moves one item document to a
  path whose folder is 901 characters.
- **D-2 (drafter) — item 10's second group is PLANTED BY SQL, identically

  assignment suggested the real repo. That cannot be mirrored: the Rust side

  v4's group-tier walk reads the group through `repos.groups.findByIdRaw`

  `readGroupStores`), and membership through the mount-index table

  scratch-store item the Guild Cloak's id build the whole premise with
  byte-identical SQL on both copies. v4's REAL route + reader still run the
