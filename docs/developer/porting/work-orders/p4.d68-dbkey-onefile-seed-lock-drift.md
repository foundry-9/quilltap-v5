# Work order P4.D68 — the 4.8.1 dbkey one-file + fail-closed-seeding + instance-lock drift (server) — v4 `03154b72`

**Status:** CARRIED OUT in lane (2026-08-12) — tiers 1 and 2 landed; see the
lane records in `status-log.md`.

**⚠ ESCALATION (deliverable 4's lock-coverage leg — a real finding, NOT
fixed in lane):** v5's boot path opens all three partitions **writable
BEFORE the instance lock is acquired** — `api/engine.rs::boot_ready` runs
`Db::open` (whose writable open sequence issues `journal_mode = TRUNCATE`,
a header/journal write) and only then calls `assemble`, where
`HostAssembler` acquires the lock (`host.rs:413`). v4 orders it the other
way (`backend.ts` `connect()` acquires the lock BEFORE `new Database`).
In the contended case (v4's bug-58 Ignite scenario: a container holds the
lock, a second process boots) v5 performs three unlocked journal-mode
header writes against a database another process believes it holds
exclusively, then refuses at assemble. All ROW writes are behind the lock
(seeds run after acquisition; the spine's ad-hoc writers run in the
already-locked process), so the exposure is the open sequence itself —
narrow but the exact class bug 58 closes, and the CLAUDE.md open-sequence
rule itself warns journal-mode writes race the cipher context. The
fresh-`Setup` provisioning path shares the shape (a new instance is
provisioned before any lock exists). Fixing it means moving lock
acquisition ahead of `Db::open` in the engine boot path (a
host-seam/trait reshape in `api/engine.rs` beyond this lane's ownership
of the ChangePassphrase test block) — it needs its own small order.

## The drift, classified (surveyed FRESH 2026-08-12 at `03154b72`)

The effective `git diff de9f70bf main` outside docs/tests is twelve files.
This lane owns the server-side set — v4's **bugs 58–60, found on Ignite**
(write-ups: `docs/developer/bugs/fixed/bug-58-migrations-bypass-instance-lock.md`,
`bug-59-failed-read-triggers-first-startup-seeding.md`,
`bug-60-phantom-per-database-key-files.md` in the v4 checkout — read all
three before coding; they carry the acceptance reasoning):

1. **Bug 60 — phantom per-database key files** (`lib/startup/dbkey.ts`,
   `lib/paths.ts`, `lib/startup/version-guard.ts`). v4's `changePassphrase`
   used to write the new wrapping to BOTH `quilltap.dbkey` and
   `quilltap-llm-logs.dbkey`. The second file was the remnant of a
   per-database-key design that was never built: **nothing ever read it**,
   and it could hold a stale wrapping. v4 removed the write, deleted
   `getLLMLogsDbKeyPath()` (both copies — paths.ts and dbkey.ts), and
   version-guard now patches `minServerVersion` into the one file. A stale
   second file on disk is **inert and left alone** — v4 does not delete it.
   **v5 REPRODUCES THE BUG FAITHFULLY**: `crates/quilltap-core/src/dbkey.rs`
   `change_passphrase` (:389 at planning) writes both files, its doc comment
   asserts "v4 keeps them in sync", the module unit test (:465) and the
   engine dispatch test (`api/engine.rs:6065`) both assert the second file
   exists. **This is the lane's tier-1 port.**
2. **Bug 59 — a failed read triggers first-startup seeding**
   (`lib/startup/seed-initial-data.ts`,
   `lib/database/repositories/base.repository.ts`). v4's `find*` family
   collapses ANY infrastructure failure into `[]`, so an unreachable
   database (instance lock held elsewhere, half-materialized iCloud file)
   read as "no characters" and sent a fully-populated instance down the
   seeding path. v4 added `countOrThrow` and both seed gates (characters +
   embedding profiles) now probe fail-closed: an unanswerable question is
   not a yes. **v5 survey verdict (verify in lane, then record):
   STRUCTURAL CONVERGENCE, no code change expected.**
   `services/quilltap_import/seed.rs::seed_sample_content` already matches
   the new fail-closed shape — `character_count` returns `Result<i64,
   DbError>` and the `Err` arm pushes a warning and RETURNS without seeding
   (:58–62 at planning). The embedding-profile analog seeds only inside
   fresh provisioning (`services/provisioning/mod.rs:189`), never on a boot
   re-check, so the failed-read-reseed hazard is structurally absent there.
   `countOrThrow` itself is additive and needs no v5 twin — v5's typed
   `Result`s never had the collapse.
3. **Bug 58 — migrations bypass the instance lock**
   (`migrations/lib/database-utils.ts`). v4's migration runner now acquires
   the instance lock before opening (re-entrant per PID; a dead holder is
   reaped as stale; deliberately NOT released by `closeSQLite()`). **v5 has
   no migration runner** (deferred by design — CLAUDE.md standing rule), so
   the fix itself is **NO-PORT**; the lane's job is the *verification leg*
   (deliverable 4) plus the recorded disposition.
4. **NO-PORT (record, zero code):** `lib/paths.ts` /
   `version-guard.ts` — v5 never ported version-guard or
   `minServerVersion` patching (grep confirms zero references), so those
   halves of bug 60 have no v5 surface. The v4-side release/merge chores
   (`c718ce54`, `6ed21621`, `0cd769f3`, `75db7e0d`, `03154b72`,
   package-version bumps) are version bookkeeping. v4's `CLAUDE.md` /
   release-notes / bug-catalogue edits are docs.
5. **The spelling-enforcement rider** (`85fd8744`:
   `scripts/check-quilltap-spelling.mjs`, `quilltap-spelling.js`, eslint
   wiring). v4 extended the "Quilltap, never Quilttap" rule past ESLint's
   reach — a standalone sweep over docs/help/scripts with an exclusion
   list. v5 has the same standing rule and no mechanical enforcement at
   all. Tier 2 below.
