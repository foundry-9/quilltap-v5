# Work order: W4.7e2 — the BUILTIN TF-IDF/BM25 embedding provider

**Size: one Opus session.** The W4.7e sub-unit 5 split-off: the BUILTIN
embedding provider is v4's zero-network fallback embedder, and NONE of it is
ported (only the `tfidf_vocabulary` STORAGE repo is — the decomposition's
"builtin already ported" claim was corrected 2026-07-07). Pure computation
end to end — no model seam, no HTTP; the differential oracle is v4's real
plugin code driven directly.

v4 sources (surveyed 2026-07-07 at `6b6e39ad`):
`plugins/dist/qtap-plugin-builtin-embeddings/` — `porter-stemmer.ts` (381:
`STOP_WORDS` set, `stem`, `tokenize(text, removeStopWords=true)`,
`generateBigrams`), `tfidf-vectorizer.ts` (253: `TfIdfVectorizer` —
`BM25_K1 = 1.5`, `BM25_B = 0.75`, `fitCorpus`/`transform`/`loadState`/
`getState`/`isFitted`, `includeBigrams` default true), and
`embedding-provider.ts` (`BuiltinEmbeddingProvider`,
`BUILTIN_MODEL_NAME = 'tfidf-bm25-v1'`, synchronous `generateEmbedding`);
plus the host glue `lib/embedding/embedding-service.ts:184–244`
(`generateBuiltinEmbedding` — loads persisted state via
`repos.tfidfVocabularies.findByProfileId`, not-fitted →
`EmbeddingError('Built-in embedding profile not yet fitted…')`), the
`EMBEDDING_REFIT` job handler
(`lib/background-jobs/handlers/embedding-refit.ts`, 153), and the debounced
refit scheduler (`lib/embedding/embedding-job-scheduler.ts`, 104).

## What to port

1. **The Porter stemmer + tokenizer** (`crate::tfidf::porter` or similar):
   `stem` (transcribe v4's hand-rolled implementation step by step — do NOT
   substitute a Rust stemming crate; classic Porter has variant edge cases
   and the vocabulary keys must be byte-identical or every stored
   `tfidf_vocabulary` row misses), `tokenize` (the exact regex/lowercase/
   stop-word pipeline — check whether its word-splitting uses JS `\w`/`\s`
   classes and reproduce with the established ASCII/JS-class idioms), the
   `STOP_WORDS` set verbatim, and `generateBigrams`.
2. **`TfIdfVectorizer`**: `fitCorpus` (empty-corpus throw; document
   frequencies; the BM25 IDF `ln((N - df + 0.5) / (df + 0.5) + 1)`;
   `avgDocLength`; `fittedAt = new Date().toISOString()` → the injected
   clock), `transform` (must-be-fitted throw; the BM25 TF
   `(tf * (k1+1)) / (tf + k1 * (1 - b + b * (dl / avgdl)))`; the output
   vector layout/order — read the source for how vocabulary indices map to
   vector positions), `loadState`/`getState` (the exact
   `{vocabulary, idf, avgDocLength, vocabularySize, includeBigrams,
   fittedAt}` bag — `vocabulary`/`idf` are the JSON-text columns the ported
   `tfidf_vocabulary` repo stores single-encoded), `isFitted`. Float math in
   f64 throughout (JS numbers); the tier-1 float tolerance is 1e-12, but
   expect exactness — same formulas, same order of operations.
3. **`BuiltinEmbeddingProvider`** implementing the ported
   `EmbeddingProvider`-adjacent local shape: synchronous
   `generate_embedding` (not-fitted → the exact error string), `dimensions`,
   batch mapping. Then the host glue: `generate_builtin_embedding` — resolve
   the profile, load state from `tfidf_vocabulary.find_by_profile_id`, parse
   the JSON-text columns, transform, and route the result through the
   already-ported `applyEmbeddingProfile` path exactly as
   `embedding-service.ts` does (check whether builtin output skips or takes
   the truncate/L2 step — read the source, don't assume).
4. **The `EMBEDDING_REFIT` job handler** (`services::embedding_refit_job`,
   registered in the W4.8 runner registry): gather the corpus (every
   character's memories via the ported reads + help_docs contents,
   help-docs failure swallowed with the warn), `fitCorpus`, persist via the
   ported `tfidf_vocabulary.upsert_by_profile_id` (its base-method-override
   minting already tier-2-verified), and the post-refit
   `EMBEDDING_REINDEX_ALL` enqueue (a plain `background_jobs` row through
   `queue_service`; the REINDEX handler itself stays on the loud fallback —
   out of scope). Empty-corpus → the skip branch, not a throw.
5. **The debounce scheduler is host-timing** — the 5 s `setTimeout` map in
   `embedding-job-scheduler.ts` does not port (no timers in the core; the
   W4.8 rule). Port only the BUILTIN-profile gate decision if it's pure;
   document the rest as the host driver's cadence seam.

## Differential plan

- **`tfidf_vectorizer_equivalence`** (tier-1): a tsx oracle driving the REAL
  plugin exports (`stem`/`tokenize`/`generateBigrams`/`TfIdfVectorizer`)
  over a committed corpus. Rows must bank: stemmer edge families (plurals,
  `-ed`/`-ing`, `-ational`/`-iveness` suffix chains, short words, y↔i,
  double consonants), stop-word removal on/off, bigram generation, a
  fit→getState round-trip (clock pinned), loadState→transform equivalence
  with fit→transform, the two throw messages, non-ASCII input (whatever the
  tokenizer does with it — bank the actual behavior), and BM25 numeric rows
  compared at 1e-12 (expect exact).
- **`embedding_refit_tier3_equivalence`** (tier-2/3): drive v4's REAL
  `handleEmbeddingRefit` over a seeded fixture (characters + memories +
  help_docs rows; clock frozen) and diff `tfidf_vocabulary` +
  `background_jobs` (the REINDEX_ALL enqueue) in the minted-timestamp form;
  plus a runner-registration E2E per the W4.8 pattern. The
  `generateBuiltinEmbedding` read path gets rows in the vectorizer
  differential (loadState from a REAL persisted row's JSON text).

## Watch-outs

- The stemmer is THE risk. Transcribe v4's file, port its tests if it has
  any, and let the differential corpus be generous (dozens of words per
  suffix family) — a one-word divergence silently shifts vocabulary indices
  and every embedding after.
- `vocabulary`/`idf` persist as JSON TEXT in plain-string columns (the
  Phase-2 `tfidf_vocabulary` banking) — parse/serialize exactly as v4
  (key order for `getState` persistence: check whether `JSON.stringify` of
  a Map-derived object is involved and reproduce insertion order).
- `fitCorpus` iterates documents in order — corpus order affects nothing
  mathematically but keep it anyway (fittedAt, any tie behavior).
- This unit has NO file overlap with W4.4b / W4.5 / the logLLMCall closures
  — safe in any parallel lane.
