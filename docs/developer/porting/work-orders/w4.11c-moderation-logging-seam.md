## Survey facts (verified 2026-07-08)

  ```ts

    userId, type: 'DANGER_CLASSIFICATION', chatId,
  ```

  Only `userId` + `chatId` (no messageId / characterId / usage /
  temperature / maxTokens — contrast the LLM path at `:396-411`).
- v4's `ModerationCategoryResult` is `{category: string, flagged: boolean,
  score: number}` (`packages/plugin-types/src/plugins/moderation-provider.ts:74-83`);
  `mapModerationResult` (`gatekeeper.service.ts:189-230`) reads only
  `category`/`score` + the top-level `flagged` — the per-category `flagged`
  exists ONLY for the log row.
- Rust: the wire parse RETAINS it — `ModerationWireCategory {category,
  flagged, score}` (`moderation_wire.rs:33-38`),
  `parse_moderation_response` populates it (`:116-127`) — and it is dropped
  at `ModerationWireResult::into_gatekeeper` (`:48-63`) before
  `ModerationOutcome::Moderated` reaches the gatekeeper. The gatekeeper's
  projected `ModerationCategoryScore` (`gatekeeper.rs:79-83`) has no
  `flagged`.
- The write location: the `ModerationOutcome::Moderated` branch of
  `classify_inner` (`gatekeeper.rs:435-454`) — it already has `db: &Db` in
  scope and carries the explanatory comment; the LLM path's
  `log_llm_call(db, params, &LogContext::none())` at `:497-539` is the
  in-file pattern.
- Harness: `danger_gatekeeper_tier3_equivalence.rs:435-441` filters
  `modelName == "moderation"` rows from BOTH sides (`strip_moderation`).
  The v4 oracle (`harness/oracle/cases/danger-gatekeeper.test.ts`) has NO
  filter — `logLLMCall` runs REAL and the moderation rows are ALREADY in
  the oracle NDJSON (`:215-237` dumps all rows). So closing the seam needs
  **no v4-side oracle change** beyond a fresh regen.

   byte-for-byte: type `DANGER_CLASSIFICATION`, `modelName: 'moderation'`,
   provider = the wire provider name, request = the single user message,
   `response.content` = the serialized `{flagged, categories}` — a typed
   struct in v4's field order (`flagged`, `categories`; each category
   `category`, `flagged`, `score`) with JS-number rendering for `score`
   (`js_number_to_json` — an integer-valued score must render bare),
   NEVER `serde_json::Value` with sorted keys. `user_id` + `chat_id` only;

   port as awaited-and-ignored (the established precedent) — a log failure

   cache hit never reaches the provider, so no row — v4 identical, comes
