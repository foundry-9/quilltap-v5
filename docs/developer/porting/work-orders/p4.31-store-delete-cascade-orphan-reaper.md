## The finding, restated (what this lane closes)

Dogfood #58's measured damage: **43 orphaned `doc_mount_file_links` + 118
orphaned `doc_mount_folders` across 21 vanished character-vault mount
points** on the real instance. Whatever removes a `doc_mount_points` row
is not taking the children with it, and nothing enforces it: read
connections don't set `PRAGMA foreign_keys`, and `generateDDL` link tables
declare NO foreign keys (only the migration-vintage schema had the
cascade). P4.28 made the RESTORE survive the orphans (reader-side skip
sentences, the 9-7-4 pin); **nothing stops them accumulating and nothing
reaps the ones already there.** This lane fixes both: delete-time
cascading through one chokepoint, and a boot repair pass.

## Survey-verified starting points (2026-08-03)

**Partition:** the whole doc-mount family is **mount-index**
(`fresh_schema.json` → `mountIndex`, 10 tables). Writer helper:
`crates/quilltap-core/src/api/mount_points.rs:575-580` (`mount_conn`).

**Only three v5 paths delete a `doc_mount_points` row:**

- **Path A — the route cascade** (`mount_points.rs:485` route →
  `cascade_delete` :512-572): chunks ✅ :514; links ✅ :525; orphaned
  files ✅ :529-535; **documents ❌ DEAD** :537-541 — the
  "deleteByMountPointId" subquery reads `doc_mount_file_links` AFTER the
  links were deleted at :525, so it deletes ZERO rows and
  `doc_mount_documents` (no FK) leaks permanently; **blobs step ❌
  DEAD/duplicate** :542-555 — it is a copy of the files step
  (re-deletes `doc_mount_files`, never `doc_mount_blobs`; harmless in v5
  only because `fresh_schema.json` gives `doc_mount_blobs` an
  `ON DELETE CASCADE` FK off `doc_mount_files` and v5 WRITERS open with
  `PRAGMA foreign_keys = ON`, `db/mod.rs:178`); folders ✅ :557;
  `project_doc_mount_links` ✅ :562; **`group_doc_mount_links` ❌ never
  touched**. The whole cascade runs as loose statements on the writer
  connection with **no explicit transaction** (`Db::write`,
  `db/runtime.rs:187-203`; no `unchecked_transaction()` in
  `cascade_delete`) — a partial failure mid-cascade is exactly how
  orphans are minted.
- **Path B — the bare repo delete**
  (`db/doc_mount_points.rs:382-387`): `DELETE FROM doc_mount_points
  WHERE id = ?1`, nothing else. No production caller today; the only
  caller is the tier-2 harness
  (`doc_mount_points_tier2_equivalence.rs:233`). The loaded gun.
- **Path C — the bulk truncate** (`services/delete_all.rs:214-244`,
  `FORMAT3_MOUNT_TABLES` = all 10) — cannot orphan; untouched.

**The correct chokepoint already exists and the cascade doesn't use it:**
`gc_orphaned_file_row` (`db/doc_mount_file_links.rs:2153-2175`) deletes
documents + blobs + the file row explicitly, *precisely because* the
tables have no FKs; `cascade_delete` inlines a raw
`DELETE FROM doc_mount_files` instead.

**v4 (at `49769ec4`) — the twin, verified:** the only app/lib delete is
`app/api/v1/mount-points/[id]/route.ts:167-215`. Links + folders ARE
deleted there today (fixed in v4 at `45dcf97d` 2026-05-15 and `ac0b7c80`
2026-05-22 — the real instance's 43+118 predate those). **Still-live v4
leaks, identical in shape to v5's:** documents (dead ordering,
`doc-mount-documents.repository.ts:327-343`), the blobs step deleting
files-not-blobs (`doc-mount-blobs.repository.ts:628-655` — and v4 has NO
FK enforcement to catch it), and `group_doc_mount_links` never deleted on
store delete (v4's only group-link delete is `deleteByGroupId`). v4
offers no sweep.

**Adjacent paths that are NOT this lane's bug (leave semantics alone):**
group delete (`api/groups.rs:259-279`) and project delete
(`api/projects.rs:325-354`) deliberately leave the official store
standing; the character cascade (`services/cascade_delete.rs:287-368`)
never touches the vault store. Those are the *source* of the stray stores
someone later deletes via path A — recorded, not changed.
`quilltap_import`'s overwrite-clear
(`services/quilltap_import/document_stores.rs:466-510`) clears
documents/links/files/chunks but NOT folders — v4-faithful; tier 2.

**Existing sweeps cannot absorb #58:** `sweep_orphaned_link_content`
(`db/doc_mount_file_links.rs:2193-2245`, run from the boot hook
`builtin_mounts.rs:162`) and `sweep_orphaned_files` (:2017-2024, run from
`scheduled_maintenance.rs:196-205`) both key off "a content row with no
LINK"; #58's rows are "a link/folder whose `mountPointId` has no PARENT"
— the opposite direction, never queried anywhere in the tree. The boot
hook (`ensure_builtin_mounts`, `builtin_mounts.rs:84`, called from
`provisioning/mod.rs:144`) is the P4.D41-precedented home for the new
pass, right next to :162.

**Divergence-pin templates (copy these shapes):**
`system_delete_data_equivalence.rs:145-158/:230-256`
(`ANNOTATION_DIVERGENCE_KEY` — v5 must be 0 AND the oracle must be
non-zero, with an explicit "v4 has CONVERGED … delete this key" failure
message; the closest template),
`doc_mount_file_links_tier2_equivalence.rs:660-745` (`CHUNK_DIVERGENCES`
triples), `system_restore_state.rs:1780-1880` (the #58 restore-side pin:
v5 zero orphans / oracle exactly 9-7-4). **The orphan-maker recipe is
ready-made**: `build-restore-archive-orphan-links.test.ts:174/:198`
deletes the point on the mount-index connection and leaves the children.

**Coverage gap in the existing route family:** `dump_cascade`
(`mount_points_routes_equivalence.rs:161-178`) counts
chunks/files/fileLinks/documents/folders/projectLinks/mountPointExists —
all **scoped to the deleted mount id**, no `doc_mount_blobs`, no
`group_doc_mount_links`, no whole-table census. ⚠ Because `documents` IS
in the scoped dump: if the groups-projects fixture's deleted store
carries document rows, the v5 fix turns that family RED (v5 deletes them,
the oracle leaks them) — check at lane start; if reachable, add the
pinned carve-out there; if not, note it and keep that family untouched.
