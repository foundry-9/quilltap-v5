### B.1 Streaming shape (the one mechanism for every generator)

v4 streams each generator as an HTTP SSE response of `data: <JSON>\n\n`
frames (`handleOptimizeStream`, `handleAiWizardStream`,
`handleAIImportStream` — all three are the same nine-line `ReadableStream`).
v5's boundary streams **only on the Event channel** (`api-boundary.md`), so:

- Each streaming verb carries a client-minted **`progressId: string`**
  (`crypto.randomUUID()` client-side; the `CreationProgressFrame` precedent
  at `core-contract.ts:4187-4220` / `services/creation_progress.rs`).
- Every v4 `onProgress(event)` becomes ONE Event:
  `{ "type": "generatorProgress", "progressId": <id>, "generator": <G>,
  "event": <the v4 progress event object, key order and bytes verbatim> }`
  where `<G>` ∈ `"optimizer" | "wizard" | "aiImport"`.
- The dispatch call resolves when the run ends server-side with
  `{ "terminal": <the LAST event v4 would emit, verbatim> }` — for the
  optimizer that is the `done` or `error` event; for the wizard `done`; for
  the AI import `done`. A refusal BEFORE the run starts (v4's Zod parse /
  route-level `badRequest`) is a dispatch `CoreError` (`badRequest`,
  message = v4's sentence, `details` = v4's Zod issues where v4 answers
  them) and emits NO frame.
- The REST SSE edges (Tier 2 in the server lanes) re-frame the same Events
  as `data: <JSON.stringify(event)>\n\n` with headers `Content-Type:
  text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`,
  and close after the terminal frame — byte-identical to v4's stream.

```
Event::GeneratorProgress { progress_id: String, generator: GeneratorKind, event: serde_json::Value }
```

edges.
