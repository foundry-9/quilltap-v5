### Quirks the port must not miss (verbatim from the survey)

1. `groups/[id]/route.ts:10–14`'s comment advertises `stores`/`linkStore`
   /`unlinkStore` actions that DO NOT EXIST — store linking is the
   `mount-points` sub-route. Valid `[id]` actions: `members`/`addMember`/
   `removeMember` only.
2. **Asymmetric deletes**: group delete drops memberships AND mount
   links; project delete nulls chats/files but never touches
   `projectDocMountLinks` (dangling links are filtered at read time —
   `mount-points/route.ts:48`). Both orphan the official store.
3. Response-envelope drift is real and per-handler: group scenarios GET
   returns `successResponse({mountPointId, scenarios, warnings})`; GET
   /projects list, get-background, and project mount-points GET return
   BARE `NextResponse.json(...)` (no `success` envelope). Port the
   envelope per-handler; the differential pins it.
4. Error-path drift: groups mostly let middleware map errors (raw
   ZodError propagates); the scenario-path routes catch ZodError and
   return a joined-message 400; project mount-points wraps everything in
   try/catch so a Zod error becomes a 500, NOT 400. Match per-route.
5. Unknown/missing `?action=` on GET/PUT/DELETE falls through to the
   DEFAULT handler (not 400); unknown POST actions → 400. Both families.
6. Group scenario routes ensure BOTH `Scenarios/` and `Knowledge/`;
   project scenario routes ensure only `Scenarios/`. The group
   `[scenarioPath]` route's `loadGroupAndStore` uses the RAW
   `officialMountPointId` and 404s ("restart the server") when null,
   while the collection routes run the full `ensureGroupOfficialStore`.
7. PUT semantics follow the P4.6c lesson: the store write overlay applies
   Zod-PARSE merge semantics (defaults materialized), never a strict
   storage struct.
8. The union route (`groups/scenarios`) ownership-gates every character
   id through the user-scoped `characters.findById` BEFORE touching the
   unscoped membership table; results sort by `localeCompare` on group
   name — use the ported ICU4X en-US collation (Phase 1). It is a static
   sibling that Next routes AHEAD of `[id]` — match that precedence in
   dispatch naming.
9. `_count.members` on group list/detail is a cross-partition read
   (main + mount-index) in one handler.
10. `list-files` two-branch DTO fabrication: store-backed rows become
    legacy-file-shaped DTOs (`category` from mime prefix, `updatedAt:
    f.lastModified || f.updatedAt`, extra `mountPointId`/`relativePath`,
    `folderPath: null`); legacy branch uses
    `resolveEffectiveFolderPath`. `mimeForMountFile`'s `blob` arm calls
    `detectMimeType(fileName)`.
11. Wardrobe create mints UUID + timestamps in the route — the
    differential needs the frozen-clock + minted-UUID remap.
12. `set-state` REPLACES wholesale (no merge); groups expose NO state
    actions even though `state.json` exists in the group store.
13. Aesthetic PUT: `req.json().catch(() => ({}))` +
    `safeParse(...).data?.content ?? ''` — malformed JSON silently
    deletes the file. `kind` ∈ `lantern|aurora` only
    (`depiction-guidelines.md` belongs to characters, already ported).
14. Roster mutations hand-roll the array via `projects.update` (the
    repo's `addToRoster` etc. are NOT used by routes); `add-character`
    is idempotent, `remove-character` succeeds silently for absent ids;
    `add-chat`/`add-file` ownership-check via `findById` but
    `remove-chat`/`remove-file` do NOT check existence.
15. Zod mixed idioms: `z.uuid()` vs `z.string().uuid()` in
    `projects/[id]/schemas.ts` (:14 vs :17–18) — match validation
    behavior, not the idiom.

The new `Request` variants (camelCase serde, the characters idiom).

request bodies until then).

`groupMembers {groupId}`, `groupMemberAdd {groupId, characterId}`,
`groupMemberRemove {groupId, characterId}`,
`groupMountPointList {groupId}`, `groupMountPointLink {groupId,

`groupScenarioList {groupId}`, `groupScenarioCreate {groupId, …}`,

Projects: `projectList {}`, `projectCreate {name, description?}`,

`projectToolSettingsUpdate {projectId, …}`, `projectMountPointList
{projectId}`, `projectMountPointLink {projectId, mountPointId}`,
`projectMountPointUnlink {projectId, mountPointId}`,
`projectScenarioList/Create/Get/Update/Rename/Delete` (mirror of
groups, `projectId` for `groupId`), `projectWardrobeList {projectId}`,
`projectWardrobeCreate {projectId, …}`, `projectWardrobeGet {projectId,
itemId}`, `projectWardrobeUpdate {projectId, itemId, …}`,
`projectWardrobeDelete {projectId, itemId}`.

Responses reuse the loose-`serde_json::Value` style — the DTO **bytes**
are pinned by the differentials, not the Rust types. Payloads the SPA
codes against (mock until unification):

- **groupList** → `{groups: [<Group row + _count: {members}>]}`
  (createdAt desc). Group row = v4 `GroupRowSchema` projection (`id`,
  `name`, `description`, `color`, `icon`, `officialMountPointId`,
  `state`, `createdAt`, `updatedAt`) — lane A pins the exact list in the
  first commit.
- **groupMembers** → `{members: [{id, name}]}` (null-filtered).
- **groupDelete** → `{success: true}`; **groupMemberAdd/Remove** → the
  updated members list per v4.
- **projectList** → `{projects: [<Project row + _count: {chats, files,
  characters}>]}` (createdAt desc, BARE array envelope per v4).
- **projectGet** → the project + enriched roster `[{id, name,
  defaultImageId, defaultImage, tags, chatCount}]` + `_count`.
- **projectChatList** → `{chats: [<enriched chat DTO: participants w/
  defaultImage, tags as objects, storyBackground {id, filepath} | null>],
  total}` (limit/offset).
- **projectFileList** → the legacy-file-shaped DTO list (both branches
  identical in shape; store-backed rows add `mountPointId`/
  `relativePath`).
- **projectStateSet** → `{success, state}`; **projectStateReset** →
  `{success, previousState}`.
- **projectBackgroundGet** → `{url: string | null, sourceChatId?}` per
  mode (pin exact fields in the first commit).
- **scenario verbs** → `{mountPointId, scenarios, warnings}` (list shape;
  every mutation returns the fresh list).
- **wardrobe verbs** → the item / item-list per v4's wardrobe schemas
  (already pinned by the P4.6f slice-4 port).

If any name or field must change, BOTH orders change and the change is
reported at unification.
