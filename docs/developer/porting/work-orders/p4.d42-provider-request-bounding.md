## The drift, classified (surveyed 2026-08-03)

**`74ec93b5` "fix(llm): bound provider requests so a stalled call can't
wedge a turn"** — a turn could sit on "Recalling X's memories…" for ten
minutes: a provider accepted the request and never answered, and provider
SDKs default to a 600 s request timeout (measured: 622,451 ms for a memory
recap whose healthy runtime is ~9 s). Nothing was logged, because llm_logs
rows are only written when a call finishes. v4 bounds at three levels:

1. **Caller deadline** — `executeCheapLLMTask` gives each attempt
   45 s remote / 180 s local, throws `CheapLLMTimeoutError`, and logs the
   abandonment with provider, model, task type, and elapsed time.
2. **Phase ceiling** — the memory recap gets 60 s in `context-manager.ts`,
   covering BOTH its embedding leg and its cheap-LLM leg (deliberately
   above the per-leg budget).
3. **Provider budget** — new `LLMParams.requestTimeoutMs`, a hard ceiling
   on a SINGLE attempt that providers must not retry past; cheap-LLM calls
   set it 5 s inside their own deadline so the socket is aborted rather
   than orphaned.

**Two corrections to the commit message's easy misreadings** (verified in
the diff):

- The provider budget is **not 5 s**. `PROVIDER_BUDGET_HEADROOM_MS = 5_000`
  is *headroom*: `providerBudgetFor(selection)` = deadline − 5 000 =
  **40 000 ms remote / 175 000 ms local**.
- The "nine text providers" have **no per-provider v5 counterpart**. v5
  replaced nine plugin SDKs with ONE `reqwest` transport
  (`TransportPolicy`), so v4's per-provider application matrix (SDK opts vs
  `AbortSignal` vs `httpOptions.timeout` vs `timeoutMs`) collapses to one
  policy — EXCEPT the streaming distinction, which does still apply and is
  the one place v4's reasoning must be carried rather than collapsed (see
  "Design decisions" §D3).

## Design decisions (locked by this order)

- **D1 — the field:** `request_timeout_ms: Option<i64>` on
  `CompletionParams` (serde as the struct is internal; mirror v4's
  optional semantics: `None`/non-positive = provider default). NOT on
  `RequestInput`; it must never serialize into a request body.
- **D2 — per-call policy:** `WireCompletionProvider` derives an effective
  `TransportPolicy` per call: when `params.request_timeout_ms` is set,
  `timeout = budget` and `max_retries = 0` (v4's
  `buildSdkRequestOptions` contract: never retry past a caller's
  ceiling); when unset, the process default applies.
- **D3 — streaming semantics:** the per-request ceiling (and the default)
  on `execute_stream` bounds **time-to-first-byte/headers only**; the body
  streams unbounded. Implement at the transport (e.g. a bounded await on
  the initial response, not reqwest's whole-body `.timeout()`), and pin
  with a unit test that a slow-but-flowing stream is NOT truncated while a
  never-answering request IS aborted. This is v4's raw-fetch idiom
  (`clearTimeout` in `finally` once headers land) carried into the one
  place the nine-SDK collapse cannot flatten.
- **D4 — the default drop:** move the non-streaming default ceiling
  600 s → **300 s** (`DEFAULT_REQUEST_TIMEOUT_MS`), matching
  plugin-utils 2.2.18's client defaults which now govern effectively every
  v4 provider. Streaming default likewise bounds first-byte at 300 s, body
  unbounded (matching SDK to-headers semantics). Keep `max_retries: 2` as
  the no-budget default (v4's `buildSdkClientOptions` uncapped arm).
- **D5 — the deadline lives in core:** implement the 45 s/180 s attempt
  deadline and the 60 s recap ceiling with `tokio::time::timeout` IN CORE,
  following the `outfit_selections.rs:750` precedent. Rationale to record
  in the lane record: D20's "core owns no timers" targets *cadence*
  (scheduling, pumps, ticks — things a host must drive); a bounded await
  on work the core itself initiated is a request deadline, not cadence,
  and core already depends on tokio time at :750. If you find this
  untenable in practice, STOP and escalate rather than inventing a new
  erased seam per call site.
- **D6 — timeout logging:** on a fired attempt deadline, emit the
  abandonment `tracing::warn!` with v4's field set
  (`chat_id, character_id, provider, model, task_type, timeout_ms,
  elapsed`) AND write the failed-call llm_logs error row per the standing
  P4.13 ruled divergence (v4 writes no row for an unfinished call — v5's
  divergence already writes error rows for failed calls; a timeout is a
  failed call; extend the divergence documentation in
  `log_failed_call`'s comment to name the timeout arm). The error string
  must carry v4's `CheapLLMTimeoutError` message bytes.
- **D7 — the recap ceiling:** wrap the `build_context.rs:2001` call; on
  fire, log (warn) and take `MemoryRecapResult::default()` — the same
  observable outcome as v4's string-message `withTimeout` rejecting into
  the existing fail-soft catch.
