### v4: the photo multipart upload

Route `app/api/v1/characters/[id]/photos/route.ts` POST: content-type
dispatch at :85 (JSON → fileId/linkId legs; otherwise
`req.formData().catch(() => null)` at :113). Fields: `file`
(`instanceof File`, :118–120), `caption` (:122), repeated `tags` via
`getAll('tags')` (:123, non-empty strings). Bytes fully buffered
(`Buffer.from(await file.arrayBuffer())`, :127); filename fallback
`'upload'`, mime fallback `'application/octet-stream'` (:131–132).
Calls `saveToCharacterGallery` → `201 created(result)`. Error mapping
(:141–160): "Character not found" → 404; the keyword list (`already
in`, `no linked database-backed vault`, `Unsupported MIME type`,
`Uploaded image is empty`, `not an image`, `not found`, `empty bytes`)
→ 400; else 500.

`saveToCharacterGallery` (`lib/photos/character-gallery-service.ts:
102–215`) — the write spine, most of which the linkId-leg port already
exercises: findById → `getCharacterVaultStore` → validation (non-empty

this route**, unlike images-v2's 10 MB) → `sha256OfBuffer` + the
same-sha dedup guard (`getPhotoLinkSummaryBySha256`, :128–136 — note
the P4.6i memory flags an `api::salon` `photo_link_summary` dup to
unify) → `keptAt = now ISO` + the kept-image markdown sidecar
(`buildKeptImageMarkdown`, :138–150) + `extractedTextSha256` → path
(prefer the sanitized uploader filename when it contains a `.`, else
the timestamped slug; `buildPhotosRelativePath`;
`resolveUniqueRelativePath`; `ensureFolderPath(mountPointId, 'photos')`;
`sanitizeLeafName` :442–447) → the single write
`docMountFileLinks.linkBlobContent` (:167–181, `extractionStatus:
'converted'`) → post-write `chunkAndInsertExtractedText`,
`invalidateMountPoint`, `emitDocumentWritten`, best-effort
`refreshStats` + `enqueueEmbeddingJobsForMountPoint` (:190–198) →
response `{linkId, mountPointId, relativePath, keptAt, sha256}`
(:208–214).

### v4: photo-save by fileId

Same route, JSON leg (:102–108; `saveByIdSchema` :68–78 refines
"exactly one of fileId|linkId"). `saveFileToCharacterGallery`
(`character-gallery-service.ts:362–390`): `repos.files.findById` (the

`LocalStorageBackend`/`ProductionFileBytes` at the web route. Then the
empty-bytes throw and delegation into `saveToCharacterGallery` with
`fileEntry.originalFilename`/`mimeType`.

### v4: SillyTavern PNG (hand-rolled — NO library)

All in `lib/sillytavern/character.ts` (355 ln). Card = V2 only:
`{spec: 'chara_card_v2', spec_version: '2.0', data: STCharacterV2}`
(:29–33; fields :8–27 incl. a `[key: string]: any` passthrough).

- **Decode** `parseSTCharacterPNG` (:143–194): 8-byte signature check
  `[137,80,78,71,13,10,26,10]`; walk chunks (BE u32 length, ASCII type,
  advance `12 + length`); for each `tEXt`, split at the first NUL;
  keyword **`chara` OR `ccv2`** accepted (:172); the payload is **raw
  JSON via `JSON.parse` — NOT base64** (:173–174; real SillyTavern
  base64-encodes — v4 diverges; port v4). Accepts a full card (unwraps
  `.data`) or bare data with `.name`. Errors → log, return null (the
  route maps null → 400 `Invalid SillyTavern PNG file`).
- **Encode** `createSTCharacterPNG` (:294–339): `exportSTCharacter` →
  `JSON.stringify` → one tEXt chunk, keyword **`chara`** + NUL + raw
  UTF-8 JSON; chunk = `u32 len | 'tEXt' | keyword\0json |
  u32 CRC32(type+data)`; hand-rolled CRC32 poly `0xedb88320`
  (:344–355); chunk inserted **immediately after IHDR** (skip
  signature, then `12 + ihdrLength`, :327–336). Avatar bytes:
  `readCharacterAvatarBuffer(defaultImageId, repos)`
  (`lib/photos/resolve-character-avatar.ts:127–150` — vault-link path
  reads `docMountBlobs.readDataByFileId(link.fileId)`; legacy path via
  images-v2 `readImageBuffer`) or, if missing,
  `generatePlaceholderPNG` (:200–268) — a hand-built 256×256 RGB PNG
  (IHDR/IDAT via `zlib.deflateSync`/IEND, name-hash palette :202–211;
  the placeholder does NOT draw the initial despite its comment).
- **Export route**: `[id]/handlers/get.ts:63–103`, PNG leg :68–92 →
  raw body, `image/png`, `Content-Disposition: attachment;
  filename="<name>.png"`.
- **Import route**: `handlers/post.ts` `handleImport` :391–510
  (dispatch :591). Multipart `file`; PNG detected by `type ===
  'image/png' || name.endsWith('.png')` → `parseSTCharacterPNG` (null →
  400); .json parsed as UTF-8 JSON; else 400. The PNG bytes become the
  imported avatar: after `characters.create`,
  `writeCharacterAvatarToVault({characterId, kind: 'main', filename,
  content: pngBytes, contentType: 'image/png'})`
  (`lib/file-storage/character-vault-bridge.ts:126–175+` — **sharp
  WebP transcode**, delete-then-insert at `images/avatar.webp` with
  `deleteWithGC`), then `characters.update(id, {defaultImageId:
  written.linkId})`; avatar-write failure is NON-FATAL (:468–476).
  Response 201 `{character: {id, name, description, defaultImageId,
  createdAt, updatedAt, _count: {chats}}}` (:490–505).

### Two known codec seams (declare them, don't fight them)

- **Placeholder-PNG deflate**: Node `zlib.deflateSync` output need not
  match a Rust deflate byte-for-byte. The real-avatar encode path is
  pure chunk math → **byte-exact differential**. The placeholder leg is
  compared at the DECODED level (parse both PNGs, diff
  dimensions + pixels + the embedded card JSON) — an explicit,
  documented seam, not a loosened assertion.
- **Avatar WebP transcode**: sharp's WebP bytes ≠ the v5 codec's WebP
  bytes. The import differential diffs the created character + link
  rows exactly and the avatar blob at the metadata level (dims/format/
  non-empty), per the established `HostImageCodec` seam precedent
  (`[[w4-9c-image-job-handlers]]`). If
  `write_character_avatar_to_vault` is not yet ported, porting it (with
  the codec injected) is part of unit 4.

- **ST import (tier 2):** drive v4's REAL `handleImport` PNG leg; diff
  the created character's cross-DB dump in remap form + the avatar link

- **Route-level integration:** axum tests posting REAL multipart bodies

Fix the port, not the diff. A legitimately nondeterministic field

## Shared contract B↔C (BINDING — identical in `p4.6l`)

Three v4-shaped quilltap-web routes (NOT dispatch variants):

1. `POST /api/v1/characters/{id}/photos` — EITHER multipart/form-data
   (`file` required, `caption?` string, repeated `tags` entries) OR JSON
   `{fileId?|linkId?, caption?, tags?}` (exactly one of fileId/linkId).
   → `201 {linkId, mountPointId, relativePath, keptAt, sha256}`.
   Errors: 404 character not found; 400 for the v4 keyword list
   (`already in`, `no linked database-backed vault`, `Unsupported MIME
   type`, `Uploaded image is empty`, `not an image`, `not found`,
   `empty bytes`); 500 otherwise.
2. `GET /api/v1/characters/{id}?action=export&format=png` →
   `200 image/png` bytes, `Content-Disposition: attachment;
   filename="<name>.png"`.
3. `POST /api/v1/characters?action=import` — multipart (`file`: a .png
   ST card or a .json ST card) → `201 {character: {id, name,
   description, defaultImageId, createdAt, updatedAt, _count: {chats}}}`;
   400 `Invalid SillyTavern PNG file` on parse failure.

If any shape must change, BOTH orders change and the change is reported
at unification.
