## The drift, classified (surveyed 2026-07-30)

**`4ac66c29`** — memories were the ONLY entity restored without their
backed-up id. v4's restore phase 9 destructured `id` off the archived memory
and let the repository mint a fresh UUID; memories reference each other
through `relatedMemoryIds`, and uuid-remap rewrites those edges in lockstep
with `id` for new-account restores — so **in every restore mode each edge
pointed at a memory that no longer existed**, flattening the Commonplace
Book's graph silently. Two changes:

1. `lib/backup/restore/restore.ts` phase 9: memories now `create(clean,
   { id })` — the archived id is preserved (in `new-account` mode that id is
   already the remapped one, since uuid-remap runs before the restore
   applies).
2. `lib/repositories/user-scoped.ts` — `UserScopedMemoriesRepository.create`
   gains and forwards the `CreateOptions` argument it had silently dropped
   (it is hand-written because it scopes by character, not userId, so it
   never inherited the generic wrapper's pass-through). Restore is the only
   caller that passes options.

The commit's other content is v4-side assurance: a new
`restore-field-fidelity.test.ts` (v4 jest — comes free with the pin) and the
release-checklist claim that all 16 columns added this cycle ride the
schema-driven backup pipeline. `commonplaceRecallHistory` /
`commonplaceSceneCache` are deliberately absent from portable `.qtap`
exports (instance-local ephemera; the export schema is
`additionalProperties: false`) while still being backed up — that is
EXISTING behavior restated, not drift.
