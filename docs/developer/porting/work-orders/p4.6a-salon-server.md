> One of the two parallel lanes of the P4.6 round (the first Salon vertical,
> milestone M4). **v4 reference baseline: HEAD `a7b1398d`**

## Mandate

Port the route-handler logic the first Salon vertical consumes — the
enriched chat list, the single-chat GET, the send-route pre-gate, the
turn/skip action, the message mutations (edit / delete / swipe), the chat
PUT, the impersonation verbs, and the chat-settings read — as dispatch
variants on the existing `Request`/`Response` contract, each
differentially verified against v4's real handler. Also deliver the
enriched committed web fixture the sibling lane's Playwright M4 e2e needs.
No SPA work in this lane.

**Survey-verified starting points (do not re-derive):**

- The send spine, `regenerate_swipe`, `skip_signal`
  (`compute_skip_eligibility` et al.), `turn_orchestrator` (incl. the
  `query`/nudge/queue/dequeue action core + `computeSpokenThisCycleAfterSkip`),
  `chats_impersonation` (add/remove/`setActiveTypingParticipant`),
  `chat_settings::find_by_user_id` (full net-read marshaling),
  `context_summary::invalidate_context_summary_if_message_covered`, the
  memory cascade (`delete_memories_by_source_messages_with_vectors`),
  `resolve_agent_mode_setting`, `photos::resolve_character_avatar` (URL
  half), `reconcile_terminal_sessions_for_chat`,
  `surface_operator_mail_for_chat`, and `chat_enrichment`
  (`enrich_participant_summary` — the SUMMARY/no-preloaded slice only) are
  ALL already ported and verified. This lane is handler assembly on top.
- **There is NO `canSkipTurn` field in v4** (grep-confirmed) — the client

## Deliverables

### 1. The enriched chat list (`listChats` upgraded)

v4: `app/api/v1/chats/route.ts` `handleList` +
`lib/services/chat-enrichment.service.ts` `enrichChatsForList` (the BATCHED
preloaded path — bulk `findByIds` for characters/files/mount-links/projects
+ `countByChatIds` for memories/chunks, threaded as `ChatListPreloaded`).
Port: the chatType filter (`salon`+legacy-null kept; `help` dropped;
`autonomous` only when `includeAutonomous` OR the room's own
`runVisibility ∈ {household, open}`), the descending
`lastMessageAt ?? updatedAt` sort, per-chat enrichment (participant
summaries with resolved `avatarUrl`, enriched tags, `messageCount`, project
`{id,name,color}`, storyBackground `{id,filepath}`, memory count, derived
`scriptoriumStatus`), `filterChatsByExcludedTags`, the post-enrichment
`limit` slice, and `cleanEnrichedChats` (strips `_allTagIds`). Extend the
existing `Request::ListChats` with the optional params and replace the thin
`chat_summary()` projection with the enriched DTO (the shell's current
consumer is the sibling lane's to update). The `?action=has-dangerous`
sub-verb is OUT (Settings vertical).

### 2. The single-chat GET (`chatGet` — the big one)

v4: `app/api/v1/chats/[id]/handlers/get.ts` `handleGet` (default branch,
~330 lines). Port faithfully: the pre-read side effects
(`reconcileTerminalSessionsForChat`, `surfaceOperatorMailForChat` — both
ported services), `enrichParticipantDetail` (the FULLER shape than the
create path's summary: character detail incl. `systemPrompts[]` +
`avatarOverrides`, `connectionProfile` incl. the apiKey summary,
`imageProfile`, `selectedSystemPromptId`, per-chat talkativeness), the
roleplay-template embed (`renderingPatterns` + `dialogueDetection`), ALL
messages via `getMessages` (no pagination — faithful) with the
`messagesWithEmbeddedTools` adjacency set, attachment resolution (linked
`files` + Scriptorium mount-file attachments with `sha256`+`linkSummary`),
the full per-message projection (the ~30-field set: role/content/tokens/
swipe fields/participantId/attachments/provider/modelName/
targetParticipantIds/isSilentMessage/systemSender/systemKind/hostEvent/
customAnnouncer/carinaMeta/pendingExternal*/reasoning*/confirmation*),
off-scene character resolution (`customAnnouncer.characterId` +
`carinaMeta.answererId` non-participants via `getCharacterDetail`),
`projectName`, and the agent-mode cascade.

**The one deliberate divergence (LOCKED for this round): no server-side
markdown pre-render.** v4 computes `renderedHtml` per message via
`renderMarkdownToHtml` (a unified/remark/rehype pipeline — npm-native, not
portable to Rust byte-exactly); v5 renders client-side in the SPA with the
identical pipeline (the sibling lane ports it). The v5 projection OMITS
`renderedHtml`; in the differential, jest-mock v4's `renderMarkdownToHtml`
to return `null` so the key is absent on BOTH sides and everything else
diffs exactly. Record this as a documented divergence (revisit only if SPA
render performance demands a server cache).

### 3. The send-route pre-gate (extend `chatSend`)

v4: `chats/[id]/messages/route.ts` +
`lib/services/chat-message/request-helpers.ts` + the Zod schemas
(`sendMessageSchema` / `continueMessageSchema`,

`browserUserAgent` scrubbing is N/A over dispatch (no UA header semantics)

### 4. The turn action (`chatTurnAction`)

v4: `chats/[id]/actions/turn.ts` `handleTurnAction`
(action ∈ `nudge|queue|dequeue|query|skipUserTurn`). The action core is
ported (`turn_orchestrator`); port the handler: participant validation
(skipUserTurn requires `controlledBy === 'user'`), the **skip guard** —
when `qualifiesForTurnSkipping` and eligibility says
`mustSpeakReason === 'all-others-skipped'`, refuse with `bad-request` and
v4's exact copy ("Everyone else has passed — it falls to {name} to say
something.") — the `computeSpokenThisCycleAfterSkip` persist, the Host
turn-pass announcement (source `'user'`, only when turn-skipping applies),
`selectNextSpeaker` + the queue persist, and v4's response shape
(`{success, action, turn:{nextSpeakerId, nextSpeakerName,
nextSpeakerControlledBy, reason, explanation, cycleComplete, isUsersTurn},
state:{queue}, participant?}`). RNG injected per the ported precedent.

### 5. Message mutations (`messageEdit` / `messageDelete` / `messageSwipe`)

v4: `app/api/v1/messages/[id]/route.ts`. All three resolve the owning chat
via `findChatIdForMessage` + the ownership check, then:

- **Edit (PUT):** `{content: string(min 1)}` → `updateMessage`, touch chat
  `updatedAt`, then `invalidateContextSummaryIfMessageCovered`.
- **Delete:** the memory-cascade **confirmation protocol**: collect the
  whole swipe group when `swipeGroupId` is set; count memories from the
  source messages; memories exist AND no `memoryAction` →
  `{requiresConfirmation, memoryCount, messageIds, isSwipeGroup}` with NO
  delete; `DELETE_MEMORIES`/`REGENERATE_MEMORIES` cascade through
  `delete_memories_by_source_messages_with_vectors`, `KEEP_MEMORIES`
  keeps; then `deleteMessagesByIds`, touch `updatedAt`, summary
  invalidation → `{success, memoriesDeleted}`.
- **Swipe:** `{swipeIndex?}` present → the switch branch (return the
  existing sibling); absent → the generate branch: v4's guards (ASSISTANT
  only, `systemSender` rows rejected) then the ported
  `regenerate_swipe::regenerate_message_as_swipe` → `{message}`.

`?action=reattribute` and `bulk-reattribute` are OUT (later vertical).

## Shared contract (BINDING — identical text in both orders)

P4.6b codes its client against these shapes without seeing this lane's
code. Implement them EXACTLY; if implementation reveals a problem with a
pinned shape, STOP and report (the unification pass arbitrates — do not
silently deviate).

Already on main (P4.6b may use today): everything in the P4.4/P4.5 round's
contract (`health`/`unlockState`/`unlock`/`lock`/`setup`/`storePepper`/
`changePassphrase`/`listInstances`/`listChats`/`chatSend`/`chatCreate`,
the global `/api/events` SSE with Green-Room replay-on-subscribe, the
binary GET routes, the terminal REST+WS surface).
`crates/quilltap-core/src/api/types.rs` is the source of truth; `Request`
internally tagged camelCase, `Response` adjacently tagged
(`{"type":…,"data":…}`), errors
`{"type":"error","data":{kind,message,pepperState?}}`.

New/changed this round (P4.6a implements; all `data` bodies are faithful
to the named v4 route body — same field names, same nesting — with the
single documented exception that message projections carry NO
`renderedHtml`):

- `listChats` gains optional fields `excludeTagIds?: string[]`,
  `limit?: number`, `includeAutonomous?: boolean`; its `data` becomes the
  array of v4 `EnrichedChatSummary` objects (`handleList`'s
  `cleanEnrichedChats` output: `id, title, contextSummary, createdAt,
  updatedAt, lastMessageAt, participants[], tags[], project,
  storyBackground, isDangerousChat, conciergeOverride, chatType,
  scriptoriumStatus, _count:{messages,memories}`).
- `{"type":"chatGet","chatId"}` → `{"type":"chat","data":{"chat":{…}}}` —
  v4 `handleGet`'s `{chat}` body (enriched participants, `user`,
  `messages[]` with the full per-message projection minus `renderedHtml`,
  `projectName`, `resolvedAgentModeEnabled`/`agentModeSource`,
  `offSceneCharacters[]`, and the chat flags incl. `turnSkippingEnabled`,
  `isPaused`).
- `chatSend` gains `nudge?: boolean` and `pendingToolResults?: […]`
  (v4 `sendMessageSchema` element shape); blank content with no
  files/tool-results → `bad-request`, v4's exact message.
- `{"type":"chatTurnAction","chatId","action":
  "nudge"|"queue"|"dequeue"|"query"|"skipUserTurn","participantId"?}` →
  `{"type":"turnAction","data":{…}}` — v4 `handleTurnAction`'s body; the
  all-others-skipped refusal is `bad-request` with v4's copy.
- `{"type":"messageEdit","messageId","content"}` →
  `{"type":"message","data":{…}}` (v4's PUT body).
- `{"type":"messageDelete","messageId","memoryAction"?,
  "skipConfirmation"?}` → `{"type":"messageDelete","data":{…}}` — either
  the confirmation body `{requiresConfirmation, memoryCount, messageIds,
  isSwipeGroup}` or `{success, memoriesDeleted}`.
- `{"type":"messageSwipe","messageId","swipeIndex"?}` →
  `{"type":"message","data":{"message":{…}}}` (v4's swipe body).
- `{"type":"chatUpdate","chatId","chat":{…partial…}}` →
  `{"type":"chat","data":{"chat":{…}}}` (v4's PUT `{chat}` body).
- `{"type":"chatImpersonate"|"chatStopImpersonate"|
  "chatSetActiveSpeaker","chatId",…}` — per-verb fields + response bodies
  faithful to v4 `actions/participants.ts`.
- `{"type":"chatSettings"}` → `{"type":"chatSettings","data":{…}}` — v4's
  `GET /api/v1/settings/chat` body.
- The chat-create DTO stays `{chat:{…}}` (v4's 201 echo semantics are a
  standing recorded follow-up — do not change its shape this round).
- **The M4 mock-LLM e2e recipe (unification runs it):** the committed
  Salon fixture (unit 8) carries an OPENAI_COMPATIBLE connection profile;
  Playwright's global setup spawns a tiny Node mock speaking
  chat-completions SSE, rewrites the profile's `baseUrl` in the fixture
  COPY via `quilltap db --write`, and the live send round-trips through
  the real binary. P4.6b ships the mock + the spec; the live run happens
