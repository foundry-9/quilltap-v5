# Work order: W4.2u — wire the real danger router into the spine

**Size: small (one Opus session, no internal parallelization needed).** This is
the deferred "unification handoff" from the W4.2 landing (see the W4.2 entry in
[`../chat-orchestration.md`](../chat-orchestration.md) and the CLAUDE.md status
bullet): W4.2 ported `services::dangerous_content` — including
`provider_routing`, the real implementor of the frozen
`provider_failover::DangerousContentRouter` trait — but deliberately did NOT
edit the spine files (they were owned by the parallel W4.4a batch). Those files
are now free.

## Goal

1. **Construct the real resolution at the orchestrator composition point.**
   `process_message` currently takes `RTR: DangerousContentRouter` generically
   and the differential injects a stub (`NoRouter` in tests). Replace the
   injected stub with the real wiring, mirroring where v4's
   `orchestrator.service.ts` resolves danger:
   - Resolve `DangerSettings` via the ported
     `dangerous_content::resolver::resolve_dangerous_content_settings` (global
     settings read + per-chat off-duty / moderation-exempt short-circuits) —
     the orchestrator currently takes `DangerSettings` as an input field; it
     should now *compute* it from the chat row + chat settings, keeping the
     input only as a test override if the differential needs one (prefer
     dropping it — read the v4 source for where the resolution happens
     relative to participant resolution).
   - Construct `dangerous_content::provider_routing::…Router` (the real
     implementor) with its `ApiKeyResolver` seam and pass it where the generic
     `RTR` goes. The trait itself is FROZEN — do not change its shape.
   - Keep the gatekeeper job (`gatekeeper_job::handle_chat_danger_classification`)
     reachable from the finalizer's already-banked
     `enqueue_chat_danger_classification` trigger (no new wiring needed there —
     the job RUNNER is W4.8).
2. **Add the two orchestrator-corpus cases W4.2 specified:**
   - `danger_off_short_circuit` — a chat whose resolved mode is `OFF`: the
     danger-resolver short-circuit must skip classification enqueue and never
     consult the router (v4 behavior; read
     `lib/services/dangerous-content/resolver.ts` + the orchestrator call
     site). The finalizer trigger gate for danger classification was banked
     with mode non-OFF only — this closes that corpus gap.
   - `danger_live_reroute` — a chat that is actively dangerous
     (`isDangerousChat` + not off-duty) with an uncensored connection profile
     available in the fixture: the primary stream must be rerouted through the
     uncensored profile (the `provider_failover` reroute path with the REAL
     router this time), and the recorded canned stream key must prove the
     reroute reached the wire (different profile → different key).
