## Scope and seam split (decided)

- **File BYTES are a host seam.** v4 reads bytes via `fileStorageManager`
  (S3/local disk). Inject a `FileBytesStore` trait (`read(file_entry) ->
  bytes`); the differential cans bytes per fileId on both sides (the oracle
  mocks the FSM identically). Real disk wiring is Phase 4.
- **Image RESIZE is a host seam.** v4 uses Sharp (progressive 80% → −20%/iter,
  max 10 iterations, JPEG quality fallback). Port the DECISION logic pure
  (`can_resize_image`, `calculate_base64_size` = `ceil(len*4/3)`,
  `get_provider_max_base64_size` default 4 MB, the loop's dimension/quality
  schedule) over an injected `ImageTranscoder` seam that performs one resize
  step and reports resulting bytes — the differential injects a deterministic
  fake on both sides (the doc_blob `transcodeToWebP` precedent). Do NOT pull
  an image codec crate into the core.
- **The vision-LLM image description** rides the existing
  `CompletionProvider` seam (it is a `provider.sendMessage` call), with the
  uncensored-retry fallback ported (the profile selection:
  `chatSettings.imageDescriptionProfileId` else auto-pick cheap vision
  profile; retry with `uncensoredImageDescriptionProfileId` only when primary
  failed/refused; the refusal heuristics — empty, reasoning-token exhaustion,
  suspicious keywords — byte-faithful).
