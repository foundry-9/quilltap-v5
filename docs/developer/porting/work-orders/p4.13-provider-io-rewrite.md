## The ruling this order executes (2026-07-23, human — recorded in `dogfood-findings.md` and the memory note `provider-io-divergence-and-post-5-0-refactor`)

Findings #23, #24, #25 were three total outages in the provider seam in two
days, all under a green differential suite. The structural cause: v5
reproduced the SHAPE of v4's provider plugins — per-provider build/parse
pairs behind a lowest-common-denominator interface — but that shape exists
because v4 must dynamically load providers as JS at runtime. v5 has no
plugins, so it carries the interface's costs (lossy intermediate types,
duplicated per-family parse, a boundary no type checks) with none of its
benefit.

1. **Provider I/O may be restructured** as an accepted divergence from
   straight-port fidelity. Drift risk accepted (the human commits to keeping
   v4 pure for provider I/O); a restructured v5 provider layer does not owe
   v4 re-portability.
2. **NOT a precedent.** Scoped to provider I/O ONLY. v4's general shape is
   retained everywhere else. Do not "while we're here" anything outside the
   seam; do not pre-emptively restructure for the post-5.0 de-Node plan.
3. **The invariant that does not move: the wire bytes stay byte-faithful to
   v4.** Internal structure is free; the request/response corpus is the
   contract. **The verification legs land BEFORE the restructuring** —
   phase A below (tool linkage to the wire + the recorded-body
   response-parse corpus) must be green before phase B touches a line of
   internal structure.

## Mandate

Deliver a provider-I/O layer where provider differences are **data plus one
typed pipeline**, message/response types can represent everything the wire
needs, and illegal states are unrepresentable (a tool result without a call
ID must not be constructible where the provider family requires one) —
while every byte the transport sends and every parse the callers receive
stays pinned to v4 by committed, regenerable corpora. Along the way: the
tool-call linkage reaches the wire on all eight providers (finding #25),
and a failed cheap-LLM call writes an `llm_logs` error row (the ruled
deliberate divergence).

**Must NOT touch:** orchestrator/tool-loop *semantics* (the loops'
decisions, prompts, whisper gates — only their conversion into wire
messages), pricing, embeddings, moderation, the transports
(`quilltap-web`/`quilltap-tauri`), the SPA, `memory_injector.rs` (P4.14's
file), the Dockerfile (P4.10's). The tracing-subscriber question and
`chat_messages.debugMemoryLogs` writer remain open items, explicitly not
here. #26/#27/#28 stay open for the post-rewrite dogfood-fixing run.

## The unit-5 design note (committed 2026-07-23, per this order's requirement)

**Target shape.** Provider differences live in exactly ONE dispatch table;
one message representation flows from the loops through the builders; the
two pipelines (`WireStreamingProvider` for streams, `execute_completion`
for sends) stay the composition roots. Concretely:

1. **One message type end-to-end.** `RequestInput.messages` becomes
   `Vec<StreamMessage>` (the phase-A carrying enum) and `RequestMessage` is
   DELETED — the builders consume the enum directly, so the conversion the
   old `request_message_of` performed disappears rather than being guarded.
   `ToolCallMsg` folds into `ToolCallPayload` (one tool-call type on the
   request side; `response_parse::ToolCall` stays — it is the parse-side
   shape). Consequences the types now enforce:
   - the id-less-tool arms in the builders (`if let Some(id)` drops at
     `responses_api.rs`/`chat_completions.rs`, the `tool_use_id: ""`
     malformed arm at `anthropic.rs`, OpenRouter's filter-then-refuse
     FILTER half) become **unrepresentable and are deleted**, each with a
     why-comment recording v4's arm. The corpus has no id-less-tool vector
     (verified), so every recorded byte is unchanged.
   - an assistant turn's calls cannot be separated from it.
2. **`cache_control` becomes representable, not populated** (corrected
   during implementation): `StreamMessage::{User,Assistant}` and
   `ThreadedMessage` gain `cache_control` (v4 `LLMMessage.cacheControl`),
   so the boundary can represent everything v4's `streamMessage` maps
   (streaming.service.ts:377 maps `m.cacheControl` explicitly). BUT the
   survey's assumed end-to-end thread would have been a **divergence**: v4's
   OWN `buildMessageContext` final mapping (context-builder.service.ts:
   753–771) picks role/content/attachments/name/thoughtSignature only — the
   summary-head `cacheControl` the context manager stamps NEVER reaches the
   provider in v4 either, and the anthropic per-message cache arm is dead
   on v4's chat path too. v5 mirrors that exactly: the field exists at the
   boundary, `message_context::FormattedMsg` drops it where v4 drops it,
   and the anthropic `honor_msg_cc` arm stays as ported v4 code reachable
   only by a caller that sets it directly (none today).
3. **One dispatch table.** A `WireFamily` selection (in
   `model/provider_io.rs`) maps a provider id to its THREE family choices —
   request builder, response parser, stream decoder — replacing the three
   independent provider-string matches (`build_request`,
   `parse_for_provider`, `decoder_selection`'s flavor split). What stays
   per-provider stays as **narrow arms of that one table**: OpenRouter's
   zod re-emission (both directions — the send builder AND the P4.13
   unit-4 response normalization), google's URL/wire framing + the
   Anthropic model-family boundary (inside their builders, where they
   already live as data-like rules).
4. **What does NOT move:** the five decoders (already family-shaped over
   committed `.wire` fixtures), the manifest registry (already the
   declarative data source), the pricing/embedding/moderation surfaces, the
   transports, and the cheap-LLM `CompletionMessage`/`CompletionParams`
   types (v4's cheap path is text-only; its canned keys must not shift —
   `request_input_from_params` maps into the enum at the boundary instead).

**Verification:** every corpus in the survey's contract list byte-identical
(request-envelopes 93 + google-wire 10 + google-request, decoders, the
unit-3 call-site pins, the unit-4 response corpus, the tier-3 canned keys),
plus regen freshness at `e646f58b`.
