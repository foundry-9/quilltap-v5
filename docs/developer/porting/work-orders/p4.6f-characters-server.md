## Deliverables (tiered)

### Tier 1 — the core CRUD + actions (blocking the SPA lane)

**1. `characterList`** — v4 `characters/handlers/get.ts`: `findByUserId` →
in-memory `npc`/`controlledBy` filter + sort → per-character enrichment
(`enrichWithDefaultImage(defaultImageId)`, partner-name lookup via
`findById(defaultPartnerId)`, chat count via `chats.findByCharacterId`) →
the **hand-assembled whitelist DTO** (`get.ts:58-92`): `id, name, title,
description, defaultImageId, defaultImage, isFavorite, controlledBy,
canBeCarina, defaultConnectionProfileId, defaultPartnerId,
defaultPartnerName, defaultTimestampConfig, defaultScenarioId,
defaultSystemPromptId, defaultImageProfileId, npc, createdAt, tags,
updatedAt, systemPrompts[{id,name,isDefault}], scenarios[{id,title,content}],
_count.chats`. Reproduce the N+1 faithfully (correctness first; batching is
a post-parity optimization). New module suggestion:
`quilltap-core::services::character_enrichment` (do NOT extend
`chat_enrichment` — keep the families separate).

**2. `characterGet`** — the detail projection: ownership check
(`findById` + checkOwnership → 404/403 semantics collapse to NotFound for
the single-user v5), `enrichWithDefaultImage`, `_count.chats`; response is
`{...character (full row spread), defaultImage, _count}`. Plus the cheap
read actions as separate variants or params: **`default-partner`**
(returns `defaultPartnerId`), **`get-tags`** (N+1 `tags.findById` →
`{id,name,visualStyle}`).

**3. `characterCreate` / `characterQuickCreate`** — v4 `post.ts:304/:353`:
`createCharacterSchema` validation, scenario normalization (fill
id/createdAt/updatedAt), empty `partnerLinks`/`avatarOverrides`/`tags`
defaults, → the ported `create_character` (which provisions the vault).
Response is the **create-echo** `{character}` 201. Apply Zod-PARSE
semantics on nested bags (the P4.6c settings-PUT lesson —
`[[p4-6c-salon-consolidation]]`).

**4. `characterUpdate`** — v4 `put.ts:86`: `findByIdRaw` first (broken-vault
chars stay editable — the ported `find_by_id_raw` exists), `updateCharacterSchema`
(pronouns / defaultTimestampConfig / physicalDescription incl.
`headAndShouldersPrompt`), scenario normalization +
`PhysicalDescriptionSchema.parse`, → the ported `update_character`
(write overlay). Response `{character}` = the update's return (v4 `_update`
returns the MERGED `{...existing,...data}` Zod-parsed — the P4.6c D4
finding applies: overlay the bag onto the pre-update read, do NOT re-read).

**5. `characterDelete`** — v4 `delete.ts:14` + `lib/cascade-delete`. Port
`executeCascadeDelete` + `getCascadeDeletePreview` (a new
`services::character_cascade_delete`): they ORCHESTRATE over ported pieces
(chat deletes via `delete_conversation_with_vault_sweep`, memory cascades,
`delete_file_completely` [P4.1b], the vault/mount teardown, wardrobe/
plugin-data/vector-index rows). Query flags `cascadeChats`/`cascadeImages`;
returns the deleted-counts DTO. `cascade-preview` (GET action) reuses the
preview half. Survey `lib/cascade-delete/` fresh before porting — enumerate
every table it touches and diff them ALL in the differential.

**6. The thin action verbs** — one dispatch variant `characterAction`
(mirroring `chatTurnAction`'s shape) or individual variants (pick one and
pin it in the Shared contract; recommendation: individual variants, matching
the settings lane's style): `favorite` (flip), `toggle-controlled-by`,
`toggle-carina`, `add-tag`/`remove-tag` (tag-exists guard → 404),
`set-default-partner` (guards: partner must exist, be `controlledBy:'user'`,
not self), `avatar` (`{imageId: string|null}` — resolver validation: the
image must resolve and be `image/*` mimeType; then `update({defaultImageId})`
+ re-enrich; response `{data:{...character, defaultImage}}`).

**7. The sub-resource routes** — thin over ported repo ops + ownership
guard:
- **prompts**: list (reads `character.systemPrompts`), create
  (`{name,content,isDefault}`), update, delete, set-default (v4 reaches it
  via `PUT [id]?action=update-prompt&promptId=` with `{isDefault:true}` —
  map to the ported `set_default_system_prompt`).
- **scenarios**: GET list, POST create (`{title,content}`), PUT/DELETE by
  `scenarioId`. (The edit form ALSO sends the whole array through the
  character PUT — both paths must work.)
- **plugin-data**: map GET (`getPluginDataMap`), upsert POST/PUT, item GET,
  DELETE. JSON-serializable guard is the only route logic.
- **wardrobe**: GET list (`find_by_character_id` — the vault read), POST
  create, GET/PUT/DELETE by itemId (`find_by_id_for_character`); DELETE
  also calls the ported `remove_equipped_item_from_all_chats` cleanup.

**8. `tags` CRUD** — v4 `tags/route.ts` + `tags/[id]/route.ts`: list with
search + cross-entity usage counts, POST create (dedup by name), GET/PUT
(rename/visualStyle/quickHide), DELETE with the **multi-entity fan-out**
(`tags/[id]/route.ts:113-159` — remove the id from every character / chat /
connection profile / image profile / embedding profile / file). The fan-out
is real route logic; diff every touched table.
