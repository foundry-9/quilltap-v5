## The defect

`services/native_tool_loop.rs:434-437` builds the continuation slate exactly
right — v4's assistant tool-call turn followed by one message per result, the
results carrying `tool_call_id` and the assistant turn carrying `tool_calls`
(`services/tool_call_threading.rs:174`). Two conversions then discard every
field except role and content:

| Site | What it does |
| --- | --- |
| `services/native_tool_loop.rs:627` (`to_completion_messages`) | maps `role` + `content` only |
| `services/brahma_console/mod.rs:256` (its own `to_completion_messages`) | same |
| `model/streaming_provider.rs:163` (`request_input_from_stream_params`) | `RequestMessage::text(role, content)` |

The intermediate type cannot represent the linkage: `CompletionMessage`
(`model/completion.rs:45`) is `{role, content}`, documented as "v4 `LLMMessage`,
role + content subset". `StreamParams.messages` is a `Vec<CompletionMessage>`
(`model/stream.rs:177`), so the information is already gone before the request
builder is reached.

**The request builders are correct and fully wired** — `RequestMessage`
(`model/request_builder/mod.rs:66`) carries `tool_call_id`, `tool_calls`,
`reasoning_content`, `thought_signature`, `name`, and every family's formatter
consumes them. Nothing on the streaming path ever populates them.

`brahma_console/mod.rs:253-256` states the false belief in a doc comment —
"`toolCalls`/reasoning are request-local continuation state the provider request
builder reconstructs, as `native_tool_loop` does". The builder cannot
reconstruct what it never receives. **Delete that comment as part of the fix**;
a wrong invariant written down is worse than none.

### What each family does with an id-less `tool` message

| Family | Behavior | Source |
| --- | --- | --- |
| Responses API (OPENAI, GROK) | **dropped entirely** | `responses_api.rs:54,79` — `if let Some(id)` |
| chat-completions (DEEPSEEK, Z_AI, OLLAMA, OPENAI_COMPATIBLE) | **dropped** | `chat_completions.rs:52` — `continue` |
| ANTHROPIC | emits `tool_use_id: ""` — malformed | `anthropic.rs:102,110` |
| OPENROUTER | filtered, then the request is refused | `chat_completions.rs:545-554` |

`tool_calls` being always empty additionally means the
`"assistant" if !msg.tool_calls.is_empty()` arm never fires, so the model is not
shown its own tool call either. The model asks, sees no answer, asks again.

### The one path that works, and why it hides the bug

`build_tool_result_messages` (`tool_call_threading.rs:178`) falls back to a
plain **`user`** message — `[Tool Result: <name>]\n<content>` — when a result
has **no** call ID. That message survives every formatter. So the failure is
conditional on the provider supplying call IDs, which the native tool path
normally does.

This is why the **Brahma Console dogfooded clean on 2026-07-20** while the Salon
loops: `brahma_console/orchestrator.rs:370-373` deliberately re-threads prior
TOOL rows as `[Tool Result: …]` user text ("the console's loop-bug fix"), and
`:524-536` detects `MAX_DUPLICATE_TOOL_CALLS` and re-injects the data as prose.
The console carries a workaround for exactly this failure; the Salon has none.

### Why no differential caught it

`request_builder_equivalence` feeds the builders a corpus that already contains
well-formed tool messages, proving the builders right. The native-tool-loop
tier-3 mocks the provider and asserts the loop's internal `ThreadedMessage`
slate, proving the loop right. **Neither executes the conversion between them.**

This is the third finding of this class — #16 (`Real*` seams), #22 (the tool
context), now #25 — all of them call sites the corpora bypass because the
corpora construct their own inputs. Treat "the corpus builds the context itself"
as a standing smell.

## Mandate

1. **The linkage reaches the wire.** A tool result carries its call ID and an
   assistant tool-call turn carries its calls, through every conversion, on the
   streaming path, for all eight providers.
2. **Make the loss impossible, not merely fixed.** The intermediate message type
   must be able to represent what v4's `LLMMessage` represents. A future edit
   must not be able to silently drop it again.
3. **Pin it at the call site.** The differential must assert the bytes the
   transport is handed — not what a corpus feeds the builder. Without this leg
   the fix is unverified in exactly the way the bug was.
4. **Prove it live** on the Friday copy, on a native-tool provider, in the
   Salon.

## Units

**Unit 1 — the carrying type.** Give the streaming boundary a message type that
carries `tool_call_id`, `tool_calls`, `reasoning_content`, `thought_signature`,
`name`. Two shapes were sized during the survey:

- widen `CompletionMessage` — matches v4's `LLMMessage`, but **50 struct
  literals** across core + harness, and it is shared with the cheap-LLM path
  (check `build_character_cache_key` and the tier-3 canned keys do not shift);
- give `StreamParams.messages` its own richer type — **21 sites**, confined to
  the streaming path, cheap-LLM keys untouched. **Recommended.**

Prefer a constructor that makes a tool result without a call ID unrepresentable,
so the `user`-message fallback becomes an explicit choice rather than the
consequence of a missing field.

**Unit 2 — thread it.** Populate the new fields at all three conversion sites
(`native_tool_loop.rs:627`, `brahma_console/mod.rs:256`,
`streaming_provider.rs:163`) and delete the false comment at
`brahma_console/mod.rs:253-256`.

**Unit 3 — the call-site differential.** Extend the native-tool-loop tier-3 (or
add a sibling) to capture the request body the transport receives on the
second iteration and assert per family: `function_call_output` with the right
`call_id` (responses API), `role:"tool"` + `tool_call_id` (chat-completions),
`tool_result` + non-empty `tool_use_id` (Anthropic), and the assistant turn
carrying its `tool_calls`. Model it on P4.11 unit 7's call-site byte pin.

**Unit 4 — the Brahma workaround.** Once results genuinely arrive, re-check the
console's loop-bug compensation against v4: v4 carries it too, so it very likely
**stays** — but confirm it is v4-faithful rather than a v5 crutch, and record
the finding either way.

**Unit 5 — re-check finding #22.** Confirm the doc-tool retry loop is gone once
results arrive, and correct #22's row in `dogfood-findings.md` if this was the
other half of it.

**Unit 6 — live proof** (💸 real spend). On the Friday copy: a Salon turn where a
character calls a tool and *uses the answer*, on OpenAI and on Anthropic (the
two distinct malformed-vs-dropped arms), plus one chat-completions provider.

## Deferrals / risks

- **`reasoning_content` and `thought_signature` are dropped by the same seam.**
  The Google thought-signature round-trip and the DeepSeek/Z.AI reasoning echo
  on a tool-call turn are therefore also not reaching the wire. They ride this
  fix; if any needs its own oracle work, say so loudly rather than pinning a gap.
- Do not "improve" the `user`-message fallback away — it is v4 behavior for
  providers without call IDs.
- The e2e host has no API keys, so unit 6 is human-walked; units 3's byte
  assertions are the automated guard.
