## The drift, classified (surveyed 2026-08-18)

v4's tabbed workspace replaced each view's own background layer with one
arbitrated backdrop and suppressed the per-view layer inside
`.qt-workspace`. v4's `ProjectDetailView` was never converted: it still
set `--story-background-url` for a hidden layer and reported nothing, so
the project's background reached the screen by neither route — what
painted instead was `ProsperoView`'s subsystem background, still
registered under the tab's id after drilling into a project. v4's fix:
`ProjectDetailView` now reports its story background to the backdrop,
falling back to the Prospero subsystem image for `'theme'` mode; the
LIST's subsystem background moved into a `ProsperoListShell` that
unmounts while a detail is shown, so ONE reporter holds the tab's
registry key at a time (two live reporters raced; the subsystem won on a
deep-linked project tab).

**v5's gap is wider than v4's bug.** Grep-verified today:

- Only the Salon reports to v5's backdrop registry
  (`screens/salon/salon-conversation.ts:139,764` — the only
  `WORKSPACE_BACKDROP_REGISTRY` consumers outside `workspace/`).
- `screens/prospero/project-detail.ts` (270 ln) has ZERO background
  handling — the project story-background *display* was never ported,
  though the `backgroundDisplayMode` setting round-trips (it lives in
  `core-contract.ts`, the image-generation card, `db/projects.rs`).
- v5 has **no subsystem-background machinery at all** — a standing
  deferred-loud divergence recorded at the My Photos lane
  (`status-log.md:28282`) and predicted by `p4.9j2` ("v5's equivalent
  surfaces must report or they will overlap in a split; survey at lane
  start").

So in v5 there is no reporter race to fix — the port is the MISSING
