## Unit 1 — the unlock / pepper-vault service

### What already exists (do not re-port)

  pepper / `.dbkey` / hash-mismatch → resolved / needs-setup /
  needs-passphrase / needs-vault-storage), unit-tested. Its differential was
  deferred to this unit — **now due**.
- `quilltap-core::dbkey` — read (Friday-verified) AND write
  (`save_dbkey`/`generate_pepper`/`hash_pepper`/`read_pepper_hash`,
  round-trip verified, v4's exact JSON field order + 0600 mode).
- `Request::{UnlockState, Unlock, Lock}` + the engine teardown/re-assembly
  (`EngineAssembler`/`EngineShutdown`), the readiness gate in dispatch, the
  web 503/423 mapping with v4's `{error:"Setup required", setupUrl:"/setup",
  pepperState}` body.

### The v4 spec (read the source — it is the spec)

`app/api/v1/system/unlock/route.ts` at `a7b1398d`:

- **`?action=setup`** (`handleSetup`): `setupDbKey(passphrase)` → mint pepper,
  write `.dbkey`, state → resolved; returns `{pepper, message: 'Encryption
  key generated and stored. Save this value — it will not be displayed
  again.'}` — the pepper is shown ONCE. v4's post-setup
  plaintext-DB-encryption pass exists because v4 migrations create the DB
  plaintext BEFORE setup; **v5 has no plaintext window** (a fresh v5 instance
  is created encrypted directly at setup), so that branch is a **named
  non-port** with the rationale recorded (the legacy plaintext-conversion /
  `db-encryption-converter` path is a legacy-instance concern — tracked
  deferral, port only if a consumer materializes).
- **`?action=store`** (`handleStore`): `storeEnvPepperInDbKey(passphrase)` —
  wraps the env-provided pepper into a `.dbkey`; the needs-vault-storage →
  resolved transition. Returns `successResponse({})`.
- **`?action=change-passphrase`** (`handleChangePassphrase`): body
  `{oldPassphrase, newPassphrase}` (either may be `''` — empty = the internal
  no-passphrase sentinel); requires resolved state; `changePassphrase(old,
  new)` re-wraps the pepper; unauthorized on wrong old passphrase; returns
  `{success: true}`.
- **`?action=unlock`** — already ported; verify the ported behavior against
  the handler once more (the deferred-startup re-trigger is v5's engine
  re-assembly — already the P4.0 shape). The **legacy pepper_vault migration
  branch** (pre-`.dbkey` SQLite vault → `unlockPepper` → migrate) is a
  **tracked deferral** (legacy instances only).
- **`GET`** — the state read incl. `hasUserPassphrase` and `autoLockMinutes`.
  Survey where `autoLockMinutes` comes from (a settings read) and where v4's
  **idle timer + 3-attempt limit** live (likely client-side — the SPA calls
  `?action=lock`; the attempt limit may be UI state). Port the SERVER half
  faithfully; record where the client half lives so the SPA vertical picks it
  up (the `UnlockStateDto.auto_lock_minutes` field already exists).

### Fresh-instance provisioning (the hard part)

Survey what a fresh v4 instance contains after first boot + setup: the
migrations / `instrumentation.ts` `register()` phases, `initializeDatabase`,
`ensureCollection` DDL, `enforce-single-user` (the `SINGLE_USER_ID` user
row), instance settings, and any other baseline rows (built-in prompt
templates? provider models? — survey, don't guess). The v5 `Setup` variant
must produce an instance the engine can boot and the SPA can use:

- Schema: the same DDL surface the tier-2 fixture builders already exercise
  (v4 `generateCreateTable` over the schemas) — but created by the CORE at
  setup time, encrypted from byte zero (ChaCha20, the standing cipher rules:
  `PRAGMA key` first, TRUNCATE journal on the writable path).
- Baseline seed: whatever v4's first boot seeds (at minimum the single user
  row; survey for the rest).
- All three partitions as v4 lays them out (main / mount-index / llm-logs —
  survey which files exist after a fresh v4 boot and when each is created).

**Differential (the provisioning proof):** initialize a fresh v4 instance
(drive v4's real migrations/startup against an empty data dir — the
jest/tsx oracle patterns in the memory notes apply; a test pepper, never the
real one) and dump `sqlite_master` + every seeded row per partition; the v5
`Setup`-provisioned instance must match structurally (normalize minted
ids/timestamps; schema byte-exact). Also prove **cross-compatibility**: a
v5-provisioned instance opens under v4's real code (the oracle boots v4
against it and reads), and a v4-fresh instance boots under the v5 engine.

**The startup backfill sweep** (`lib/startup/backfill-*.ts`,
`ensure-group-scenarios.ts`, `enqueue-headshoulders-backfill.ts`, …) heals
OLD instances at boot — **tracked deferral** except any piece a FRESH
instance genuinely needs (survey; state which and why in the report).

### Deliverables (unit 1)

- `quilltap-core`: the unlock-service module (likely

- `quilltap-host`: only if the survey shows a server-side auto-lock timer

- Differentials: the provisioning diff above + a `.dbkey`

  small tsx oracle.

## Shared contract (BINDING — identical text in both orders)

The P4.5 lane codes its client against these shapes without seeing this
lane's code. Implement them EXACTLY; if implementation reveals a problem
with a pinned shape, STOP and report (the unification pass arbitrates —
do not silently deviate).

Already on main (P4.5 may use today): `POST /api/dispatch`, `GET
/api/events` (global SSE, scope-tagged, `data:` frames + `id:` fields +
15 s keep-alive comments), `GET /health` (200/423/409/503), and the
`Request` variants `health` / `unlockState` / `unlock{passphrase}` / `lock`
/ `listInstances` / `listChats` / `chatSend{…}` with their `Response` DTOs
(`crates/quilltap-core/src/api/types.rs` is the source of truth; the Locked
refusal is `{"type":"error","data":{"kind":"locked","message":…,
"pepperState":…}}` and HTTP 503 carries v4's `setupUrl` body alongside).

New this round (P4.4 implements):

- `{"type":"setup","passphrase":"…"}` →
  `{"type":"setup","data":{"pepper":"<the minted pepper, shown once>",
  "message":"Encryption key generated and stored. Save this value — it will
  not be displayed again."}}`. Refusals use the standard error envelope
  (`bad-request` when the state is not `needs-setup`, etc.).
- `{"type":"storePepper","passphrase":"…"}` → `{"type":"ack","data":{}}`.
- `{"type":"changePassphrase","oldPassphrase":"…","newPassphrase":"…"}` →
  `{"type":"ack","data":{}}` (empty strings allowed — the no-passphrase
  sentinel); wrong old passphrase → error kind mapping to 401-family
  (survey v4's `unauthorized`; extend `ErrorKind` if needed).
- `{"type":"chatCreate", …}` → `{"type":"chatCreate","data":{…}}` — the body
  and DTO are THIS lane's to design from the v4 POST body (P4.5 does not
  consume it this round; the first Salon vertical does next round).
- Creation-progress events: `Event` envelope rows on `/api/events` carrying
  `progressId` scope + a payload with `level`
  (`log|info|warn|error|status`) / `message` / terminal `done|error` —
  field names faithful to v4's frame shapes (survey
  `creation-progress.ts`); P4.5 does not consume these this round.
