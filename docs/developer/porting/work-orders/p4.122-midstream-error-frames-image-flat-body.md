## The gap (why this order exists)

**(A)** P4.118 plugged the refusal side into the six text HTTP sites — the
NON-2xx path. A refusal that arrives INSIDE a 200 stream never reaches the
side: v5's chat-completions decoder hands every parsed frame to
`handle_chunk` with no `error` check, and the responses decoder matches
three event names and drops the rest, so the stream ends EMPTY and the turn
takes the empty-response recovery instead of the hard-error failover. The
P4.118 record wrote the failure case out and named it a follow-up. **The
planning survey re-measured it (§Survey) and moved four of the record's
claims** — the order below is written from the measurements, not the
record. **(B)** The image dialect's own SDK-error helper predates P4.118's
reconstruction and never applies the SDK's `{error: body}` wrap; a flat
refusal body loses its code and the image Concierge failover misses a
refusal it should reroute. Both are the same family (`provider_error`) and
the same recorder discipline, so one lane.

## Mandate

(A) Make a mid-stream error frame produce, on v5, exactly the `StreamError`
v4's thrown `APIError` produces — same message bytes, same `code` /
`error.code` on the refusal side, `status: None` — at exactly the frames
v4 throws on and NOWHERE v4 does not (§Survey 1–2: the two chat-completions
