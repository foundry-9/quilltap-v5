### v4 — the engine (`lib/mount-index/document-text-search.ts`, NEW, 231 lines)

- Constants: `DEFAULT_LIMIT = 100`, `SCAN_CAP = 200` (per SQL scan),
  `SNIPPET_LENGTH = 200`. Only `EDITABLE_TEXT_FILE_TYPES =
  ['markdown','txt','json','jsonl']` (NEW const in
  `lib/schemas/mount-index.types.ts` ~:97) are searched.
- `searchDocumentText(query, opts) → { results, totalCount }`. Flow:
  trim (empty → zeros, no repo touched) → `docMountPoints.findEnabled()` →
  build the excluded set from `opts.excludeMountPointIds` +
  `getArchivedCharacterVaultMountPointIds()` — **on throw, FAIL CLOSED**:
  exclude every `storeType === 'character'` store (strict compare — a NULL
  `storeType` vault survives the sweep; carry the edge) while ordinary
  stores still search, with the exact `logger.error` sentence — → two scans
  in `Promise.all`, both capped at `SCAN_CAP` → `buildDocStoreRefResolver()`
  once → merge.
- Merge/ranking quirks (pin all of these): name/path hits inserted FIRST and
  unconditionally overwriting (they shadow content hits per link);
  `matchedField = fileName-contains ? 'fileName' : 'relativePath'`; snippet
  for a name/path hit IS `relativePath`; `matchPriority = 0` only when the
  WHOLE lowercased fileName equals the WHOLE lowercased query (so
  `manifesto` vs `manifesto.md` is 1, not 0); content hits skipped when the
  link already has a name hit, `matchedValue = content.slice(0, 200)` (a
  hard-coded 200, NOT the constant), `matchPriority = 2`; final sort
  priority asc then `updatedAt` recency desc; return
  `merged.slice(0, limit)` with `totalCount = merged.length` — **capped by
  the scans, knowingly** (the module's own doc comment says so; do not
  "fix" it).
- `buildContentSnippet`: `lead = floor((SNIPPET_LENGTH − query.length) / 3)`
  (**/3, not /2** — one-third in, not centred; `query.length` in UTF-16
  units), indices from the LOWERCASED string slicing the ORIGINAL (the same
  case-fold skew v5's `ui_search.rs` header already documents), `.trim()`
  BEFORE the `...` ellipses, heading joined as
  `` `${headingContext} — ${snippet}` `` (em dash, spaces),
  `matchIndex === -1 → start = 0`.
- A hit whose store isn't in the resolver's map is silently dropped;
  `storeType` defaults `?? 'documents'` in `describe()`. Logging: debug with
  `queryLength` (never the query text), the no-stores debug, the fail-closed
  error.

### v4 — the repo scans + LIKE escape

- `lib/database/repositories/like-escape.ts` (NEW, 32 lines):
  `LIKE_ESCAPE_CHAR = '\\'`, `escapeLikeLiteral` escapes exactly `\ % _`
  each with a single backslash, `likeContainsPattern` lower-cases INSIDE the
  helper and wraps `%…%` (callers compare against `LOWER(col)` because
  SQLite LIKE folds ASCII only). v4 ships 5 unit cases.
- `docMountFileLinks.searchByNameOrPath(query, mountPointIds, limit)`
  (repo :627): guards empty ids/query → `[]`; `safeQuery` fallback `[]`
  with message `'Error searching file links by name or path'`; **no
  `isMountIndexDegraded()` check** (deliberate asymmetry — the chunks scan
  HAS one; carry both). SQL (bind order: ids…, the four types, pattern,
  pattern — the SAME pattern bound TWICE, limit):
  `SELECT l.id, l.mountPointId, l.relativePath, l.fileName, l.updatedAt
  FROM doc_mount_file_links l JOIN doc_mount_files f ON f.id = l.fileId
  WHERE l.mountPointId IN (…) AND f.fileType IN (…) AND
  (LOWER(l.fileName) LIKE ? ESCAPE '\' OR LOWER(l.relativePath) LIKE ?
  ESCAPE '\') ORDER BY l.updatedAt DESC LIMIT ?`.
- `docMountChunks.searchContent(...)` (repo :214): same guards +
  `isMountIndexDegraded() → []`. SQL groups `GROUP BY c.linkId` with
  `MIN(c.chunkIndex)` and **relies on SQLite's documented bare-column rule**
  (bare `content`/`headingContext` come from the min-chunkIndex row) — v5
  on the same engine inherits this; do NOT rewrite as a window
  function/subquery without preserving "lowest chunkIndex among MATCHING
  chunks". Scope filter is **`c.mountPointId`** (the chunk's own
  denormalized column), not `l.mountPointId` — keep the asymmetry.
