### The four primitives, exactly (`uuid-remapper.ts`)

- **`remap(oldUuid)`** :34 — memoized old→new in a `Map`. Same input always
  yields the same output **for the life of the instance**; that memo is the
  entire mechanism by which cross-references stay connected, so the map must be
  shared across every entity pass. New ids come from `crypto.randomUUID()`.
- **`remapArray(uuids)`** :54 — `Array.isArray` guard; a non-array logs a warning
  and returns `[]`. Otherwise `uuids.map(remap)`. **Note:** reachable only via
  `remapArrayFields`, which already checks `Array.isArray` — so the `[]` branch
  is dead in practice. Port it anyway (it is public API) and record that it is
  dead.
- **`remapFields(obj, fields)`** :74 — shallow copy, then for each field:
  rewrite **only if** `field in obj && typeof obj[field] === 'string'`. A `null`,
  a number, or an absent key is left exactly as it was. Non-object `obj` or
  non-array `fields` → warn and return `obj` unchanged.
- **`remapArrayFields(obj, fields)`** :110 — same shape, rewrites only if
  `field in obj && Array.isArray(obj[field])`.

**The keying trap.** `remap` keys a JS `Map`, so keys compare by value for
primitives and by *identity* for objects. Every array v4 remaps is a UUID array
per the schemas (`attachments` is `z.array(UUIDSchema)`), so in practice the keys
are always strings — but the faithful port keys by a representation that
distinguishes `"5"` from `5` (a `serde_json::Value`-discriminant-aware key, not a
bare string), and every OUTPUT is a fresh UUID string regardless of input type.
Record this rather than quietly narrowing the API to `&str`.

### ⚠ The three order-sensitivity traps

`serde_json` is built with `preserve_order` in this workspace (an `IndexMap`), so
object key order is observable and this lane's differential is byte-level. Match
JS object semantics exactly:

1. **`{ ...remapFields(x, [...]), userId: targetUserId }`** — a JS spread
   followed by an explicit key. If `userId` already exists it keeps its
   **original position** with the new value; if it is absent it is **appended**.
   `IndexMap::insert` has exactly these semantics. Use it; do not rebuild the
   map.
2. **`delete` must be `shift_remove`, never `swap_remove`.** v4 deletes
   `personaLinks` (:114), `physicalDescriptions` (:132) and `clothingRecords`
   (:142). `IndexMap::swap_remove` moves the last entry into the hole and would
   scramble every following key. Use `shift_remove`.
3. **The `remapFields` → `remapArrayFields` chain order is load-bearing** and v4
   flags it itself (:82, "IMPORTANT: Chain remapFields → remapArrayFields so
   array spread doesn't overwrite remapped scalar fields"). Always apply the
   scalar pass FIRST and the array pass to its result — never the reverse, and
   never both to the original.
