answer-confirmation.service.ts` (407 lines) + its finalizer integration

## What to port (new module `services::answer_confirmation`)

Read the v4 source first; the shape (from a 2026-07-06 survey):

1. **The pure/leaf functions** (tier-1-testable):
   - `isAnswerConfirmationActive(chatOverride, projectOverride, globalEnabled)`
     — tri-state cascade, chat wins, `'OFF'` beats inherited `'ON'`.
     ⚠️ Part of this may already exist in the finalizer's ported gate — check
     `message_finalizer.rs` first and HOIST rather than duplicate (single
     source of truth; the finalizer should call the service's function).
   - `hasCheckableInputs(whisper, toolMessages)` — whisper `trim().length > 0`
     OR any tool message whose `toolName` is in `CONFIRMATION_READ_TOOLS =
     {search, read_conversation, doc_read_file, doc_grep, doc_read_heading,
     doc_read_frontmatter, doc_open_document}` (a static name set — no runtime
     tool introspection).
   - `findLatestCommonplaceWhisper(messages, participantId)` — backward scan
     for the most recent `systemSender: 'commonplaceBook'` message whose
     `targetParticipantIds` includes the participant, non-empty content.
   - `isUserDrivenTurn(chat, participantId)` — already ported in the
     finalizer gate; hoist/share.
   - `gatherConfirmationInputs(whisper, toolMessages)` — the reference block:
     `=== What the character recalled this turn (Commonplace Book) ===` +
     per-tool `=== Lookup result ===\n[Tool: name]\nArguments: {...}\nResult:
     content` sections, joined `\n\n`, `REFERENCE_CHAR_BUDGET = 24_000`
     truncation **oldest-first** with the
     `[…earlier reference material truncated…]\n` prefix. All string caps are
     JS UTF-16 semantics → use `jsstr`.
2. **`runAnswerConfirmation`** (the model-calling core, never throws):
   - The consistency check: `CONSISTENCY_SYSTEM_PROMPT` (byte-exact — put the
     body in a generated `prompt_text` submodule per the established
     precedent) + the `--- REFERENCE INFORMATION --- / --- REPLY TO CHECK ---`
     user message, via `executeCheapLLMTask` (the ported
     `services::cheap_llm_exec`), `taskType: 'answer-confirmation'`,
     `maxTokens: 512`, 25 s timeout. **Timeouts are host-timing** — port the
     timeout as an injected/no-op concern like the gate's 500 ms retry delay
     (no tokio timers in the core); the differential never exercises a real
     timeout, only the failure→`confirmed: null` mapping.
   - The verdict parser (`extractJson` — fence-strip + `{...}` extraction,
     strict, throws on parse failure; `discrepancies` defaults `''` when not
     a string). Check whether v4's `extractJson` here is the same
     `strip_code_fences` family already ported — reuse if identical, port
     fresh if not.
   - The **uncensored escalation** for the check: `isChatActiveDangerous`
     (ALREADY PORTED — `dangerous_content::chat_override`) +
     `resolveUncensoredCheapLLMSelection` (ALREADY PORTED in `cheap_llm`).
     Compose, don't re-port.
   - The re-affirmation pass on `consistent: false`: the `onAffirming`
     callback (→ the SSE status frame `{stage: 'affirming', message:
     'Requesting affirmation...'}` — add to `chat_events` if not present,
     byte-exact), the re-affirmation selection built from the CHARACTER'S OWN
     connection profile (NOT escalated — carry that why-comment), the
     byte-exact re-affirmation prompts, `taskType: 'answer-reaffirmation'`,
     `maxTokens: 4096`, 60 s timeout, and the four outcome mappings
     (revise+reply → confirmed:true/revised:true + notes + revisedContent;
     revise+empty-reply → confirmed:null; revise:false → confirmed:false;
     error → confirmed:null with notes).
3. **Close the finalizer seam**: replace `NoAnswerConfirmation` at the
   composition point with the real runner. The finalizer's post-outcome logic
   is ALREADY ported (rewrite → `confirmationOriginalContent` stash, tool
   anchor invalidation, reasoning collapse to a single offset-0 block,
   `confirmationChecked` semantics, the field-omission-when-undefined
   persistence) — verify against v4 rather than re-implementing; the seam
   outcome struct (`AnswerConfirmationOutcome`) already matches.

## Differential plan (`answer_confirmation_tier3_equivalence`)

Jest real-DB oracle driving v4's REAL `finalizeMessageResponse` (or
`runAnswerConfirmation` directly for the unit half + finalizer corpus cases
for the integration half — prefer the finalizer-driven form since the gates +
persistence interplay is the risk), per `[[jest-real-db-oracle]]` +
`[[tier3-completion-oracle]]` (completions pinned by oracle-recorded canned
keys — the recorded keys prove the prompt bytes, including the reference-block
assembly and the 24 K truncation). Mock ONLY the model boundary + API keys.

Corpus must bank:
- gate matrix: chat OFF beats project ON; project ON with global false; global
  true no overrides; feature fully off (no columns written — SQL NULLs);
- user-driven turn → `confirmed: null` + event, no LLM call (canned-miss
  proves it);
- no checkable inputs (no whisper, no in-scope tools) → silent skip;
- whisper-only reference; whisper + in-scope tool results (and an OUT-of-scope
  tool result excluded); the 24 K oldest-first truncation (build a >24 K
  reference — ASCII is fine but add one non-ASCII row to pin UTF-16);
- consistent verdict → confirmed:true;
- inconsistent → re-affirmation stands-by → confirmed:false + notes;
- inconsistent → revision → confirmed:true/revised:true, original stashed,
  anchors invalidated, reasoning collapsed, the `confirmationResult` event
  carrying `content`;
- inconsistent → revision with empty reply → confirmed:null;
- check parse-failure / LLM error → confirmed:null;
- dangerous chat → the check escalates to the uncensored cheap selection
  (recorded canned key proves the profile switch) while the re-affirmation
  stays on the character's profile.

Diff: per-op result objects + the ordered event trace + `chat_messages` +
`chats` dumps (sentinel-aware minted timestamps per the established forms).

Re-verify after: `message_finalizer_tier3_equivalence` (regenerated — the
seam is now real; pre-existing cases must be behavior-identical),
`orchestrator_tier3_equivalence` (the spine constructs the real runner — add
one spine-level case with the feature ON if cheap to do, else leave the
finalizer differential as the proof and keep the spine corpus feature-off).

## Watch-outs

- `executeCheapLLMTask`'s `logLLMCall` maps this task to the
  `ANSWER_CONFIRMATION` log type — logLLMCall is still the standing host-side
  deferral; don't port it here.
- The re-affirmation runs on the character's own model → in the canned-key
  scheme that's the PRIMARY profile's provider/model, not the cheap one. Two
  distinct canned namespaces in one corpus case — follow the memory-processor
  precedent for multiple completion keys per case.
- The `onAffirming` status frame ordering relative to `content`/`done` frames
  must match v4's enqueue order exactly — diff the ordered trace.
- v4's `withTimeout` wraps both calls; a timeout REJECTS the promise and maps
  to the error outcome. Keep the mapping; skip the timer.
