`systemKind` pair, v4's render path vs v5's, side by side — fix every
divergence found in v5's chat rendering components, and pin each fix with

module; `core-contract.ts` (lane A); anything outside `apps/web`.

## Tiered deliverables

### Tier 1 — must land

1. **The measurement** of the renderedHtml/patterns lead, first, with the
   verdict recorded either way. If real: route the announcement body
   through the same pattern/dialogue pass every other message gets, spec'd
   and mutation-proven.
2. **The audit table**: every systemSender × systemKind pair v4 can render,
   compared against v5 on — bar contents (dot, sender name, kind label,
   accent), collapsed chip vs group packing, expanded body pipeline,
   spacing/width/avatar-suppression, and identity/ARIA attributes. Each
   row: MATCHES / DIVERGES (how) / N-A-in-v5 (why). The table is the lane
   record's centerpiece — the complaint is about consistency ACROSS kinds,
   so no sampling.
3. **Fixes for every DIVERGES row** that is SPA-side, each pinned by a
   component spec (mutation-proven where the assertion is new).
4. **E2e beats** (new spec file) for at least the two worst fixed pairs,
   asserting the rendered DOM shape live.

### Tier 2 — should land

5. A side-by-side screenshot record (v4 dev server vs v5 e2e instance) for
   the audit table's DIVERGES rows — evidence for the lane record, and the
   fastest way to spot spacing-class drift the DOM diff hides.

### Tier 3 — explicit loud deferrals

- SERVER-side divergences (missing wire fields, enrichment gaps): record
  with evidence, do not fix — they seed a follow-up order.
- The broader message-rendering dialect gaps already on the books (the
  composer backslash-escape seam, the block-separation gap) stay where
  they are — this lane is announcements, not the markdown dialect.

## The differential requirement, restated

This is an SPA parity lane — the equivalence discipline is the exhaustive
audit table adjudicated against v4's REAL components (read the v4 source
per pair; screenshot live where in doubt), specs that pin each fixed
behavior, and mutation proof on new assertions (the D24 rule). Where the
markdown-parity fixture corpus (`markdown-fixtures.json`) already covers a
render question, extend IT rather than inventing a parallel proof — but
only if the extension is announcement-specific; the corpus regen recipe
runs v4's real renderer (P4.d9's recipe).
