## The findings, verified (surveyed FRESH 2026-08-13)

### 1. The open-before-lock sequence (the P4.D68 escalation, scope WIDENED)

Current ordering, verified against main:

| step | site |
|---|---|
| `CoreEngine::boot` | `crates/quilltap-core/src/api/engine.rs:607` |
| `open_ready(...)` from boot | `engine.rs:630` |
| **`Db::open` — writable, UNLOCKED** | `engine.rs:5436` (fn `open_ready` at :5416) |
| `assembler.assemble(...)` | `engine.rs:5439` |
| `Writer::open_writable` ×3 | `db/runtime.rs:135/:137/:141` (fn :129) |
| `PRAGMA journal_mode = TRUNCATE` | `db/mod.rs:204` (fn `open_writable` :194) |
| **`lock::acquire_instance_lock`** | `crates/quilltap-host/src/host.rs:413` (in `HostAssembler::assemble` :400; release :395; heartbeat :628-636) |

v4 orders it the other way (`backend.ts` `connect()` locks BEFORE
`new Database`). In the contended case (bug 58's Ignite scenario) v5
performs three unlocked `journal_mode = TRUNCATE` header writes against a
database another process believes it holds exclusively, then refuses at
assemble — the exact class v4's bug-58 fix closes, and the CLAUDE.md
open-sequence rule itself warns journal-mode writes race the cipher
context. **The survey widened the escalation's stated scope:**

- **Unlock has the same shape** — `engine.rs:5062 fn unlock` →
  `open_ready` :5081. Every unlock repeats the unlocked open sequence.
- **Setup is WORSE than "shares the shape"** —
  `provision_fresh_instance` (`services/provisioning/mod.rs:128`) issues
  three more `Writer::open_writable` calls (:134/:142/:149) plus full DDL
  replay and seed ROW writes (:135-137/:143-144/:150), all before
  `open_ready` at `engine.rs:5152` and therefore all before any lock.
  The P4.D68 header's "all ROW writes are behind the lock" holds for
  boot/unlock but NOT for first-run setup.

The lock machinery itself is sound and ported (`quilltap-host/src/lock.rs`
— `acquire_instance_lock` :383, stale-reap + `Conflict` :409-414,
re-entrant-per-process semantics, heartbeat, `on_lock_lost`). The defect
is purely the ordering.

### 2. Setup can eat the display-once pepper (v4 parity gap)

At `engine.rs:5165`, if `open_ready` fails AFTER `save_dbkey` (:5142) and
`provision_fresh_instance` (:5146) both succeeded, v5 returns a bare
`ErrorKind::Internal` — the pepper is never returned. `SetupResultDto`
(`api/types.rs:3459-3464`) has only `pepper` + `message`. v4's bug-64 fix
is explicit that the response must still carry the key ("it is displayed
exactly once, so it is never withheld behind an error") with a
`requiresRestart` notice beside it; the SPA wizard
(`apps/web/src/app/screens/setup/setup-wizard.ts:200-206`) just renders
an error today.

### 3. A failed Setup retry is destructive (v5-specific hazard)

After a late Setup failure the state stays `Locked{NeedsSetup}` but
`quilltap.dbkey` and all three `.db` files exist on disk. A second
`Setup` mints a NEW pepper and overwrites `.dbkey` (`save_dbkey` →
`write_dbkey_file`, no existence check); `provision_fresh_instance`'s doc
says the files "MUST NOT already exist" but nothing checks, and the DDL
has **0 of 79 statements using `IF NOT EXISTS`**. The new pepper cannot
open the old files → the instance is bricked with the original pepper
overwritten.

### 4. `.dbkey` unknown-field drop (bug-65 interop rider)

v4's fixed version guard writes `minServerVersion` into the ONE
`quilltap.dbkey` via read-modify-write (top-level string field appended,
all other fields preserved, 2-space pretty, mode 0600). v5's parser
tolerates it (`dbkey.rs:47-61`, no `deny_unknown_fields`) — but
`DbKeyFileOut` (:239-255) is a fixed 10-field struct and both
`save_dbkey` (:266) and `change_passphrase` (:363, write :394-395) do a
FULL REPLACE. A v4 instance that had `minServerVersion` set loses it the
first time v5 changes the passphrase — and an older v4 binary would then
boot without the shell-level floor.

### 5. Dispositions to record (no code)

- **Bug 64 core = NO-PORT** with the survey's evidence (no cached
  handles; `Db` is `Arc<DbInner>`, writer thread exits on last drop; the
  named non-port note at `engine.rs:5119-5122` — v5 has no plaintext
  window, so there is nothing to convert; all three partitions encrypted
  from byte zero).
- **Bug 65 = NO-PORT** (no version guard, no migration runner), plus:
  v5 reads `instance_settings.highest_app_version` (Almanack premise
  :129-141; export blocklist `db/instance_settings.rs:638-645`) but
  never writes it — a v5-provisioned instance renders the premise null
  and has no downgrade tripwire. Record as a deliberate no-write with
  the reasoning (writing v5's own version string into v4's semver guard
  would be meaningless at best and lock-out-inducing at worst); flag it
  for a future human ruling if v4-interop instances become common.

## Deliverables

### Tier 1 — must land

1. **Lock before ANY partition open, on all three entrances.** Move
   instance-lock acquisition ahead of `Db::open` for boot and unlock, and
   ahead of `provision_fresh_instance` for setup. Design constraint, not
   prescription: the lock lives host-side and the engine is
   transport-agnostic, so this is a host-seam reshape (e.g. a pre-open
   hook on the assembler trait the engine calls before touching disk, or
   lifting acquisition into the engine's open path via a seam the host
   injects). Whatever the shape: acquisition stays idempotent/re-entrant
   per process (setup → open_ready must not deadlock on its own lock),
   release stays exactly at shutdown (`host.rs:395`), heartbeat/
   `on_lock_lost` semantics unchanged, and a conflict surfaces as the
   same refusal class as today.
2. **The contended-boot proof.** A test that plants a live contender lock
   and asserts the boot/unlock/setup refusal arrives with **zero bytes
   changed on the `.db` files** (hash or mtime+size before/after — the
   thing the old ordering could not guarantee). Mutation-check: with the
   ordering reverted, the test must fail.
3. **Setup pepper preservation.** A late `open_ready` failure still
   returns the pepper with a restart/attention notice —
   `SetupResultDto` gains an additive `requiresRestart: bool` (mirroring
   v4's contract), the SPA wizard renders the pepper + a warning instead
   of a bare error (the small `apps/web` rider; setup-wizard.ts is
   untouched by every sibling).
4. **The destructive-retry guard.** `Setup` against a data dir that
   already carries `quilltap.dbkey` (or any of the three partitions)
   refuses loudly, naming the file, instead of minting a new pepper over
   it. This is deliberate v5 hardening (v4's conversion-shaped setup has
   no analog arm) — document it as such in the lane record.

### Tier 2 — should land

5. **Unknown-field preservation through `change_passphrase`.** The
   re-encrypt path becomes read-modify-write at the JSON level: fields
   v5 does not model (e.g. `minServerVersion`) survive a passphrase
   change byte-meaningfully (fresh `save_dbkey` on a new instance has
   nothing to preserve and stays as-is). Extend the dbkey cross-compat
   differential (both directions exist since P4.D68 — the recipe is in
   its order/lane record): plant `minServerVersion` per v4's exact write
   format on the v4 side, drive v5's real `change_passphrase`, assert
   the field survives and v4's real loader still opens the result.
6. The disposition records (§5 above) in the status log, plus the
   P4.D68 order-header escalation note updated to point here as
   discharged (append-style; do not rewrite its history).
