**`orchestrator.service.ts` anatomy:**

- `handleBrahmaConsoleMessage(repos, chatId, userId, options)` — L114, the
  entry point. Saves the user message (L131-139), resolves the profile
  (L142, via the already-ported resolver), runs `processBrahmaResponse`,
  then `triggerAsyncTasks` — **context-summary/auto-title ONLY, never
  memory extraction**.
- `processBrahmaResponse` (L181-583) — the multi-turn agent loop:
  `while (agentTurnCount <= maxAgentTurns)`, `maxAgentTurns = 25`
  (L261/325). Per turn:
  - Tools via `buildTools(...)` with the Brahma flag vector (L202-221):
    agent mode ON, help tools OFF, doc read/write ON, wardrobe/Carina/
    workspace OFF, `excludeMemorySearch=true`, `sqlAccess=true` (read-only
    `run_sql`).
  - Native-vs-text-block tool-mode resolution (L225-258); `simple-json`
    downgraded to `text-block`.
  - System prompt: `buildBrahmaSystemPrompt({ profile, toolInstructions,
    includeSqlAccess: true })` (L269).
  - History threaded through `buildConversationMessages` +
    `buildAssistantToolCallMessage`/`buildToolResultMessages` (the same
    tool-threading the Salon spine uses — v5 has these ported).
  - Per-turn `streamMessage(...)` with reasoning accumulation
    (`priorReasoning`/`runReasoning`, display-only), native/text-block
    tool-call detection, `submit_final_response` handling, the stuck-loop
    guards (`MAX_DUPLICATE_TOOL_CALLS = 2`, `staleIterations`,
