## The v4 architecture (survey 2026-07-10 — copy it, don't invent)

v4 **already virtualizes** and this order is a port of that design, not a
performance project:

- **`@tanstack/react-virtual`** over the flat render-item list —
  `app/salon/[id]/SalonView.tsx:501-507`: `estimateSize: () => 150`,
  `overscan: 5`, `getItemKey` = render-item id, dynamic measurement via
  `measureElement`. The windowed loop + absolute-positioned rows +
  total-size spacer: `components/VirtualizedMessageList.tsx:188-366`.
- **No pagination / no "load earlier"** — the GET returns ALL messages and
  the whole history is in the virtualized list from first render. Do not
  add paging.
- Virtualization indexes **render items**, not raw messages (packed
  announcement groups collapse into one virtual row) — v5's
  `chat-view-model.ts` already builds an equivalent render-item array;
  virtualize over THAT.
- **Scroll behavior** — `hooks/useAutoScroll.ts`, port the semantics:
  `SCROLL_THRESHOLD = 100` px (distance-from-bottom = "at bottom"),
  `SETTLE_DELAY_MS = 400` (post-load settle before the initial scroll),
  `SCROLL_CHECK_DEBOUNCE_MS = 100`. Initial load → one-time instant
  multi-strategy scroll-to-bottom (`useAutoScroll.ts:125-163`:
  scrollToIndex(last, align end) → 50ms scrollTop correction → 150ms
  endRef scrollIntoView → 300ms final correction; NEVER smooth-behavior
  with dynamic sizes). A debounced scroll listener maintains
  stick-to-bottom intent (scrolled up past 100px → auto-scroll
  suppressed). Streaming does NOT scroll per chunk — only on completion,
  and only if the `autoScrollOnResponseComplete` chat setting is true
  (default FALSE) AND the user is stuck to bottom. A user SEND always
  scrolls and re-enables. A floating **jump-to-bottom button** shows when
  not at bottom (`VirtualizedMessageList.tsx:394-404`).
- **v4's row-cost containment** is server-side `renderedHtml` +
  memoized rows. **v5's locked divergence stands: markdown renders
  client-side** — under windowing only ~viewport+overscan rows pay the
  cost, which is the fix. Do NOT add `renderedHtml` to the server GET.

## Deliverables

### 1. Virtualize the message list

Adopt **`@tanstack/angular-virtual`** (the official Angular adapter of
the exact library v4 uses; pin the version in package.json) in
`chat/message-list.ts` over the existing render-item array: estimate 150,
overscan 5, stable item keys, dynamic measurement, total-size spacer +
translated absolute rows. Preserve the #3a host classes / scroll-chain
fix — the scroll container must remain the bounded-height element the
virtualizer measures against. If the adapter fights Angular zoneless
signals, fall back to using `@tanstack/virtual-core` directly (it's
framework-agnostic; the React package is a thin binding) — note which
path you took.

### 2. Memoize row rendering

The markdown render in `message-content.ts` must be cached per
`(content, renderingPatterns, dialogueDetection)` so re-measure/re-mount
cycles under virtualization don't re-render markdown (v4 memoizes at
`LazyMessageContent`/`MessageRow`; the Angular equivalent is a keyed
cache + OnPush + track-by). v4 REMOVED lazy/deferred preview-then-swap
rendering because height changes mid-scroll janked the virtualizer
(`LazyMessageContent.tsx:9-34`) — render rows eagerly-when-visible,
never placeholder-then-swap.

### 3. Port the scroll controller

A `chat/auto-scroll.ts` (or equivalent) implementing the
`useAutoScroll.ts` semantics above: initial settle + one-time scroll,
stick-to-bottom tracking, completion-gated auto-scroll (read
`autoScrollOnResponseComplete` from chatSettings), scroll-on-user-send,
and the jump-to-bottom button. Unit-test the state machine (the settle
gate, the 100px threshold, the suppress/re-enable transitions) with a
fake scroll element.

### 4. The long-chat fixture + e2e beat

Build a SEPARATE committed fixture (`crates/quilltap-web/tests/fixtures/
salon-long-*.db` via a NEW builder
`harness/oracle/fixtures/build-long-chat-fixture.ts` — do NOT modify
`build-salon-fixture.ts` or the existing salon fixtures; the salon
differentials' oracles are pinned to them). Content: one chat with
~300 messages of realistic mixed shape (markdown-heavy assistant
messages, user messages, a few staff announcements + whispers so
render-item packing is exercised), built through v4's REAL
`repos.chats.addMessages`. New Playwright spec `e2e/salon-scroll.spec.ts`
against this fixture: open the long chat → it renders in bounded time
(assert an upper bound well under the old 10s — e.g. interactive < 3s)
→ lands AT THE BOTTOM → only a window of rows is in the DOM (assert row
count ≪ 300) → scroll up → jump-button appears → click → back at bottom
→ send disabled-free (composer visible). Reuse the e2e recipes from
`[[p4-6b-salon-spa]]` (fixture user-id rewrite pre-launch, mock LLM on
the fixed port, unlock-state tolerance).

### 5. Regression guard

The existing salon Playwright specs and all component tests stay green —
the virtualized list must be behavior-identical for small chats
(streaming append, swipe collapse, announcement groups, skip banner,
edit/delete flows). Update component tests that assumed all rows in the
DOM to query through the window (or force a tall test viewport).
