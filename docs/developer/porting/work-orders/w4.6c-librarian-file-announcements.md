Librarian *save* announcement (`change: {created,body} | {edited,diff}`) is
wired through the five mutating text/markdown handlers, but v4 also announces

## The threading design (decided)

Generalize G6's `DocEditToolResult.pending_librarian_announcement` from
`Option<LibrarianWriteAnnouncement>` to
`Option<PendingLibrarianAnnouncement>` — an enum with one variant per
announcement kind (`Write` [the existing G6 payload], `Move`, `Copy`,
`Delete`, `FolderCreated`, `FolderDeleted`, `Open`, `BlobWrite`), each
carrying exactly the ported writer's argument struct. Keep the field
`#[serde(skip)]` (the ~23-handler serialized result shape must stay
byte-identical) and keep the post in the executor spine (`run_doc_edit`
`take`s it out of the `Db::write` closure return and posts AFTER the closure
— the G6/wardrobe-drain precedent, best-effort, a failed post never fails the
tool). The direct-drive differentials post via the synchronous
`post_*_conn`-style path the G6 `doc_text` oracle established — add
`_conn` variants for the writers that lack one.

## What to port

1. Each database-store handler branch builds its announcement inside the
   closure with v4's exact argument construction: `path.basename` display
   titles (the ported `path_dirname` sibling — add `path_basename` if
   missing), `uriForResolvedPath` old/new URIs (ported), `resolveActorOrigin`
   (ported, G6) — EXCEPT `doc_open_document`'s bespoke findById origin
   (port as written), `isFolder` flags, and `hiddenFromCharacters` (the
   ported `contentHiddenFromCharacters`/`documentHiddenFromCharacters`
   gates — check which one each site uses in v4 and match).
2. The fs-mount branch sites stay behind the existing `FsSeam` (out of
   scope — the branch never executes for database stores; do NOT thread
   announcements for unreachable branches).
3. `syncChatDocumentsAfterFileMove` stays the existing corpus-verified no-op
   seam (its real body is the unported `chatDocuments.renameFilePathInStore`
   — Phase-4-adjacent, second consumer noted in the 2026-07-05 drift check).

## Watch-outs

- v4 awaits each post INSIDE the handler (before the return) — the v5
  executor posts after the closure. Row order in `chat_messages` can differ
  from v4 only if a handler posts more than one announcement or interleaves
  with another write; survey says one post per op, and the dump sort is by
  `content`, so this is safe — but verify no handler has a two-post path
  (folder delete with descendants?) before relying on it.
- `doc_open_document`'s announcement fires on BOTH the open-existing and the
  create-new paths (`isNew` differs); the create-new fs path is a tracked
  FsSeam — only the database-store open is in scope.
- The delete announcements for files vs blobs share one writer with
  different args — don't collapse the two call sites' argument construction.
