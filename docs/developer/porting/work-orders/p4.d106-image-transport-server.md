### Bug 91 — images silently dropped for four providers

A profile's `supportsImageUpload` tick states the *model* reads pictures; it
says nothing about whether the *plugin* can send them. v4 asked only the
first question, so ticking the box on NanoGPT/DeepSeek/OAC/Ollama suppressed
the describe-fallback AND handed bytes to a plugin that discarded them.

1. **NEW `lib/llm/image-transport.ts`** (50 lines, server-only). One export:
   `providerCanTransportImages(provider): boolean` — three-tier resolution:
   - registry initialized AND `getAttachmentSupport(provider.toUpperCase())`
     answers → `support.supportsAttachments === true && (supportedMimeTypes
     ?? []).some(t => t.startsWith('image/'))`;
   - else `staticProviderCanTransportImages(provider)` (the client-safe map);
   - the static fn returns **`true` for an unknown provider** ("so a
     third-party vision plugin isn't crippled by our ignorance of it").
2. **`lib/llm/attachment-support.ts` (+43)**: the static
   `PROVIDER_ATTACHMENT_CAPABILITIES` gains/updates NANOGPT (`:102`),
   DEEPSEEK (`:109`), Z_AI (`:116`) — the §C1 values; and the new export
   (`:164`) `staticProviderCanTransportImages` — note it keys off `types`
   (`capabilities.types.some(t => t.startsWith('image/'))`), **not**
   `supportsAttachments`, after an `isKnownProvider` guard that returns
   `true` for unknown.
3. **`lib/chat/file-attachment-fallback.ts` (+55)**, three edits, all
   guarded by the new predicate:
   - `getImageDescriptionProfile` (`:62-63`): the vision filter becomes
     `profileSupportsMimeType(p, 'image/jpeg') &&
     providerCanTransportImages(p.provider)`;
   - `needsFallbackProcessing` (`:115`): after the mime-support check, a
     second arm — `mimeType.startsWith('image/') &&
     !providerCanTransportImages(profile.provider)` → `true`, with a
     `logger.info('[Attachment] Profile claims image support but its plugin
     cannot transport images; routing to describe-fallback', {profileId,
     provider, modelName})`. The `image/` prefix gate is load-bearing —
     non-image types unaffected (v4 tests assert it);
   - `describeImageWithProfile` (`:253`): the **describer guard** — a
     configured describer whose plugin cannot transport returns
     `type: 'unsupported'` with the error verbatim:
     `Image description profile (${provider} ${modelName}) cannot send
     images — the ${provider} plugin does not forward image attachments.
     Pick a describer on a provider that does (OpenAI, Anthropic, Google,
     Grok, OpenRouter, Z.AI).` — an Ollama describer would have described a
     picture it never received, **which v4's test suite had encoded as
     expected behavior** (the pre-existing uncensored-fallback test's
     fixture changed from OLLAMA/llava-uncensored to
     OPENROUTER/uncensored-vision-model — mirror that fixture correction).

### Bug 93 — provider refusals reported as transient faults

1. **NEW `lib/llm/moderation-finish-reason.ts`** (67 lines). The literal set
   (verbatim, **no substring guessing**): `sensitive`, `content_filter`,
   `content-filter`, `refusal`, `safety`, `prohibited_content`, `blocklist`,
   `spii`, `image_safety`, `recitation`. (Attribution: Z.AI `sensitive`;
   OpenAI CC + Azure `content_filter`; Responses API `refusal`; the Google
   five; `recitation` is Google copyright — "the same shape of dead end";
   the hyphenated `content-filter` is a tenth literal the docblock doesn't
   call out.) Exports: `isModerationFinishReason(reason)` —
   `reason.trim().toLowerCase()` set-membership, false for null/empty — and
   `describeModerationRefusal(reason, provider, modelName): string | null`,
   template verbatim:
   `${provider} ${modelName} refused this turn on content grounds — it
   reported \`finish_reason: ${reason}\` and returned nothing. This is the
   provider's own moderation layer, not a Quilltap error and not a transient
   fault: resending the same content will be refused again. Route the chat
   to an uncensored provider (Concierge settings), or change what is being
   asked for.`
   ⚠ v4's module docblock mis-numbers itself "(bug 94)" — port the CODE and
   note the discrepancy in a comment; do not propagate the wrong number into
   v5 prose.
2. **`provider-failover.service.ts` (+20)**: `getEmptyResponseReason`
   (`:217`) gains `finishReason?/provider?/modelName?` and a **first**
   branch (`:237`) ahead of every existing one: if `describeModerationRefusal`
   answers, return it — appending
   ` An uncensored provider was tried as well and also returned empty.`
   when `uncensoredRetryAttempted`. The five pre-existing sentences
   (v5 `provider_failover.rs:294-324`) are untouched; the "known issue"
   default merely stops being reached for a named refusal.
3. **`orchestrator.service.ts` (+12)**: the empty-response `else` branch
   (`:1700`) computes `extractFinishReason(streamingState.rawResponse)`
   (v5 twin: `crates/quilltap-core/src/finish_reason.rs:23`, pinned probe
   order, no changes needed there), passes reason + provider + modelName
   into `getEmptyResponseReason`, and adds `finishReason` +
   `moderationRefusal` to the existing `logger.warn` payload.

### Bug 95 — attachments anchored to the wrong message

Staff whispers format as role=user, so "the last user-role message" stopped
meaning the human's turn: on a regenerate the image landed on a
connection-profile-change bubble; after a tool call nothing matched and
attachments dropped without a log line.

1. **`lib/chat/context/message-selector.ts` (+5)**: `selectRecentMessages`
   `unshift` gains `id: msg.id` (the source `chat_messages` row).
2. **`lib/chat/context-manager.ts` (+11)**: `ContextMessage.metadata` gains
   `isUserTurn?: boolean`; history pushes gain
   `metadata: msg.id ? { messageId: msg.id } : undefined`; the
   `newUserMessage` push gains `metadata: { isUserTurn: true }`.
3. **`context-builder.service.ts` (+75 — this file's entire delta is bug 95,
   NOT bug 91)**: new export `selectAttachmentAnchorIndex(contextMessages,
   userTurnMessageIds): number` — three reverse scans in order: (1) last
   `metadata?.isUserTurn` (role NOT checked in this tier); (2) last
   `role === 'user' && id && userTurnMessageIds.has(id)`; (3) last
   `role === 'user'` (the old rule as a floor); else `-1`. Call sites in
   `buildMessageContext`:
   - `:749` builds the id set from the **pre-normalization** array:
     `type === 'message' && role === 'USER' && !systemSender && id` — the
     `!systemSender` clause is what excludes staff whispers;
   - `:943` selects against `builtContext.messages` (v4's comment: the
     provider format map is pure, indices stay parallel);
   - `:948` `logger.warn('Image attachments could not be anchored — no
     user-role message in context; images will not reach the model',
     {attachmentCount, contextMessageCount})` when attachments exist and
     the index is `-1`;
   - `:957` `isLastUserMessage` is REPLACED by `isAnchor = idx ===
     attachmentAnchorIndex`, driving **both** the `lanternImagePrefix`
     prepend and the attachment splice.
4. **NEW `attachment-anchor.test.ts`** (75 lines, six cases) — the tier-1
   corpus source; case 2 is the observed failing shape (user row, then
   Librarian upload announcement, Host off-scene intro,
   connection-profile-change bubble, all role user → anchor index 1), case
   6 pins that a user-turn id on an assistant-role message falls to the
   floor.
