## Mandate

Restore v4's best-effort conversation-chaining fallback in
`WireStreamingProvider::stream_message`: when the prepared request
carried `previous_response_id` and `execute_stream` fails **pre-stream**,
rebuild the request with `previous_response_id = None` (the full-input
body) and retry `execute_stream` ONCE; on the retry's failure,
`single_error` exactly as today. This makes v5 MATCH the oracle — v4
has always done this (`plugins/dist/qtap-plugin-openai/provider.ts:463-533`,
log line *"conversation chaining failed, falling back to full input"*) —
so it is a dropped-behavior restoration, not a divergence. Without it,
every OpenAI multi-turn chat wedges the moment OpenAI can't find the
prior `resp_…` id (which happens often: both apps send `store: false`,
and store-false responses are not reliably chainable); a failed turn
writes no new id, so `find_previous_response_id` keeps returning the
same dead one forever.

Scope guards:
- **Pre-stream failures only.** Mid-stream errors (the pump thread,
  `streaming_provider.rs:339-391`) are a different catch in v4 too — do
  not touch them.
- **Gate on `previous_response_id.is_some()`** — a plain pre-stream
  failure with no id must keep today's single-error behavior
  byte-for-byte (the existing test
  `pre_stream_failure_is_a_single_error` pins that).
- The retry is a second real API call **on failure only** — v4 does the
  same. 💸-neutral in the happy path.
- Do NOT touch: `responses_api.rs` (no change is needed — see survey),
  `orchestrator.rs`, `primary_stream.rs`, `completion_provider.rs`, any
  `api/**`, `quilltap-host/**`, `quilltap-web/**`, `apps/web/**`.

## Survey-verified starting points (2026-08-06, fresh on main)

### v5 — the exact seam

- **The Err arm:** `crates/quilltap-core/src/model/streaming_provider.rs:330`
  — `Err(e) => return single_error(e.message)` after
  `self.transport.execute_stream(&request, &self.policy).await` (:328).
- **`prepare` is called synchronously OUTSIDE the async block** (:321).
  A retry needs a second prepared request; the clean shape is to compute
  the fallback preparation up front when
  `params.previous_response_id.is_some()` (clone `params`, set the id to
  `None`, `prepare` again) before entering the async block — the
  returned future borrows `self`/args, so both preparations can also be
  done inside; pick whichever keeps the borrows simple. `prepare`
  (:239-299) is a pure function of `(provider, base_url, params)`:
  url/headers/auth/decoder do not depend on the id.
- **`StreamParams.previous_response_id: Option<String>`** —
  `model/stream.rs:370` (default `None` at :561). Reaches the wire via
  `request_input_from_stream_params` (`streaming_provider.rs:159-186`,
  the clone at :182) → `RequestInput.previous_response_id`
  (`request_builder/mod.rs:94`).
- **The body split is already correct** —
  `request_builder/responses_api.rs:440-461` (`build_openai_body`):
  with the id, `input` becomes `extract_last_user_message` + the id
  (:449-453); without it, the `else` arm (:456-460) keeps the full
  `item_input` set in `openai_base` (:353-358, incl. `store: false` at
  :358) and emits no `previous_response_id` key. **Rebuilding with
  `None` is byte-identical to a never-chained request** — verified by
  reading; pin it with the wire test below. Grok's builder (:467) never
  reads the id, so the fallback is inert for it — correctly OPENAI-only.
- **Blast radius is exactly the primary-stream turn.** The ONLY
  production site that ever sets the id non-`None` is
  `services/orchestrator.rs:2089` (fed by `find_previous_response_id`,
  `services/primary_stream.rs:1227-1245`, at `orchestrator.rs:2048-2049`).
  Every other `previous_response_id: None` in the tree is a hard-coded
  literal (recovery :301, native_tool_loop :696, text_tool_loop :760,
  provider_failover :449, carina_query :1065, initial_greeting :177,
  brahma ×2). The non-streaming path hard-codes `None`
  (`completion_provider.rs:78-95`, :91) — **no fallback needed there**;
  record that in the lane record.
- **The wedge mechanic (why this matters):** on a failed turn
  `run_primary_stream` preserves a partial (`primary_stream.rs:1211`)
  and errs (:1213) — no new assistant row with a `rawResponse.id` is
  written, so the next turn's newest-first scan (:1231-1243) finds the
  same stale `resp_…`.
- The provider manifest doc **already promises this behavior**:
  `provider_manifest/mod.rs:82` — "OpenAI: `previous_response_id`
  chaining + fallback-to-full-input." This lane makes the comment true.

### v4 — the oracle behavior

`plugins/dist/qtap-plugin-openai/provider.ts:463-533` — BOTH
`streamMessage` and `sendMessage` wrap the chained `responses.create`
in a `try/catch`; on ANY error they log and re-issue with the FULL
conversation and no `previous_response_id`. v4's catch is around the
whole create (its non-streaming path CAN chain; v5's cannot by
construction — a shape difference to note, not to "fix").

### The test seams

- **Fake transport:** `streaming_provider.rs` `mod tests` (:393).
  `FakeStreamTransport` (:401-405) is **single-shot** — `fail_before_stream`
  fails EVERY call and `seen` holds only the LAST request. Extend it (or
  add a sibling) to script per-call outcomes (fail first, succeed
  second) and record `Vec<TransportRequest>`. Helpers: `params(model)`
  :455-469 (sets the id `None` at :466 — you need a variant), `drain`
  :471, `keys()` :481 (has `"OPENAI"`). Model the new test on
  `pre_stream_failure_is_a_single_error` (:773-793) and the
  `seen`-readback idiom of `auth_injection_per_manifest_scheme` (:551).
- **The byte pin:**
  `crates/quilltap-harness/tests/tool_wire_call_site.rs` drives the
  REAL `WireStreamingProvider` with only the transport faked
  (`RecordingStreamTransport` :73-101, records `Vec<TransportRequest>`)
  and asserts on request BYTES — the natural home for "the retry body
  carries no `previous_response_id` and its `input` is the full item
  array." Runs in plain `cargo test`, no oracle env.
- **Tier-3:**
  `crates/quilltap-harness/tests/primary_stream_tier3_equivalence.rs` —
  already imports `find_previous_response_id` (:66) and asserts it
  (:533). Its `QueuedStreamingProvider` seam (:211-299) queues chunk
  sequences per key and can express fail-then-succeed (an `{error}` row
  maps to `Err(StreamError)` at :246-249). ⚠ Its
  `canned_stream_key(provider, model, temperature, messages)`
  (:234, :274-279) does NOT include `previous_response_id` — convenient
  (both attempts hit the same key, so two queued sequences model the
  retry), but it means the differential cannot itself prove the id was
  dropped. **The byte proof lives in the unit/wire tests; the tier-3
  proves turn-level outcome parity** (v4 recovers the turn, v5 recovers
  the turn, same persisted rows). Inject the same fail-then-succeed
  both sides — the oracle side mocks the OpenAI SDK create to throw
  once then succeed, per the existing recipe in that family's header.

## Tiered deliverables

**Tier 1 (must land):**

1. The fallback in `stream_message`: pre-stream `execute_stream` Err +
   `params.previous_response_id.is_some()` → retry once with the
   `None`-id preparation; retry failure → `single_error` with the
   RETRY's error message (v4 surfaces the second failure). Emit a
   `tracing::warn!` at the fallback site mirroring v4's
   "conversation chaining failed, falling back to full input" (log
   output is outside the differential contract per the P4.18 ruling,
   but the sentence should match v4's for operator grepability).
2. Unit tests on the (extended) fake transport: (a) fail-then-succeed
   with an id → two transport calls, second body has no
   `previous_response_id` and carries the full input, stream proceeds;
   (b) fail-then-fail with an id → single error, exactly two calls;
   (c) fail with NO id → single error, exactly ONE call (no retry);
   (d) the existing `pre_stream_failure_is_a_single_error` stays green
   unmodified.
3. The wire-byte pin in `tool_wire_call_site.rs`: the retry request's
   recorded bytes diff clean against a from-scratch non-chained build
   of the same params.

   the pin, zero SKIP.
