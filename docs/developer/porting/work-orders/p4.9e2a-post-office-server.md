### `writer.ts` — the shape to port (:21-54)

```ts
export type StaffSender =
  | 'lantern' | 'aurora' | 'librarian' | 'concierge' | 'prospero'
  | 'host' | 'commonplaceBook' | 'ariel' | 'suparna' | 'pascal';

export type AnnouncerSender =
  | { kind: 'staff';     staffId: StaffSender }
  | { kind: 'character'; characterId: string }
  | { kind: 'custom';    displayName: string };
```

`postAdhocAnnouncement` returns `MessageEvent | null` and **never throws** — v4's
own header says so explicitly (`:45-51`: "Errors never propagate — this matches
the established Staff-announcer convention (Host, Librarian, Lantern) and avoids
tearing the composer UX over a transient repo failure"). It returns `null` on
empty-after-trim content or on failure, and the route turns `null` into a
`badRequest('Failed to post announcement (empty content or unknown chat).')`.
**Carry that why-comment into the Rust.** v5's post-office writers (W4.6b) already
establish the persisted-announcement idiom — reuse it rather than inventing one.

### The three server-side authorization arms (port them exactly)

1. **`send-mail`** re-verifies `fromCharacterId` against the participant list
   (`send-mail.ts:32-40`) — "never trust the client to send as an LLM character or
   a stranger". Rejection is `badRequest("You can only post a letter as a
   character you are playing in this scene.")`.
2. **`mailbox`** authorizes the same way but rejects with **`forbidden`**, not
   `badRequest` (`mailbox.ts:34-36`): `"You may only inspect the mailbox of a
   character you are playing in this scene."` The status difference is real —
   do not unify them.
3. **`announcement`** verifies only the `character` branch's referenced character
   exists (`announcement.ts:26-31`) → `notFound('Character')`; `staff` and
   `custom` senders are unchecked.

### Two v4 read quirks a faithful port must reproduce

- `send-mail` and `mailbox` read the sender/recipient with
  **`findByIdRaw`**, not `findById` — `send-mail.ts:42-44` explains it: "Use raw
  rows (existence-only) so a hollow-but-present vault doesn't 503 here; delivery
  re-provisions the vault idempotently anyway." `announcement.ts` and
  `announcement-preview.ts` use the overlay `findById`. Match each call site.
- `mailbox` calls `ensureCharacterVault(character)` before listing
  (`mailbox.ts:44`), so **reading a mailbox can provision a vault**. That is a
  write on a GET path; it is v4's behavior and the differential must diff the
  resulting rows, not normalize them away.

## Shared contract (BINDING)

### §1 — the wire surface (written verbatim and identically in P4.9E2A and P4.9E2B)

Four new `Request` variants. Field names, casing and nesting are **frozen**; only
this lane may add them, and neither lane may deviate.

```rust
/// v4 `POST /api/v1/chats/[id]?action=announcement` — post an ad-hoc
/// announcement bubble. 201 on success.
#[serde(rename_all = "camelCase")]
ChatAnnouncementPost {
    chat_id: String,
    content_markdown: String,
    sender: AnnouncerSenderWire,
},

/// v4 `POST /api/v1/chats/[id]?action=announcement-preview` — generate an
/// in-character rewrite. Persists nothing.
#[serde(rename_all = "camelCase")]
ChatAnnouncementPreview {
    chat_id: String,
    seed_markdown: String,
    character_id: String,
    connection_profile_id: String,
    system_prompt_id: Option<String>,
},

/// v4 `POST /api/v1/chats/[id]?action=send-mail` — post a letter as one of the
/// operator's player-characters. 201 on success.
#[serde(rename_all = "camelCase")]
ChatSendMail {
    chat_id: String,
    from_character_id: String,
    to_character_id: String,
    body_markdown: String,
    in_reply_to_path: Option<String>,
},

/// v4 `GET /api/v1/chats/[id]?action=mailbox&characterId=…` — list a
/// player-character's `Mail/` letters, for the Compose Mail "In reply to"
/// dropdown. NOTE: v4 provisions the vault on this read path.
#[serde(rename_all = "camelCase")]
ChatMailboxList {
    chat_id: String,
    character_id: String,
},
```

The sender union, tagged on `kind`, mirroring v4's discriminated union:

```rust
#[serde(tag = "kind", rename_all = "camelCase")]
pub enum AnnouncerSenderWire {
    Staff { staff_id: StaffSenderWire },
    Character { character_id: String },
    Custom { display_name: String },
}

/// v4 `STAFF_SENDER_ENUM` (`schemas.ts:180`) — exactly these ten, this spelling.
#[serde(rename_all = "camelCase")]
pub enum StaffSenderWire {
    Lantern, Aurora, Librarian, Concierge, Prospero,
    Host, CommonplaceBook, Ariel, Suparna, Pascal,
}
```

**Response shapes (frozen):**

| Verb | Success | Named error arms |
| --- | --- | --- |
| `ChatAnnouncementPost` | `{ "success": true, "message": <MessageEvent> }`, HTTP **201** | `notFound('Character')` (character branch only); `badRequest('Failed to post announcement (empty content or unknown chat).')` |
| `ChatAnnouncementPreview` | `{ "success": true, "proposedMarkdown": "…" }` | `notFound('Character')`; `notFound('Connection profile')`; `badRequest(result.error ?? 'Failed to generate in-character announcement.')` |
| `ChatSendMail` | `{ "success": true, "path": "…" }`, HTTP **201** | `badRequest('You can only post a letter as a character you are playing in this scene.')`; `notFound('Sender character')`; `notFound('Recipient character')`; `badRequest("That letter is no longer in your own postbox, so there's nothing to reply to.")` |
| `ChatMailboxList` | `{ "letters": [{ "path", "from", "sentAt" }] }` | `badRequest('characterId is required')`; `notFound('Chat')`; **`forbidden`**`('You may only inspect the mailbox of a character you are playing in this scene.')`; `notFound('Character')` |

Validation floors carried from Zod: `contentMarkdown` / `seedMarkdown` /
`bodyMarkdown` are `min(1)`; `custom.displayName` is `min(1).max(120)`;
`inReplyToPath` is `min(1).nullable().optional()`; every id field is `z.uuid()`.

**Constraint on E2B:** the SPA calls these four verbs and nothing else for this
family. The Whisper dialog is **not** here — it posts to the existing chat-send
