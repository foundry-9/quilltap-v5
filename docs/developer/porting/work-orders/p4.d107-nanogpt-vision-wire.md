## The drift, classified (surveyed 2026-08-23, fresh at `a14a1811`)

The NanoGPT plugin moves 1.0.3 → **1.1.0** and becomes the fifth
image-transporting provider. v5's `build_nanogpt_body` is currently
text-only and must gain the serialization; the manifest must flip. All in
`plugins/dist/qtap-plugin-nanogpt/` (v4 `provider.ts` +121, `index.ts`
+8/-3, `index.js` +90 — the esbuild bundle is the runtime artifact and is
hand-consistent with `provider.ts`; the oracle drives the dist bundle, so
recordings capture the real behavior either way):

1. **`index.ts` `attachmentSupport` flips** to `supportsAttachments: true`,
   the four image MIME types, `description: 'Images (JPEG, PNG, GIF, WebP)
   — requires a vision-capable routed model'`, plus a new `notes` field
   explaining the host-decides posture. This is the object bug 91's
   predicate reads through the registry — the §C1 contract point.
2. **`provider.ts`**: new `ChatContentPart` union (`{type:'text',text}` |
   `{type:'image_url',image_url:{url}}`);
   `NANOGPT_SUPPORTED_IMAGE_MIME_TYPES = ['image/jpeg','image/png',
   'image/gif','image/webp']` (comment: mirrors `attachmentSupport` in
   `index.ts` — "keep the two in step"); the constructor's
   `attachmentErrorMessage` default changes from
   `'NanoGPT chat requests are text-only in Quilltap. Send text-only
   messages.'` to
   `'NanoGPT forwards images only for image MIME types NanoGPT accepts.'`;
   `attachmentToImageUrl(attachment)` — `attachment.url` if present, else
   `` `data:${mimeType};base64,${data}` ``, else `null`.
3. **`buildUserContent(msg, sent, failed)`** returns `string |
   ChatContentPart[]`:
   - no attachments → `msg.content` **as a plain string** (the shape only
     becomes an array when attachments exist — a corpus-pinnable fact);
   - else `if (msg.content) parts.push({type:'text', text})`, then per
     attachment: unsupported MIME →
     `failed.push({id, error: `Unsupported file type: ${mimeType}. NanoGPT
     forwards images only (${LIST.join(', ')}).`})`; no url/data →
     `failed.push({id, error: 'Attachment missing data or URL'})`; else
     push the `image_url` part and `sent.push(attachment.id)`;
   - `parts.length === 0` → push `{type:'text', text:''}`.
4. **The ledger plumbing**: `formatMessages` returns
   `{messages, attachmentResults: {sent, failed}}`; `buildBody` returns
   `{body, attachmentResults}`; BOTH `sendMessage` and `streamMessage`
   drop their `collectAttachmentFailures` line (the base class's blanket
   "all attachments failed") for the real ledger — **advertised and
   executed can no longer disagree**.
5. **No vision-model list, deliberately** — NanoGPT fronts hundreds of
   models, a list "would be stale within the week"; the host has already
   decided (an arriving attachment means the operator asserted the model
   reads images, or the describe-fallback already substituted text).
   Carry the why-comment.
6. `manifest.json`/`package.json` → `1.1.0`; README (+29) documents the
   attachment contract; `docs/developer/PROVIDER_PLUGIN_DEVELOPMENT.md`
   (+35) grows the plugin-author attachment contract (mirror refresh).

DeepSeek / OpenAI-Compatible / Ollama **still cannot send images** in v4 —
fixing them is gated on a `packages/plugin-utils` publish. v5's three
droppers stay droppers; only their routing changes (bug 91, P4.D106's
lane). No work here beyond confirming the drop consts stay.
