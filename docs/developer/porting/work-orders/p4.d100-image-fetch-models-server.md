## The drift, classified (surveyed 2026-08-22, fresh at `d5830439`)

v4 `ca22ec45` (2026-08-21) does three things to ported surfaces, plus one
new-surface addition:

1. **The image-profiles `?action=list-models` action becomes honest.** v5
   currently REFUSES this action loudly
   (`crates/quilltap-core/src/api/image_profiles.rs:679-681`,
   `not_available("list-models")` — the P4.D33 bank note at `:658-674`
   records what porting it owes). v4's handler
   (`app/api/v1/image-profiles/route.ts:114-199`) now live-queries the
   provider when a key is supplied, labels the result
   `source: 'provider' | 'builtin'` (+ `fetchError` on live-fetch
   failure), and caches ONLY live lists.
2. **All FIVE image plugins gain (or harden) a keyed
   `getAvailableModels(apiKey?)`** — openai, google, grok, z-ai, AND
   openrouter (the order-of-record correction: openrouter moved too — its
   silent fallback-to-static-on-error became throw-on-error). Signature
   change: the method takes the key; without a key it returns the static
   list; **on live failure every provider THROWS** (the route catches and
   labels `builtin` + `fetchError`).
3. **Z.AI image generation was broken end-to-end and is now real**: Z.AI
   returns URLs while every consumer reads only base64; the provider now
   downloads and converts. v5 measurably HAS this bug: `parse_zai`
   (`model/image_dialects.rs:415-431`) keeps both `b64_json` and `url`,
   but the consumer (`tools/generate_image.rs:2367`) decodes only
   `img.data` — a URL-only Z.AI row decodes an empty string → zero bytes.
4. **Google's gemini-vs-imagen routing** now sends ANY `gemini*` id
   through generateContent (live-fetched ids like
   `gemini-2.0-flash-preview-image-generation` must not fall through to
   `predict`).

No DB schema change anywhere in the round's three commits (verified
mechanically — no `generateDDL`/migration/`lib/db` movement); no D23
re-dump. The help-doc rewrite is a `docs/v4` mirror + `p4.9i2` bank item.

## Shared contract (BINDING — identical text in P4.D100 and P4.D102)

The `list-models` response envelope, verbatim from v4
(`app/api/v1/image-profiles/route.ts:188-194`):

```
{
  "provider":        <echoed provider string>,
  "models":          string[],          // the list to show
  "supportedModels": string[],          // always the plugin's curated list
  "source":          "provider" | "builtin",
  "fetchError":      string             // present ONLY on keyed live-fetch failure
}
```

Error bodies: missing provider → 400 `Provider is required`; unknown
provider → 400 `Provider ${provider} is not available`; dangling
`apiKeyId` → 404 (API key not-found shape); outer failure → 500
`Failed to fetch models`. `fetchError` is omitted (not null) when absent.
Cache: only `source === "provider"` lists are cached (capability
`image`). Request: dispatch verb `imageProfileListModels`
(`ImageProfileListModels { provider, api_key_id }`,
`api/types.rs:901-908` — already typed on both sides;
`core-contract.ts:4158-4162` client-side).
