- v4 layout: the engine is `lib/services/brahma-console/one-shot.service.ts`
  (358); the Carina branch (`answerAsBrahma`, `carina.service.ts:340-406`)
  calls `runBrahmaQuery({repos, userId, chatId, question})` and maps the
  result (`detail === 'no-profile'` → the no-profile CarinaError, anything
  else → llm-failed; post via `postCarinaResponse` with the sentinel
  answerer id — that mapping + post path are ALREADY PORTED in
  `carina_query::answer_as_brahma`). Helpers imported from
  `orchestrator.service.ts` (the SEPARATE Phase-4 streaming console — do
  NOT port it): `resolveBrahmaConnectionProfile`,
  `normalizeToolCallSignature`. System prompt:
  `lib/brahma-console/system-prompt-builder.ts` (base brief at `:37-43`)
  + `lib/brahma-console/brahma-sql-prompt.ts` (`BRAHMA_SQL_PROMPT`,
  `:18-73`) joined `[base, sql, toolInstructions].join('\n\n').trim()`.
- The engine's flow (all of it composes ALREADY-PORTED v5 units):
  1. Profile: `resolveBrahmaConnectionProfile(repos, userId, null)` — the
     `null` forces the user's default-profile chain; `null` →
     `{ok:false, detail:'no-profile'}`.
  2. API key: `requiresApiKey(provider)` → `findApiKeyById`; missing →
     the two exact detail strings (`'no API key configured…'` /
     `'API key not found'`).
  3. Tool slate via `buildTools` — the Brahma flags: `agentModeEnabled`
     true, `documentEditingEnabled` true, `askCarinaEnabled` FALSE
     (recursion guard), `includeWorkspaceTools` false,
     `excludeMemorySearch` true, `sqlAccess` true; wardrobe/help/image
     false. (v5: `tool_build::build_tools` — check the existing
     Brahma-flag rows in `tool_build_equivalence`.)
  4. Tool mode: profile `pseudoToolMode`, `simple-json` COERCED to
     `text-block`; else native-vs-textblock via the ported check.
  5. Instructions: `buildTextBlockSystemInstructions` (fixed options slate
     — only `search` + conditional webSearch true) OR the native builder,
     ALWAYS + `buildAgentModeInstructions(MAX_AGENT_TURNS = 25)`.
  6. ISOLATION: messages = `[{system: prompt}, {user: question}]` — never
     the Salon transcript.
  7. The 25-turn agent tool loop — its OWN loop, faithful, NOT a reuse of
     `native_tool_loop` (different guards): stream (no-op sink — nothing
     streams; the live emit is Carina's, post-return) → detect (native via
     `detectToolCallsInResponse` / text-block via the ported parsers +
     strip) → `submit_final_response` accept (args `response`, fallback
     `extractSubmitFinalResponseFromText` on raw text) → the stuck-loop
     guard (`normalizeToolCallSignature` dup count,
     `MAX_DUPLICATE_TOOL_CALLS = 2` exact repeats OR 2 stale iterations →
     content-only assistant turn + the byte-exact user nudge with the
     `lastToolResultText` reminder) → thread
     (`build_assistant_tool_call_message`) → execute via
     `process_tool_calls` with `ToolExecutionContext {chatId, userId,
     operatorSurface: true, pendingWardrobeAnnouncements: fresh set}` →
     thread results (`build_tool_result_messages`); fingerprint
     `${toolName}:${success}:${content}` feeds stale detection; tool SIDE
     EFFECTS stand, result messages never persisted. Turn 25 pushes
     `buildForceFinalMessage()`.
  8. Finalize: extract-submit again, trim; empty →
     `{ok:false, detail:'empty response'}`; else `{ok:true, answer}`.
     **Never throws** — internal catch-all → `detail`.
- The v5 trait to satisfy (`carina_query.rs:111-118`, FROZEN):
  `RunBrahmaConsole::run(&self, user_id, chat_id, question) -> impl
  Future<Output = BrahmaConsoleResult> + Send` with
  `BrahmaConsoleResult {ok, answer, detail}`; `detail: Some("no-profile")`
  is the load-bearing sentinel string. DB/provider deps go on the impl's
  CONSTRUCTOR, not the trait args.
