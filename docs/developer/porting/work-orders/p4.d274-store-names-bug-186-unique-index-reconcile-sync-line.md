## Rulings made at planning (the planner's calls; the human may overrule before lane start — a STOP item if they do)

- **R-A — a bad ROW is dropped as v4 drops it; a WHOLE-QUERY failure
  stays STRICT** (§R.11 P4.D274 R-A, as amended). v4 reads
  `docMountPoints.findAll()` and `characters.findAllRaw()`, both
  `_findAll` (`base.repository.ts:263-277`).
  1. **Per-row drop — FAITHFUL.** A row failing its schema is DROPPED,
     with v4's two lines (`validate` logs ERROR `Data validation failed`,
     then `validateSafe` `:146-157` logs WARN `Safe validation failed
     {collection, error}`), and the rest is answered. This half is
     non-negotiable: a row v4 drops but v5 keeps would be planned by v5
     alone, and that IS the ping-pong.
     **The dogfood plant:** on a CLONE, a character row whose `id` is not
     an RFC uuid. v4 and v5 must both retire exactly that character's vault
     and nothing else.
  2. **Whole-query failure — STRICT** (the named recorded divergence
     **`RECONCILE_READ_FAILURE_STRICT`**, under the 2026-08-03
     write-path-reads-strict rule; P4.149 R-E's
     `strict-by-ruling(write-path)` class).
     - **v4's behaviour.** A failed `findAllRaw()` answers `[]` (ERROR
       `Error finding all entities {collection, error}`). The plan then
       sees every vault as unlinked and RETIRES every vault-shaped
       `character` store. A failed `findAll()` of the stores plans
       nothing. Inside `with_strict_repository_failures` (the `.qtap`
       import, `execute.ts:427-432`), the line gains `strictFailures=true`
       and the throw reaches the caller (`safe-query.ts:57-71`).
     - **v5's behaviour.** The read logs v4's SAME ERROR line (with
       `strictFailures=true` inside the scope) and returns `Err`, in and
       out of the scope. That is the ONE strict-aware read this lane adds
       to `db/fallback.rs`: `find_all_logged_strict(collection, read) ->
       Result<Vec<T>, DbError>`, appended at the end under `// === P4.D274
       (append-only) ===`, beside `find_by_filter_strict_aware`
       (`fallback.rs:167-179`).
     - **The reconcile then SKIPS.** It logs WARN `Store-name reconcile
       skipped: a store or character read failed` `{trigger, collection,
       error}` (a v5-only line; `error` = `fallback::error_text`), writes
       nothing, publishes nothing, and returns `Ok({renamed: [],
       skipped_reason: Some(ReadFailed)})`. Callers proceed as on any
       no-op: the boot still runs the head-shoulders enqueue, the import
       pushes no warning, and the character hooks log nothing more.
     - **Why it is safe on a shared instance.** A whole-query failure is a
       transient or structural condition, not a stable data shape. Skipping
       makes v5 lag v4; it never undoes v4's names.
     - **Pin it both ways** (unit 4, scenario (e2)). The v4 side shows
       every vault retired; the v5 side shows the skip and zero writes.
       Record it in a named table, so a v4 convergence trips it.
