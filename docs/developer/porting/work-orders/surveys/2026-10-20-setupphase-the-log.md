## 0. The span for this slice, in one paragraph

`e4a60ad9e` ("Feature: the Log", `dev.44`, 54 files +1,719 / −47, 32 production files) adds **one new table in the LLM-logs partition** — `log_entries` (`id`, `message` 1..4000, `chatId`, `characterId` nullable, `createdAt`, `updatedAt`), owned by a new `LogEntriesRepository extends AbstractDedicatedDbRepository<LogEntry>` (`dbTarget: 'llmLogs'`) whose `generateDDL` ensure runs on first repository use and, because the PHASE 3.1 structural pass drives every such repository, on every v4 boot; `onTableEnsured` adds two composite indexes beside generateDDL's `createdAt DESC` one. A new `regexp(pattern, value[, flags])` SQL scalar backed by JS `RegExp` is registered on the llm-logs connection only, with a 64-entry compile cache and the `REGEXP` operator form. Three built-in tools — `log_create_entry` (write one line stamped with the call's chat and character, never the model's), `log_grep` (a JS regex over every entry in the instance, newest first, `ignore_case`, `limit` 1..200 default 50) and `log_read` (any of `conversationId` incl. `"current"`, `character` by name-or-id, `from` / `to` ISO instants, `limit`) — are always offered to character surfaces (pushed after the Scriptorium trio inside the workspace block), dispatched in `tool-executor.ts` to `log-handler.ts`, listed under a new `log` category / "The Log" group in tool settings, and answer JSON `{ entries: [{id, message, conversationId, characterId, characterName, createdAt}], count, limit }` / `{ entry: {id, message, conversationId, createdAt} }`. Pascal custom tools gain a fourth effect kind, `log` (a template string 1..1000 rendered like an outcome message; empty → skipped; applied LAST, fail-soft, recorded as `{target:'log', next:{id,message}}`), with its schema / JSON-Schema mirror / resolver / applier / vocabulary / draft / Workbench UI / `run_custom` description clause `writes to the log`. `LLM_LOG_CLEANUP` prunes `log_entries` on the LLM-log retention days BEFORE the logging-enabled early return. The job child's write partition routes `logEntries.*` to the llm-logs partition. The Brahma SQL prompt, `run_sql`'s `database` description and the CLI `db schema` domain map learn the table. `a495faa26` (`dev.45`, 11 files +55 / −16) then fixes two things in that shape: a bare-date `to` means the END of that UTC day (one helper, `logReadBoundInstant`, used by both the refine and the handler; the `to` description changes), and `compileSqlRegexp` strips V8's own `Invalid regular expression:` prefix so callers' prefix is not doubled. This survey ports the POST-FIX shape.

## 6. Traps

- **T1 — DDL.md is not the DDL.** `docs/developer/DDL.md:1809` renders `"id" TEXT PRIMARY KEY,`; generateDDL emits `"id" TEXT PRIMARY KEY NOT NULL` (`schema-translator.ts:345-351`; the committed `llm_logs` row proves the rule). DDL.md also quotes all three index names; two are UNQUOTED on disk (`log-entries.repository.ts:44-45`). And its retention paragraph says the table is "treated like `llm_logs`" for logical backups, but `llm_logs` IS backed up (`backup-service.ts:175`) and `log_entries` is not (no reference anywhere in `lib/backup`, `lib/qtap`, `delete-service.ts`). Port from the dump and the repository, not the doc. (The ledger row `:412` copied DDL.md's `"id" TEXT PRIMARY KEY` implicitly by quoting the schema, not the bytes — §8.)
- **T2 — "lazily created, not at boot" is false in effect** (§Headline 1). The ledger's hazard analysis ("a pre-round v5 never reads the table") still holds, but the "lazy" premise affects: the re-dump (carries it — the dumper's `count()` pass), the provision oracle (carries it), any Friday copy booted by v4 ≥ `e4a60ad9e` (HAS it), and the dogfood note "v5's `replace` restore … never recreates the llm-logs file, so a v4-created `log_entries` table survives it untouched" (still true).
- **T3 — the regex engine must be V8's, not `regex`'s.** The `regex` crate has no lookahead/lookbehind, no backreferences, and Unicode-aware `\d`/`\w`/`\s`/`\b` by default, so `log_grep` would (i) refuse `(?<=a)b` where V8 accepts it (and refuse `\1`), (ii) match `\d` against Arabic-Indic digits where V8 (without `u`… and even with `u`) matches ASCII only, (iii) treat `.` as not-`\n` where V8's `.` excludes `\n`, `\r`, ` `, ` ` (and with `s` matches all), (iv) differ on `i` without `u` (V8 uses simple case folding with the non-`u` quirks: `ſ` does not match `s`, `K` (Kelvin) does not match `k`), (v) differ on `^`/`$` with `m` (V8 line terminators are the four above), (vi) accept `{` / `}` / `]` as literals where V8 does too but `regex` errors on some, (vii) produce DIFFERENT error texts. V8's `REGEXP_ERROR_MESSAGES` (fetched 2026-10-20 from `v8/src/regexp/regexp-error.h`, main): `Maximum call stack size exceeded`, `Stack overflow`, `Regular expression too large`, `Unterminated group`, `Unmatched ')'`, `\ at end of pattern`, `Invalid property name`, `Invalid escape`, `Invalid decimal escape`, `Invalid Unicode escape`, `Nothing to repeat`, `Lone quantifier brackets`, `numbers out of order in {} quantifier`, `Incomplete quantifier`, `Invalid quantifier`, `Invalid group`, `Multiple dashes in flag group`, `Cannot be executed in linear time`, `Repeated flag in flag group`, `Invalid flag group`, `Too many captures`, `Invalid capture group name`, `Duplicate capture group name`, `Invalid named reference`, `Invalid named capture referenced`, `Invalid property name in character class`, `Invalid character class`, `Unterminated character class`, `Range out of order in character class`, `Invalid set operation in character class`, `Invalid character in character class`, `Negated character class may contain strings`, `Unsupported Bytecode`. The full text the handler shows is `Invalid regular expression: /<pattern>/<flags>: <message>` (the `a495faa26` strip removes only the FIRST prefix). Flags-side: the `unsupported flags "…" — use any of i, m, s, u` reason is v4's own (em dash), checked BEFORE compilation. The port options (§8 Q2): (A) the `regress` crate (an ECMAScript regex engine in Rust — not in `Cargo.lock`; would need the human's dependency ruling, like `@xterm/headless`'s crate); (B) `fancy-regex` 0.19.1 (already transitive in `Cargo.lock:1235`; lookaround + backrefs, but Rust syntax/Unicode classes and its own error texts — a translation layer for `\d`/`\w`/`\b`/`.`/`i` and a V8-message mapper, partial fidelity); (C) a typed refusal: `log_grep` answers `success:false` for any pattern the chosen engine cannot compile identically — fails the oracle on every "exotic" row by design. Recommend (A) with a V8-message mapping table pinned by the compile-row corpus; the `MAX_LOG_GREP_PATTERN_LENGTH` 500 and the 64-entry cache are not engine-dependent.
- **T4 — `String.prototype.slice(0, 4000)` and `.length` are UTF-16.** `writeLogEntry` clips at 4000 code units; a 4000-emoji message is 8000 units and clips to 2000 emoji; a pair split at unit 4000 yields a lone high surrogate, which SQLite stores as the WTF-8/`\uD83D` bytes better-sqlite3 writes (ill-formed UTF-8) — the Rust twin must count UTF-16 units (`js_slice_utf16` exists? check `jsstr`) and, for the lone-surrogate case, either reproduce better-sqlite3's bytes or RECORD a divergence (`LONE_SURROGATE_CLIP`). Likewise Zod's `.max(4000)` on `message` in the TOOL schema counts UTF-16 units (Zod 4.6.7 `.length()` counts code points per the memory note `carrier-oracle-measurement-gotchas.md` — VERIFY which of `.max()` / `.length()` counts what at 4.6.7 before pinning the 4000-boundary row; the two bounds (tool schema vs `writeLogEntry`'s clip) may disagree on the same string).
- **T5 — the bounds are strings, and V8's `Date.parse` is the gate.** `instant` accepts anything `Date.parse` accepts (`'October 1, 2026'`, `'2026-10-01 18:00'`, `'2026-02-31'` (rolls over), `'+275760-09-13'`) and `logReadBoundInstant` renders `toISOString()` — an expanded year renders `+275760-09-13T00:00:00.000Z`, which sorts LEXICALLY after every normal ISO string (`'+' < '0'` is false in ASCII; `'+'` is 0x2B < `'0'` 0x30, so it sorts BEFORE — the refine `from <= to` then passes/fails on the sign character, not the instant) — reproduce, don't fix; v5 has `js_date_parse_ms` (V8's whole `Date.parse`, memory note `v8-sort-and-memory-calendar-gotchas.md`) and `iso_from_unix_ms` for expanded years (`toISOString expanded years` in the unify-findings note). A bare-date `to` of `2026-02-31` renders `2026-02-31T23:59:59.999Z` by concatenation (no parse round-trip) while the same `from` renders `2026-03-03T00:00:00.000Z` — pin both. The column compare is a TEXT compare against `createdAt` strings v4 wrote with `toISOString()` (always `.sssZ`), so a `to` without milliseconds is normalized by the render — never compare raw input.
