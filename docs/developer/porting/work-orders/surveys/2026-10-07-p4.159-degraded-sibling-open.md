deliberate. Ported as v4 has it; candidate filing: "the LLM-logs client lacks
the mount index's cold-open retry ladder". The human

## 2. The integrity plant

A sound encrypted file (`CREATE TABLE t …` + 2,000 rows of ~204 bytes, 111
pages) with page 3 overwritten by the garbage pattern opens (page 1 is
intact) and `quick_check` REPORTS — it does not throw — through SQLite3MC's
page authentication failure:

```
*** in database main ***
Tree 2 page 3: unable to get the page. error code=11
Tree 1 page 1: unable to get the page. error code=11
```

v4 and v5 produce this text byte-for-byte over the same recipe (the
differential's `integrity` rows — so both builds lay the pages out
identically). On the host arms the plant is page 3 of a PROVISIONED sibling
(mount index and LLM logs alike): the FAILED arm, every time. Overwriting the
LAST page instead yields one `unable to get the page` line per page from the
end down to ~12 (a long result string — not used).

**No plant reaches the `threw` arm** (`quick_check` raising): a bad page 1
fails the OPEN first, and every interior-page plant is reported. The arm is
pinned by `db::runtime::tests::the_integrity_verdict_has_v4s_three_arms` over a
stubbed outcome (both partitions).

## 3. The backend-level catch lines (Tier 3, item 17)

`backend.ts:588` (`Failed to initialize LLM logs database — logs will be
unavailable`) and `:613` (`… document mounts will be unavailable`) fire only
when `loadLLMLogsConfig()` / `loadMountIndexConfig()` throws (path
resolution, a failed `mkdirSync`, `SQLiteConfigSchema.parse` rejecting an env
value). The client, the integrity check, the checkpoint start and the async
backup are non-throwing by construction. v5 has no config loader on this path
(paths come from the data dir; there are no SQLite env knobs) — **unreachable
from any v5 state; not ported.** When v4's catch does fire, the instance is
left UNINITIALIZED (flag unset, handle null), not degraded.

## 4. Pre-existing divergence recorded (Tier 3, item 15): the ABSENT sibling

v4's `new Database(path)` CREATES a missing sibling file, so v4 has no
"absent" state after a boot. v5's `open_ready` passes a sibling path only when
the file exists; an instance without the file runs with the partition ABSENT
(`PartitionState::Absent` — skipped by the structural pass, R4). Every v5
instance is provisioned with both siblings, so this needs a deleted file to
reach. Not closed this round (the order's mandate).

**The shared character-overlay fix (DEFERRED, named):** in v4 a character read
over a degraded mount index does not fail at the database — the vault doc
reads are `withRawDb([])`, so `hydrateOne` throws `CharacterVaultUnavailableError`
for a VAULTED character only (→ the middleware's 503 `Character vault
unavailable`, which v5 already renders from `DbError::StoreUnavailable`), and
an unvaulted character reads normally. v5 requires the mount-index connection
up front at every one of those callers and answers 500. The fix — an overlay
read over an unavailable mount answering as if the docs were empty — spans the
character read layer and five callers; it belongs to a follow-up order.

**R-A consequence (ruled, recorded both ways):** after a failed integrity
check v4 sets the flag but KEEPS the handle, so `getRaw*Database()` stays
non-null: `run_sql` still QUERIES the integrity-failed file, and a child job's
apply still commits to it. v5 drops the writer and the pool (R-A), so `run_sql`
answers the not-available sentence and nothing writes. Every guarded
repository refuses identically on both sides.
