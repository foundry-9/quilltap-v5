**Title:** Folder moves match folder paths case-sensitively, so a move typed in another casing leaves rows and links behind

**What happened**

Three folder-path matches that drive a folder move are case-SENSITIVE, while
the filesystem (macOS / Windows) and the database store's own folder lookups
(`COLLATE NOCASE`) treat `notes` and `Notes` as one folder:

1. **A filesystem store's `move-folder` typed in a different casing renames the
   directory but strands its index.** `lib/mount-index/folder-ops.ts:152` finds
   the source folder row with `f.path === fromRel`, and the descendant row /
   link rewrites (`:162`, `:175`) test `startsWith(oldPrefix)` — all exact. On a
   case-insensitive disk `fs.access('…/notes')` and `fs.rename` succeed for a
   directory named `Notes`, so the bytes move while every row keeps the old
   path. The next scan then drops the "missing" files with their chunks,
   embeddings and descriptions, and re-adds the moved ones as new.
2. **`chatDocuments.findUnderFolder` misses a document recorded in another
   casing.** `lib/database/repositories/chat-documents.repository.ts:260-271`
   filters `r.filePath.startsWith(prefix)`. A Document-Mode row recorded as
   `Notes/a.md` is not swept by a doc-tool / Document-Mode folder move of
   `notes`, while `under()` (`folder-ops.ts:200`, lower-cased) and the database
   store's `findByMountPointAndPath` (NOCASE) treat them as one folder.
3. **The Scriptorium's `move-folder` never sweeps `chat_documents` at all.**
   `git grep sweepChatDocumentsAfterFolderMove 624d0d25c` finds only the doc
   tools (`file-management-handlers.ts:592`, `:663`) and the document core; the
   action route's `moveFolder` (`folder-ops.ts`) has no sweep, so an open
   document under a folder moved from the store browser keeps its old path.

**Steps to reproduce (shape 1, measured)**

1. A filesystem store whose folder is `Notes/` on disk, scanned (rows:
   folders `Notes`, `Notes/sub`; links `Notes/alpha.md`, `Notes/beta.txt`,
   `Notes/styled.md`, `Notes/sub/deep.md`).
2. `POST /api/v1/mount-points/<id>?action=move-folder` with
   `{"fromPath": "notes", "toPath": "archive"}`.

**Measured output**

- The answer is a success: `{"mountPointId": "<id>", "fromPath": "notes",
  "toPath": "archive", "destMountPointId": "<id>"}`.
- On disk: `archive/`, `data/`, `empty/`, `scratch.tmp` — `Notes/` is gone.
- `doc_mount_folders`: still `Notes`, `Notes/sub`.
- `doc_mount_file_links`: still `Notes/alpha.md`, `Notes/beta.txt`,
  `Notes/styled.md`, `Notes/sub/deep.md`.

Shape 2 (measured): with a `chat_documents` row at `Notes/a.md`,
`findUnderFolder('notes')` → `[]`, `findUnderFolder('Notes')` → `['Notes/a.md']`,
while `docMountFolders.findByMountPointAndPath(<database store>, 'NOTES')` →
the folder `notes` (NOCASE).

**Expected**

A folder move addressed in any casing carries every row and link under the
folder (as the database store's `moveDatabaseFolder` does through its
case-insensitive lookup), and a store-browser folder move sweeps the open
documents under it as the doc tools' moves do.

**Suggested fix site**

`folder-ops.ts` `moveFolderWithinMount` (match the source row and prefixes
case-insensitively, as `under()` already does, and call
`sweepChatDocumentsAfterFolderMove` after the link rewrite);
`chat-documents.repository.ts` `findUnderFolder` (a case-insensitive prefix).

**Provenance:** found by the v5 port (P4.D381, R-6 — porting `c34986421`'s
filesystem folder-row carry). v5 ports all three shapes FAITHFULLY
(`services/mount_index/folder_ops.rs` `move_folder_within_mount`'s exact
`f.path == from_rel`, the case-sensitive prefixes, no sweep); v5's
`find_under_folder` is P4.D380's. Not a v5 divergence — it converges when v4
fixes it.
