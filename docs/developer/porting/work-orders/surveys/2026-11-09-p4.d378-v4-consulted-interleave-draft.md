**Title:** Inventory pool lists consulted stores in promise-settlement order instead of tier order, so the title lint's Census `pools` order varies

**What happened**

`loadInventoryPool` reads the pool's four tiers concurrently and every tier
pushes into ONE shared `consulted` array:

- `lib/inventory/pool.ts:260` creates `consulted`;
- `lib/inventory/pool.ts:261-270` runs the own / group / project / General
  `readTier` calls under one `Promise.all`;
- `lib/inventory/pool.ts:157` (`readTier`) does `consulted.push(mountPointId)`
  before each awaited read.

So the array interleaves the tiers by microtask resolution: one tier's second
mount lands after another tier's first, depending on which awaited read
settles first. Within a tier the order is the settled one (`0c47f4539`: the
earlier mount wins, read reversed); ACROSS tiers it is not tier order.

The order is observable:

- `pool.consultedMounts` is returned to callers;
- `lib/inventory/title-lint.ts:206` iterates `new Set(pool.consultedMounts)` to
  build the protected set's `pools` labels;
- `lib/inventory/title-lint.ts:287-291` logs them as the DEBUG
  `[InventoryTitleLint] Census` `pools` field.

**Steps to reproduce**

A character whose vault, a group store and Quilltap General are in the pool,
plus one DANGLING group store id (a store row that does not exist), then a
title-lint create / archive against the character's Inventory.

Two rows in the v5 harness reproduce it on v4's real code:

1. `lint-fail-closed-dangling-group` (door `create`, character scope);
2. `lint-leaving-unverifiable-mount` (door `archive`, character scope).

**Measured output**

`consultedMounts` on v4 (vault, then the group tier's dangling id, then
General, then the group store — General interleaves between the group tier's
two mounts):

```
[vault, dangling, general, covenant]
```

so the Census DEBUG's `pools` on v4 is:

```
["store \"Friday Character Vault\"", "store \"Quilltap General\"", "store \"Group Files: The Covenant\""]
```

**Expected output**

Tier order (own → group → project → General), each tier in its settled order:

```
[vault, dangling, covenant, general]
["store \"Friday Character Vault\"", "store \"Group Files: The Covenant\"", "store \"Quilltap General\""]
```

The v5 port reads the tiers one after the other and produces exactly this.

**Why it matters**

The refusal OUTCOME is unaffected (the set of pools, the unread list and the
verdict are the same). But `consultedMounts` and the Census `pools` order
depend on how promises settle rather than on tier order, so the same request
can log different orders under different I/O timing. That makes the Census
line unstable for diagnosis and for any caller that reads `consultedMounts`
as an ordered list. The `unreadMounts` array shares the same `Promise.all`
shape (`pool.ts:153-170`), though its WARN arm is unreachable through the
fallback folder read at the pin.

**Suggested fix**

Give each `readTier` its own `consulted` / `unread` arrays and concatenate them
in tier order after the `Promise.all` resolves (the reads stay concurrent; only
the bookkeeping becomes ordered).
