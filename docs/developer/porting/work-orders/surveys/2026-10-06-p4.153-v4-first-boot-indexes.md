## Findings (beyond the order's predictions)

1. **`idx_doc_mount_folders_mp_path` is UNIQUE on a real v4 instance and
   was PLAIN on a fresh v5 one: RULED and FIXED (the human, 2026-10-06:
   "make the folders mp_path index UNIQUE to match v4").** Three
   `provision-*-mount` migrations and `convert-project-files-to-document-stores`
   make it `CREATE UNIQUE INDEX`; `doc-mount-folders.repository.ts:44`'s
   `onTableEnsured` makes it plain. The real boot keeps the migration's,
   because migrations run first. Under R-D as written (a shared name keeps the
   generateDDL copy), a fresh v5 instance would have accepted a duplicate
   `(mountPointId, path)` folder row that v4 refuses. v5's own
   `builtin_mounts.rs:258` already asked for `CREATE UNIQUE INDEX IF NOT
   EXISTS` there, which was a silent no-op behind the plain copy. The fix
   follows the real boot without hand-writing anything. The dumper carries a
   shared name when the migration's text is UNIQUE and generateDDL's is not
   (exactly this one at the pin, so the artifact is mount-index 5, not 4). The
   provisioner skips `fresh_schema.json`'s copy of any name the artifact
   carries. `provisioning_equivalence` now requires the name byte-equal (its
   `SHARED_NAME_SQL` `UNIQUE` row is gone). `host_boot_fresh_indexes`'s
   `idx_doc_mount_folders_mp_path_refuses_a_duplicate_path` refuses with v4's
   measured bytes `UNIQUE constraint failed: doc_mount_folders.mountPointId,
   doc_mount_folders.path`; red on the pre-ruling artifact (ACCEPTED).
2. The other 16 shared names differ only by `("userId" ASC)` (generateDDL) vs
   `("userId")` (migration). That is the same index, since ASC is SQLite's
   default. They are pinned as `SHARED_NAME_SQL`'s `ASC` rows.
3. **The order's R-A premise ("the SAME column set") is FALSE on a real first
   boot.** The migration-built `characters` (−15 columns), `projects` (−19) and
   `groups` (−5) are the slim store-backed rows (`cutover-characters-to-vault`,
   `cutover-projects-to-store`, `create-groups-table`). `chat_settings` keeps 3
   schema-dropped columns and lacks `timezone`. `chats` has the 3 columns v5
   adds at boot. `users` keeps 4 legacy auth columns. All of these are recorded
   (not closed) in `TABLE_COLUMN_ASYMMETRY`, both ways. R-A's TABLE ruling is
   unchanged. v5 already runs on the slim shape of the Friday copy.
4. **The `chat_informs` three are NOT made by v5's boot on a fresh
   instance.** The order's R-C counted them as boot-made, but
   `ensure_chat_informs_table` fires only when the TABLE is absent, and the
   provisioner makes the table. So `find_pending_for_participant` had no index
   on a fresh v5 instance before P4.153.
5. A real v4 first boot logs about 2,400 ERROR lines that do not touch the
   index question: the forked job child's `attempt to write a readonly
   database` ensures (747 × 3), 129 help-doc embedding failures, and the
   sample-content seed racing a not-yet-ensured `doc_mount_files` (`no such
   table: doc_mount_files` 30×, the two sample characters NOT created). The
   last of these is a candidate v4 note (a first-boot ordering race), outside
   this lane.
