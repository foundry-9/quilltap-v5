### D.3 Ordering subtleties
- **Backfill filter vs derivation precedence** (`add-chat-concierge-mode`): rows selected by `conciergeOverride IN ('OFF','UNCENSORED') OR isDangerousChat = 1`, then derived with override FIRST — `OFF` + `isDangerousChat=1` → **locked** (label ignored; a Vouched-Safe-over-Flagged chat loses its Flagged memory, by design). Only rows with `conciergeModeSetBy IS NULL` are touched; a Moderated derivation writes NOTHING (so `conciergeMode` stays at the column default `'moderated'` on migrated rows, NULL on fresh-DDL rows created before v5 writes it). `isDangerousChat` is read as `=== 1` (a raw INTEGER), NOT the hydrated boolean.
- **`isDangerousChat` NULL branch**: `deriveConciergeModeFromLegacy` tests `=== true`; NULL/0/undefined all → moderated. In v5 the hydrated read OMITS a NULL nullable-optional (`v4-turns-every-null-cell-into-undefined-on-read`), so a Rust derive over the hydrated `Value` must treat absent == false.
- **`expected` compare-and-set NULL rule**: `expected === 'moderated'` matches `conciergeMode IS NULL` too; `expected === 'unmoderated'|'locked'` matches only that literal. In SQL: `WHERE id=? AND (conciergeMode = 'moderated' OR conciergeMode IS NULL)` vs `WHERE id=? AND conciergeMode = ?`. `matchedCount > 0` — a write that matched but changed nothing still counts as written.
- **Whole-row `update` vs patch-only**: v4's `_update` re-reads a snapshot, validates the merged row, and `$set`s everything except the three patch-only columns unless named. v5 has no snapshot-rewrite (`ChatUpdate` sets only named columns), so the hazard the hook closes does not exist in v5 — but the RULE "no writer but `setConciergeMode` names the three columns" must still hold: `ChatUpdate` must NOT gain the three fields; `reclassify-danger`, `setDangerClassification`, the flip's `'moderated'` telemetry clear must touch only the five danger columns.
- **Flip step order**: `setConciergeMode` FIRST (state lands), THEN the `'moderated'` case's telemetry clear + ledger reset + announcement. A crash between leaves state=moderated with stale telemetry — v4-faithful; do not reorder into one transaction unless the ordering is preserved.
- **Provenance-only write**: same-state operator adoption writes `{ conciergeMode: current, setBy: nextBy, reason: nextReason }` — for `requested==='unmoderated'` by the operator, `nextReason` is `'manual'` and REPLACES `'refusals'`/`'classifier'`/`'migration'`; for `'locked'` it is always `operator/manual`; for `'moderated'` the same-state branch never writes (currentBy is always null there).
- **`getConciergeProvenance` on a migrated-but-odd row**: a non-Moderated row with NULL `conciergeModeSetBy` reads `'operator'` (the fallback), never null — the chat GET/list payloads thus never carry `conciergeSetBy: null` unless Moderated.
- **Announcement kind vs provenance**: `'unmoderated'` by `concierge`+`classifier` posts the DANGER announcement (`postConciergeDangerAnnouncement` with `options.classification`), not a manual kind — the pre-#75 `ChatDangerClassification` handler no longer announces itself.
- **`readCurrentConciergeState` fallback**: `snapshot ?? 'moderated'`; the image chokepoint passes `getConciergeState(ctx.chat)` (so a `chat: undefined` dialog call reads Moderated and, with a `chatId`, re-reads anyway).
- **`resolveConciergeSettings` branch order**: exempt → off-duty → locked → unmoderated → moderated; `inert('chat-locked')` is spread and THEN `onDuty:true, display: settings.display` overlaid; `source` is `'global'` only when `globalSettings?.conciergeSettings` is truthy, else `'default'` (the seeded/default row from `chat-settings.repository` writes `DEFAULT_CONCIERGE_SETTINGS`, so real instances read `'global'`).
- **`readConciergeSettings` merge**: a shallow spread of `stored` over the defaults with `display`/`preScreen` merged one level — a stored `preScreen: null` would spread `{}` (`?? {}`), a stored `display: undefined` likewise; unknown extra keys survive.
- **Summary classifier gate moved into the CHAT**: #76's `chat-danger-classification`/`context-summary` chain/`memory-trigger`/`scheduled-danger-scan` all resolve WITH the chat, so `summaryClassification` is false for Unmoderated/Locked/exempt chats even when the user opted in; v5's `gatekeeper_job.rs:213` and `context_summary_job.rs:193` currently resolve with `None`.
- **`resolve-external-turn` now passes the chat** (was chatless) — a Locked/Unmoderated chat's external turn changes memory-trigger behaviour; a behaviour delta hidden in a "rename" hunk.
- **Migration order**: `add-chat-refusal-ledger-v1` (#74) → `add-chat-concierge-mode-v1` (depends on it) → `add-concierge-settings-v1` (depends on `add-dangerous-content-fields-v1` + mode; its `hasUnmoderatedChats` needs `chats.conciergeMode`) → `drop-chat-concierge-override-v1` (depends on mode). `add-concierge-settings` writes EVERY row lacking the column (even all-defaults), with `JSON.stringify(MigratedConciergeSettings)` key order — which differs from `DEFAULT_CONCIERGE_SETTINGS`' key order only in that both list `enabled` first then the four ids… (identical order, in fact: enabled, uncensoredText, uncensoredImage, uncensoredVision, imagePrompt, autoSwitch, newChatsStartAs, display, preScreen) — but the migrated `preScreen` has `customClassificationPrompt` BEFORE `summaryClassification` while the Zod `.default()` literal (fresh DDL DEFAULT + a Zod-materialized PUT) OMITS `customClassificationPrompt` entirely. Three distinct stored byte shapes for "the same" settings: migrated JSON, the DDL DEFAULT literal, and `JSON.stringify(ConciergeSettingsSchema.parse(x))` (Zod v4 output key order = schema declaration order, with `customClassificationPrompt` present only when supplied). v5's hand-rolled twin must reproduce the PUT-materialized order (`enabled, uncensoredTextProfileId?, uncensoredImageProfileId?, uncensoredVisionProfileId?, imagePromptProfileId?, autoSwitchAfterRefusals, newChatsStartAs, display{mode, showWarningBadges}, preScreen{enabled, threshold, scanTextChat, scanImagePrompts, scanImageGeneration, customClassificationPrompt?, summaryClassification}`) and the two nested `.default()` objects (present when the key is absent; a partial `display`/`preScreen` object is filled per key).
