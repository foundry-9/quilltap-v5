## Mandate

Deliver the home-dashboard data surface the SPA lane consumes: v4's
`getHomeData` service composed as one new dispatch verb (`systemHome`) plus
its REST edge (`GET /api/v1/system/home`), with a committed fixture family
and a differential against v4's REAL `home-data.service.ts`. This is a
**pure composition lane** — every repo/service it calls is already ported
(chats/projects/characters/files repos, `services::chat_enrichment`,
`services::character_enrichment`); the port is the 224-line orchestration:
the parallel fetches, the salon-chat filter, the slice caps, the
three-source project-activity sort, the character sort chain, and the DTO
shapes. This lane owns `crates/**` and `harness/oracle/**`; it must NOT
touch `apps/web/**`. Every ported unit ships with its differential against
v4's real code — no exceptions. There are no LLM calls, no codecs, no fs
watchers: **no refusal arms are expected in this lane.**

### The v4 logic, step by step (the subtle bits to carry)

1. `repos.users.findById(userId)`; `displayName = user?.name || fallbackName
   || 'there'`.
2. Parallel fetch: `chats.findByUserId`, `projects.findAll`,
   `characters.findByUserId`, `files.findAll` (each `[]` when no userId —
   in v5 single-user the userId is always present; follow the established
   single-user pattern of the other system verbs).
3. **Help-chat filter:** keep chats where `!c.chatType || c.chatType ===
   'salon'`.
4. `enrichChatsForList` → `cleanEnrichedChats` (BOTH already ported in
   `crates/quilltap-core/src/services/chat_enrichment.rs` — reuse, do not
   re-derive), then `.slice(0, 12)`; `lastChatId` = first id or null.
5. `recentChats` mapping: note `storyBackgroundUrl:
   chat.storyBackground?.filepath || null` (JS `||` — empty string becomes
   null), `defaultImageId: … || undefined` (omitted when falsy) vs
   `defaultImage: … : null` (explicit null) — the omit-vs-null split is
   wire-visible; match it exactly (the P4.6p rule: reads omit vs echo null
   is per-field, prove it in the differential).
6. **Project activity sort:** per project, `max(project.updatedAt, latest
   chat lastMessageAt among its chats, latest file updatedAt among its
   files)`; sort desc, `.slice(0, 12)`; `lastActivity` re-serialized via
   `new Date(t).toISOString()`.
7. **Character chat counts** count EVERY chat participant with a
   characterId (over `allChatsRaw`, i.e. BEFORE the help-chat filter —
   carry that faithfully).
8. **Character list:** filter `!c.npc && c.controlledBy !== 'user'`; sort
   favorites first, then chatCount desc, then
   `a.name.localeCompare(b.name, undefined, { sensitivity: 'base' })` —
   **the base-sensitivity collator**, not the vault's code-unit compare;
   Phase 1 shipped the ICU4X en-US collation — check what sensitivity the
   ported comparator implements before reusing it, and add a tier-1 case if
   base-sensitivity is a new option. Then `.slice(0, 24)`, then
   `enrichWithDefaultImage` per character (ported —
   `services/character_enrichment.rs`).
9. `HomepageCharacter` carries `isFavorite: char.isFavorite ?? false`,
   `npc: char.npc ?? false`, `chatCount`, `defaultConnectionProfileId:
   … || null`.

## Shared contract (BINDING — identical in all three orders)

### §1 — the `systemHome` surface (lane A provides; lane B consumes)

- **Dispatch verb:** wire name `systemHome`, Rust `Request::SystemHome`
  (no parameters — single-user; the engine supplies the user scope as the
  other system verbs do).
- **REST edge:** `GET /api/v1/system/home` → v4 `successResponse` envelope
  around the payload; on internal failure v4's
  `serverError('Failed to load the home dashboard')` body.
- **Payload** (v4 `HomeData`; field names verbatim, omit-vs-null exactly as
  written):

```ts
{
  displayName: string,
  lastChatId: string | null,
  recentChats: Array<{
    id: string, title: string, updatedAt: string,
    lastMessageAt: string | null,
    isDangerousChat?: boolean,
    storyBackgroundUrl?: string | null,
    participants: Array<{
      id: string, type: 'CHARACTER', isActive: boolean, displayOrder: number,
      character?: {
        id: string, name: string,
        defaultImageId?: string,
        defaultImage?: { id: string, filepath: string, url?: string } | null,
        tags?: string[]
      } | null
    }>,
    _count: { messages: number }
  }>,                                   // max 12
  projects: Array<{
    id: string, name: string,
    description?: string | null, color?: string | null, icon?: string | null,
    chatCount: number, lastActivity: string
  }>,                                   // max 12, activity-sorted
  characters: Array<{
    id: string, name: string, title?: string | null,
    defaultImageId: string | null,
    defaultImage: { id: string, filepath: string, url?: string | null } | null,
    tags?: string[],
    isFavorite: boolean, npc: boolean, chatCount: number,
    defaultConnectionProfileId?: string | null
  }>                                    // max 24, favorites→chatCount→name
}
```

- `defaultImage.filepath` / `storyBackgroundUrl` are **server-relative
  paths, v4-faithful** — do NOT absolutize server-side (dogfood finding
  #12; lane C fixes resolution at the client origin).

### §2 — the URL-resolution freeze (lane B ↔ lane C)

- Lane B routes every server-supplied image/file path through the EXISTING
  shared helpers (`apps/web/src/app/ui/avatar-stack.ts` normalization,
  `apps/web/src/app/core/api-url.ts` `apiUrl()`) — no inline URL building
  in the new home components.
- Lane C may change the RUNTIME resolution of those helpers under the Tauri
  origin but must NOT change any exported helper signature
  (`apiUrl(path: string): string` stays) and must not edit lane B's files.
