## The drift, classified (surveyed 2026-08-17, from the `d123658d` diff)

Bug 74 — tagging a connection profile had never worked in v4, three layers
deep: TagEditor's profile branch called `/api/v1/profiles/<id>` (a route that
never existed); the connection-profile GET had no `get-tags` action and
answered an unknown action with the whole profile body; ProfileCard read
`tag.name` off `enrichWithTags`'s `{tagId, tag}` envelope and drew empty
pills. v4 settled the two tag shapes with **`resolveEditorTags`** — a
flattening of `enrichWithTags` that both `get-tags` routes (characters +
connection profiles) now share — plus an `EditorTag` type, and the GET now
**refuses unknown actions**.

v5's current state (surveyed 2026-08-17):

- v5 has **no profile tag verbs at all** — `types.rs:128–161` carries only
  List/Create/Update/Delete/Reorder/ResetSort/Test/TestMessage. Tag editing
  is a named deferral in the SPA card's header
  (`connection-profiles-card.ts:22`). This lane retires the server half of
  that deferral by porting the surface **in its fixed v4 form**.
- v5's profile LIST/GET enrichment already carries the `{tagId, tag}`
  envelope (`settings.rs:1192` `connection_profile_list` →
  `enrich_profile(conn, p, true)`; doc comment says apiKey + tags) — verify,
  don't re-implement.
- v5's characters `get-tags` twin (`api/characters.rs:241`, projection
  helper `db/tags.rs:176`) reproduces v4's OLD N+1 `tags.findById` loop.
  v4 converged it onto `resolveEditorTags`; this lane converges v5's twin
  the same way and proves the refactor output-neutral by differential.

## Shared contract (binding — identical in P4.D85 and P4.D86)

- **Verbs** (Request, serde camelCase like the character trio at
  `types.rs:440–460`):
  - `connectionProfileGetTags { profileId }`
  - `connectionProfileAddTag { profileId, tagId }`
  - `connectionProfileRemoveTag { profileId, tagId }`
- **Wire shapes** (v4 `route.ts` at `d123658d` is the oracle):
  - get-tags success: `{ "tags": [ { "id", "name", "visualStyle" } ] }` —
    the FLAT `EditorTag` shape (`enrichment.ts:113–124`), entity order
    preserved, missing tag ids dropped silently.
  - add-tag success: status **201**, `{ "success": true, "tag": <full tag
    row> }`; unknown `tagId` → 404 `notFound('Tag')`.
  - remove-tag success: `{ "success": true }` (no tag existence check).
  - Unknown GET action → 400
    `Unknown action: <action>. Available actions: get-tags`.
  - Unknown POST action → 400
    `Unknown action: <action>. Available actions: add-tag, remove-tag,
    auto-configure`.
  - `auto-configure` → v5's loud typed refusal (this lane owns the
    sentence; D86 must not depend on it).
- **PUT baseUrl**: the client ALWAYS sends the `baseUrl` key (`''` when the
  resolved provider takes no base URL; the stored value verbatim when the
  provider is unknown/unloaded); the server arm stores `baseUrl || null`
  (v4 `route.ts:234–236`) so `''` lands as NULL. No server change; the
  coercion is load-bearing for the client's poisoned-row clear.
- **Card display**: the profile LIST/GET enrichment keeps the
  `{ tagId, tag }` envelope (`EnrichedTag`); `get-tags` is the FLAT shape.
  Two shapes, each with one owner — never conflate
  (that conflation WAS bug 74's second layer).
