## Mandate

Port v4's **cast management** half of the chat action surface: the participant
mutation verbs (`add-participant`, `update-participant`, `remove-participant`,
`rebuild-system-prompt`) and the per-chat avatar-override family
(`get-avatars`, `set-avatar`, `remove-avatar`, `toggle-avatar-generation`).
These are dispatch verbs on `quilltap-core`'s boundary; v5 has **no** `?action=`
REST edge for chats (verified: no `chats_routes.rs` exists, and
`quilltap-web/src/lib.rs` registers no `/api/v1/chats` route), so no REST edge
is owed and none may be added.

**This is a genuine hole, not a refinement.** v5 today can create a chat with a
participant list and never change it: there is no `ChatAddParticipant`,
`ChatUpdateParticipant` or `ChatRemoveParticipant` variant anywhere in
`api/types.rs`. A character cannot be added to or removed from an existing
conversation in v5 at all.

**⚠ v4 has TWO entrances to participant mutation and this lane closes both.**
Besides `POST …?action=*-participant`, v4's `PUT /api/v1/chats/{id}` accepts a
`chat` bag carrying `addParticipant` / `updateParticipant` / `removeParticipantId`
(`helpers.ts:442` `processChatUpdates`). v5's `chat_update`
(`crates/quilltap-core/src/api/salon.rs`, the doc comment above the fn) **names
the participant families as a deferral in so many words**. Closing only the
action verbs would leave the bag entrance still refusing. This lane therefore
owns `api/salon.rs`'s `chat_update` as well — and note it deliberately writes
via a raw single-column `UPDATE` rather than `db/chats.rs` (the
`standalone-write-avoids-frozen-chatupdate` pattern), precisely because
`db/chats.rs` belongs to the sibling lane. **Keep that pattern.**

**Must NOT touch:** `apps/web/**` (E1B's), `db/chats*.rs` and the chat-column
write path (E3A's), anything under `services/backup/`, `services/quilltap_import/`
or `services/restore*` (the coming v4 drift round's), and the eleven verbs
listed in P4.9E3A's mandate.

### The three semantics a faithful port must reproduce

**1. `nullish` fields are three-valued and the tri-state is load-bearing.**
`updateParticipantSchema` marks `imageProfileId`, `selectedSystemPromptId`,
`joinScenario` and `talkativeness` as `.nullish()` — absent | `null` | value.
`helpers.ts:159-160` and `:180` then branch on **`!== undefined`**, so *absent*
and *explicit null* take different paths: an explicit `null` clears the
override, an absent key leaves it alone. Model these as
**`Option<Option<T>>`** with `#[serde(default, skip_serializing_if = "Option::is_none")]`.
A flat `Option<T>` collapses the two and is wrong.

> This is the same shape as the standing `chat_settings.cheapLLMSettings`
> explicit-`null` gap recorded at the P4.9G5 unification (still tripwired).
> **Do not repeat it here** — get the tri-state right at the wire, and say so in
> the lane record.

**2. `controlledBy` drives impersonation as a side effect** (`helpers.ts:180-200`).
Flipping a participant to `'user'` appends its id to
`chat.impersonatingParticipantIds` and, **only when
`activeTypingParticipantId` is currently falsy**, sets that too. Flipping back
to `'llm'` removes the id and, **only when it was the active typing
participant**, promotes `newImpersonating[0] || null`. Both branches issue a
SECOND `repos.chats.update` after `updateParticipant` returns, then re-read the
chat. The existing `chats_participants_tier2_equivalence` differential already
banks the repo-level half of this — read its header before porting; your job is
the service layer above it.

**3. A connection-profile change posts a Prospero announcement**
(`helpers.ts:159-178`) — only when `connectionProfileId !== undefined` **and**
it differs from the old value **and** the participant has a `characterId`. It
resolves both profile labels (old may be `null`) and calls
`postProsperoConnectionProfileChangeAnnouncement`. The Post Office writer family
is ported (`services/announcer/`, P4.9E2A) — reuse it, do not fork it.

## The differential requirement, restated

Every ported unit ships with an equivalence test that drives v4's **real**
`lib/` and `app/` code — never a reimplementation. This lane is **tier 2**
(structural DB diff): both sides run the same op sequence against a fresh copy
of the same fixture, then the touched tables are dumped canonically and diffed,
with only legitimately-nondeterministic fields normalized (timestamps, minted
UUIDs via a remap).

- **Closest existing recipes:** `chats_participants_tier2_equivalence.rs` (the
  same table, the same participant-id remap, the same "chat `updatedAt` never
  bumps" invariant) and `post_office_routes_equivalence` (a route-level tier-2
