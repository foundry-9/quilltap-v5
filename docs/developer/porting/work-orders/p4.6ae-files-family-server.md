### Quirks the port must not miss

1. **Sorts differ by endpoint:** files list `createdAt` DESC; folders
   `path.localeCompare` ASC (ICU4X collation, not byte order —
   `[[vault-yaml-icu-decisions]]`).
2. **Two response shapes for a file:** `serializeFileEntry`
   (list/upload — dual filename fields, RESOLVED folderPath,
   `fileStatus||'ok'`) vs `buildManagedFileResponse` (move/promote —
   `filename` only, RAW folderPath). Pin both; never unify.
3. **Overwrite reuses the fileId** and returns 200 (vs 201 new);
   nullable-projectId scoping means a general file only collides with
   general files (`createNullableFilter`).
4. **No size limit and no permission check** on the collection upload
   (v4's explicit comment, upload.ts:48) — do not "fix" this.
5. `fileDelete`'s associations arm distinguishes REAL associations
   from stale linkedTo (stale is silently cleared, then delete
   proceeds).
6. cleanup-orphans **rescues** referenced orphans (character id OR
   sha256 match OR non-empty linkedTo → back to `'ok'`) before any
   delete/move.
7. The chat-file conflict fields are **`resolution` +
   `conflictingFileId`** (NOT `conflictResolution`) — locked on both
   v4 and the shipped SPA client.
8. `move`/`promote` are metadata-only (storage key untouched); the
   project check is an existence gate via `findByIdRaw` (degraded
   stores must not throw).
9. The generate response's `metadata` block is unread by the SPA but
   diffed by the oracle — emit it.
10. Folder create is idempotent + auto-creates the parent chain;
    folder delete's two refusal messages are distinct strings.
