## Survey-verified starting points (fresh survey 2026-08-26)

### Unit 1 — `914b59e13` (the chokepoint; port FIRST)

- v4 `lib/backup/restore/delete-service.ts` (+10/−5): `deleteUserData`
  used to loop `repos.memories.findByCharacterId(character.id)` and call
  `repos.memories.delete(memory.id)` per row. Now: collect ALL doomed
  ids across characters into one `memoryIds: string[]`, then ONE
  `await deleteMemoriesWithUnlinkBatch(memoryIds)`. v4's why-comment to
  carry: with the whole corpus in one doomed set the neighbour scrub is a
  no-op (every candidate is itself doomed), so this degrades to
  per-character bulk deletes instead of the per-row loop.
- v4's regression test (`delete-service.test.ts` +35) asserts the direct
  repository delete is **never hit** on this path;
  `delete-service-annotations.test.ts` +4 re-asserts annotations survive.
- v5 twin: `crates/quilltap-core/src/services/delete_all.rs` — find the
  per-row memory deletion leg and route it through the v5 unlink-batch
  twin (`db/memories.rs` `delete_memories_with_unlink_batch`-family,
  ~:560–630). The DB end-state is IDENTICAL by design, so the
  differential is blind to the routing — the pin is a v5 unit/wiring
  test in v4's shape (the direct bulk/per-row delete not reached from
  `delete_all`), mutation-proven by reverting the call.

### Unit 2 — `805ef12bf` (the chunking; port SECOND, on the moved call site)

- v4 NEW `lib/utils/chunk.ts`: `SQLITE_VARIABLE_CHUNK_SIZE = 900`
  (doc-comment: the compile-time cap is 999 old / 32766 current; 900 stays
  safely under both) and `chunkArray(items, size)` — order-preserving,
  empty input → no chunks, **throws on a non-positive/non-integer size**
  (`chunkArray size must be a positive integer, got ${size}`).
- Site A — `lib/memory/memory-gate.ts:594-608`: the doomed-ids →
  characterId resolve (`SELECT id, characterId FROM memories WHERE id IN
  (…)`) now loops `chunkArray(memoryIds, SQLITE_VARIABLE_CHUNK_SIZE)`,
  accumulating into the same `idsByCharacter` map. v5 twin:
  `db/memories.rs:607-617` (the doomed-set resolve).
- Site B — `lib/database/repositories/memories.repository.ts:556-570`:
  `bulkDelete`'s `$in` filter now loops chunks, summing `deletedCount`.
  v5 twin: `db/memories.rs:332-345` (`bulk_delete`, one bind per id).
- v4's tests pin the **chunked query shapes with 2,000-id batches** at
  both sites plus the helper itself (35 cases). v5 red-first proof is
  cheap and REAL: before the fix, a >32,766-id batch against an in-memory
  fixture returns SQLite's "too many SQL variables" — write that test
  first, watch it fail, then land the chunking and keep it as the pin
  alongside v4's 2,000-id shape assertions. Keep 900 as a named shared
  constant (one home; both sites import it).
