# Feature 5.1 — Native Embeddings + Chunk-Granular Retrieval

**Status:** Proposal / Not started. First planned divergence from the 5.0 parity
baseline.
**Depends on:** 5.0 (total parity with v4 `4.8.0`), the embedding-profile
abstraction, the self-describing embedding blob codec (db-size-reduction Step 3),
the `EMBEDDING_REINDEX` infrastructure, `EngineAssembly.memory_embedding`.
**Author:** planning session, 2026-07-13.

---

## 1. Why this exists

Charlie's corpus is deliberately heterogeneous. The same embedding space has to
hold three very different objects:

- **short memories** (a sentence or two),
- **chat messages** (short),
- **chapter summaries of books** at roughly **46 KB each** — about
  **11,000–12,000 tokens**, or 7,000–8,000 words.

Today those summaries are pushed at a "large" embedding model in the hope of
capturing each whole document in a single vector. The premise is false: every
model in play — OpenAI `text-embedding-3-large`, `nomic-embed-text` — caps
around **8,192 tokens** of context. A 46 KB summary overshoots that ceiling, so
a single-vector embedding silently truncates to roughly the opening two-thirds
and drops the tail. There is no "whole-document embedding" to preserve; there is
only truncation we haven't been naming.

This feature makes two coupled changes:

1. **Chunk-granular retrieval** becomes the standard unit for large documents —
   not a downgrade from a working whole-doc embedding, but a repair for
   truncation, and the thing that lets us drop the long-context requirement.
2. **A first-party native embedder** (in-process, zero-network) is added as a new
   embedding-profile provider, running under one runtime on every target
   platform — macOS (arm64 + x64), Windows/Linux x64, iOS, Android — so the
   embedding space is identical everywhere the synced database travels.

Terminal mode and autonomous rooms are explicitly **out of scope for mobile**
(consistent with the enclave's ~30 s iOS background limit). The embedder,
unlike those, genuinely has to make the crossing to mobile because memory search
runs there.

---

## 2. What 5.0 already gives us (the baseline to build on)

Framing matters: much of the substrate exists at parity and should be **reused,
not reinvented**.

- **Embedding-profile abstraction.** v4 already routes embeddings through
  pluggable profiles (OpenAI `text-embedding-3-small/large`, Voyage, Ollama/
  nomic-over-HTTP, and the built-in `tfidf-bm25-v1` zero-network fallback).
  `applyEmbeddingProfile` already performs **MRL truncation + L2 normalization**;
  stored vectors are unit-normalized. **The native embedder is just a new
  provider behind this same seam** — no new retrieval math, no new storage path.
- **Chunking already exists.** `conversation_chunks` chunks conversations;
  conversation-summary vault files are chunked + embedded; the (proposed)
  help-doc index chunks by heading. Three embedding-bearing tables today:
  `memories.embedding`, `vector_entries` (keyed by `characterId`), and
  `conversation_chunks`.
- **Storage codec.** `lib/embedding/float32-conversion.ts` is the single
  chokepoint (float32↔blob). The db-size-reduction plan's **Step 3** replaces it
  with a self-describing blob header `[magic 0xEB | ver | dtype | dim | scale |
  body]`, header-aware on read (legacy f32 + int8 + optional f16). Because all
  search consumes hydrated arrays, dtype/dim changes are transparent to callers.
- **Reindex infrastructure.** `handlers/embedding-generate.ts` +
  `embedding-reindex.ts` (`EMBEDDING_REINDEX_ALL`), debounced re-embed-on-open,
  and (planned) a per-scope entry point rather than only system-wide.
- **Recall blends, it doesn't rank on raw cosine.** Memory recall is
  `0.4·cosine + 0.6·effectiveWeight` (importance × 30-day decay); the
  inter-character pool filters on presence. This matters for §5 (aggregation):
  the single-vector paths already have their own ranking and are undisturbed.

The net: 5.1 slots a native provider into an existing profile system and
standardizes chunking parameters + document-level aggregation. It is a smaller
change than "add embeddings" would be.

## 3. The retrieval model

### 3.1 Hybrid granularity — one model, variable chunks per item

Keep the retrieval unit matched to the object:

- **Memories** → one vector each (already true). Short, self-contained; nothing
  to chunk.
- **Chat messages** → one vector each (already true, via `conversation_chunks`
  where a short message is a single chunk).
- **Large documents** (46 KB chapter summaries, mount/Scriptorium files, vault
  documents) → **N chunks**, embedded individually.

This preserves the "one embedding model for everything" goal Charlie wanted —
one **model**, not one **vector per document**. The single-model constraint is
kept; only the one-vector-per-document constraint is dropped, and only where
documents are long.

### 3.2 Chunk parameters (default policy)

- **Target size:** ~**512 tokens** per chunk.
- **Overlap:** ~**15%** (~64–80 tokens) so a fact straddling a boundary survives.
- **Boundaries:** **structure-aware first** — split on Markdown headings, then
  paragraph/sentence boundaries, falling back to fixed-size only inside an
  oversized block. Chapter summaries are Markdown, so heading-aware splitting is
  natural and gives each chunk a coherent topic.
- **Why 512 and not larger** even though the recommended model allows 8,192:
  smaller chunks give **sharper** retrieval (a query about one plot point matches
  the chunk about that plot point, not a vector diluting it across 45 KB), and
  512-token chunks keep the door open to swapping in a 512-context model later
  **without re-chunking**. A 46 KB summary yields ~22–25 chunks at this size.

### 3.3 Contextual prefixing (recover the lost global context)

A bare chunk loses provenance — "he betrayed her" doesn't know who "he" is.
Before embedding, **prepend a short context line** to each chunk: book / work
title, chapter, and (optionally) a one-line document summary. Cheap, and a large
retrieval-quality win on narrative text. This composes with the model's required
task prefix (§4.3) — the order is `task-prefix + context-line + chunk-body`.

### 3.4 Optional parent-child document vectors

For the cases where "find the single most relevant *whole* summary" is the real
question (not "find the relevant passage"), store a **document-level summary
vector** alongside the chunk vectors — embed the document's own summary/abstract
as one additional vector, tagged as the parent. Retrieval can then consult chunks
for passage-level context and the parent vector for document-level ranking. The
conversation-summary-vault bridge already produces summary text we can reuse for
this. Mark as **optional / phase-two within 5.1** — land chunking first.

## 4. Recommended embedder

### 4.1 Recommendation: `nomic-embed-text-v1.5`

**Primary recommendation, medium-high confidence.**

| Property | Value |
|---|---|
| Parameters | ~137M (0.1B) |
| Dimensions | 768, Matryoshka-truncatable to **512 / 256 / 128 / 64** |
| Context | **8,192 tokens** |
| License | **Apache-2.0** |
| MTEB (avg) | 62.28 @ 768 dims |
| Runtime | Candle (native BERT example exists); ONNX/fastembed as fallback |
| Prefix | **Required** — `search_document:` / `search_query:` (asymmetric) |

Why it wins for *this* system specifically:

1. **It is already one of Charlie's two reference points.** Running the exact
   weights natively reproduces nomic quality bit-for-bit — no quality surprise,
   just no network call.
2. **Apache-2.0** — clean for a distributed desktop/mobile app.
3. **137M runs on mobile** — comfortably on modern iPhone via Metal, tolerably on
   mid-range Android CPU (and only for incremental work — see §7).
4. **768→256/128 Matryoshka** feeds the int8 + dimension-reduction DB-size plan
   directly (see §6).
5. **8,192 context is the "never truncate anything else" insurance.** Even though
   summaries are chunked to 512, the same model handles an occasional long memory
   or an over-size chunk without truncating — the one model that never silently
   drops text anywhere in the corpus, while staying small. This is the
   "one model for everything" instinct, made real and local.
6. **Portable** — pure-Rust Candle path compiles to every target (see §8).

The cost, stated honestly: MTEB 62.28 sits **below** the ~335M "OpenAI-large
parity" class (mxbai-embed-large, bge-large ≈ 64). For a fiction/memory corpus
retrieved chunk-first, that gap is marginal, and it buys mobile-viability +
one-model-everywhere + no-truncation. That is the right trade for Quilltap.

### 4.2 Alternatives considered

| Model | Params | Ctx | Dims / MRL | License | Note |
|---|---|---|---|---|---|
| **snowflake-arctic-embed-m-v1.5** | 109M | 512 | 768→256, engineered to survive **128-byte** vectors via MRL + scalar quant | Apache-2.0 | Best-in-class **compression** — pick this if DB size dominates. But 512 ctx makes it **chunk-only** (truncates any >512-token item, e.g. a long memory), and its query prefix differs. |
| **EmbeddingGemma** | 308M | 2,048 | 768→512/256/128 | Gemma (use-restricted) | Purpose-built for **on-device**, strong for size, multilingual. Downsides: 2–3× the size (heavier on low-end Android) and a **non-Apache** license to vet for distribution. |
| **mxbai-embed-large-v1 / bge-large-en-v1.5** | ~335M | 512 | 1024 | Apache/MIT | OpenAI-large parity, but the size the floor Android device may not run at interactive latency. Rejected as the universal model; viable **desktop-only** if ever wanted. |
| **bge-small-en-v1.5** | 33M | 512 | 384 | MIT | Smallest/fastest; no official MRL; a fallback if nomic is too heavy on the floor device. |

**Decision rule if the recommendation is revisited:** the model is bounded by
the *weakest* device it must run on (§7) and by the need for **one identical
model everywhere** (§5.1). Within that, prefer Apache-2.0 + MRL + enough context
to never truncate non-chunked items → `nomic-embed-text-v1.5`. Fall to
`arctic-embed-m-v1.5` only if the int8/128-byte compression win outweighs losing
whole-item embedding, or to `bge-small` only if nomic misses the mobile latency
budget.

### 4.3 The prefix gotcha (must not get this wrong)

nomic **requires** an asymmetric task prefix: stored chunks/documents get
`search_document:`, queries get `search_query:`. Getting this wrong silently
degrades retrieval with no error. The native provider must apply the prefix
**per role** inside the `applyEmbeddingProfile` path, before embedding, and the
reindex/query code must agree on which role each call is. Bake it into the
provider so no call site has to remember.

## 5. Aggregation — the "will a less-relevant file win?" question

The concern: a less-relevant document that happens to contain *more* matching
chunks outranks a genuinely-relevant one. Resolution:

### 5.1 Retrieve at chunk granularity by default

For feeding context to the model, **rank chunks, inject the best chunks** — do
not rank whole files at all. The relevant chunk from the relevant summary still
scores high and is retrieved; it is irrelevant that another document also
contributed chunks to the pool. The "spurious file wins" failure only exists when
the *file* is the retrieval unit, which for context injection it needn't be.

### 5.2 When document-level ranking IS needed, never sum

Where a document score is genuinely required (e.g. "most relevant whole
summary"), aggregate chunk scores by **max-pool** (document = its single best
chunk) or **mean of top-k chunks** — **never sum or count-over-threshold**.
Additive aggregation is exactly what lets a long, loosely-relevant document
accumulate many mediocre hits and out-score a short sharp one.

**This is sharper for Charlie's corpus than for most**, because item lengths span
~three orders of magnitude (a one-line memory next to a 46 KB summary). That
spread is the precise condition under which additive scoring is most biased
toward the long documents. **Max or top-k mean, never sum** — and if a parent
vector exists (§3.4), prefer it for document-level ranking over any chunk
aggregation.

### 5.3 Single-vector paths are undisturbed

Memory recall keeps its `0.4·cosine + 0.6·effectiveWeight` blend; messages stay
single-chunk. Those objects have no aggregation to get wrong. Aggregation policy
applies only to multi-chunk documents.

**Realistic verdict:** with chunk-granular retrieval (or max/top-k when
aggregating), the feared failure is unlikely. It becomes likely **only** under
additive aggregation over this length-skewed corpus — a design choice we simply
decline.

## 6. Vector count, DB size, and the int8 budget

Chunking multiplies vector count, which pushes directly on the db-size-reduction
plan. Worked estimate per 46 KB summary:

- ~11–12K tokens ÷ 512-token chunks (with 15% overlap) ≈ **~22–25 chunks**.
- Storage per vector, 768-dim:
  - f32: 768 × 4 = **3,072 B**
  - int8 (Step-3 codec): 768 × 1 + header ≈ **~780 B**
  - **MRL-256 + int8: 256 × 1 + header ≈ ~270 B** ← recommended for chunk store
- So one summary's chunks: ~25 × 270 B ≈ **~6.75 KB** of vectors at MRL-256/int8,
  vs ~25 × 3,072 B ≈ **75 KB** naive. ~**11× smaller**.

Guidance:

- Store chunk vectors at **256-dim MRL + int8** by default. nomic's Matryoshka
  training means the 256-dim truncation keeps most retrieval quality; the Step-3
  self-describing header already carries `dim` + `dtype` + `scale`, so this is
  **not a new migration** — it is exactly what the codec was built to hold.
- Keep **memories** at a higher fidelity (768 or 512, int8) if desired — they are
  few and high-value; the volume is in document chunks.
- Validate compression the way the db-size plan already specifies: **top-10
  neighbor overlap ≥ 0.95** against the f32 baseline before committing; fall back
  to **f16** (Node/Rust both have it) if int8 recall regresses on this corpus.

## 7. The mobile ceiling (why the model choice is capped)

The embedding vectors are **shared, synced state** — they ride iCloud/Dropbox
between desktop and phone; a memory embedded on the Mac has its neighbors
searched on the phone. That only works if **both devices produce vectors in the
same space**, i.e. **one identical model on every platform**. Consequently the
model is capped by the *weakest device it must run on*. You cannot run a 335M
model on desktop and a small one on mobile — the neighbor sets would disagree and
the differential discipline would have nothing clean to check.

Mitigation that makes the cap painless — **split the workload**:

- **Desktop** does bulk work: full reindex, re-embedding the corpus, the 46 KB
  summaries. A full reindex on a phone is a thermal/battery event and is
  **desktop-only** by policy.
- **Mobile** does **incremental only**: embed the handful of new memories/messages
  created in a session, and otherwise **consume desktop-computed vectors** for
  search (read-mostly). nomic-137M via Metal handles single-item embedding on an
  iPhone trivially; a single 512-token chunk on Android CPU is fine.

This is why `nomic-embed-text-v1.5` (137M) is the ceiling-respecting pick, and
why chunking matters twice over: chunk-first retrieval lets us drop the
long-context requirement, which lets us use a **small** model, which is what makes
mobile viable at all.

## 8. Runtime — Candle (pure Rust), one build for all targets

Established in the design conversation and reaffirmed here:

- **Candle** (pure Rust) is the runtime. It cross-compiles as *just another crate*
  into the same `uniffi`-bound core already shipping to mobile:
  `aarch64-apple-ios`, `aarch64-linux-android`, and every x64 target. Metal
  acceleration is shared between the Mac and the iPhone; x64 uses AVX2; Android
  uses CPU + NEON. A CoreML path exists (`candle-coreml`) if wanted later.
- **ONNX Runtime / fastembed is the fallback, and desktop-only.** It has 46
  turnkey models but **no prebuilt mobile binaries** — iOS/Android mean
  self-compiling and static-linking ORT per platform/ABI, plus a heavier binary
  exactly where size and battery are tightest. Acceptable as a desktop
  convenience; not the cross-platform answer.
- **One runtime everywhere also protects the oracle discipline.** Two runtimes
  computing the "same" model are not bit-identical (ONNX graph vs Candle forward
  pass); with vectors meant to be comparable across synced devices, that
  divergence is exactly what we don't want. Single runtime → single numeric
  behavior.

**Weights:** download-on-first-run into the instance/app-support dir (desktop may
alternatively bundle). Ship a **quantized** variant (f16 ≈ ~260 MB, int8 ≈
~140 MB) so the mobile footprint stays sane. The model file is *not* the DB — it
does not sync; each device fetches its own copy once.

## 9. Migration & rollout (opt-in, non-parity)

Because 5.0 is strict parity, the native profile is **opt-in in 5.1**. Existing
instances keep their current embedding profile (OpenAI/Voyage/Ollama/TF-IDF)
until the user chooses to adopt the native one.

- Adopting native = **create a new embedding profile + full reindex**. Vectors
  from different models are **not comparable**, so this is a one-time
  re-embedding of the whole corpus under the new model. Use the existing
  `EMBEDDING_REINDEX` infrastructure; make it **per-scope and resumable**, and
  keep it a **desktop** operation (per §7).
- **One-way; back up first** — same posture as the int8-quantization migration.
  A copy of the DB before reindex; never point the writable reindex at the only
  copy of live Friday data.
- **Seam:** the native provider registers behind the existing embedding-profile
  registry and `EngineAssembly.memory_embedding` (already wired live for
  `memoryCreate` / `memorySearch`). The prefix logic (§4.3) lives inside the
  provider. No on-disk schema change beyond the Step-3 codec, which is already
  planned independently.

## 11. One-paragraph summary

Add a native, in-process `nomic-embed-text-v1.5` embedder as a new
embedding-profile provider running under Candle on every platform, and make
chunk-granular retrieval (≈512-token, heading-aware, 15% overlap, context-
prefixed) the standard for large documents while keeping memories and messages as
single vectors. Retrieve chunks directly for context injection; where a document
score is needed, aggregate by max/top-k, never by sum — critical given the
corpus's three-orders-of-magnitude length spread. Store document chunks at
256-dim MRL + int8 via the already-planned self-describing codec (~11× smaller
than naive f32). Because the vectors are synced shared state, the model is capped
by the weakest mobile device and must be identical everywhere; nomic-137M with
its 8,192-token headroom is the ceiling-respecting pick that never truncates
non-chunked items. Adoption is opt-in, one-way, desktop-driven reindex; mobile
does incremental embedding only.
